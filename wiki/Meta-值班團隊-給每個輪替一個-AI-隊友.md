# Meta 值班團隊 給每個輪替一個 AI 隊友

來源：AI Engineer CODE 2026 線上場次〈Give Your On-Call Its Own AI Teammate〉，講者為 Meta 的 Chinmay Gandhi、Swaapnika Motapothula、Vlad Tsvang。官方閱讀頁正文與機器逐字稿落地於 [[AI-Engineer-Motapothula-On-Call-AI-Teammate]]；影片是 Day 1 直播（YouTube `ZZ19zhYnDKY`，約 1:58:35–2:14:14），全場約 16 分鐘。逐字稿把 on-call 辨識成「uncle」，引用時要自行還原。

**一句話**：值班已經有好用的 AI 助理，但助理要人問才動、答完就停，值班的人仍然要自己串起所有線索。Meta 的做法是每個值班輪替配一個常駐的 AI 隊友：一個迴圈接住所有訊號、一份屬於團隊的記憶、自己的身分、一道人類核准閘門。自主權以「單一行動」為單位逐級賺取，不是整個 agent 一次放行。

## 講者與立場

- **身分**：三人自述屬於 Meta 打造事故應變、值班體驗與 mitigation 工具平台的工程團隊。一手核對：Meta Engineering 2025-12 的 [DrP 根因分析平台文章](https://engineering.fb.com/2025/12/19/data-infrastructure/drp-metas-root-cause-analysis-platform-at-scale/) 作者列有 Chinmay Gandhi，與「事故調查平台團隊」的自述相符。另兩位講者未找到一手來源可核對。
- **分工**（依逐字稿交接語）：Chinmay Gandhi 開場講問題與架構前提，交給 Swaapnika Motapothula 講自主階梯、決策佇列與三條自動化，最後由 Vlad Tsvang 講團隊共用記憶、跨團隊擴展、成效與下一步。
- **立場**：講的是 Meta 內部系統，沒有對外販售的產品，談不上推銷；但它是自家團隊的成果發表，成效說法都屬自報。系統名稱、使用的模型、上線輪替數，演講都沒有交代。

## 演講的完整論證脈絡（依時間順序）

### 1. 開場：瓶頸從寫碼移到運維（1:58–1:59）

- 他們說 Meta「約四分之三的新程式碼現在用 AI 寫」，AI 產生的變更每天進到 production，其中有些會像任何程式變更一樣造成故障（這個數字的回查見下方，未能核實）。
- 「高品質的程式碼可以通過 review，仍在 production 壞掉」，壞了還是有人凌晨 2 點被叫醒。他們的判斷是**瓶頸從寫程式移到在 production 運作程式**，而值班是運維負擔落地的地方。問題於是變成：AI 寫了程式，能不能也幫忙運作它？

### 2. 同一個凌晨兩點的兩種走法（2:00–2:01）

簡化範例：凌晨 2 點，12 個 alert 同時響。

- **左邊（現況，已經有好的 AI）**：你自己排 alert 優先序（checkout、payments、disk 先看哪個），挑了 checkout 後問助理「為什麼 P99 latency 高」。助理很有用：拉 metrics、找到 1:49 的部署，被問才去讀改了什麼、查 runbook，發現 timeout 設定被調低，依 runbook 建議 rollback。但它**等人問**、**每一步都是你挑的**、**你是問題之間的膠水**、答完就休眠。2:39 你知道原因了，rollback、修改、後續追蹤仍然全是你的。
- **右邊（AI 隊友）**：同樣 12 個 alert，隊友在你醒來前已經開始：排好順序（checkout 優先、payments 判為同一原因合併、其他 10 個分開處理），讀了 dashboard、比對兩起過去事故。你拿到的是一個假設、一個 30 秒可驗證的方法、一個等你 review 的修復。2:11 驗證完、回去睡。
- 閱讀頁的轉述重點：人沒有消失，人一開始面對的是**一個要做的決策**，而不是一場要從零拼湊的調查。

### 3. 為什麼人變成膠水：各自為政的自動化（2:01–2:03）

- 各團隊一次一個筒倉地把自動化接到值班上：alert 腳本管 alert、triage bot 管 ticket、deploy bot 管部署、fix-it agent 管事故。每個解決自己那一片、保留自己的 context，然後忘掉。
- 重播凌晨那一頁：alert 腳本看到 P99 超過 2 秒，triage bot 看到三張「checkout 很慢」的 ticket，deploy bot 知道 1:49 有設定變更，事故歷史裡有兩起類似事件。**每條線索都存在，但沒有東西把它們連起來**，所以值班的人成了膠水。
- **他們的押注**：每個輪替一個 AI 隊友，四個要素：
  1. 一個迴圈涵蓋所有訊號；
  2. 一份每個班次都在學習的團隊記憶；
  3. 自己的身分，以自己的名義行動；
  4. 一道人類閘門，讓人「核准」而不是「操作」。
- 但把所有 context 與觸及範圍交給一個 agent 會提高風險，**所以自主權必須用賺的**。
- **底層很簡單**：隊友本身是「最簡單的 agent」，模型在迴圈中使用工具、作用於環境、讀回饋。演講其餘部分都在講「圍繞這個迴圈要建什麼，才能放心讓它一直跑」。

### 4. 自主階梯：像帶新人上值班（2:03–2:05）

- **類比**：新工程師上值班先 shadow（調查、建議，不碰 production），再 pair（自己寫修復、另一位工程師核准），隨時間累積知識。agent 走完全相同的階梯：
  - **Level 1 建議**：調查並告訴你發現了什麼，不改任何東西。
  - **Level 2 經核准才行動**：草擬修復，人核准前什麼都進不了 production。
  - **Level 3 自主處理低關鍵度工作**：自己清掉低關鍵度的項目，只為重要的事打斷你。**高關鍵度工作留給人**。
- **升級的判準**（投影片明列）：犯錯代價多高、多容易抓到。一個行動只有在三個條件都成立時才往上爬：
  1. 犯錯的代價低；
  2. 錯誤會被測試、CI 或 review 抓到；
  3. agent 在**這個確切的行動**上已經有良好紀錄。
- 所以 agent 可以自己關掉一個雜訊 alert，production mitigation 仍然要等人。閱讀頁的說法是：**信任的單位是行動，不是 agent 的整體聲譽**；處理前者可靠，不代表就有資格做後者。
- **Level 1 的細節**：調查是分層的，**在第一個有信心的答案就停**；使用團隊的記憶與 runbook，給出根因分析，但修復要人自己套用。
- **Level 2 的細節**：寫出修復，附根因與 test plan；回應 reviewer 留言、修 CI；人核准前不進 production。**「大部分草稿不會被合併，這沒關係，review 就是過濾器。」**

### 5. Level 3 縮小待辦堆，而不只是讓每項更好處理（2:05–2:06）

- 他們的反省：在 Level 1、2，agent 做功課，但「你仍然要批改每一份作業」。協助品質大幅提升，**需要人介入的工作量卻沒有變少**。Level 3 才是縮小那一堆。
- **範例看板**：進來 23 項，只有 3 項需要你。右欄是 agent 處理掉的長尾：雜訊 alert、重複項、走正常 review 與 CI 的例行修復；另有 2 項仍在處理中，你不必逐項推到完成。中間是小得多的**決策佇列**，每一項都寫清楚需要你做什麼，附一個帶行動呼籲的「run this」按鈕。
- 凌晨 2 點的 checkout 事故**仍由人負責**：agent 帶來調查結果，人做關鍵決策。重點是「不只是每項工作變少，而是等你處理的項目變少」。

### 6. 決策佇列要送到人面前（2:06–2:08）

- 看板是工作所在，但沒有人一直盯看板。所以 agent 也出現在聊天與原生事故介面等多個介面。
- **每天早上 9 點發 digest**：23 項進來、3 項需要你、18 項已處理。需要你的每一項附一鍵下一步，例如在手機上點一下就核准 quota 調升。已處理的 18 項**只摘要、不逐條列出**；2 項處理中的會說明它正在做什麼。閱讀頁把這歸納為三種狀態：需要決策、已處理、處理中，**它們是不同狀態，不該全部變成通知**。
- **在討論串裡追問**：打開 checkout 事故要證據，它已經準備好：8:41 開始出錯，在一次 config push 調低 payment client timeout 的 2 分鐘後，和兩起過去事故同一模式。追問「只有 EU 嗎？」，它回一份分區分解。它草擬 rollback，你在同一處核准，錯誤開始恢復。「你從沒打開 dashboard，也不必解釋 context，因為它已經在那裡。」核准仍是獨立的一步。
- 閱讀頁特別註明：這些例子展示的是**期望的互動方式，不是量測過的省時**。

### 7. 底層：三條自動化（2:08–2:10）

1. **調查**：每個新訊號觸發 auto-triage，分類、判斷關鍵度、啟動對的 agent。alert 給事故調查 agent，task 給團隊自己的 agent，測試失敗給 coding agent，查詢給記憶與 code search。
2. **保持系統健康**：「無人看管的自動化會安靜地失敗。」所以排程掃描卡住或失敗的 run，重試、修復壞掉的排程，**修不了才叫人**，「沒有東西會無聲停擺」。閱讀頁的轉述：**安靜的 agent 不一定是健康的 agent**，維護自動化本身是一條獨立路徑。
3. **交班**：每次換班與每天早上 9 點摘要這一班，需要你的（附備好的修復）與它自己處理的，貼到團隊聊天室。不只早上，每個需要人注意的緊急問題都會帶著發現與修復草稿通知；交班時也會在聊天裡 tag 下一位值班者。
- **Bring your own agent**：因為它屬於團隊，所以跑的是團隊原本就信任的 agent 與 skill。如果團隊已經有一個掌握自家 runbook 與知識庫的 agent，自動化就直接用它；另外搭配平台自己的事故調查 agent 與深入的 coding session。
- 工作來源：alert、ticket、事故、團隊貼文、聊天。**agent 本身是通用的**，讓它勝任某個輪替的是團隊的 agent、skill、記憶與 playbook。
- **每次 run 都留紀錄**：團隊任何人都能檢視軌跡（trajectory）或接續對話，不必接受一個不透明的結論。

### 8. 記憶屬於團隊，而且要能被糾正（2:10–2:12）

- 值班不屬於單一個人，所以 agent 也不能只屬於一個人。每個輪替一個隊友、一個看板，當班的人都可以問它、糾正它、在調查中途接手它的工作。它把團隊的值班專長、playbook、負載特徵（逐字稿「lord profiles」，推測為 load profiles）與過去的決策，像好的交班那樣從一班帶到下一班。
- **範例**：週一凌晨 2 點，Sam 值班，告訴它「如果 checkout 在 config push 後 timeout，先 roll back config」，它存進記憶。三天後 Jordan 值班遇到同一個 alert，只問要怎麼修；agent 給出修法、**說明出處**，並備好 rollback 草稿。「教一次，下一個值班的人就得到了。」
- **身分與權限**：它有自己的身分，由輪替擁有，只拿到團隊願意授予的權限。
- **從每一班學習**：交班、決策、糾正都流進記憶，所以第 30 班比第 1 班好。
- **記憶會隨時間劣化，所以每條要「掙得位置」**：語意檢索、使用找到的內容、**評分它實際上有沒有幫上忙**、自動提升或淘汰條目。有人說「那是錯的」，該項目重新開啟，糾正本身變成記憶。閱讀頁的轉述：agent 不該只因為有人曾經很有自信地寫下某個錯誤指示，就一直保留它。

### 9. 讓它跨團隊可用的三件事（2:12）

1. **一個不停傾聽的迴圈**：每一則回饋或方向修正都會重開項目，最終被吸收進記憶。「回饋是系統的輸入，不是一季讀一次的故事。」
2. **客製而不 fork**：團隊帶自己的 playbook 與 skill workflow，底下仍是同一個隊友。
3. **一個輪替到底**：身分、設定、記憶、權限都是每個團隊各自一份，共用的是基礎設施。新增一個輪替變成「設定」，不是「新專案」。**agent 是通用的，專長屬於團隊。**

### 10. 對值班的人改變了什麼，與下一步（2:12–2:14）

- **工作性質轉變**：從推動深入調查，變成做關鍵決策；起點是一個附連結證據的假設，不是空白 task 或 dashboard。
- **負載在變輕**：自主運行的團隊「早期跡象樂觀」，但**要嚴謹量測後才會給數字**。
- **每個 agent 寫的變更仍會遇到人**：修復只透過正常 review 與 CI 進去，大部分草稿不會合併，「這就是重點，review 是過濾器」。值班從「一堆 task」變成「一個 review 佇列」。
- **下一步**：
  1. 讓 mitigation 被核准，而不只是被草擬：替 agent 提出的每個 mitigation 評分、把結果回饋，讓它**靠成績賺到下一級，而不是被直接授予**。
  2. 從聊天直接寫 skill，讓團隊不寫程式就能把 runbook 變成 skill。
  3. 用嚴謹研究量測省下的值班時間，**而不是用使用次數**。
  4. 階梯的下一階：**用證據賺到中關鍵度工作的自主權**。

## 可直接搬到個人 Claude Code／Codex 工作流程的做法

他們的規模是全公司值班，個人開發者沒有 alert 洪流，但「以行動為單位放權」「安靜不等於健康」「三態交班」「記憶附出處、可淘汰」都能縮小來用。

1. **把權限按「單一行動」列清單，逐項升級**（對應第 4 段）。在 Claude Code 的 permission 設定裡，不要一次對整個工具放行，而是寫到具體指令，例如 `Bash(gh pr view:*)`、`Bash(npm test:*)`。某個行動要從「每次問」改成「直接允許」，先自問三個條件：錯了代價低嗎？錯了會被測試、CI、review 抓到嗎？我已經核准過它很多次、從沒改過它的做法嗎？三個都是才升級；`git push`、改 production 設定這類就留在 ask 或寫成 deny。Codex 的對應是 approval 與 sandbox 模式設定，粒度較粗，做不到同樣細。auto mode 分類器與 deny 規則的分工細節見 [[Claude-Code-放手運行的安全與驗證]]。
2. **長跑或排程任務一定要配一個「健康檢查」**（對應第 7 段第 2 條）。如果有用 `/loop`、排程 routine 或 cron 跑 agent，另外排一個檢查：上次該跑的有沒有跑、有沒有卡住、有沒有失敗後就沒下文。沒有錯誤訊息不代表在跑。最簡單的做法是讓每次 run 結束時寫一行狀態檔（時間、結果），檢查端只看這個檔有沒有更新。
3. **session 收尾用「三態交班」格式**（對應第 6、7 段）。長 session 或背景 agent 結束時，要求它輸出：
   - 需要我決定的（每項一行，附具體下一步，例如「核准這個 PR」「選 A 或 B」）；
   - 已處理的（只給摘要與數量，不逐條列）；
   - 進行中的（現在卡在哪、下一步是什麼）。
   寫進檔案或 PR 描述，下一個 session（或明天的自己）從這份交班開始，而不是重讀整段對話。
4. **調查型任務要求「先給可驗證的假設」**（對應第 2、4 段）。除錯時要 agent 交付「假設＋證據連結＋30 秒內能驗證的方法＋修復草稿」，並在第一個有信心的答案就停；你只負責驗證與核准，不負責串線索。
5. **記憶條目附出處，糾正就改原條目**（對應第 8 段）。在 `CLAUDE.md`／`AGENTS.md` 或 memory 檔寫規則時，附上「為什麼、哪一次事件、日期」；被證明錯的規則直接改掉或刪除，不要在後面再追加一條相反的規則。定期刪掉一段時間都沒派上用場的條目。注意這和第 8 段的「自動」淘汰不同：個人規模用人工判斷就夠，見下方張力一節的失效模式風險。
6. **保留可接續的軌跡**（對應第 7 段）。背景或長跑的 agent 工作，結論要能回溯到 transcript；Claude Code 與 Codex 都能 resume 之前的 session。要接手別人（或自己昨天）的工作時，從軌跡接續，而不是只看結論。
7. **追蹤「草稿被合併的比例」，而不是「agent 做了幾次」**（對應第 10 段）。如果讓 agent 自動開 PR 或草擬修改，記下哪些被合併、哪些被丟掉；要放更多權給某類任務，依據是這類任務的合併紀錄，不是使用次數。

**不能直接搬的部分與原因**：

- **每個輪替一個獨立身分與權限**：需要組織層級的 service account、權限系統與事故平台；個人開發者沒有輪替、也沒有多人共用一個 agent 的情境。
- **24 小時常駐、多訊號自動 triage**：需要 alert、ticket、部署系統的整合，Meta 內部工具不公開。個人能做到的是第 2 點那種小規模排程。
- **自動評分並提升、淘汰記憶**：演講沒說怎麼判斷「實際上有沒有幫上忙」，也沒有公開實作；照字面自己做自動淘汰，有反覆固化把記憶改壞的風險（見張力一節）。
- **Level 3 自主處理**：個人環境通常缺「錯了會被抓到」的那一層（沒有完整 CI、沒有第二個 reviewer），依他們自己的判準就不該升到 Level 3。

## 證據強度與限制

- **單一公司、單一團隊的自報經驗**：沒有對照組、沒有公開數據、沒有說明上線了多少輪替、用了什麼模型。所有成效描述（「早期跡象樂觀」「第 30 班比第 1 班好」）都是自報。
- **範例是示意**：凌晨兩點的 12 個 alert、23/3/18/2 看板、9 點 digest、Sam 與 Jordan 的記憶故事，都是簡化情境，不是真實事故紀錄。
- **講者自己的限縮值得保留**：負載降低沒給數字、大部分草稿不會合併、高關鍵度留給人、中關鍵度自主「還要用證據賺」。這些讓整場比多數 agent 演講保守。
- **最有參考價值的是設計原則，不是數字**：以行動為單位的升級判準（代價低、會被抓到、該行動有紀錄）、三條自動化分工、三態交班、記憶屬團隊且可糾正。這些是可借用的框架，不是驗證過的效果。

### 勿引用

- 「Meta 四分之三的新程式碼由 AI 撰寫」當成已證實數字：公開資料只有內部**目標**與更早的預測，未見實測發布。
- 「AI 隊友讓值班時間減少 X%」：演講沒給數字，任何轉述的百分比都沒有出處。
- 「Meta 值班 AI 的根因準確率 42%」：42% 是 2024 年另一套系統的回測數字，不能套到本演講。
- 「DrP 讓 MTTR 降低 20–80%」當成本演講 AI 隊友的成效：那是 DrP 程式化 analyzer 平台的自報，與本演講的 agent 不是同一件事。

## 張力與互補

- **與 [[Claude-Code-放手運行的安全與驗證]]：同一個問題的兩種放權粒度**。該頁整理的 Claude Code 路線是 auto mode 分類器判斷「這個動作安不安全」，再用 deny 規則硬擋「錯一次收不回」的動作。Meta 的判準多了一條：**該行動要有紀錄**，自主權靠累積的成績逐項升級，而不是由分類器當下判斷。兩者可以疊用：分類器與 deny 管底線，「以紀錄升級」管哪些動作值得從 ask 移到 allow。
- **與 [[Diogo-Almeida-助理不等於自動化]]：互相印證**。Almeida 說 LLM 為「協助」最佳化，無人值守要求每次都對；Meta 的 Level 1、2 正是協助，並且直接承認「人仍要批改每份作業、待辦沒變少」，只在「錯了會被抓到、代價低」的窄範圍放到 Level 3。這是 Almeida「先挑對任務、要求窄而可靠」在運維上的實例。
- **與 [[Agent-維護知識庫的已知失效模式]] 第 5 條：自動淘汰記憶的風險**。Meta 讓記憶「自動評分、提升或淘汰」，並把每次糾正吸收進記憶。該頁整理的研究顯示，反覆把經驗改寫成抽象記憶，效用會先升後降，建議保留原始紀錄並讓固化有明確閘門。Meta 的設計有兩點對得上那份建議（每次 run 留完整軌跡、記憶附出處），但「自動」提升淘汰的閘門是什麼、怎麼評「有沒有幫上忙」，演講沒交代，是否避開了這個失效模式無從判斷。
- **與 [[Lauren-Tan-把糾正寫進程式庫]]：糾正落在哪一層**。Tan 主張糾正要盡量落到 API、lint、驗證等確定性層，散文最弱。Meta 把糾正落在團隊記憶（加上 runbook 轉成 skill），屬於較軟的一層。值班情境裡很多知識（例如「config push 後 timeout 先 rollback」）本來就是操作判斷，不容易寫成 lint，所以兩者不矛盾；但能變成自動檢查的（例如 config 變更的 timeout 下限），按 Tan 的順序應優先寫成檢查。
- **與 [[AI-產碼加速下的-review-瓶頸]]、[[Matt-Pocock-的-PR-瓶頸解法]]：值班變成 review 佇列**。Meta 的結論是「值班從一堆 task 變成一個 review 佇列」，且「大部分草稿不會合併，review 是過濾器」。這等於把負載從調查移到 review，正是那兩頁討論的瓶頸。Meta 的對策是 Level 3 縮小佇列，以及只看「被核准的 mitigation」而非草稿數。
- **與 [[OpenClaw-與-Hermes-的實地使用心得]]：維護常駐 agent 的成本**。那頁的使用者證詞指出常駐 agent 的維護成本會吃掉價值。Meta 把「維護自動化本身」獨立成一條排程路徑（找卡住、失敗的 run，修不了才叫人），是對這個問題的正面回應；但這是組織規模的投資，個人自架不一定負擔得起。
- **與 [[Building-Effective-Agents-Anthropic]]：定義一致**。講者直接沿用「模型在迴圈中用工具、讀回饋」的定義，並說工程重點都在迴圈之外，與該頁「先用簡單模式、複雜度留給周邊」的路線一致。
