# Dmitry Buykin 每週小幅修剪取代大重寫

來源：AI Engineer CODE 2026 線上場〈Agents Made Code Free. Maintaining It Didn't Get Cheaper.〉的官方閱讀頁與機器逐字稿，落地於 [[AI-Engineer-Buykin-Agents-Made-Code-Free]]。影片為官方單場重錄版 [`oeknLUsN_GE`](https://www.youtube.com/watch?v=oeknLUsN_GE)（2026-11-11 上傳，18 分鐘；閱讀頁說明此版補回了直播剪段缺掉的結尾）。下文時間碼都用這支影片的時間。

**一句話**：agent 讓寫碼變便宜，但讓「熵」更便宜。不要等系統大到看不懂再整個砍掉重寫，而是畫一條「可審查上限」，每週用小幅、有證據的修剪把系統壓在線下；判斷什麼該留下的，是真實任務與領域專家，不是測試綠燈。

## 講者與立場

- Dmitry Buykin，Maersk（全球航運與物流公司）。AI Engineer 的 [Maersk 組織頁](https://ai.engineer/orgs/maersk)另列他在 World's Fair 2026 的一場〈Tribal Dungeons of Global Shipping: AI Agents at Global Scale〉，內容本頁未查。
- **沒有推銷產品**：整場沒有提任何自家或第三方工具名稱，講的是內部系統的維護方法。結尾承認這套方法是他「已經在燃燒殆盡時」才學會的。
- **系統型態要先講清楚，因為它決定能搬多少**：他維護的不是一般應用程式，而是「coding agent 寫指令、runtime agent 在生產環境照指令做事」的業務流程系統。自述跑在 110 個國家、約 10,000 個 prose 指令情境，系統約四分之三是散文（他自己的估計）。所以演講裡的「程式碼」常常是指 agent 讀的散文指令，「測試」是對這些指令的驗證。

## 演講結構：六顆寶石＝六個問題

他用 Thanos 的無限手套當比喻。開場：某個專案像 Titan 星球一樣被自身成長壓垮，他發現 agent 做了什麼之後，刪掉沒人用的測試與 boilerplate、整個重寫，結果丟了一些有用的部分；而且重寫沒撐住，agent 繼續寫、亂象又長回來。兩難是「淹死在混亂裡」或「弄壞大家在用的東西」，他要建的是第三條路：**在「變更量超過任何人能檢查的線」之下，用每週小幅掃除與系統內建的回饋迴圈維持住**（0:00–1:30）。

六顆寶石對應六個問題，在投影片角落逐一亮起：

| 寶石 | 問題 | 出現章節 |
|---|---|---|
| Time | 怎麼留在線下？ | 開場提出，第 6 章用指標回答 |
| Space | 一個變更可以擴散到哪裡？預設只留在自己的 slice | 第 1 章 |
| Reality | 這是真的，還是只是在模型看來像真的？ | 第 2 章（散文對不對）、第 5 章（變更對不對） |
| Mind | 模型知道什麼？ | 第 3 章 |
| Power | 什麼可以被改變？ | 第 3 章 |
| Soul | 誰來判斷、代價是什麼？ | 第 4 章，結尾再回來 |

每一章都用「我以前以為 X」開頭，再推翻它。

## 第 1 章：「對」由誰定義（1:34–4:56）

**以前以為**：測試決定什麼是對的。

- **貫穿全場的例子**：有人要修改一張已核准訂單的金額。兩種 agent 在此相遇：coding agent 寫指令，runtime agent 在生產環境照做。
- **Slice**：每個任務落在一個 slice，也就是「一個流程 × 一個國家」。Space 寶石的答案是：變更預設只留在自己的 slice 裡。
- **散文也需要工程**：他借用 mutation testing，故意改壞一句指令，看測試會不會紅。「幾乎沒有一個變紅。」他的延伸：就算你的 wrapper 全是程式，agent 指令與測試本身就是你的散文。
- **重寫很容易，難的是知道什麼必須在重寫後存活**。程式碼可以靠測試告訴你；散文只有人能判斷。agent 無法自己建出複雜系統：它們修好容易看見的地方，順手破壞一致性。
- **人的判斷要省著用**：業務說「跟團隊確認」時，背後藏著一個真問題：這是必須由人做的步驟，還是可以自動化？專家答不出來，因為他們看不到系統內部怎麼連；開發者帶著 coding agent 翻 trace 與 log 來決定。在訂單例子裡，team lead 的決定留給人，「金額上限」則是可以接上的資料。
- **bug 多住在水面下的連結裡**：業務專家看得到規則，開發者看得到底下的資料與系統連結。開發者讓 coding agent 把這些連結寫下來，讓 runtime 能檢查。給專家的指南一句話：「業務告訴我們做什麼，我們想辦法怎麼做。」
- **一份文件、兩種讀者**：agent 讀其中的結構化區塊，所以區塊必須精確；專家讀區塊周圍的說明並簽核。只保留一份，另開一份就會漂移，而且是雙向漂移。程式碼也要附白話描述給專家看，因為專家只能修他看得到的東西。
- **專家審查方式**：每位專家照 agent 當時看到的樣子審一個任務；專家的註記成為 coding agent 的下一個變更，並在同一個任務上測試。
- 結論：「對」取決於人，而且沒有單一個人知道，要由一群專家決定，所以從一開始就要把他們拉進來。

## 第 2 章：判斷該留在哪裡（4:56–7:24）

**以前以為**：目標是把所有東西都搬進程式碼。

- **追蹤結果**：專家一次修一個任務，agent 整天跑同一份散文。每個結果都記「接受／拒絕」，準確率告訴他們人還需要看哪裡。
- **散文與程式互相矛盾**：散文說上限 1,500，程式說 1,000（逐字稿口述；閱讀頁截圖顯示的是金額 1,250 對上限 1,000）。同一張訂單在一處沒事、在另一處超標，而且沒有任何東西報錯。
- **「不要呼叫 X」會教模型 X 存在**（5:31）。這就是 Reality 寶石的問題：它是真的，還是只在模型看來像真的？
- **散文沒有編譯器，所以自己做一個**：作者把每個改過的檔案 lint 一遍，結果寫進 ledger，「就像程式碼一樣」。
- **Lint 擋不住複本彼此漂移，所以觀察「walk」**：walk 是一個 agent 走過散文的路徑。agent 一直走同一條路時，就把它變成一個 workflow tool，並刪掉描述那條路的散文。
- **第一版反而更糟**：散文仍點名了 tool 內部的步驟，agent 就把那些步驟再做一次。修法是散文只保留決策。
- **什麼時候才程式化**：walk 必須既重複、又在各國一致，才變程式；否則留在散文。會變動的部分留在框架裡的散文中。
- **分工**：程式準備事實、執行決定；專家擁有決策表；模型只挑一列；沒有任何一列符合就交給人。（閱讀頁截圖：超限送 team lead、未超限送確認、無法匹配送人。）
- **還沒做的下一步**：讓模型做小決定、用 workflow 把它們串起來，他明說尚未建成。
- **邊界是雙向的**：他們把「數百行」運算式從程式碼搬回散文，因為專家讀不懂。regex 用來抓一個關鍵訊號還可以，多了就搬進 config。判斷留在「答案會變動、且專家讀得到」的地方。

## 第 3 章：控制模型看到什麼、寫入能做什麼（7:24–9:20）

**以前以為**：控制就是給 agent 設權限。

- **Mind：控制從模型看到什麼開始**。讓模型自己決定載入什麼時，它全部載入，然後因為價格剛好看得到，就自己發明了一個價格檢查。「context 裡的任何東西都會變成行動的理由。」
- **runtime 決定模型看到什麼**：訂單任務只給三個事實，完整紀錄留在 runtime，模型的錯誤動作變少。
- **大資料用 handle**：模型傳一個指向 runtime 已持有資料的短名稱，runtime 在任何寫入前檢查它；context 保持小但足以決策，同時驗證 context 一致性。
- **Power：有正確事實的模型仍可能造成損害**。變更被控制兩次：開發時一次，執行時一次。執行時只有程式碼能打開寫入路徑，所以散文可以一天改很多次。
- **寫入前五道牆、寫入後第六道確認有落地**。寫入看起來失敗時 agent 會重試，journal 確保它只執行一次。結論：控制遠不只是 agent 的權限。

## 第 4 章：系統之外，也要保護審查者（9:24–13:05）

**以前以為**：所有控制保護了系統就夠了。實際上沒有任何東西保護他的注意力。

- **他怎麼變成瓶頸**：一開始他讀每一個變更，系統也因此吸收了他的習慣。量大到一個人讀不完之後他開始燃燒殆盡，於是停止逐一閱讀。每個 tech lead 都當過「所有變更都在等的那個人」，agent 只是讓你幾週內就走到這一步，而不是幾年。
- **第一個指標是他自己**：累到說不出改了什麼，就是訊號。儀表板可以是綠的，這個指標卻在響。這時先停下修流程，不等數字。
- **觀察變化率的工具**：讀不了每個 diff，就做觀察「變化與其導數」的工具。例子是 blast radius：上線一條新檢查前，先把規則重播到「數千個」過去 session，發現只會在不到 1% 上觸發。數字跳動的地方他才下去讀。
- **單一訊號先等**：看起來不對時先等它再出現，即使來自專家也一樣。跨 slice 出現一群就不同了，那時修背後的概念一次。
- **agent 會過擬合**：放著不管，agent 會一直加條件直到今天的任務通過。把這些條件拿掉，eval 分數會掉，你就得到一份誠實的缺口清單。
- **兄弟 slice 掃描**：紅的 slice 很少單獨出現。專家的註記變成 eval，agent 到兄弟 slice 找同樣的失敗。兄弟之間刻意因市場與當地法律而不同，所以修正只套到確認失敗的地方。
- **不當訊息匯流排**：任何時刻有 10–20 個這種迴圈開著。他一度成了使用者與 agent 之間的訊息匯流排。在這個規模，每個使用者都必須是有畫面可以給回饋的 evaluator，架構師的工作是把這些迴圈建進系統。每個迴圈寫進 ledger，沒有東西等他的記憶、也沒有東西等他。
- **記憶要落檔，分兩種**：session 結束 agent 就忘光，所以記憶住在檔案裡：「發生了什麼」與「現在什麼是真的」。下一個 session 從「現在什麼是真的」開始。
- **每個 issue 都要連到根因**，否則 agent 會依錯誤的事實做決定，檢查也沒有東西可數。沒有證據就不行動。

## 第 5 章：綠燈要有證據（13:05–15:05）

**以前以為**：綠燈可以相信。Reality 寶石回來了，這次問的是「這個變更是真的嗎」。

- **驗證速度才是限制**：他的 agent 處理一個變更時，近十分之九的時間在檢查；檢查也佔掉他自己一週更大的比例。
- **證據分級**：依證據能證明什麼來排序，真實任務的重播排最高。資料進來之前先寫下「什麼結果會證明我們錯」。每條新檢查都要先故意讓它失敗一次，才能相信它。
- **AI 重構會安靜地失敗**：每個條件、每列決策表都是一個分支，重構後每個分支都必須「剛好落地一次」。例子裡超限的分支在重構中丟了，訂單會不經 team lead 就通過（閱讀頁 14:00 的前後分支圖，該重構被擋下）。
- **真實任務決定測什麼**：把真實任務凍結成一組，拿舊版與新版重播比較。沒有任何真實任務走過的分支，記為「沒有證據」，不是「正確」。
- **第二個 agent 審查**：一個 agent 不能判斷自己的工作。第二個 agent 拿 checklist、看不到作者的推理去審，所以無法被說服而同意。六個月內它長成他大部分的檢查工作。
- **批次會被安靜跳過**：coding agent 做完一批裡的大部分、安靜跳過其餘，context 滿的時候尤其如此。ledger 會顯示跳過了什麼。某個 backlog 裡多數項目看起來已覆蓋，但只有約四分之一真的能結案。所以能改變他們想法的，是「可以計數的證據」。

## 第 6 章：連行為帶測試一起修剪（15:05–16:50）

**以前以為**：只有兩種選擇，全留或一彈指。問題變成「什麼值得帶下去」。

- **一個流程一年的分支**：有些合併回來了，有些仍在漂移，有些已經死了卻看起來還活著。修正只是一個瞬間，之後各種力量會立刻再推回來；這一章處理再生長與分支。
- **程式碼的指標與 ratchet**：第一個指標（他自己）在第 4 章；這些是給程式碼的指標，開場那條線在這裡變成一個數字。ratchet 的意思是計數只能往下。目前兩個指標在跑，另外六個是下一步（具體是哪些指標，逐字稿與閱讀頁都沒說）。
- **每週由真實使用決定去留**：沒有真實任務走到的東西，在移除前先取名、附上證據。這正是他當初彈指時沒有的證據。
- **測試會讓舊變體活著**：agent 會保留任何一個測試仍提到的選項。現在退役一個變體時，它的測試跟著一起退役。
- **整套方法就是一週的流程**（投影片呈現，逐字稿沒有逐項念）。他每週小劑量使用整副手套，「之後再也不必彈指」。

## 結尾：Soul 的第二個代價（16:55–18:00）

交付生產後，他發現自己的工程原則被寫進了系統設計：系統的 skill 與記憶帶著他的習慣與偏見。「Conway 說系統複製組織圖；我們的系統複製糾正它的人。」

他給了 18 個問題（每顆寶石 3 個），建議暫停、挑一個你的 repo 還答不出來的，從那裡開始。**這 18 題只在投影片上**，逐字稿與閱讀頁都沒有列出內容，本頁無法轉述。最後一句建議：趁你還讀得完每個變更時就開始用這些寶石。

## 可以搬到個人 Claude Code／Codex 工作流程的做法

他的系統是多國、多專家的生產流程，個人開發者能直接搬的是下面這些，依投入成本由低到高：

1. **退役功能時連測試與指示一起刪**：移除一個選項或舊行為後，`grep` 它的名稱，刪掉仍提到它的測試、`AGENTS.md`／`CLAUDE.md` 段落與 skill 內文。否則 agent 會把殘留的測試當成「這個行為要保留」的指示。
2. **把「不要做 X」改寫或拿掉**：檢查指示檔裡「不要呼叫 X／不要用 X」的句子。能用程式擋就改用 hook 或 deny 擋，指示裡只寫正向要求；X 跟任務無關就整句刪掉，連提都不提。
3. **重複流程寫成腳本或 skill 後，刪掉散文裡的步驟**：散文只留「什麼情況下用它、做什麼判斷」，不再列出腳本內部的步驟，避免 agent 跑完腳本又手動重做一遍。
4. **新檢查先故意讓它失敗一次**：新加的 hook、lint 規則或測試，先製造一個會違規的改動，確認它真的會紅，再相信它的綠。
5. **動手前寫下反證條件**：重構或修 bug 前，在任務描述裡先寫「出現什麼結果就代表這個改法錯了」，驗收時對照。
6. **重構前凍結真實輸入做新舊比對**：從實際使用中取一組真實輸入（API 請求、資料檔、使用者操作紀錄），重構前後各跑一次比對輸出。沒有任何輸入走到的分支，在完成回報裡標「沒有證據」，不寫「已驗證」。
7. **獨立審查只給 diff 與 checklist**：在 Claude Code 開 subagent 審查時，prompt 只放 diff、需求與 checklist，不貼主 agent 的推理或總結，避免被說服。（本 vault 的 lint 語意層已拍板不加獨立 refuter，此項只適用一般專案的程式變更。）
8. **批次任務用 ledger 逐項記結案證據**：讓 agent 處理多個項目時，維護一份清單，每項要有「證據」欄（測試輸出、檔案路徑、指令結果）。完成回報以有證據的項數為準，不以 agent 說「全部完成」為準；context 快滿時特別要對帳。
9. **記憶檔分「事件」與「現況」**：事件留在 git log 或工作日誌；另一份只寫「現在什麼是真的」，新 session 從現況檔開始。
10. **把「說不清改了什麼」當停止訊號**：發現自己無法用幾句話說明 agent 這輪改了什麼，就先停下來縮小下一輪的範圍或補檢查，而不是繼續放行。

**不適合個人直接搬的**：

- 專家擁有的決策表、使用者當 evaluator、兄弟 slice 掃描：前提是有多位領域專家與大量平行變體（國家 × 流程），個人專案沒有這個結構。
- Runtime 的 handle、寫入前五道牆、journal 防重複寫入：這是生產環境 agent 執行業務動作的防護，coding agent 寫碼時對應的是 deny、沙箱與 git，不必自建。
- Blast radius 重播與 ratchet 指標：需要「數千個」歷史 session 與已定義的複雜度指標；他沒公開指標內容，照抄無從下手。

## 與既有頁的關係

- 與 [[Lauren-Tan-把糾正寫進程式庫]] **部分衝突**：Tan 的信任金字塔把散文放在程式與 lint 之下，方向是盡量從散文搬進程式；Buykin 明說他「以前以為目標是把所有東西搬進程式」，後來發現邊界是雙向的，還把數百行運算式搬回散文讓專家讀。差別在讀者：Tan 的散文只給 agent 讀，Buykin 的散文同時要給簽核的業務專家讀。Tan 禁掉約 99% 的註解，Buykin 則要求程式附白話說明給專家。兩人一致的是「每次糾正都要變成可執行的檢查」：Tan 變 lint，Buykin 變 eval。
- 補強 [[用測試約束-AI-產碼]]：該頁的 mutation testing 只談原始碼，Buykin 把它用在散文指令上（幾乎全部存活）。他另外點出一個該頁沒列的失效模式：**過時的測試會成為 agent 保留舊行為的指示**，退役變體時測試要一起退役。
- 回應 [[Uncle-Bob-的不讀碼約束閘門]] 指出的缺口：那頁的結論是驗證全由 agent 在本地跑、由 agent 回報，沒有獨立副本。Buykin 的凍結真實任務重播與「看不到作者推理的第二個 agent」是部分解法，但第二個 agent 仍是 agent，只是隔離了推理。
- 給 [[AI-產碼加速下的-review-瓶頸]] 的 verification tax 一個從業者自報的量級（檢查佔近十分之九），以及「審查者本身會燃燒殆盡」的第一人稱描述。
- [[Claude-5-世代的指示精簡原則]] 建議互相衝突的規則只留一條；Buykin 的上限 1,500 對 1,000 例子說明為什麼要做：散文和程式衝突時沒有任何東西會報錯，他的對策是給散文做 lint。
- 與 [[Agent-維護知識庫的已知失效模式]] 第 5 條互補：該條的 preprint 證據顯示反覆固化會讓記憶變壞，建議保留原始紀錄。Buykin 同時保留「發生了什麼」與「現在什麼是真的」，但讓新 session 從後者開始；後者正是一份會被反覆改寫的固化產物，要防它漂移就得能回查前者。本 vault 的 `raw/`（write-once）＋ `wiki/`（現況）也是這個形狀。
- [[AI-Engineer-2026-演講精華-AI-工作流程]] 綜合同屆 28 場，本場在其中的「驗證證據」「skill 與指示設計」「多 agent 協作」三節被引用；本頁是完整版。

## 張力與限制

- **他的系統不是典型程式庫**：約四分之三是給 runtime agent 讀的業務散文、有專家簽核、有 110 國的平行變體。「兄弟 slice 掃描」「專家決策表」在一般 repo 沒有對應物，不要硬套。
- **「再也不必彈指」沒有時間軸**：他沒說這套流程跑了多久（只提到第二個 agent「六個月」、一個流程「一年」的分支），也沒有前後對照數字。
- **ratchet 的指標是黑箱**：「只能往下的計數」是演講第 6 章的核心機制，但計的是什麼沒有說，無法驗證也無法照做。
- **人仍是最後的指標**：第 4 章的第一個指標是他自己的疲勞。這很誠實，但也代表這套方法沒有消除對單一架構師判斷的依賴，結尾的「系統複製糾正它的人」就是他自己承認的代價。
- **與「少寫散文」的潮流相反**：同屆多位講者主張少靠散文、多靠程式強制。Buykin 的情境裡散文是業務規格本身，不能消滅，只能工程化（lint、ledger、mutation）。這是情境差異，不是誰對誰錯。

## 勿引用

- **把 110 國當作 Maersk 全公司 AI agent 的部署範圍**：他說的是「我們在 110 國跑這個」，指他這套系統；Maersk 公司層級的國家數是另一個數字。
- **18 題 checklist 的內容**：只在投影片上，沒有公開文字版。任何轉述這 18 題的二手來源都無法對照原文。
