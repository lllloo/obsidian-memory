測試流程是**堆起來的**，不是一次設計好的。每一層都要在下一層開始之前真的在跑，否則後面那些昂貴的手段（mutation、property-based）建在流沙上——這點在 [[用測試約束-AI-產碼]] 第六節的順序建議裡是核心約束。

**適用背景**：前後端分離，前端 Vue、後端 Laravel，兩端各自獨立部署、透過 HTTP API 溝通。

```
   ┌─────────────────────┐                  ┌─────────────────────┐
   │  Vue (SPA)          │    HTTP / JSON   │  Laravel (API)      │
   │    components       │ ◀──────────────▶ │    Controller       │
   │      composables    │                  │      Service        │
   │        utils        │                  │        Model / DB   │
   └─────────────────────┘                  └─────────────────────┘
            前端 repo                              後端 repo
```

分離架構對測試流程的關鍵影響是：**兩端各有一套完整的測試堆疊，而「兩端接起來對不對」變成一個誰都不擁有的獨立問題**。中間那條 HTTP 邊界是分離架構最容易出事的地方，也是本頁第三層存在的理由。

四層的射程如下——前兩層兩端各走各的，後兩層才跨越邊界：

```
第 1 層 · 單元測試 ── 不啟動框架、毫秒級
    ├ 前端：utils、純 composable
    └ 後端：Service、Value Object

第 2 層 · 框架內測試 ── 啟動框架，但仍在單邊之內
    ├ 前端：掛載元件、驗互動
    └ 後端：Feature 測試、打 route、碰 DB

第 3 層 · 契約測試 ── 分離架構特有，跨越 HTTP 邊界
    └ 前端假設的 API 形狀  ⟷  後端實際回的形狀

第 4 層 · 端到端 ── 真瀏覽器 + 真後端，最慢最脆
    └ 只留關鍵路徑
```

第 1、2 層全綠**不代表系統是對的**：兩端可以各自完美，而前端以為欄位叫 `total`、後端回的是 `total_amount`。這種錯只有第 3 層抓得到，而它是分離架構獨有的成本。

本頁逐層展開，每層固定回答三件事：**做什麼、怎麼知道這層完成了、什麼時候該停下不再加碼**。

## 第一層：單元測試

### 起點不是「怎麼寫測試」，是「有沒有東西可以測」

絕大多數專案卡在這裡而不自知，而且 Vue 與 Laravel 卡的是**同一個坑**：框架讓你很容易把邏輯寫在「必須啟動框架才能執行」的地方，而那正是不可測的地方。

前端，邏輯埋在元件裡：

```vue
<!-- ❌ 折扣計算埋在 script setup 裡，要測它得先掛載整個元件 -->
<script setup>
const total = computed(() => {
  let sum = items.value.reduce((a, i) => a + i.price * i.qty, 0)
  if (sum > 1000) sum = sum * 0.9
  return Math.round(sum)
})
</script>
```

後端，邏輯埋在 Controller 裡：

```php
// ❌ 要測這段折扣規則，得發一個 HTTP request、還要有 DB
public function store(Request $request)
{
    $sum = collect($request->items)->sum(fn($i) => $i['price'] * $i['qty']);
    if ($sum > 1000) { $sum = $sum * 0.9; }
    return response()->json(['total' => round($sum)]);
}
```

兩段都**沒有單元可以測**。要驗證那條「滿 1000 打九折」的規則，前端得掛載元件、後端得跑起 HTTP 與資料庫——慢、脆，而且失敗時不會告訴你是哪一段錯了。

```
❌ 抽離前 ── 判斷長在框架內部
    Vue 元件
      └ script setup
          └ 折扣規則          要測它，得先掛載整個元件

    Laravel Controller
      └ store()
          └ 折扣規則          要測它，得發 HTTP request + 起 DB


✅ 抽離後 ── 判斷脫離框架
    Vue 元件 ──呼叫──▶ utils/pricing.js
                          └ 折扣規則      ← 測這裡

    Laravel Controller ──呼叫──▶ PricingService
                                    └ 折扣規則      ← 測這裡

    框架那一側只剩「呼叫它、把結果交出去」，沒有判斷、不需要測
```

所以第一層真正的第一個動作是**把判斷抽出來**，讓它脫離框架：

```js
// ✅ src/utils/pricing.js — 純函式，不 import 任何 Vue 的東西
export function calcTotal(items) {
  const sum = items.reduce((a, i) => a + i.price * i.qty, 0)
  return Math.round(sum > 1000 ? sum * 0.9 : sum)
}
```

```php
// ✅ app/Services/PricingService.php — 不碰 Request、不碰 Model
class PricingService
{
    public function calcTotal(array $items): int
    {
        $sum = collect($items)->sum(fn ($i) => $i['price'] * $i['qty']);
        return (int) round($sum > 1000 ? $sum * 0.9 : $sum);
    }
}
```

抽完之後，元件與 Controller 都只剩下「呼叫它、把結果交出去」，而測試變成幾行、毫秒級：

```js
// src/utils/__tests__/pricing.spec.js
import { describe, it, expect } from 'vitest'
import { calcTotal } from '../pricing'

describe('calcTotal', () => {
  it('未滿門檻不打折', () => {
    expect(calcTotal([{ price: 100, qty: 2 }])).toBe(200)
  })
  it('滿 1000 打九折', () => {
    expect(calcTotal([{ price: 500, qty: 3 }])).toBe(1350)
  })
  it('空清單為 0', () => {
    expect(calcTotal([])).toBe(0)
  })
})
```

```php
// tests/Unit/PricingServiceTest.php
public function test_滿_1000_打九折(): void
{
    $service = new PricingService();
    $this->assertSame(1350, $service->calcTotal([['price' => 500, 'qty' => 3]]));
}
```

注意後端這個測試**沒有繼承需要資料庫的 TestCase、沒有 `RefreshDatabase`**——那是它能留在第一層的原因。

**判準**：一個函式若要測它得先準備環境（掛載元件、啟動框架、連資料庫、開網路），它就還不是單元。先抽，再測。

### 該測什麼、不該測什麼

第一層只測**你自己寫的判斷邏輯**，也就是「給定輸入 → 應該得到什麼輸出」的地方：

| 前端 (Vue) | 後端 (Laravel) |
|---|---|
| `utils/` 的格式化、計算、驗證函式 | Service 類別裡的業務規則 |
| composable 中不依賴生命週期的純計算 | Value Object、DTO 的轉換與驗證 |
| 表單驗證規則、金額與日期的處理 | 純方法：狀態機轉換、權限判斷、價格計算 |

不測的：框架本身的行為、第三方套件是否正常運作、單純把 A 傳給 B 的膠水碼。測 Eloquent 能不能存進資料庫、測 `computed` 會不會重算，抓到的是框架的 bug 不是你的。**元件的渲染與互動、API endpoint 的行為都不屬於這一層**，它們需要啟動框架，留到第二層。

每個函式起手三種案例就夠了：

| 案例 | 問的問題 |
|---|---|
| 正常輸入 | 該成功的時候有沒有成功 |
| 邊界／空值 | 空陣列、`null`、`0`、剛好等於門檻的值會不會出錯 |
| 明確的錯誤輸入 | 格式不對時是回預設值還是丟例外——而且這是刻意決定的 |

上面折扣的例子裡，`1000` 這個門檻**剛好等於**時該不該打折，就是一定要有一條測試釘死的邊界。

斷言要具體。`expect(x).toBeTruthy()`、`assertNotNull()` 這類弱斷言是 AI 產測試最高頻的失效模式（見 [[用測試約束-AI-產碼]] 第一節），它們看起來綠，但容忍錯誤的值。PHP 端優先用 `assertSame()` 而不是 `assertEquals()`——後者不比較型別，`"1350"` 會等於 `1350`。

### 怎麼跑

測試必須能一個指令跑完，而且那個指令要寫在專案文件裡。沒有統一入口的測試，實質上等於沒有測試——下次沒有人（包含 agent）會記得怎麼跑它。分離架構本來就是兩個入口，這是正常的：

```bash
# 前端
npm run test:unit

# 後端（只跑不需要資料庫的那批）
php artisan test --testsuite=Unit
```

前端用 Vitest（Vue 官方測試指南推薦的 runner，與 Vite 共用同一份設定，不必再維護第二套 transform 設定）。後端沿用 Laravel 內建的測試設定，`phpunit.xml` 預設就把 `Unit` 與 `Feature` 分成兩個 testsuite，第一層只跑前者。

這條分界線在檔案結構上是看得見的，值得刻意維持：

```
前端                                   後端
npm run test:unit                      php artisan test
  │                                      │
  ├─ src/utils/__tests__/               ├─ tests/Unit/          ◀ 第 1 層
  │     pricing.spec.js        ◀ 第 1 層 │     PricingServiceTest
  │     validators.spec.js              │     DiscountRuleTest
  │        純函式、無 import vue         │        不繼承需要 DB 的 TestCase
  │                                      │        無 RefreshDatabase
  │                                      │
  └─ src/components/__tests__/          └─ tests/Feature/       ◀ 第 2 層
        CartItem.spec.js       ◀ 第 2 層       OrderApiTest
           需要 mount()                          打 route、碰 DB
```

**判斷一個測試該放哪邊，只問一個問題：拿掉框架它還能不能跑。** 能，就是第 1 層；不能，就是第 2 層。

這裡有個好用的副作用：**如果 `--testsuite=Unit` 跑起來很慢，那就是訊號**——代表有測試偷偷連了資料庫，它其實不屬於這一層。

### 這一層完成的樣子

四個條件同時成立才算：

1. 業務規則已從元件與 Controller 抽成不依賴框架的函式／類別
2. 兩端各一個指令跑完，且**全綠**
3. `Unit` 那批**不需要資料庫也不需要掛載元件**就能跑（這條會被日後偷懶的改動破壞，值得盯）
4. 兩個指令都寫進 `README.md`，下一個人（或 agent）不用猜

第 2 點的「全綠」要真的驗證過。測試寫了但沒人跑、跑起來是紅的，比沒有測試更糟——它讓人以為有保護。

### 什麼時候該停

**不要追覆蓋率數字。** 第一層的目標是「每條業務規則至少有一個具體斷言」，不是 80%。追高覆蓋率會逼你為膠水碼、Model 的欄位宣告、元件的樣板寫沒有意義的測試，那些測試日後只會變成改碼時的阻力。

**測試是要維護的負債。** 覆蓋率從 60% 推到 90% 的那 30%，通常是最沒價值、最難維護的部分。

當你發現「再加測試也想不出什麼輸入會讓它出錯」時，這一層就夠了，往下一層走。
