測試流程是**堆起來的**，不是一次設計好的。每一層都要在下一層開始之前真的在跑，否則後面那些昂貴的手段（mutation、property-based）建在流沙上——這點在 [[用測試約束-AI-產碼]] 第六節的順序建議裡是核心約束。

**本頁是總覽**：講分層、判準與兩端共通的紀律。各端的具體做法分開走，因為 Vue 與 Laravel 的工具、檔案結構與坑都不一樣，混在一頁讀起來會一直左右橫跳：

- [[專案測試流程-前端-Vue]] — Vitest、composable 與元件的分界、`mount()` 的成本
- [[專案測試流程-後端-Laravel]] — `Unit`／`Feature` 兩個 testsuite、資料庫的隔離

另有兩頁不分端，橫跨兩端：[[E2E-測試的資料庫隔離]]（第 3 層的環境前提）與 [[測試手段的優先序與成本]]（先做哪個、各要付多少）。

## 適用背景

前後端分離，前端 Vue、後端 Laravel，兩端各自獨立部署、透過 HTTP API 溝通。

```
   ┌─────────────────────┐                  ┌─────────────────────┐
   │  Vue (SPA)          │    HTTP / JSON   │  Laravel (API)      │
   │    components       │ ◀──────────────▶ │    Controller       │
   │      composables    │                  │      Service        │
   │        utils        │                  │        Model / DB   │
   └─────────────────────┘                  └─────────────────────┘
            前端 repo                              後端 repo
```

分離架構對測試流程的關鍵影響，不是「工作量變兩倍」，而是**多出一個誰都不擁有的問題**：兩端各自全綠，接起來仍然可能是壞的。中間那條 HTTP 邊界是分離架構最容易出事的地方，也是第三層存在的理由。

## 三層的射程

前兩層在單邊之內，第三層跨越 HTTP 邊界：

```
第 1 層 · 單元測試 ── 不啟動框架、毫秒級
    ├ 前端：utils、純 composable
    └ 後端：Service、Value Object

第 2 層 · 框架內測試 ── 啟動框架，但仍在單邊之內
    ├ 前端：元件測試 —— 掛載元件、驗互動，API 一律 mock
    └ 後端：整合測試（Laravel 命名為 Feature）—— 打 route、碰 DB

第 3 層 · 端到端 ── 真瀏覽器 + 真後端，最慢最脆
    └ 只留關鍵路徑
```

**第 2 層的兩個名字要分開講**。前端叫元件測試（component test）、後端叫整合測試（integration test），對外一律用這兩個詞；「框架內測試」是本頁自創的說法，好處是判準無歧義（啟動框架、但不跨 HTTP），代價是不通用。Laravel 的 `Feature` 是框架專有命名，跟別的生態溝通時說 integration，否則會被理解成 BDD 的驗收測試。前端第 2 層並非全是元件測試——Pinia store 串接、有副作用的 composable 也在這層，判準始終是「啟動框架但沒跨 HTTP」而非「有沒有元件」。

第 3 層有一個前兩層沒有的前提：它會真的寫進資料庫，而且**收不回來**——跨進程的請求包不進測試端的交易，`RefreshDatabase` 那套在這裡失效。這使得「E2E 的資料庫放哪、什麼時候重置」變成開跑前就得決定的事，見 [[E2E-測試的資料庫隔離]]。

**第 1、2 層全綠不代表系統是對的。** 兩端可以各自完美，而前端等的欄位叫 `total`、後端回的叫 `total_amount`——這種錯不在任何一邊的測試射程內：前端測試裡的 API 回應是自己 mock 的（形狀是手寫的，與後端無關），後端斷言的是自己回了什麼（不知道對面在讀哪個欄位）。單體專案沒有這條邊界，所以也沒有這個成本；這是分離架構自己買單的部分。**這條縫在本分層裡沒有專屬的一層負責**，處置見下節。

> ⚠️ 精緻版架構圖 [`docs/architecture/testing-layers-vue-laravel.html`](../docs/architecture/testing-layers-vue-laravel.html) 畫的是**四層**版本，為 2026-08-09 快照，與本節現行的三層不一致；該層產物為快照、不回頭同步。

## 契約測試：不採（2026-08-28 拍板）

**已被取代（2026-08-28）**：本頁原本的分層為四層，第 3 層是契約測試（Contract／CDC，前端是 consumer、後端是 provider），E2E 為第 4 層。使用者拍板移除該層，改為三層，E2E 遞補為第 3 層。以下保留這層的知識與不採的理由。

那條縫是真的：**沒有任何一層在驗「前端手寫的 mock 形狀，跟後端實際回的形狀是否一致」**。後端改欄位名，兩端測試都會全綠——後端的斷言跟著改了，前端測的是自己寫的假資料。

不採的理由不是它沒價值，是**建置成本與適用條件不合**：契約測試真正不可取代的時機是兩端的部署節奏分開（後端能在前端不知情的情況下上線），此時型別是編譯期的、擋不到已部署的舊前端，才需要執行期的契約驗證。前後端同一批人維護、同步部署時，成本高於它擋掉的 bug。正統 CDC（Pact + broker）解決的是「不知道有誰在用我的 API」——多消費端、跨團隊、獨立部署節奏，與本專案情境不符。

**這條理由有外部佐證**：consumer-driven contract testing 在 Thoughtworks Radar 確實位於 **Adopt** 環，但該 blip **最後更新停在 2016 年 11 月**，原文是「decided to bring consumer-driven contract testing back from the archive for this edition」，語境為微服務普及。也就是說那個 Adopt 是給**微服務、多消費端、獨立部署**的，不是給單團隊前後端分離的。（**medium-high**：Radar 官方頁面一手，2026-08-28 查；環位與日期會隨改版變動，引用前回查。）

**目前的處置**：只有兩件事在做，都不新增測試層。

| 手段 | 覆蓋 | 性質 |
|---|---|---|
| 後端整合測試 | 全部 endpoint 的**自身正確性** | 已在第 2 層，本來就該做 |
| E2E | 走過的少數路徑的**串接** | 已在第 3 層 |

**那條縫目前沒有自動化保護**：E2E 沒走到的 endpoint，欄位名或型別變了要靠人工發現。這是明知的取捨，不是疏漏。

### 重開條件與候選方案

任一發生就值得回頭評估：**真的被欄位不一致咬過一次**（最實際的訊號）、前後端部署節奏分開、出現第二個消費端、或 endpoint 多到人工追不動。

重開時的第一步不是補契約層，而是先做成本最低的那條：**讓後端產出 OpenAPI spec，前端所有對 API 形狀的假設都從那份 spec 長出來**。以下工具的維護狀態為 2026-08-28 經 GitHub API 實查，**本專案皆未實測**。

```
Laravel route/FormRequest/Resource
   ↓ Scramble（靜態分析，不需寫 PHPDoc）
OpenAPI spec  ─┬→ openapi-typescript  → 前端型別
               ├→ Orval / Hey API     → 前端 MSW mock handler
               └→ Schemathesis        → 打真 API 驗實作是否偏離 spec
```

| 工具 | 定位 | 現況 |
|---|---|---|
| [Scramble](https://github.com/dedoc/scramble) | Laravel → OpenAPI 3.1，讀 route／FormRequest／Resource／enum | MIT，2,190 stars，v0.13.42 (2026-08-21)，Laravel 10–13、PHP ^8.1 |
| [openapi-typescript](https://github.com/openapi-ts/openapi-typescript) | spec → TS 型別，純編譯期零 runtime | MIT，8,337 stars，7.13.0，需 Node 20+ |
| [Orval](https://github.com/anymaniax/orval) | spec → client + 型別 + **MSW handler** | 6,401 stars，2026-08-27 |
| [Hey API](https://github.com/hey-api/openapi-ts) | 同上，MSW 為 plugin | 5,321 stars，2026-08-24 |
| [Schemathesis](https://github.com/schemathesis/schemathesis) | spec → property-based 自動產 API 測試，零 per-endpoint 維護 | 3,563 stars，2026-08-27 |

**中間那條（MSW mock 從 spec 產）是最直接關掉這條縫的做法**：前端元件測試的假資料不再手寫，而是從後端真實定義來的，後端改欄位名重產即紅，且不新增測試層、不需要後端跑著。Schemathesis 是 Python CLI，只吃 spec 與 HTTP，**與後端語言無關**，不進 PHP 專案。

⚠️ **整條鏈的成敗押在一個未驗證的前提**：Scramble 能否從既有碼推出準確的 spec。對動態組出的回應、多型 Resource 推得多準無資料，官方稱可用 PHPDoc 補標但比例未知。所以重開時的第一個動作是裝上去看 `/docs/api` 產出什麼，spec 準則後面全部成立、不準則全部打折。

不採的替代路線：spatie/laravel-typescript-transformer 需先把回應改寫成 laravel-data DTO，屬侵入式重構；[Specmatic](https://github.com/znsio/specmatic)（395 stars，MIT）把 OpenAPI 當可執行契約兼 mock server，社群規模小、本情境用不上。

**另一個概念差異**：上述為 **code-first**（從既有碼反推 spec，零改動，但 spec 永遠跟隨實作）。**schema-first** 反過來——先設計 spec 並與消費端評審，兩邊都對它實作，改 spec 要雙方同意。後者更嚴謹但要求流程改變（每次改 API 先開設計會），既有專案不划算；等前後端真的分家再考慮。

**注意本頁術語表仍收 Contract Test／CDC 詞條**——那是查閱用附錄，涵蓋範圍刻意比正文廣，不代表採用。

## 一個測試該歸哪一層

不必憑感覺分類。三個問題依序問下去，每個測試都有唯一歸屬：

```
一個測試
   │
   ├─ 拿掉框架還能跑嗎？ ── 能 ──▶ 第 1 層 · 單元
   │        │
   │        └ 不能
   │            │
   │            ├─ 只在單邊之內嗎？ ── 是 ──▶ 第 2 層 · 框架內
   │            └────────────────── 否 ──▶ 第 3 層 · 端到端
```

**第一個問題就能擋掉大部分的混亂。** 「拿掉框架還能不能跑」在兩端都有現成的檢查訊號，各自寫在子頁裡。

分層不是為了分類學上的整齊，而是為了**跑的頻率不同**：第 1 層每次存檔都該跑得起，第 3 層通常只在合併前跑。層次混在一起，最慢的那個會拖垮整批，最後的下場是整批都不跑。

跨出單邊之後不必再問「需不需要真瀏覽器」——三層分法裡答案一律是 E2E。原本用來分流「不需要瀏覽器的跨邊界測試」的那一問，隨契約層一起移除（見上節）。

## 兩端共通的紀律

以下四條與框架無關，兩端都適用，子頁不再重複。

### 起點不是「怎麼寫測試」，是「有沒有東西可以測」

絕大多數專案卡在這裡而不自知，而且 Vue 與 Laravel 卡的是**同一個坑**：框架讓人很容易把判斷寫在「必須啟動框架才能執行」的位置，而那正是不可測的地方。

```
❌ 判斷長在框架內部              要測它，得先把整個框架跑起來
     框架外殼
       └ 判斷

✅ 判斷脫離框架                  框架那側只剩「呼叫它、把結果交出去」
     框架外殼 ──呼叫──▶ 判斷     沒有判斷，因此不需要在第一層測它
```

**判準**：一個函式若要測它得先準備環境（掛載元件、啟動框架、連資料庫、開網路），它就還不是單元。先抽，再測。兩端各自怎麼抽，見子頁。

### 斷言要具體

`toBeTruthy()`、`assertNotNull()`、`length > 0` 這類弱斷言是 AI 產測試最高頻的失效模式（見 [[用測試約束-AI-產碼]] 第一節），它們看起來綠，但容忍錯誤的值。要斷言**確切等於什麼**。

每個函式起手三種案例就夠了，不必更多：

| 案例 | 問的問題 |
|---|---|
| 正常輸入 | 該成功的時候有沒有成功 |
| 邊界／空值 | 空集合、`null`、`0`、剛好等於門檻的值會不會出錯 |
| 明確的錯誤輸入 | 格式不對時是回預設值還是丟例外——而且這是刻意決定的 |

「滿 1000 打九折」這種規則，**剛好等於 1000** 就是一定要有一條測試釘死的邊界。

### 一個指令、寫進文件、而且真的是綠的

測試必須能一個指令跑完，且那個指令要寫在專案文件裡。沒有統一入口的測試，實質上等於沒有測試——下次沒有人（包含 agent）會記得怎麼跑它。分離架構本來就是兩個入口，這是正常的，不必勉強合成一個。

「全綠」要真的驗證過。**測試寫了但沒人跑、跑起來是紅的，比沒有測試更糟——它讓人以為有保護。**

### 不追覆蓋率數字

每一層的目標都是「每條業務規則至少有一個具體斷言」，不是 80%。追高覆蓋率會逼你為膠水碼、欄位宣告、樣板寫沒有意義的測試，那些測試日後只會變成改碼時的阻力。

**測試是要維護的負債。** 覆蓋率從 60% 推到 90% 的那 30%，通常是最沒價值、最難維護的部分。當你發現「再加測試也想不出什麼輸入會讓它出錯」時，這一層就夠了，往下一層走。

## 進度

本頁與子頁採漸進撰寫，一次展開一層。

| 層 | 狀態 |
|---|---|
| 第 1 層 · 單元 | ✅ 兩端都完成 |
| 第 2 層 · 框架內 | 📝 做法已寫進兩個子頁，**尚未實作** |
| 第 3 層 · 端到端 | 環境前提已寫（見下），測哪些路徑未定 |

**兩個先行記錄的例外**（都尚未在本專案實測）：

- [[E2E-測試的資料庫隔離]] — 屬第 3 層，講的是環境前提而非測試寫法，先行記錄以免真的動手做 E2E 時才發現資料庫選錯。
- [[測試手段的優先序與成本]] — 不屬任何一層，是「有限資源下先做哪個」這一軸：各手段的速度量級、建置與維護成本、該跑在哪個迴圈，以及變異測試為何是體檢不是門禁。

**第 2 層的做法雖已寫下，實作要回各自的 repo 做**，不在本 vault 內進行。

| Mutation Score / MSI | 變異分數／變異測試指標 | 作為品質權威指標**方法論上不成立**，理由見 [[用測試約束-AI-產碼]] |
