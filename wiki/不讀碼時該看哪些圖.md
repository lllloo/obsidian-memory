當程式碼由 agent 產出、量大到無法逐行閱讀且本來就陌生時，「用圖表理解專案」這個直覺需要先改一個前提：**圖的用途不是看懂 agent 寫了什麼，而是把 agent 不准越過的線寫下來，並讓機械檢查它有沒有越過。**

追實作是無底洞——那一層每天都在變；而**架構層變得很慢，慢到可以當參照物**。這條分界不是偏好，C4 官方把它列成了可查的變動速度階梯（見下）。

> 本頁為 2026-08-10 deep-research 回存（6 搜尋角度 → 26 來源 → 129 主張 → 對抗查證 25 條，22 確認、3 否決）。每條主張就地標**證據強度與票數**；被否決者列於「勿引用」節。**本輪覆蓋嚴重不均**，未查證的部分列於末節，不得由本頁內容推導。

## 選層依據：變動速度階梯

C4 官方 FAQ 逐字列出四層的過期速度（**high，3-0**，[c4model.com/diagrams/faq](https://c4model.com/diagrams/faq)）：

| 層 | 內容 | 變動速度 | 對 AI 產碼的意義 |
|---|---|---|---|
| context | 系統與外界誰互動 | `very slowly` | 幾乎不受影響 |
| container | 可部署／可執行單元、各自技術、彼此怎麼通訊 | `relatively slowly` | **選這層**；過期＝架構真的變了，而那正是該知道的時刻 |
| component | 單一 container 內部的程式碼群集 | `frequently` | 邊界值得人定，內容不值得追 |
| code | class 圖 | `very quickly` | 官方原話建議「**(1) 根本不要畫，或 (2) 用 IDE 之類的工具隨需產生**」 |

agent 一天產出的變更幾乎全部落在第三、四層。**手繪投資集中在高層、低層交給工具即時生成**，這是 C4 官方自己劃的人工／自動分界線（**high，3-0**）。官網另註多數團隊只需要 context 與 container 兩層。

## 這三張在完整視圖地圖上的位置

上一節的 C4 階梯是**抽象層級**（放大倍率：系統 → 容器 → 元件 → 類別）。但「架構視圖」還有一條正交的軸——**關注面向**（同一個系統，從結構看／從執行期看／從部署看／從資料看）。兩條軸容易被混為一談，而下面要選的「畫哪些、不畫哪些」發生在第二條軸上。

四套主要體系攤開對照（**medium-high**；arc42 12 章與 Rozanski & Woods 7 個 viewpoint 為 2026-08-10 一手 fetch 官網取得，但拿到的是頁面摘要而非逐字全文；**4+1 的五個視圖名稱未在本輪複驗，屬通用知識**）：

> **2026-08-10 補查：本表為選圖服務而精簡，完整清單見 [[架構視圖體系完整對照]]。** 三處會改變讀法：(a) **C4 其實有七種圖不是四層**——官網把 system landscape／dynamic／deployment 列為 supporting diagrams，其中**多系統全景只有 C4 有**，本表沒有那一列；(b) **品質屬性（安全、效能、可演化性）不是缺一張圖**，Rozanski & Woods 另有十個與 viewpoint 正交的 **perspective**，作法是回頭審每張既有圖而非新增視圖；(c) **arc42 十二章裡只有 5／6／7 是視圖**，把它當視圖體系會誤解——它是文件模板。該頁另補上 RM-ODP 與 SEI Views and Beyond 兩套、UML 官方分類，以及 ISO/IEC/IEEE 42010 已於 2022-11-30 出第二版。

（ISO/IEC/IEEE 42010 只定義 viewpoint／view 這組概念框架本身，不提供具體清單，故不列入。）

**這張表最關鍵的一格是「資料」那列：四套體系裡只有 Rozanski & Woods 把資料當成一等視圖，C4、arc42、4+1 全都沒有。** 這具有實務後果——當處境是「想先看懂資料怎麼來回」時，從 C4 出發會結構性地答不到點，因為那個東西根本不在它的清單上。本頁的 ② ER 切片圖等於是自己補上這個空缺，沒有現成框架範本可抄。

### 為什麼不畫另外三個

- **執行期行為視圖**（dynamic／runtime／process）——C4 官方自己在 Recommended 欄標 **No**（**high，3-0**，見下節引述），且它以靜態模型為輸入。靜態圖都還沒穩定就先畫這層是本末倒置。
- **部署視圖**——除非真的在管叢集／failover，否則單機或單一 PaaS 的部署圖只會是三個框，不值一張圖的維護成本。
- **開發組織視圖**（development）——對應 C4 的 component 層，官方標 `frequently` 變動；agent 一天產出的變更幾乎全落在這裡，追不完。

### 一個框架集體漏掉、但在 AI 產碼下反而變重要的視圖

**Operational viewpoint（維運）只有 Rozanski & Woods 有**，而它的價值在這個處境下被放大了一層：**那是 agent 改不到的地方**。agent 會改程式碼、改測試、甚至改 CI 設定，但它動不了「生產環境實際發生了什麼」。當所有描述性文件都可能被 agent 產出的變更悄悄推翻時，執行期的真實訊號（trace／log／metrics）是少數還能當參照物的東西。

⚠️ 這段是**推論而非查證結論**（強度 low，本輪無來源支撐此一命題），但它與下文「靜態分析與執行期追蹤缺口互補」一節的 OTel service graph connector 同向——後者正是從 trace 反推服務拓撲、完全不碰原始碼。

### 本頁三張圖的定位

對回上表：① container 圖 ＝ **靜態結構**視圖，② ER 切片圖 ＝ **資料**視圖（框架集體缺席處），③ 依賴規則 ＝ **不在任何框架清單上的第四類**。第三類值得單獨說明：四套體系全都預設「視圖是描述現狀」，而當產碼的是 agent 時，描述性的圖每天都在過期——真正站得住的是**規範性的約束**。這就是本頁開頭「圖從文件變成驗收界面」那句話在視圖分類學上的位置：它不是既有分類裡的某一格，是這些框架成形的年代還不需要的一格。

## 近期有沒有人推薦該畫哪些圖：沒有，但方向轉了

查證日 2026-08-10。結論是**沒有任何機構級來源在推薦「AI 產碼時代該畫哪些架構圖」**——而這個「沒有」比任何一份清單都更能說明現況。

Thoughtworks Technology Radar **Vol 34（2026-04）** 的 techniques 分類中，架構相關條目共五條，**沒有一條在講該畫什麼圖或文件該怎麼結構化**（**medium-high**；本節皆為 WebFetch 頁面摘要，非逐字全文，引用個別語句前應回讀原頁）：

| 條目 | Ring | 內容 |
|---|---|---|
| **Feedback sensors for coding agents** | **Trial** | 建立 agent 能**直接讀取**的回饋迴路，作為 feedback backpressure；點名 compilers、linters、structural tests、test suites、custom linters。**明確不涉及架構圖、依賴規則或架構約束** |
| Mapping code smells to refactoring techniques | Trial | 引導 agent 走向特定重構手法 |
| Architecture drift reduction with LLMs | Assess | 靜態分析結合 LLM 評估，點名 ArchUnit、Spectral、Spring Modulith |
| Code intelligence as agentic tooling | Assess | agent 經 LSP 取用 AST 工具、以 OpenRewrite 等 codemod 做架構強制 |
| Context graph | Assess | 把決策、政策、例外建成可查詢的圖結構 |

**這張表的成熟度梯度對選擇有直接意義**：越靠近程式碼層的確定性檢查，成熟度越高（Feedback sensors 已到 Trial）；越靠近架構層，越不成熟（drift reduction 只到 Assess）。也就是說本頁 ③ 的方向有機構背書，但那個背書比「編譯器與測試」弱一級。

### 唯一提出視圖清單的論文，文件化的對象不同

RAD-AI（arXiv 2603.28735）提出五個視圖：System Context、Component（ML pipeline 階段與資料流）、**Data**（資料血緣與品質）、**Model**（模型規格、訓練方法、部署）、**Operational**（監控與 AI 專屬維運），外加決策紀錄、風險與合規對應、訓練/推論管線文件。

⚠️ **不可直接套用**：它文件化的對象是 **AI 系統本身**（含 ML pipeline 與模型生命週期），不是「用 AI coding agent 寫出來的一般系統」。一般 Web 專案裡沒有 Model View 要記的東西。這與本頁勿引用節裡「EU AI Act 主張混淆 AI 系統與 AI 產碼」是同一類混淆，只是換了層皮。且該提案**完全未經驗證**——無 case study、無比較評估、無專家評審，是基於文獻回顧的概念性貢獻（**high**，作者自陳）。

### 一個弱但有意思的收斂

RAD-AI 主張 arc42 與 C4 缺的項目中，有兩項恰好是上一節對照表裡的空格：**data flow and lineage** 與 **model lifecycle and operational concerns**。一群從完全不同問題出發的人（他們煩惱怎麼記錄 ML 系統，本頁煩惱 agent 產碼看不懂），獨立指向了同樣的**資料**與**維運**兩格。

這不構成證據（**low**，兩者的問題域不同、樣本為一），但作為「那兩格可能是四套老框架的結構性缺陷、而非本頁處境特殊」的旁證，值得記下。

### 據此的四點取捨

1. **不必等一份「AI 時代圖表推薦清單」**——目前不存在，機構注意力明顯不在那裡。本頁三張圖沒有競品可比較，不是因為最優，是因為沒人在做這件事。
2. **投資順序上，agent 可直接讀取的訊號優先於圖**：編譯錯誤、linter、測試是唯一到 Trial 級的方向。
3. **本頁 ③（依賴規則 CI 檢查）維持現有定位**：方向有 Assess 級背書、值得做，但無量化實證，不值得押重注。
4. **圖的價值定位要分清楚**：它幫**人**做決定（該不該接受這個改動、這條線該不該存在），不是幫 agent 幹活——agent 要的是它讀得懂的確定性訊號。這與本頁開頭「圖是驗收界面」並不矛盾：界面是給人用來判讀的，機械檢查才是給 agent 撞的牆。

## 三張圖

### ① Container 圖 — 大方向本體，人畫一次

回答「有哪些可部署／可執行單元在跑、各用什麼技術、彼此怎麼通訊」，**不回答容器內部的程式碼結構**，也不含叢集／負載平衡／failover（那屬 deployment 圖）（**high，3-0**）。

對「程式碼陌生」這個處境，它的關鍵性質是**讀這張圖不需要讀碼**——框是「各自跑起來的東西」（前端 app、API 行程、資料庫、queue worker、排程、第三方服務），不是資料夾也不是類別。

**這張要人畫**，因為它記錄的是意圖而非實作。畫的時候有四個問題要答，其中第四個是多數專案從未寫下來的：

1. 有哪些東西是各自跑起來的？
2. 各自用什麼跑？
3. 誰主動呼叫誰、走什麼協定？
4. **哪一條連線希望永遠不要出現？**

第四題的答案畫成圖上一條「不存在的線」（禁令），是整張圖唯一能直接轉成機械檢查的部分——圖由此從文件變成驗收界面。

> C4 的 **dynamic diagram**（展示一次操作經過哪些節點，類 UML sequence 但用編號互動）官方在「Recommended?」欄明確標 **No**，主張只在展示重複出現的模式或互動特別複雜的功能時才畫，且它**以靜態模型為輸入**——先有結構圖才疊執行順序，不是拿它取代結構圖（**high，3-0**）。注意這個 No 針對的是「要長期維護的文件產出」，不是說 sequence 式的圖對理解陌生程式碼無用。

### ② ER 圖（切片版）— 唯一可信的自動產物

可信的原因是**它讀資料庫 metadata，不猜程式碼**：資料庫裡有什麼就是什麼，沒有靜態分析那種漏邊問題。同理它與應用程式語言／框架無關。

兩條成熟路線（**high，3-0**）：

- **tbls**：Go 單一 binary，經 DSN 連線，支援 PostgreSQL／MySQL／MariaDB／SQLite／BigQuery／Cloud Spanner／Redshift／SQL Server／DynamoDB／MongoDB／ClickHouse 等（截至 2026-08 的 README；Snowflake 與 Databricks 官方標為 **Experimental**，成熟度不等同前者）。ER 圖可輸出 png／jpg／svg（預設）／mermaid，另可經 `tbls out` 產 PlantUML 與 DOT（**high，3-0**）。
- **SchemaSpy**：經 JDBC 讀 metadata，宣稱支援多數 JDBC 相容 DBMS 且可自行擴充 `databaseType`。**它的「中立」是對你蓋的東西中立、不是對你要裝的東西中立**——需要 JVM、Graphviz（高品質渲染）與各 DBMS 的 JDBC driver。

**兩個實務陷阱**：

- **legacy schema 常常沒宣告 FK**（或為效能拿掉），純靠宣告 FK 產圖會近乎空白。SchemaSpy 能用「欄位名＋型別比對主鍵」推論隱含關聯並以虛線畫出，但**誤報實質存在**：GitHub issue #609 由在舊資料庫上實跑的使用者提出，回報「找出一堆對我們來說是錯的關聯」，因為 `id`／`status`／`created_by` 這類泛用欄名在許多表重複卻無關。預設是開啟推論的（`-noimplied` 可關），實務上常改用 `-meta` XML 手動供關聯。**讀圖前先確認每條邊是宣告的還是猜的**（**high，3-0**）。
- **可讀性上限是真的**，公認解法是切片而非畫一張大圖（**high，3-0**）：tbls 用 `include`／`exclude` 過濾、`viewpoints` 依領域分組出多個聚焦視圖、`distance` 限制關聯跳數（**預設 1**）；Azimutt 走「載入後預設什麼都不顯示 → 全域搜尋起點 → 只顯示需要的表／欄 → 沿關聯外走 → 每個 use case 存一張圖」。Dataedo、Vertabelo 等非廠商來源描述同一失效模式與同一解法。⚠️ Azimutt 自述的「數百張表」門檻與 3000／716 entity 為**廠商自報**，未見獨立實測，不可升級為「已證實 N 張表以上不可讀」。

執行面補充（只想快速拿到一張 ER 圖、不碰 diagram 語法時的三條路）見 [[取得-ER-圖的快速途徑]]。

### ③ 依賴規則 — 不是圖，是會 fail 的檢查

第 ① 張圖上那條禁令的落地形式。`dependency-cruiser` 可在 CI 用 `severity: error` ＋非零 exit code 強制依賴規則（來源為 [[AI-生成流程圖與架構圖]] 既有記錄，工具官方 docs，**high**；**非本輪查證**）。

這張不必看——它替人看。寫下「UI 層不准直接碰 DB 層」「Service 不准反向依賴 Controller」之後，agent 一違規就紅燈，**不讀碼也知道它越了界**。同一形式的最高性價比案例見 [[Uncle-Bob-的不讀碼約束閘門]]：那裡真正防住繞過的不是 prompt，是 CI 上把驗收規格檔機械鎖死的 guard。

## 明確不畫：自動產生的呼叫關係圖

「掃程式碼自動生架構圖」聽起來正好解決這個處境，但實測是負面的：

| 實證 | 數字 | 強度 |
|---|---|---|
| ICSE 2020（Sui／Dietrich 等）對 **31 個真實 Java 程式**以動態執行為 oracle 實測靜態 call graph | 中位 recall **0.884**——漏掉約 11% 已知可達方法（built-in oracle 0.859／生成測試 oracle 0.904） | **high，3-0** |
| 同研究：開啟 state-of-the-art 反射支援 | recall 升至 **0.935**，但 31 個程式有 **11 個在 6 小時上限逾時**，只能改用 20 個程式的縮減資料集報告；且仍 < 1 | **high，3-0** |
| 同研究：漏邊主因 | **不是反射**（`Method::invoke` 只解釋 8.08%）；是 native method 配置的物件（40%）與 JVM 主動發起、程式中無對應 call site 的呼叫（52%，其中 86% 為 static initialiser） | **medium，2-1** |
| ISSTA 2024（Samhi／Ernst 等）在 **1000 個 Android app** 上跑 **13 個靜態分析工具**與動態比對 | 平均漏掉 **61%** 實際被執行到的方法；工具作者受訪皆表示不意外，並說「產生 sound 且 complete 的 call graph 本來就不是我們工具的目標」 | **medium，2-1** |

**限定條件必須一起帶走**：0.884 是 Java／JVM／Doop、31 個 XCorpus 程式（多為較舊程式、lambda 代表性不足）的中位數；52%／40% 是「可由此解釋」的**重疊比例而非互斥分割**（加總約 148%），且為 DOOP base 組態。61% 是 Android 專屬——event/callback 驅動、reflection、ICC、外部框架，是靜態分析的**最壞情境**，且該數字只出現在摘要、內文無對應表格，區間從 CHA 系最好的 40% 到 SootFX 的 100%，head-to-head 只用 13 個工具都跑得完的 126 個 app，動態基準本身覆蓋率極低（Monkey 隨機跑 5 分鐘，method 覆蓋率 mean 8%／median 4%，作者自陳低估了真實差距）。

**兩個數字都不可外推成「所有語言的自動 call graph 都漏 X%」**。但方向足以支撐一條可操作的結論：**自動產的呼叫圖可拿來探索，不能當「系統就長這樣」的依據**——對一個本來就不熟的 codebase，一張漏了一成到六成的圖比沒有圖更危險。

這與 [[AI-生成流程圖與架構圖]] 的準確度警訊（工具自陳「無法對動態語言產生完美呼叫圖」、「只反映設計的架構而非執行期真實行為」）同向，但把它從**工具自陳**升級為**第三方量化實證**，補上該頁「尚待釐清」第 2 條（逆向生圖工具無獨立 benchmark）在 call graph 這一段的缺口。

## 兩種自動化的缺口互補，不重疊

若仍要自動化，關鍵不是問「準不準」而是問「漏什麼」：

- **靜態分析**漏動態綁定、框架與執行環境主動發起的邊（上表）。
- **執行期追蹤**漏沒跑到與未插樁的路徑。OpenTelemetry Collector 的 **service graph connector** 純從 trace 自動推服務拓撲、完全不碰原始碼：依語意慣例配對 span（client↔server ＝直接呼叫、producer↔consumer ＝訊息系統、client 且帶 `db.name` ＝資料庫呼叫），每條配對成功的請求即圖上一條邊（**high，3-0**）。五項限制全出自官方 README：輸出是 metrics 不是圖（渲染靠視覺化層，Grafana 自 v9.0.4 原生支援）、必須同一 collector 實例看到整條 trace（官方解法是前置 load balancing exporter）、未配對 span 暫存記憶體預設 TTL 2 秒／上限 1000 筆、**穩定度標示 alpha**、覆蓋率受流量與 sampling 決定。

C4 官方 FAQ 另列出依層級的自動化資料來源（**high，3-0**；措辭為 "Possible approaches"，屬示例非規範）：context 用 service catalog（Backstage、ServiceNow）、container 用 OpenTelemetry 或 log 解析、component 用原始碼靜態分析、deployment 用 IaC 解析（Terraform、CloudFormation）。

⚠️ 但 component 層的自動化有前提且不充分：C4 說 component 元素「**應該**（should，非 must）對應到程式碼中真實存在的抽象」（**2-1**），而 Structurizr 官方文件自陳「**幾乎不可能建立一組能盲目套用到所有 codebase 的通用規則，component 識別需要對該 codebase 的知識**」——其 component finder 靠 `@Controller`／命名後綴等 codebase-specific 啟發式，即所謂 architecturally-evident coding style。

## 圖與程式碼同步：唯一具體可抄的循環

schema 層有現成做法（**high，3-0**）：`tbls doc` 產文件並 commit 進版控 → 開發期間改 schema → CI 跑 `tbls diff`／`tbls lint` → 回到第一步；官方附 GitHub Actions 與 Travis 範例。

三個落地細節官方沒說清、須自己補：

- **`tbls diff` 才是漂移偵測**（比對 DB 實際 schema 與已產生文件）；`tbls lint` 實為 schema 品質 linter（table/column 需有 comment、FK 需有 index、欄數上限、required columns），兩者職責不同。
- 自動重生由 `tbls doc` 負責，diff／lint 只做校驗。
- README 未載明 `tbls diff` 的 exit code 行為，也未提 `--error-on-diff` 類旗標；實務常見做法是擷取輸出、有差異才 exit 1 讓 CI 紅燈——**「放進 CI」不等於「開箱即擋 PR」**。

架構層（container／component）的漂移偵測**本輪未找到可用做法**，列入未解問題。

> ⚠️ **2026-08-10 更新：上句需分層修正。** 補查後發現架構層不是整片空白，而是**component 層有解、container 層無解**（**high**，ArchUnit 官方 user guide）。
>
> **component 層可以**：ArchUnit 的 `adhereToPlantUmlDiagram()` 直接讀 `.puml` 元件圖，**箭頭方向即依賴約束**，圖檔本身變成 CI 測試——
> ```
> classes().should(adhereToPlantUmlDiagram(diagramFile, consideringAllDependencies()))
> ```
> deterministic、免費、不經 LLM，是架構層目前最接近 `tbls diff` 的對應物。限制：僅支援 PlantUML **component 圖**、元件須用 `[Name]` 加 package stereotype、箭頭僅認 `-->`／`<--`，官方文件未提 C4／Structurizr 支援，且為 Java 專屬。
>
> **container 層仍然無解**，2024–2026 無工具填補。技術原因有二：(a) container 邊界的證據散在部署設定、網路呼叫、訊息 topic 裡，不像 component 的 import graph 可從單一 codebase 靜態還原；(b) 從碼還原 component 需 codebase-specific 啟發式，Structurizr 的 `structurizr-component` 官方定位就是「pluggable and customisable set of matching and filtering rules」，故做不成 `tbls doc` 那種開箱即用的 round-trip。**無解的那層，恰好是本頁主張「不讀碼時最該看」的那層。**
>
> **一個比工具清單更有訊息量的反向訊號**：2024 年後出現的漂移偵測工具**普遍放棄拿圖當基準**——`drift` 改用「已觀測到的 directory-to-directory import」當基準、首次跨界即告警；ArchSteer 用自宣告 invariant 算 Drift Index 並在 CI 走 ratchet「只擋淨新增違規」。僅 `erode`（36★、無量化評估）仍以圖為基準且靠 LLM 比對。這暗示的共識是**圖太貴、太容易自己過期，不適合當 CI 基準**；能守住的是「不准新增違規」這種相對規則。
>
> ⚠️ 另外必須知道：**沒有任何 diagram-as-code 工具能檢查「圖是否還符合程式碼」**。Mermaid／PlantUML／D2／Structurizr 的 `validate`／`inspect`／`--check-syntax` 全部只驗語法或模型內部一致性。防過期的真正機制是**流程**——模型檔與程式碼同 repo、改碼的 PR 順手改模型、靠 review 抓。CI 不會替你抓。

## 本輪未查證（不得由本頁推導）

原研究問題涵蓋四個層面，實際只有兩個獲得證據支撐。**2026-08-10 以 12 項平行查證補了其中四項**，補查結論見下；仍未查證者保留原樣。

1. ~~**ER 記法差異與取捨**~~ → **已補查（high，工具原始碼一手）**：**這不是一個真實的決策點。** `tbls`（dot 模板 `arrowtail=crow`）、SchemaSpy（`Edge.java`）、Mermaid（官方原句「uses the most popular crow's foot notation」）三個工具**把 Crow's Foot 寫死在原始碼裡、沒有選項**；唯一給選項的 DBeaver 把它做成檢視時的即時切換。獨佔有機制原因：**Crow's Foot 的 min／max 兩枚符號恰好對應 DB metadata 拿得到的東西**——`tbls` 的 `detectCardinality` 子側看 constraint 含 `UNIQUE`／`PRIMARY KEY`、父側看子欄位是否 nullable，整張圖的關係語意可由 metadata 完全推導。換 Chen（需 relationship 實體與屬性語意）或 UML（需 association／aggregation／composition 語意）都得人手補，圖立刻退回會過期的手繪圖，**把「唯一可信自動產物」這個性質弄丟**。附帶：IDEF1X 的 FIPS 184 已於 2008-09-02 撤回，現以付費 ISO/IEC/IEEE 31320-2:2012 存續，已離開開源工具鏈。⚠️ **無任何量化可讀性實證**（Chen vs Crow's Foot vs UML 理解度實驗），「Crow's Foot 較易讀」僅有 blog 層級斷言；正確說法是「沒有證據顯示差異大到值得花時間選」。
2. ~~**資料流向與生命週期**~~ → **已補查（high，官方整合清單一手）**：**想要的那個工具不存在。** data lineage 工具（OpenLineage／Marquez／DataHub／dbt docs）**只適用資料工程與 ETL 管線**——OpenLineage 官方整合清單全部是資料處理／編排工具（Airflow、Spark、dbt、Flink…），無任何 Web 框架整合；DataHub 的 MySQL source 雖標示支援 column lineage，但**只涵蓋 view 定義推導出的依賴**。它們答的是「倉儲內表與欄位間的血緣」，不是「一筆請求怎麼流過 controller → service → 幾張表」，**不是同一個問題**。DFD 本身沒死但轉移到安全威脅建模，且已有 as-code 形態可抄：OWASP `pytm`（模型寫成 Python 檔進版控，`./tm.py --dfd | dot -Tpng`）與 `Threagile`（YAML 版），卡點是**模型仍需人寫、不從碼逆推**。唯一嘗試「從原始碼產 DFD」的 Threatspec 最後一次 push 為 2020-12-30，該路線無活躍實作。
3. ~~**狀態轉換**~~ → **已補查（primary 為主，無量化實證）**：**原判斷「可能是唯一只能人工畫的」是錯的——它其實是自動化程度最高的一項**，但決定因素不是工具成熟度，而是**狀態機寫成資料還是寫成條件判斷**。三條路徑分別是：(a) **宣告式函式庫可直接 dump**，成本近乎零（Symfony `php bin/console workflow:dump <name> --dump-format=mermaid`、`python -m statemachine.contrib.diagram`、XState／Stately 匯出 Mermaid；Spatie `laravel-model-states` 無內建指令但可用 `getStatesFor()` ＋ `transitionableStates()` 十餘行自產）；(b) **散在服務層的條件判斷查不到任何靜態分析工具**，只能 grep 狀態常數寫入點 ＋ LLM 補語意 ＋ 人工核；(c) **從 audit log 反推可行且門檻低**——PM4Py 的最低需求僅 case id ＋ activity ＋ timestamp，一般 audit log 即滿足，但實務上一句 `LAG(status) OVER (PARTITION BY record_id ORDER BY ts)` 就能取得 `(from, to)` 集合，不必上 PM4Py；限制是**只得實際發生過的轉換，缺 guard 與禁止規則**。防過期可抄 golden-file 模式：`workflow:dump > docs/state.mmd` 接 `git diff --exit-code`。**獨門用法**：把 (c) 得到的實際轉換集合與圖上的邊做差集——圖上沒有卻發生過 ＝ 圖過期或有後門寫入；圖上有卻從沒發生 ＝ 死路徑。
4. ~~**diagram-as-code 四者的正面比較**~~ → **已補查**，見 `artifacts/arch-views-2-auto.html` 的對照表。要點：Mermaid 89,658★ 是唯一被 GitHub／GitLab／Obsidian 原生渲染的；PlantUML 13,232★ 圖種最全但佈局弱到會逼人換工具；D2 24,887★ 佈局最強但**最強的 TALA 引擎為 proprietary 收費閉源**、無原生 C4、且最後 tagged release 停在 2025-08-19；Structurizr DSL 是唯一 model-first。**四者皆無法檢查「圖是否還符合程式碼」**。唯一的 LLM 產圖正確率量測是 MermaidSeqBench（arXiv 2511.14967，8B 級 syntax 91.29%／logic 87.23%），⚠️ preprint、只測 8B 級開源模型、**只測 sequence diagram**，不可外推 frontier 模型產架構圖。

- [[AI-產碼加速下的-review-瓶頸]] — 本頁是該頁四條路線之外的一個補位：當 review 本身是瓶頸而人又不讀碼時，圖不是拿來替代 review，而是把 review 判準的一部分（架構邊界）外移成機械檢查。該頁 DORA 建議第 1 條「把 AI 回饋移到 author 端」與本頁 ③ 同構——CI 上的依賴規則正是在 author 端就攔下越界。
- [[Uncle-Bob-的不讀碼約束閘門]] — 同一處境（不讀 agent 產碼）的另一組答案：以測試、mutation 與 CRAP 度量包圍。兩者的交會點是**都靠 CI 上的機械鎖**——該頁最高性價比結論是鎖規格檔的 CI guard，本頁 ③ 是鎖依賴方向，形式相同。
- [[用測試約束-AI-產碼]] — 該頁處理「行為對不對」，本頁處理「東西放對地方沒有」。兩者互補且都不可替代：依賴規則全綠不代表邏輯正確，測試全綠也不代表架構沒被侵蝕。
- [[AI-生成流程圖與架構圖]] — 工具層前作（靜態 CLI vs LLM coding-agent 生圖、diagram-as-code 選型）。本頁與它的分工是**選型 vs 選層**：該頁答「用什麼工具生圖」，本頁答「該生哪一層、哪一層不該生」，並以第三方實證補上該頁「無獨立 benchmark」的缺口。⚠️ 該頁的 Mermaid 實踐約定已撤銷，工具查證仍有效。
- [[專案測試流程]] — 分離架構下的測試分層；本頁的 container 圖恰好是該頁「契約層跨越 HTTP 邊界」講的那條邊界的視覺化——前端等 `total`、後端回 `total_amount` 這類問題發生在圖上 Vue → API 那條箭頭上。
