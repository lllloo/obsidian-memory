MCP 在 `2026-07-28` 這版把**無狀態**寫進 base protocol 的規範性條款。這是協議層的分水嶺，不是任一家 client 的產品變更——版本號在此必須留，因為它就是行為切換的界線。

## 改了什麼

| 舊版行為 | 2026-07-28 |
|---|---|
| `initialize` 握手起手 | 移除；改為可選的 `server/discover` |
| `Mcp-Session-Id` header 維持 session | 移除；狀態不再綁連線 |
| protocol version 與 capabilities 隱含在連線狀態 | 每個請求的 `_meta` 都帶 `protocolVersion`（必填）、`clientCapabilities`（必填）、`clientInfo`（建議） |
| 通知靠連線推送 | 改為 opt-in 的 `subscriptions/listen` 長連線，狀態屬於該請求而非底下的連線 |

核心條款是「所有處理一個請求所需的資訊都在該請求裡；server 逐一獨立處理，**不從先前請求推論任何狀態**，即使來自同一條連線或串流」。跨請求的狀態（長時任務、application-level handle）**MUST** 由 client 每次明確傳 identifier 帶著走。

直接後果：remote server 可丟上 serverless／edge，或擺在任意 round-robin load balancer 後面水平擴展，不必自己實作 session 黏著。

## 規範範圍涵蓋 stdio，不只 HTTP

容易誤讀成「只影響遠端 server」。規範的 Statelessness 一節是 transport-agnostic 的，明確點名 stdio：

- Server **SHOULD NOT** 要求 client 重用同一連線或 process 來完成關聯操作
- Client **SHOULD NOT** 把單一 task／thread／對話當成 stdio process 的生命週期邊界
- 附註原話：一個開著的連線，例如 STDIO process，**不是**一個對話或 session；client 可在同一條 transport 上交錯送不相干的請求

整份規範只有 **Auth** 那節是 HTTP-only（stdio 明確被排除，改從環境取憑證）。

## 同版的退場：這是減法

無狀態化的直覺常被讀成「能力變多」，實際相反——這版**砍掉的能力多於新增**。官方 deprecated 註冊表（SEP-2577／SEP-2596）：

| 被 deprecate | 原本的用法 | 遷移路徑 |
|---|---|---|
| Sampling | server 借用 client 的 LLM 做推論，自己不必接 provider、保持模型無關 | 自己直接接 LLM provider API |
| Roots | client 告知 server 工作目錄／檔案範圍 | 改用 tool 參數、resource URI 或 server 設定 |
| Logging | server 送 log 給 client | stdio 寫 `stderr`；可觀測性走 OpenTelemetry |
| Dynamic Client Registration | OAuth 動態註冊 | Client ID Metadata Documents |
| HTTP+SSE transport | 舊的雙端點傳輸 | Streamable HTTP |

**Elicitation 未被棄用**，只是改走同版的 Multi Round-Trip Requests（MRTR）：server 回 `resultType: "input_required"` 並把所需 context 編進 `requestState`，client 帶 `inputResponses` 重試原請求。這正是「server 要反問 client 卻不能維持狀態」的解法，也讓 server 發起的請求不再需要常駐雙向串流；代價是舊的 server-initiated request 模式直接被移除（breaking change）。

最早移除時間為 **2027-07-28 之後的第一個 revision**（HTTP+SSE 另計）。Sampling 那條是實質的能力縮減：以前寫 server 可以完全不帶 LLM SDK。

舊 client／server 可繼續用舊協議版本，直到雙方能協商到新版——協商是**逐請求**的，server 不支援就回 `UnsupportedProtocolVersion`（`-32022`）讓 client 退版重試。

## 新用法來自 extensions，Tasks 是補洞不是紅利

真正開出新用法的是同版 graduate 的擴充框架，其中 **Tasks** 最實用。它出現的原因正是無狀態化本身：不能再靠 hold 住連線跑長任務，所以狀態必須顯式化成 `taskId`。

換來的能力比原本的「阻塞式 block 連線」強：

- **崩潰可續**：task ID 是 durable handle，client 重啟後以同一 ID 繼續 poll
- **進度可見**：`working`／`input_required`／`completed`／`failed`／`cancelled` 五態加狀態訊息
- **中途要輸入**：任務轉 `input_required` 並在 `tasks/get` 回應帶 `inputRequests`，client 以 `tasks/update` 回答，不需第二條連線或 server 主動推訊息
- **可取消**：`tasks/cancel`，協作式、server 不保證停

適用場景：CI pipeline、批次匯入、模型訓練、人工審批 gate、行動端不穩定網路。另有 **MCP Apps**（互動式 UI）。兩者都需 client 與 server 雙方明確 opt-in（client 在每請求 capabilities 的 `extensions` 宣告，server 在 `server/discover` 廣告），官方以 client matrix 追支援度。

**所以精確的因果不是「無狀態 → 更多用法」，而是「狀態從隱式（連線）改成顯式（task ID）→ 更多用法」**：顯式狀態能跨連線、跨崩潰、跨 server instance 存活，隱式的不行。無狀態是讓這件事成為必要的推力，不是能力本身。

## Client 採用實測（2026-08-03）

規範定案不等於手上的工具已照新規則跑。以下為當日直查本機二進位檔與上游原始碼的結果，**會隨版本過期**，回查方式一併記在表後。

| Client | 版本 | 狀態 | 依據 |
|---|---|---|---|
| Codex CLI | 0.146.0 | **已實作，預設關閉** | feature flag `mcp_2026_07_28` 標 `under development`／`default_enabled: false`；`McpProtocolMode` 的 `#[default]` 為 `Legacy`（preferred = `2025-06-18`），開啟後才切 `Auto { preferred: [2026-07-28], legacy: 2025-06-18 }` |
| Claude Code | 2.1.220 | **無跡象** | binary 內 protocol version 常數只到 `2025-11-25`；`Mcp-Session-Id` 相關錯誤訊息仍在；CHANGELOG 2.1.178–2.1.220 的 MCP 條目全是錯誤訊息／重試／權限修正 |

Codex 另有 `CODEX_MCP_PROTOCOL_VERSION` 環境變數控制 stdio server 端協商，並帶 `mcp_2026_stdio_discovery`、`mcp_2026_discovery`、`mcp_2026_message_limits` 等測試；binary 內也有 `tasks/list`／`tasks/get`／`tasks/cancel`（Tasks extension）。

**回查方式**：Codex 跑 `codex features list` 看該 flag 的 stage 與預設；Claude Code 見下節的 wire 層探針法（比抽字串可靠，字串到位不等於實際採用）。

## Claude Code 複驗（2026-08-07，2.1.224）

> **已被取代（2026-08-21）**：本節「程式碼已就位、未對一般 MCP server 啟用」的結論只適用 2.1.224；2.1.238 實測已全面走 modern 路徑，新結論見下一節。本節保留，因為它是「binary 字串到位不等於行為採用」的方法論實例。

四天後複驗，**binary 層與 wire 層給出相反的表面訊號**，兩者都要看才不會誤判。

**binary 已 bundle 完整 2026-07-28 SDK**（2.1.220 完全沒有）：era negotiation、`_meta` envelope 驗證訊息、`server/discover`、`tasks/get|list|cancel`、`subscriptions/listen`、`input_required`。supported versions 陣列有兩份共存——一份 `["2026-07-28","2025-11-25","2025-06-18",…]`、另一份仍以 `2025-11-25` 為首。另有 feature gate `tengu_mcp_stateless_skip_init`（程式碼內建預設 `true`），但它屬 `[claudeai-mcp]` 路徑：把 client capabilities 投影成 `anthropic-mcp-client-capabilities` header 以**跳過 initialize**，送出的 `MCP-Protocol-Version` 仍是 `2025-11-25`。那是 Anthropic 自家 connector 端點的私有無狀態化捷徑，不是本規格。

**wire 層仍是舊協議**。架一個 HTTP 探針 server 記錄 Claude Code 實際送出的請求（`claude -p … --mcp-config … --strict-mcp-config`），結果：

| 觀察點 | 實際行為 |
|---|---|
| 首個請求 | `initialize`，**不是** `server/discover` |
| 宣告版本 | `protocolVersion: "2025-11-25"` |
| `_meta` envelope | 不存在（無 `io.modelcontextprotocol/protocolVersion`／`clientCapabilities`） |
| 後續請求 | 帶 `MCP-Protocol-Version: 2025-11-25` header |
| 連線 | 送 `notifications/initialized`，並開一條 SSE 長連線 |

即使探針在 `server/discover` 廣告 `2026-07-28`，Claude Code 根本沒問就直接走舊握手。**結論：程式碼已就位、未對一般 MCP server 啟用。**

**探針法**（日後複驗照做，比抽字串可靠）：起一個記錄 request body 的 HTTP server，用 `--mcp-config` 內聯設定連上去（不必寫進任何設定檔），看第一個請求是 `initialize` 還是 `server/discover`。

## 三度複驗（2026-08-21，2.1.238）：已全面採用

同一探針法第三次複驗，結果與前兩輪相反：**Claude Code 對一般 MCP server 已預設走 modern（`2026-07-28`）路徑**，無需任何設定。

探針設計成 **modern-only server**——`server/discover` 回合規 `DiscoverResult`（`supportedVersions: ["2026-07-28"]`），對 `initialize` 一律回 `UnsupportedProtocolVersionError`（`-32022`），亦即舊協議在這台 server 上根本走不通。整輪 HTTP 只有三個請求，全部成功：

| 觀察點 | 2.1.224（2026-08-07） | 2.1.238（2026-08-21） |
|---|---|---|
| 首個請求 | `initialize` | **`server/discover`** |
| 宣告版本 | `2025-11-25` | **`2026-07-28`** |
| `_meta` envelope | 不存在 | **每個請求都帶** `protocolVersion`／`clientInfo`／`clientCapabilities` |
| HTTP header | `MCP-Protocol-Version: 2025-11-25` | **`mcp-protocol-version: 2026-07-28`**，另帶 `mcp-method: <方法名>` |
| session | 走 `initialize` + `notifications/initialized` | **無 `Mcp-Session-Id`、無 `notifications/initialized`** |
| SSE 長連線 | 連線後即開一條 `GET` | **不開**（探針未宣告 `listChanged`） |
| 整輪請求數 | 握手＋清單＋長連線 | `server/discover` → `tools/list` → `tools/call`，共 3 個 |

client 自己的 MCP log 直接寫明這件事（路徑 `~/.cache/claude-cli-nodejs/<cwd-slug>/mcp-logs-<server 名>/`，比抽 binary 字串或猜 wire 行為都直接）：

```
Connection established with capabilities: {... "protocolEra":"modern",
  "negotiatedProtocolVersion":"2026-07-28"}
no auto-opened subscriptions/listen on a modern connection; running the listen
  open through the reopen machinery (no-op if the server advertises no listChanged capability)
```

**切換發生在 2.1.224 與 2.1.238 之間**，中間 13 個版本未逐版測，確切版本不明；官方 CHANGELOG 與文件同樣沒有對應條目（沿用上一輪的查法，`stateless` 仍零命中），所以這是**無公告的行為變更**——純使用端無感是預期中的（協商逐請求進行），但自建 server 者不會從發行說明得知對面已換era。

### 附帶實測發現

- **`tools/list` 的回應驗證比規格嚴**：規格把 `ttlMs` 與 `cacheScope` 列為選填（caching 一節），但 2.1.238 缺任一個就判 `Invalid result for tools/list`，重試 4 次後放棄，向使用者呈現的是「server 沒有提供任何工具」而非驗證錯誤。自建 modern server 若工具莫名不出現，先查這兩欄。錯誤原文：`Invalid input: expected number, received undefined`（`path: ["ttlMs"]`）、`Invalid option: expected one of "public"|"private"`（`path: ["cacheScope"]`）。
- **`resultType: "complete"` 是必要的**：modern 路徑下每個 result 都要帶（`tools/list`、`tools/call` 皆然）。
- **client 仍宣告已 deprecate 的 capability**：`clientCapabilities` 送的是 `{"roots":{"listChanged":true},"elicitation":{}}`——Roots 在同版被 deprecate，但棄用期未到，宣告本身不違規。
- **`mcp-method` header** 為實測所見，用途未查證（規格頁未確認有此欄），推測供中介層路由用。

## 「不用架 server」與「無狀態」是兩件事

容易混談。無狀態化解除的是「連線＝session」的綁定，**不解除 server 本身的存在**；即使全面落地，stdio server 仍要有個 process 被啟動、remote server 仍要有個 endpoint 在。

真正「不用自己架」的路徑早已成立，且與協議版本無關：`claude mcp add --transport http <name> <url>` 接託管 endpoint，OAuth 走瀏覽器登入或以 `--header "Authorization: Bearer …"` 帶靜態 token；在 claude.ai 加的 connector 也會自動出現在 Claude Code（限 claude.ai 訂閱作為當前認證方式）。反過來說，Claude Code 仍是**啟動時建立連線並維持整個 session**（啟動逾時預設 30 秒、`MCP_TIMEOUT` 以毫秒調整），所以「每次呼叫即起即停」在今天做不到——最接近的只有 discovery cache（延後首次連線時機，非用完釋放）。**已被取代（2026-08-21）**：此處原寫「per-session」並以自動重連的 SSE 長連線為佐證；2.1.238 走 modern 時已無 session 概念，server 未宣告 `listChanged` 時連 SSE 長連線都不開（見上節）。維持連線是 client 的實作選擇，不再是協議意義上的 session。

## 強度標註

- **協議條款**：一手，直讀 spec 的 Base Protocol 與 Statelessness 章節。
- **Codex 已實作但預設關閉**：一手，本機 `codex features list` 輸出＋上游 `codex-rs/features/src/lib.rs`、`codex-rs/rmcp-client/src/protocol_mode.rs` 原始碼。強度最高的一條。
- **Claude Code 2.1.238 已採用**：**一手直證**（2026-08-21 wire 層探針＋client 自身 MCP log 的 `protocolEra: "modern"`）。同法在 2.1.224（2026-08-07）測得未採用，兩輪同法反向，故「Claude Code 未採用」的說法自 2.1.238 起**已被取代**。這條也再次證明「binary 字串到位」不可當採用依據——2.1.224 字串已到位而行為未變。
- **兩份版本陣列中「誰在用」**：2.1.224 時為推論（minified binary 無法歸屬）；2.1.238 實測顯示 MCP client 路徑已用新版陣列，該推論不再需要。
- **`tengu_mcp_stateless_skip_init` 預設啟用**：只是程式碼內建預設值 `!0`，伺服器端 statsig 可覆寫，本機無法驗證實際下發值。
- **Claude Code 官方文件零記載**：quickstart 與 mcp 參考頁全文檢索 `stateless` 皆 0 命中，無任何無狀態相關設定欄位；**沒有可寫的「stateless 模式」設定項**，日後落地預期不改設定面（transport 名不變），差別在 wire 層。
- **Anthropic 端時程**：官方僅稱 rolling out across Claude products，**未給時程**；Claude Code 這端已於 2026-08-21 前落地，但**無公告**（CHANGELOG／文件皆無對應條目）。2026-08-07 曾實測官方自家 `code.claude.com/docs/mcp` endpoint 仍回 `protocolVersion: 2025-06-18`，該項**未於 2026-08-21 重測**，不可據以宣稱現況。
- **未查**：Claude Code 對 MRTR、tasks extension 的**實際行為支援**——2.1.238 已走 modern，但本輪只驗到 `server/discover`／`tools/list`／`tools/call` 三個方法，擴充可不可用仍零證據，本頁不作宣稱。`subscriptions/listen` 只知道 client log 有「modern 連線不自動開、由 server 的 `listChanged` capability 觸發」的行為描述，未實測。
- **推論（未驗證）**：風險方向已翻轉——2.1.238 起，會踩到的是**只實作 legacy 的舊 server**（client 先送 `server/discover`）。本輪未測 legacy-only server 的 fallback 是否正常，規格要求 client 在非 modern 錯誤時退回 `initialize`，但**未驗證 Claude Code 實作是否照做**。
- **stdio transport 未測**：本輪三次探針全為 HTTP。stdio 的 era 探測路徑不同（規格另有 backward-compatibility 條款），不可由 HTTP 結果外推。

**勿引用**：

- 不要說「MCP 改成無狀態是 Claude Code 的變更」——這是協議層變更，Claude Code 只是跟上的一方；也不要說「stateless 只影響 remote server」，規範明文涵蓋 stdio。
- 不要再說「Claude Code 程式碼已就位但未啟用」——該結論只在 2.1.224 成立，2.1.238 已推翻（見三度複驗節）。引用此頁的採用狀態前先看版本號。
- 不要把「無狀態」讀成「不用架 server」——見上節，兩件事。
- 不要說「2026-07-28 尚未 final、仍在 RC」——該說法出自 2026-05-21 的 RC 貼文，已被最終版與 `/specification/versioning` 標示的 current 取代（2026-08-07 對抗式查證 3-0 否決）。
- 不要把 Sampling 的棄用歸因於「它需要常駐雙向連線」——同版的 MRTR 正好讓 server 發起的請求**不需要**常駐串流，因果相反。
- 「serverless and edge」「first-class HTTP workload with no session management」是 claude.com 產品 blog 的行銷措辭，引用時降權；中性等價說法用規格 blog 的「any instance behind a plain round-robin load balancer without shared storage」。

## 對本 vault 的意涵

純使用端（用別人的 MCP server）不需要任何動作：協商是逐請求的，client 升級時無感——2026-08-21 的實測正是這句的驗證，Claude Code 已換 era 而使用面零變化（設定寫法、transport 名稱、工具呼叫方式全同）。要主動處理的觸發點只有兩個——**想用 MCP Apps／Tasks 這類新擴充**，或**自己寫 server 且打算部署到 serverless**。

這條界線與 [[Mem0]] 的拍板一致：該頁把 Mem0 定位成 MCP-only 的隨手記收件匣，走的正是純使用端路徑，因此不受本次協議改版影響。至於 [[第二大腦整合的現成工具與做法]] 盤點的那批把 vault 餵給 coding agent 的 MCP server（obsidian-claude-code-mcp、istefox MCP Connector），若哪天要自建同類 server，無狀態化才會變成設計約束——server 不能再拿 process 身分當對話身分用。
