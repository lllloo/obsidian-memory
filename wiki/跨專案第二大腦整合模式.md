# 跨專案第二大腦整合模式

跨專案使用第二大腦的關鍵不是讓所有 repo 共用一個文件夾，而是明確區分：**共用研究知識放 vault，專案事實與決策留專案，兩者以可追溯的唯讀引用或查詢連接。**本頁整理五種由輕至重的整合模式；它們可並存，但不應一次全上。

## 模式比較

| 模式 | 解決的問題 | 何時採用 | 與本 vault 的關係 | 主要風險 |
|---|---|---|---|---|
| 專案 context manifest | 讓 agent 在該 repo 知道應讀哪些共用知識 | 每個有 coding agent 的專案 | **現在即可採用** | 只放連結不會自動進 context；需明確叫 agent 讀 |
| ADR 回鏈 | 保留某次專案選擇如何引用通用研究、為何落在此取捨 | 出現難以逆轉的架構選擇 | **現在即可採用** | 把通用論點複製成專案文件，日後漂移 |
| 唯讀聯邦查詢 | 跨 vault、專案 docs、會議筆記找資料 | 檔案夠多且找頁已成痛點 | 視需要加在讀取端 | 過寬索引會混入私密或不相關 context |
| 軟體目錄 | 看清多 repo 的系統、API、資源與依賴 | 多服務、多人協作、共享 API | 不取代 wiki，補「系統地圖」 | 為少數 repo 導入完整平台過重 |
| 可攜知識 bundle | 對外部 agent／工具交付可驗證的一組知識 | 有外部消費者或跨組織交換 | 做選擇性標準 bundle 匯出 | 全庫遷移或雙寫造成維護成本 |

## 1. 專案 context manifest：最小且推薦的入口

[AGENTS.md 開放格式](https://agents.md/)將 repository root 的 `AGENTS.md` 定位為給 coding agent 的專案脈絡；大型 monorepo 還可在子目錄以較近的檔案覆蓋規則。對本 vault 而言，這啟發的是每個專案保有自己的 agent 指令，但以一個短區段列出**本專案真的會用到**的共用研究頁。

範例放在專案自己的 `AGENTS.md` 或既有 agent 規則檔，連結要使用所有協作者可解析的 vault remote URL，而非個人電腦絕對路徑：

```md
## 共用研究脈絡

- 本專案的 LLM 選型與 agent 記憶設計，先讀：
  `<vault-remote-url>/blob/main/wiki/Claude-Code-記憶系統六層比較.md`
- 若要新增長期知識，保留專案具體決策在本 repo；可泛化的研究再明確要求 ingest 至 vault。
- 執行涉及上述主題的設計任務前，先讀相關頁並在結論註明引用頁與 `updated` 日期。
```

這是**指標，不是自動注入**。agent 是否能讀到外部 repo，仍取決於其檔案／網路權限；做不到時，將該次必要結論濃縮成專案內的 decision context，並附 vault 原始頁 URL 與日期，避免複製整篇 wiki。

**讀取順序**：消費端讀 vault 時，先看 `wiki/01.index.md` 頂部的「最近更新」區塊定位近期動過的頁，再按需展開全目錄與單頁——即這條路線版的「先近期、後全量」讀取契約。本 vault 刻意**不建獨立熱檔**（2026-07-15 拍板；如 claude-obsidian 的 hot.md，那依賴常駐 runtime hook），近期性改由 index 區塊承載、完整時序靠 git；取捨與各家做法見 [[LLM-Wiki-生態實作比較]] 的「近期/熱脈絡層的承載光譜」。

## 2. ADR 回鏈：通用研究落到局部決定

[Architectural Decision Records](https://adr.github.io/)用一則記錄保存一個架構上重要的選擇、理由、取捨與後果；一組 ADR 構成專案的 decision log。這正好處理「vault 說什麼普遍成立」與「本專案此刻為何選 A 不選 B」的差異。

每個專案在 `docs/adr/` 保留自己的 ADR；ADR 只摘要與當前決定有關的前提，並連回 vault，不把通用比較複製進來：

```md
# ADR-012：以結構化 Markdown 保存 agent 研究記憶

## Context
本專案需要可審查、可在 Git diff 中追蹤的長期研究脈絡。

## Decision
採用專案內 `docs/` 保存本專案決策；通用方法論引用 vault wiki。

## References
- <vault-remote-url>/blob/main/wiki/LLM-Wiki-知識管理模式.md
- <vault-remote-url>/blob/main/wiki/Claude-Code-記憶系統六層比較.md

## Consequences
跨專案洞見不直接複製；需要時由使用者明確要求回存 vault。
```

## 3. 唯讀聯邦查詢：當「知道在哪」成為瓶頸

[qmd](https://github.com/tobi/qmd)可將 Markdown notes、專案文件、會議記錄分為多個本地 collection，提供 BM25、向量檢索與 rerank，並有 CLI 與 MCP server。它適合讓 agent 在需要時**查詢**多個知識來源，而不是把它們全部塞進每個專案的 context。

本 vault 目前的跨專案唯讀查詢入口已由 `ask-vault` 承載——由**呼叫端專案**發起 headless 唯讀查詢、在 vault 內走 Query、附引用、答完即退，不需常駐索引；qmd 這類檢索層只在 `wiki/01.index.md` + Grep 定位失效時才需再評估。升級時機缺量化實證，唯一可參考的是 [[LLM-Wiki-生態實作比較]] 記錄的 nvk「約 100 篇上 qmd」經驗值（單一實作者經驗、非實證，勿當門檻定值）。

真要採用時守兩項界線：

- vault 與每個專案設成獨立 collection，查詢時指定 collection；不要預設搜尋所有私人資料。
- 搜尋結果只是候選，agent 仍需讀原頁、保留引用，不能把檢索排序當成事實依據。

這與本 vault 的「不主動伸手進其他 repo」相容：檢索是專案端或使用者明確發起的唯讀動作，不是 background sync 或反向寫入。

## 4. 軟體目錄：當問題是依賴地圖，不是文件檢索

[Backstage 的 System Model](https://backstage.io/docs/features/software-catalog/system-model/)將 Component、API、Resource 作為核心實體，再以 System 與 Domain 表達較大的服務邊界。這不是第二大腦的替代品，而是當 repo 變成服務網路時的正確補層：回答「誰擁有這個服務、依賴誰、暴露哪個 API」。

只有在多個專案共享 runtime 資源或 API、而這些關係已難靠 README 維護時才考慮。小規模先以每個 repo README／ADR 中的少量依賴連結維持即可；不要為了跨 repo 知識搜尋而引進完整 developer portal。

## 5. 可攜知識 bundle：對外交換的邊界層

當別的 agent、工具或組織需要消費一組知識時，可參考 [Open Knowledge Format（OKF）spec](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)做選擇性匯出（本 vault 對 OKF 的適用邊界與 2026-07-11「不遷移、僅保留為未來匯出 profile」拍板見 [[OKF-與本-vault-的相容性]]；該格式仍處早期草案階段，確切版本與穩定度請回查上游 spec）：輸出已選定的概念頁、轉換內部 wikilink、保留來源 citation 與更新時間。這比讓外部工具直接修改私有 wiki 安全，也不會迫使內部結構遷就單一交換標準。

## 建議的採用順序

1. 每個專案加入少量、主題導向的 context manifest 連結。
2. 對重要選擇寫 ADR，連回其採用的 vault 頁與日期。
3. 跨專案查詢先用既有的 `ask-vault`；只有跨來源尋找真的反覆失敗時，才再往上加檢索層。
4. 只有系統依賴與所有權本身失去可見性時，建立軟體目錄。
5. 有實際外部消費者時才輸出 OKF 或其他 bundle。

## 證據限制

- AGENTS.md、qmd、Backstage 與 ADR 的一手文件定義各自的格式或產品能力；它們不是「跨專案第二大腦能提升產能」的獨立實證。
- qmd 的向量／rerank 功能會增加本地模型、索引與權限治理成本；在本 vault 規模下，現有 index + Grep 仍是預設。
- 本頁的採用順序是依本 vault 的單向邊界與維護成本推導，不是通用最佳實務。
- 五種模式**全屬唯讀或單向交接**：工具間雙向同步（如 Readwise highlights 自動灌入 `raw/`）本輪未撈到通過驗證的實作，該缺口見 [[第二大腦整合的現成工具與做法]] 的「面向 B」一節；本頁不宜被讀成已涵蓋同步寫入。
