- 2026-08-08 [[專案測試流程]]、[[專案測試流程-前端-Vue]]、[[專案測試流程-後端-Laravel]]（新三頁）— 使用者要一篇說明專案測試流程的文章，背景指定**前後端分離（Vue／Laravel）**，要求**漸進式展開、一次一層**，並在寫完第一層後**拆成總頁＋兩個端各一頁**（同一頁裡前後端交錯講，加到四層會一直左右橫跳）。分工：總頁放四層射程、**一個測試該歸哪一層的三問判準**、兩端共通紀律（起點是「有沒有東西可以測」／斷言要具體／一個指令且真的是綠的／不追覆蓋率）；子頁只放該端專屬做法與坑。核心洞見是**兩個框架卡同一個坑**——框架讓人很容易把判斷寫在「必須啟動框架才能執行」的位置，而那正是不可測的地方，所以第一個動作不是寫測試而是**把判斷抽離框架**。兩端各有一個**自動化訊號**取代人工 review：前端 `grep -rl "mount(" src/utils src/composables` 應永遠為空；後端 `--testsuite=Unit` 跑起來變慢即代表有測試繼承了 `Tests\TestCase` 或偷連 DB。後端另記一個易無聲踩到的陷阱：`tests/Unit` 底下繼承 `Tests\TestCase` 照樣全綠，只是每條都付了啟動框架的成本，**目錄名稱不構成保證**。並記下第 1、2 層全綠**不代表系統是對的**（前端等 `total`、後端回 `total_amount` 只有第 3 層契約測試抓得到），這是分離架構獨有的成本。配套 `artifacts/testing-layers-vue-laravel.html`（四層射程／抽離前後測試要穿過什麼／判準流程，三張手寫 inline SVG）

- [[AI-產碼加速下的-review-瓶頸]] — AI 產碼加速後的四條約束路線地景（review 工具／測試／約束前移／部署層），與一個**認知與觀測互斥**的核心矛盾：85% 相信瓶頸在 review，但 >90% 團隊的變更 review 完仍積壓等部署——附成本近零的自我檢驗；含 DORA 一手建議「投資測試自動化的 ROI 可能高於優化人工 review」與 verification tax 的機制解釋（2026-08-06 Query 回存）。
- [[用測試約束-AI-產碼]] — 上頁測試路線的展開：AI 產測試的四種失效模式（同義反覆／弱斷言／過度 mock／繞過護欄）、**「叫 agent 遵循 TDD」為何可能比不介入更糟**（TDAD：程序性指示使 regression 升到 9.94%，價值在指明驗證標的）、mutation 與 property-based testing 的分工與各自的方法論缺口（含 Anthropic agentic PBT 的一手數據與 merged PR），末節防繞過五層。**分類骨架是「判準的權威在實作之內還是之外」**（source-of-authority taxonomy：spec-derived 28/54、其餘 26 篇無 spec 就下判決），據此並列 metamorphic／differential／contract 等其他 oracle 與其證據厚度落差；含 Thoughtworks Radar Vol.34 的業界定位（只押 mutation、Trial 環）、Meta ACH 的生產規模一手（工程師接受 73%，關鍵是只產目標導向 mutant）與 PBT 的限制面（GPT-4 僅 21% 可提取性質能正確合成）；4 條勿引用（2026-08-06 Query 回存，同日補外部證據）。
- [[Uncle-Bob-的不讀碼約束閘門]] — [[用測試約束-AI-產碼]] 的**人物案例層**：Robert C. Martin「不讀 agent 產碼、改用極端約束包圍」主張的逐項解剖。因為他把每道閘門都寫成公開工具（三語言各一套 mutation／CRAP／DRY，加 `deintroverter4clj`、`Acceptance-Pipeline-Specification`、編排層 `swarm-forge`），研究得以全部建立在原始碼與 README 而非轉述。兩項實質補進既有頁：**gherkin acceptance mutation**（變異 Gherkin example 值，抓「場景綠但資料沒接到系統」的驗收層假測試）與 **introverted test 靜態偵測**（斷言溯不到 production code）。**CRAP 公式經原始碼確認實為複雜度上限**（CC>30 無論覆蓋率多高都過不了門檻），而 coverage 單獨當閘門被 ICSE 2014 的 31,000 組測試套件研究否定。**推文字面的「沒有人讀碼」不成立**：`adversaries` 分支派了對抗式 reviewer agent 讀碼，判準是 Clean Architecture 四項——真正的命題是「review 判準可被寫下來交給 agent 執行」。人的閘門在**規格邊界**（`specifier.prompt` 要求未經使用者核准不得交手），且 `acceptanceTests/` 被 CI **機械鎖死**。撐不住處：驗證全由 agent 本地跑無獨立權威副本、`empire-2025` 是規格封閉的單機遊戲不可外推、「very high confidence」屬自評無外部量測；末節附 Vue／Laravel 逐項可搬性，最高性價比是**鎖規格檔的 CI guard**（2026-08-09 ingest，同日二輪深挖）。
- [[專案測試流程]] — [[用測試約束-AI-產碼]] 的**執行面**（總頁）：前後端分離專案該照什麼順序把測試堆起來。四層射程為單元 → 框架內 → 契約 → 端到端，前兩層在單邊之內、後兩層跨越 HTTP 邊界；含**一個測試該歸哪一層的三問判準**（拿掉框架還能跑嗎／只在單邊之內嗎／需要真瀏覽器嗎）與兩端共通紀律。記下第 1、2 層全綠不代表系統是對的——前端等 `total`、後端回 `total_amount` 只有契約層抓得到，這是分離架構自己買單的成本。配套圖見 `artifacts/testing-layers-vue-laravel.html`。**漸進撰寫中，目前展開到第一層**（2026-08-08）。
- [[專案測試流程-前端-Vue]] — 上頁在 Vue 端的落地：判斷從 `script setup` 抽到 `utils`／composable，**composable 分兩種而只有純計算型屬第一層**（用了 `onMounted`／`watch` 副作用的需要掛載環境）；Vitest 檔案落點與「測試檔出現 `mount()` 即非第一層」的 grep 判準；紅線是不為覆蓋率去測樣板輸出（改版面就整批壞）。
- [[專案測試流程-後端-Laravel]] — 同一套紀律在 Laravel 端的落地：判斷從 Controller 抽到 Service；**`tests/Unit` 繼承 `Tests\TestCase` 會無聲啟動整個框架且測試照樣全綠**，目錄名稱不構成保證，真第一層須繼承 `PHPUnit\Framework\TestCase`；`--testsuite=Unit` 的執行時間即為該紀律的自動化證明；規則寫在 Model 裡的解法是再往外抽一層，紅線是不測 `$fillable` 與關聯宣告。
