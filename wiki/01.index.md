- 2026-08-08 [[專案測試流程]]、[[專案測試流程-前端-Vue]]、[[專案測試流程-後端-Laravel]]（新三頁）— 使用者要一篇說明專案測試流程的文章，背景指定**前後端分離（Vue／Laravel）**，要求**漸進式展開、一次一層**，並在寫完第一層後**拆成總頁＋兩個端各一頁**（同一頁裡前後端交錯講，加到四層會一直左右橫跳）。分工：總頁放四層射程、**一個測試該歸哪一層的三問判準**、兩端共通紀律（起點是「有沒有東西可以測」／斷言要具體／一個指令且真的是綠的／不追覆蓋率）；子頁只放該端專屬做法與坑。核心洞見是**兩個框架卡同一個坑**——框架讓人很容易把判斷寫在「必須啟動框架才能執行」的位置，而那正是不可測的地方，所以第一個動作不是寫測試而是**把判斷抽離框架**。兩端各有一個**自動化訊號**取代人工 review：前端 `grep -rl "mount(" src/utils src/composables` 應永遠為空；後端 `--testsuite=Unit` 跑起來變慢即代表有測試繼承了 `Tests\TestCase` 或偷連 DB。後端另記一個易無聲踩到的陷阱：`tests/Unit` 底下繼承 `Tests\TestCase` 照樣全綠，只是每條都付了啟動框架的成本，**目錄名稱不構成保證**。並記下第 1、2 層全綠**不代表系統是對的**（前端等 `total`、後端回 `total_amount` 只有第 3 層契約測試抓得到），這是分離架構獨有的成本。配套 `artifacts/testing-layers-vue-laravel.html`（四層射程／抽離前後測試要穿過什麼／判準流程，三張手寫 inline SVG）
- 2026-08-08 [[用測試約束-AI-產碼]]（二手轉述升為一手）— 頁內第二節原有一句標著「強度 low、未核一手」的括號註記，稱 UC Berkeley 2026-04 發現主流 agent benchmark 皆可刷分。回查一手後**升級並修正**：出處是 BenchJack（arXiv 2605.12673，Wang 等，UC Berkeley RDI，2026-05 提交；官方 blog 為 2026-04），稽核 10 個 benchmark、盤出 219 個 flaw 歸八類，exploit 在多數 benchmark 拿接近滿分而零題解出、多數情況連 LLM 都沒呼叫；與本頁最直接相關的是 **SWE-bench Verified 靠 10 行 `conftest.py` 的 pytest hook 把每個測試改寫成 passed，500 題 100%**。**原敘述兩處不準已就地修正**：「皆可被刷分」過度概化（OSWorld 只到 73%），且漏了論文的另一半——迭代修補管線把四個 benchmark 的 hackable ratio 從近 100% 壓到 10% 以下、WebArena 與 OSWorld 三輪內全補，故正解是「評估管線尚未內化對抗式思維」而非「benchmark 全不可信」。強度定 medium-high（一手、方法規模明確、工具開源，但 arXiv v1 未同儕審查），並進證據強度總表

## 概念頁

- [[Context-優先與多-agent-的適用邊界]] — 決策判準：能力來自 context 注入、agent 數量只是編排選擇；多 agent 有實證邊界。把 Anthropic（多 agent 高 90.2%）與 Cognition（別建多 agent）的表面對立，經 UC Berkeley MAST 失敗實證（1,642 traces、41–86.7% 失敗率）統一為「可平行/讀重/確定性協調」的適用域之分（2026-07-14 回存）。
- [[LLM-Wiki-知識管理模式]] — Karpathy 的個人知識庫 pattern：LLM 漸進維護互聯 markdown wiki，知識編譯一次後持續維護，與 RAG 每次重檢索形成對比（本 vault 的設計原型）。
- [[OKF-與本-vault-的相容性]] — Open Knowledge Format 與本 vault 的邊界：不遷移內部 Obsidian LLM Wiki，日後有跨工具交換需求再建獨立 OKF 匯出層。
- [[設計品質的可量化檢測]] — 壞設計的標準訊號可量化：眼動熱區、可讀性/無障礙、任務可完成性、CSS 一致性四項檢測串成閉環交 AI 修正；工具只能推到及格線，及格線之後「留哪個偏離」是品味。是實證檢驗頁「驗證用 agent 改不到的判準」在設計領域的落地（2026-07-15 ingest）。
