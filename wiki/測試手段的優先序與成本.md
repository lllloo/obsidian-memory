> [[專案測試流程]] 回答「照什麼順序把層堆起來」，本頁回答**「有限資源下先投哪個、各要付多少」**。兩者是不同的軸：分層講射程，本頁講投報率。

**本頁狀態**：排序與成本評估是工程判斷，**未在本專案實測**。速度欄只有兩格有依據，已就地標明；其餘為量級估計，不可當實測數字引用。

## 排序用的尺

**抓到真 bug 的能力 ÷ 建置與維護成本**，套進前後端分離（Vue + Laravel）、單一團隊、AI 產碼比重高的情境。換一個情境排序會變，尺本身比名次重要。

## 優先序

| # | 手段 | 為什麼在這個位置 |
|---|---|---|
| 1 | 型別檢查 + lint | 成本近零、每次存檔就回報、不可能 flaky。它一個行為都驗不到——排第一是**投報率**最高，不是最有價值 |
| 2 | 單元測試 | 所有其他手段的前提：mutation 要有測試才能改壞、PBT 是它的變體、上層測試建在它的抽離成果上 |
| 3 | 整合／元件測試 | 實際 bug 密度最高處。後端尤其：route、middleware、FormRequest、Eloquent 全部只有這層碰得到 |
| 4 | E2E（關鍵路徑） | 唯一驗證「真的能用」的手段，但最慢最脆最貴。價值集中在極少數路徑，超過 10 條就要懷疑 |
| 5 | 變異測試 | 位置隨 AI 產碼比重浮動——判準是「有多少測試是自己沒逐行看過的」。是業界權威層唯一押注 AI 場景的一項（見 [[用測試約束-AI-產碼]]） |
| 6 | 性質測試（PBT） | 甜蜜點窄（純函式、往返性質、edge case 多）但命中時抓的是真 bug |
| 7 | 無障礙測試（a11y） | 位置**由外部決定**：有法規或合約要求就跳到第 3 位，沒有就在這裡 |
| 8 | 視覺回歸（VR） | 成本失控機制明確（粒度 × 狀態 × 模式相乘），見 [[視覺回歸測試的落地與陷阱]] |
| 9 | 快照測試 | 最容易變成噪音——改版面就整批紅，但紅了不代表壞了 |

契約測試不在表內：本專案已拍板不採，理由與重開條件見 [[專案測試流程]]。

## 速度

| 手段 | 每次執行 | 依據 |
|---|---|---|
| 型別檢查／lint | 秒級，增量更快 | 估計 |
| 單元測試 | **毫秒/條，幾百條 1–2 秒內** | ✅ 有依據——且這是判準本身：`--testsuite=Unit` 變慢即代表有測試偷連 DB |
| 整合／元件 | 數十～數百 ms/條，幾百條到分鐘級 | 估計（啟框架 + DB round-trip） |
| E2E | 數秒～數十秒/條 | 估計 |
| VR | E2E 基礎再加截圖與比對 | 估計 |
| 性質測試 | 單例的 ~100 倍量級 | 半有依據：預設約 100 組輸入，乘數是推的 |
| 變異測試 | 整套測試 × mutant 數 | ✅ 一筆實測：7 檔、394 mutant、36 秒（單一作者、小規模） |

**跨五個數量級（毫秒 → 分鐘）才是重點。** 所以該問的不是「多快」，是「跑在哪個迴圈」。

## 成本與該跑的時機

| 手段 | 建置 | 維護 | 跑在哪 |
|---|---|---|---|
| 型別檢查／lint | 低 | 極低 | 存檔時 |
| 單元測試 | 低 | 低 | 存檔時／每次 commit |
| 整合／元件 | 中 | 中 | 每次 push |
| E2E | 高 | **高**（環境、時序、資料狀態） | PR／部署前 |
| VR | 中 | **極高**（基準圖治理、flake） | PR，且要能一鍵忽略 |
| 性質測試 | 中（難在想出不變量） | 低 | 跟單元一起 |
| 變異測試 | 低（裝工具即可） | 低 | **nightly，不進 gate** |

三個值得注意的不對稱：

- **維護成本與速度不是同一件事。** VR 跑起來不算最慢，維護成本卻是全表最高。E2E 慢但紅了通常代表真的壞了；VR 紅了多半不代表。
- **變異測試看起來最慢，卻幾乎不佔人的時間**——它掛 nightly，慢在機器。E2E 的慢則直接卡在等 PR 的路徑上。
- 契約測試是少見的「建置高、維護低」型：契約定下來就穩定待著，不像 E2E 每次改 UI 都要跟著修。

**設計原則**：按執行頻率倒過來配。存檔時跑的必須毫秒級，PR 才跑的可以分鐘級，nightly 跑的隨便多慢。一旦讓分鐘級的東西跑進存檔迴圈，人就會關掉它，那條防線等於不存在。

## Gate 與體檢的分界

**Gate（閘門）＝ 沒過就不准 merge／部署的自動檢查點**，有否決權。體檢只回報、不擋。

判準是**紅燈的意義穩不穩定**：

| 訊號 | 紅了代表什麼 | 適合當 gate |
|---|---|---|
| 單元／整合測試紅 | 幾乎一定是真的壞了 | ✅ |
| 型別檢查／lint 紅 | 真的有問題 | ✅ |
| 變異分數掉了 | 可能只是新加了還沒測的碼 | ❌ 體檢 |
| VR 紅了 | 多半只是渲染飄了 1px | ❌ 除非另建核可流程 |

紅燈意義不穩定，人就會學會忽略它；養成忽略的習慣後，那條防線比不存在更糟——因為大家以為它還在。

**mutation 當 gate 會誘發「為了分數寫測試」**，那正是它本來要抓的「為覆蓋率表演」換了個殼。同理，VR 設成 gate 的下場是有人一次 `=all` 全部核可，既有漂移就此烙進基準圖。

**導入既有專案的關鍵是只擋新的**：設 baseline 或只跑 changed files，存量慢慢還、增量立刻擋。全開會產生幾百上千個錯誤，然後工具被關掉，之後再提會被抵制。Gate 必須是機器擋且與 merge 權限綁定——本機 pre-commit hook 是輔助不是 gate，`--no-verify` 一行就繞過。

## 變異測試的定位

它是本表最容易被誤解的一項，三件事要分清：

**依附關係：是。** 它沒有自己的測試，吃既有測試套件。改壞一行產品碼 → 重跑測試 → 紅了＝殺掉變異體，還綠＝存活變異體，代表測試有洞。沒有測試就沒有東西可跑。

**執行時機：不跟著跑。** 掛 nightly、不進 gate。它的產出是一份清單給人讀，不是一道要通過的關卡。

**它是個迴圈，終點還是單元測試**：寫單元測試 → 跑 mutation → 讀存活變異體 → 補上缺的單元測試。花的力氣最後都變成更好的單元測試，不會變成另一種測試資產。所以它不是「進階測試」，是**檢查主體有沒有偷工的工具**。

第一次跑的目的是**知道現況**，不是達標：不加 `--min-msi`、不進 CI、不訂目標分數，看的是存活變異體清單而非百分比。只掃高價值目錄（Service、金額計算、權限判斷、parser），全庫掃是成本失控主因。

### 兩端的優先度不同

**後端值得深挖，前端做完第 1 層就該往第 2 層走。** 這不是工具好壞問題：

| | 後端 | 前端 |
|---|---|---|
| 工具 | Pest 3.x 內建 `--mutate`；PHPUnit 走 Infection | Stryker |
| 工具的坑 | — | ⚠️ 不支援 Vitest 的 browser mode（instrumentation 假設 Node 執行） |
| 可掃面積 | 大——業務邏輯多半能抽成純函式 | 小——邏輯多長在渲染與互動裡，純計算只剩格式化、驗證、排序過濾 |

根因是 bug 的所在地不同：後端的 bug 多在判斷邏輯（第 1 層射得到），前端的多在互動與狀態流轉（只有第 2 層射得到）。**對著射不到的地方加深度，不如往射得到的地方擴廣度。**

門檻用 `--min-covered-msi` 比 `--min-msi` 可行動——前者只衡量已寫過測試的碼，不被未測區塊稀釋；但那是看趨勢用的，不是卡 CI 用的。變異運算子的存活率由高到低是邊界（`<` ↔ `<=`）> 布林邏輯 > 回傳值 > 語句移除；**邊界類大量存活通常代表一件很具體的事：測試只寫了正常輸入，沒寫邊界值。**
