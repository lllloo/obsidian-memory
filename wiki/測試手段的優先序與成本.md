> [[專案測試流程]] 回答「照什麼順序把層堆起來」，本頁回答**「有限資源下先投哪個、各要付多少」**。兩者是不同的軸：分層講射程，本頁講投報率。

**本頁狀態**：排序與成本評估是工程判斷，**未在本專案實測**。速度欄只有兩格有依據，已就地標明；其餘為量級估計，不可當實測數字引用。

## 排序用的尺

**抓到真 bug 的能力 ÷ 建置與維護成本**，套進前後端分離（Vue + Laravel）、單一團隊、AI 產碼比重高的情境。換一個情境排序會變，尺本身比名次重要。

## 優先序

| # | 手段 | 為什麼在這個位置 |
|---|---|---|
| 1 | 型別檢查 + lint | 成本近零、每次存檔就回報、不可能 flaky。它一個行為都驗不到——排第一是**投報率**最高，不是最有價值 |
| 2 | 單元測試 | 所有其他手段的前提：mutation 要有測試才能改壞、PBT 是它的變體、上層測試建在它的抽離成果上 |
| 3 | 整合／元件測試 | 實際 bug 密度最高處。後端尤其：route、middleware、FormRequest、Eloquent 全部只有這層碰得到 |
| 4 | E2E（關鍵路徑） | 唯一驗證「真的能用」的手段，但最慢最脆最貴。價值集中在極少數路徑，超過 10 條就要懷疑 |
| 5 | 變異測試 | 位置隨 AI 產碼比重浮動——判準是「有多少測試是自己沒逐行看過的」。是業界權威層唯一押注 AI 場景的一項（見 [[用測試約束-AI-產碼]]） |
| 6 | 性質測試（PBT） | 甜蜜點窄（純函式、往返性質、edge case 多）但命中時抓的是真 bug |
| 7 | 無障礙測試（a11y） | 位置**由外部決定**：有法規或合約要求就跳到第 3 位，沒有就在這裡 |
| 8 | 視覺回歸（VR） | 成本失控機制明確（粒度 × 狀態 × 模式相乘），見 [[視覺回歸測試的落地與陷阱]] |
| 9 | 快照測試 | 最容易變成噪音——改版面就整批紅，但紅了不代表壞了。指的是**整個元件的 HTML 快照**；API 回應快照與小範圍快照另論，見下節 |

契約測試不在表內：本專案已拍板不採，理由與重開條件見 [[專案測試流程]]。

## 前台網站情境的補充（2026-11-23）

情境：有註冊、登入、下單的前台網站；後台、會刪資料與真實付款的操作不測。上表是通用排序，前台多出幾項表內沒有的手段。**下表的位置是工程判斷、未實測**；工具行為的依據就地標強度，標「未查證」的只是經驗說法。

| 手段 | 合併後位置 | 角色 | 依據與限制 |
|---|---|---|---|
| API 回應快照 | 併入第 3 位整合測試，不另列 | gate | 快照適用任何可序列化輸出，原文 "whether that interface is an API response, UI, logs, or error messages"，並應 "focused, short"（[Jest 文件](https://jestjs.io/docs/snapshot-testing)，**high**；但出自 Jest，Pest 內建 `toMatchSnapshot` 如何遮掉 ID、時間戳等動態欄位未查）。分層看範圍、快照只是斷言寫法，所以不是新的一層。它抓「後端改欄位、前端不知情」，算是 [[專案測試流程]] 那條縫的低成本局部補丁 |
| 小範圍／inline 快照 | 同上 | 同上 | 格式化文字、錯誤訊息、emit 內容這類穩定小輸出可用；不能取代互動斷言 |
| 連結與圖片檢查＋逐頁收 console 錯誤 | E2E 之後 | 體檢、nightly | Playwright 官方建議 "Don't try to test links to external sites or third party servers that you do not control"（[best practices](https://playwright.dev/docs/best-practices)，**high**），支持拆成獨立 job；lychee／linkinator 工具本身未查證 |
| 效能：Lighthouse CI | 其後 | 體檢，先用 `warn` | assertion 分 `off`／`warn`／`error`，`error` 會以非零 exit code 擋 build（[configuration 文件](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/configuration.md)，**high**） |
| 安全：ZAP baseline | 其後 | 體檢、nightly | 只跑 spider 再等被動掃描，"doesn't perform any actual 'attacks'"（[ZAP 官方](https://www.zaproxy.org/docs/docker/baseline-scan/)，**high**）；Vue SPA 要加 `-j` 啟用 Ajax spider，傳統 spider 不執行 JS 會漏路由。**full scan 會真的送攻擊與表單**（[action-full-scan](https://github.com/zaproxy/action-full-scan)），與「不刪資料」衝突，不對正式站跑 |
| 視覺回歸 | 改當 PR review 輔助，不擋合併 | 輔助 | 目的若是「知道畫面改了什麼」，價值高於上表第 8 位的抓 bug 排名；只挑關鍵頁、一種寬度。落地坑見 [[視覺回歸測試的落地與陷阱]] |
| 探索式測試（AI＋瀏覽器自動化） | 視覺回歸之後 | 體檢、大改版前 | 找到的流程回補 E2E；未查證 |
| monkey 隨機測試（gremlins.js 等） | 末段，可不做 | — | 錯誤難重現、易誤觸刪除與送出，有價值的 console 收集已併進連結檢查那項；未查證 |

**分類軸要分開**：E2E 是**範圍**（真瀏覽器＋真後端走完流程），monkey 與探索式是**案例怎麼產生**，兩軸正交——用 Playwright 寫隨機點擊，範圍上是 E2E、方法上是 monkey。只有範圍清楚、有預期結果的那種適合當 gate。（工程判斷，未查證。）

**無障礙的法規觸發**（**high**：條文一手）：歐盟 EAA 依 Art. 31(2) 自 2025-06-28 適用，Art. 2(2)(f) 涵蓋對消費者的電子商務服務，Art. 4(5) 豁免提供服務的微型企業（只豁免服務、不豁免產品），另有第 32 條過渡條款，實際義務以各成員國轉化法為準（[指令全文](https://www.legislation.gov.uk/eudr/2019/882/body/adopted/data.pdf)）。台灣[身權法第 52 條之 2](https://law.moj.gov.tw/LawClass/LawSingle.aspx?pcode=D0050046&flno=52-2) 的義務對象只有「各級政府及其附屬機關(構)、學校」，民間電商屬自願。觸發時 a11y 提前到第 3 位附近，否則在 E2E 內用 axe 順手掃即可。

**變異測試落地補充**：

- Pest 需 Xdebug 3.0+ 或 PCOV，每個 mutant 只跑 "the tests covering the mutated code"；範圍靠測試裡的 `covers()`／`mutates()` 宣告，`--everything` 掃全部類別但很吃資源，官方建議搭配 `--covered-only`（[Pest 文件](https://pestphp.com/docs/mutation-testing)，**high**）。
- 能否跑 Laravel `Feature` 測試：官方範例是 `$this->getJson('/todos')` 這類 HTTP 測試，但全文沒出現 Feature 一詞（**medium**：依範例推論）。
- 「AI 寫的測試越多越該早做」的一個佐證：有論文舉例 LLM 產的測試達 100% 行與分支覆蓋，mutation score 只有 4%（[arXiv 2506.02954](https://arxiv.org/html/2506.02954v6)）。**單一 preprint 中的單一例子、作者在推廣自家方法**，不能寫成「通常如此」。

## 速度

| 手段 | 每次執行 | 依據 |
|---|---|---|
| 型別檢查／lint | 秒級，增量更快 | 估計 |
| 單元測試 | **毫秒/條，幾百條 1–2 秒內** | ✅ 有依據——且這是判準本身：`--testsuite=Unit` 變慢即代表有測試偷連 DB |
| 整合／元件 | 數十～數百 ms/條，幾百條到分鐘級 | 估計（啟框架 + DB round-trip） |
| E2E | 數秒～數十秒/條 | 估計 |
| VR | E2E 基礎再加截圖與比對 | 估計 |
| 性質測試 | 單例的 ~100 倍量級 | 半有依據：預設約 100 組輸入，乘數是推的 |
| 變異測試 | 整套測試 × mutant 數 | ✅ 一筆實測：7 檔、394 mutant、36 秒（單一作者、小規模） |

**跨五個數量級（毫秒 → 分鐘）才是重點。** 所以該問的不是「多快」，是「跑在哪個迴圈」。

## 成本與該跑的時機

| 手段 | 建置 | 維護 | 跑在哪 |
|---|---|---|---|
| 型別檢查／lint | 低 | 極低 | 存檔時 |
| 單元測試 | 低 | 低 | 存檔時／每次 commit |
| 整合／元件 | 中 | 中 | 每次 push |
| E2E | 高 | **高**（環境、時序、資料狀態） | PR／部署前 |
| VR | 中 | **極高**（基準圖治理、flake） | PR，且要能一鍵忽略 |
| 性質測試 | 中（難在想出不變量） | 低 | 跟單元一起 |
| 變異測試 | 低（裝工具即可） | 低 | **nightly，不進 gate** |

三個值得注意的不對稱：

- **維護成本與速度不是同一件事。** VR 跑起來不算最慢，維護成本卻是全表最高。E2E 慢但紅了通常代表真的壞了；VR 紅了多半不代表。
- **變異測試看起來最慢，卻幾乎不佔人的時間**——它掛 nightly，慢在機器。E2E 的慢則直接卡在等 PR 的路徑上。
- 契約測試是少見的「建置高、維護低」型：契約定下來就穩定待著，不像 E2E 每次改 UI 都要跟著修。

**設計原則**：按執行頻率倒過來配。存檔時跑的必須毫秒級，PR 才跑的可以分鐘級，nightly 跑的隨便多慢。一旦讓分鐘級的東西跑進存檔迴圈，人就會關掉它，那條防線等於不存在。

## Gate 與體檢的分界

**Gate（閘門）＝ 沒過就不准 merge／部署的自動檢查點**，有否決權。體檢只回報、不擋。

判準是**紅燈的意義穩不穩定**：

| 訊號 | 紅了代表什麼 | 適合當 gate |
|---|---|---|
| 單元／整合測試紅 | 幾乎一定是真的壞了 | ✅ |
| 型別檢查／lint 紅 | 真的有問題 | ✅ |
| 變異分數掉了 | 可能只是新加了還沒測的碼 | ❌ 體檢 |
| VR 紅了 | 多半只是渲染飄了 1px | ❌ 除非另建核可流程 |

紅燈意義不穩定，人就會學會忽略它；養成忽略的習慣後，那條防線比不存在更糟——因為大家以為它還在。

**mutation 當 gate 會誘發「為了分數寫測試」**，那正是它本來要抓的「為覆蓋率表演」換了個殼。同理，VR 設成 gate 的下場是有人一次 `=all` 全部核可，既有漂移就此烙進基準圖。

**導入既有專案的關鍵是只擋新的**：設 baseline 或只跑 changed files，存量慢慢還、增量立刻擋。全開會產生幾百上千個錯誤，然後工具被關掉，之後再提會被抵制。Gate 必須是機器擋且與 merge 權限綁定——本機 pre-commit hook 是輔助不是 gate，`--no-verify` 一行就繞過。

## 變異測試的定位

它是本表最容易被誤解的一項，三件事要分清：

**依附關係：是。** 它沒有自己的測試，吃既有測試套件。改壞一行產品碼 → 重跑測試 → 紅了＝殺掉變異體，還綠＝存活變異體，代表測試有洞。沒有測試就沒有東西可跑。

**執行時機：不跟著跑。** 掛 nightly、不進 gate。它的產出是一份清單給人讀，不是一道要通過的關卡。

**它是個迴圈，終點還是單元測試**：寫單元測試 → 跑 mutation → 讀存活變異體 → 補上缺的單元測試。花的力氣最後都變成更好的單元測試，不會變成另一種測試資產。所以它不是「進階測試」，是**檢查主體有沒有偷工的工具**。

第一次跑的目的是**知道現況**，不是達標：不加 `--min-msi`、不進 CI、不訂目標分數，看的是存活變異體清單而非百分比。只掃高價值目錄（Service、金額計算、權限判斷、parser），全庫掃是成本失控主因。

### 兩端的優先度不同

**後端值得深挖，前端做完第 1 層就該往第 2 層走。** 這不是工具好壞問題：

| | 後端 | 前端 |
|---|---|---|
| 工具 | Pest 自 3.x 起內建 `--mutate`（現行主版本仍附 `pest-plugin-mutate`）；PHPUnit 走 Infection | Stryker |
| 工具的坑 | — | ⚠️ 見下方三條限制 |
| 可掃面積 | 大——業務邏輯多半能抽成純函式 | 小——邏輯多長在渲染與互動裡，純計算只剩格式化、驗證、排序過濾 |

**Stryker 的 Vitest runner 有三條限制**，官方文件明列（**high**：一手文件，2026-08-28 查）：只支援 `threads: true`（停用執行緒不可用）、**browser mode 不支援**（原文 "Currently, Browser Mode is not supported"）、`coverageAnalysis` 設定會被忽略並一律用 `perTest`。第二條影響選型：Vitest 的 browser mode 若成為前端第 2 層的主力，那批測試就進不了 mutation 的射程。（⚠️ 二手來源稱 browser mode 已於 Vitest 4.0 轉正式，但 [Vitest 官方 browser 指南](https://vitest.dev/guide/browser/)未載明穩定性狀態，**此說未經核實**，勿引用。）

> **已被取代（2026-10-07）**：上段「browser mode 不支援」與據此推出的「進不了 mutation 射程」不再成立。[官方文件](https://github.com/stryker-mutator/stryker-js/blob/master/docs/vitest-runner.md)的 Limitations 段確實仍留著 "not supported" 那句，但它與實作脫節：[vitest-runner CHANGELOG](https://github.com/stryker-mutator/stryker-js/blob/master/packages/vitest-runner/CHANGELOG.md) 記錄早期版本遇 browser mode 是明確報錯，之後經 [PR #4628](https://github.com/stryker-mutator/stryker-js/pull/4628)「support browser mode」加入支援（PR 內文稱原本就大致能跑、補的是測試），後續又跟進支援 Vitest 3 的 browser mode 並修過 bug；repo 內也有 [browser mode 整合測試](https://github.com/stryker-mutator/stryker-js/blob/master/packages/vitest-runner/test/integration/browser-mode.it.spec.ts)。搭配 Vitest 4 仍有「能跑但有小毛病」層級的 issue（如 [#6097](https://github.com/stryker-mutator/stryker-js/issues/6097)）。2026-11-23 回查，[官方文件](https://stryker-mutator.io/docs/stryker-js/vitest-runner/) Limitations 仍寫 "Currently, Browser Mode is not supported"，尚未更新。（**medium-high**：CHANGELOG、PR 與測試檔皆一手，但官方文件與實作不一致、本 vault 未實測——落地前先實跑確認。）另，括號內「Vitest 4.0 轉正式」**已核實（2026-10-07）**：[Vitest 4 發佈文](https://vitest.dev/blog/vitest-4)原句 "With this release we are removing the `experimental` tag from Browser Mode"（**high**：官方一手）。前端仍建議做完第 1 層往第 2 層走廣度，但理由回到下段的 bug 所在地與上表的可掃面積，不再以工具不支援為由。

根因是 bug 的所在地不同：後端的 bug 多在判斷邏輯（第 1 層射得到），前端的多在互動與狀態流轉（只有第 2 層射得到）。**對著射不到的地方加深度，不如往射得到的地方擴廣度。**

這條判斷與業界模型獨立同向：2026 的普遍說法是**前端用 Testing Trophy、後端用 Pyramid**——Trophy（Kent C. Dodds）把地基放在靜態分析、單元層薄、整合層厚、E2E 薄，理由是「一個會抓資料、處理錯誤、寫回 store 的元件不是 unit，是個小系統」。本頁的結論是從 bug 所在地推的，兩者殊途同歸。（**low-medium**：僅從業者部落格層級，無 Radar 或研究背書；當方向參考，不作權威。）

門檻用 `--min-covered-msi` 比 `--min-msi` 可行動——前者只衡量已寫過測試的碼，不被未測區塊稀釋；但那是看趨勢用的，不是卡 CI 用的。變異運算子的存活率由高到低是邊界（`<` ↔ `<=`）> 布林邏輯 > 回傳值 > 語句移除；**邊界類大量存活通常代表一件很具體的事：測試只寫了正常輸入，沒寫邊界值。**
