# 第二大腦整合的現成工具與做法

本頁專收**別人已做出、可直接裝用的現成工具，以及可照抄的 context-injection 契約**——即「怎麼把知識庫接進 AI／對外發佈」的實作層。與既有頁分工，不重複：模式論（context manifest／ADR／聯邦查詢／bundle）在 [[跨專案第二大腦整合模式]]，人類 PKM 方法論在 [[第二大腦方法論比較]] 與 [[第二大腦實踐與本-vault-優化]]，Karpathy LLM Wiki 各實作與 RAG 取捨的實證在 [[LLM-Wiki-生態實作比較]]。

出自 deep-research（2026-07-14，5 搜尋角度、22 來源、25 條主張三票對抗式查證，24 確認 1 否決）。**來源強度分層**：MCP 工具、Quartz Syncer、claude-obsidian 皆有 primary source（GitHub repo／官方 docs／plugin store），可信度高；PKM 活用共識與整合哲學多為 blog／書級，屬設計主張非受控實證，已就地標註。

## 餵 vault 給 coding agent 的現成 MCP 工具（面向 A）

把 vault 當 context 源接進 coding agent，已有成熟的現成 MCP server，不必自建：

| 工具 | 形式 | 具體能力 | 支援 client |
|---|---|---|---|
| [obsidian-claude-code-mcp](https://github.com/iansinnott/obsidian-claude-code-mcp) | Obsidian 外掛內建雙傳輸 MCP server | 檔案操作（view／str_replace／create／insert）＋工作區操作（get_current_file／get_workspace_files）；Claude Code 走 WebSocket、Claude Desktop 走 HTTP/SSE | Claude Code 跑 `/ide` 選 Obsidian 即自動連上 vault 當 context |
| [istefox MCP Connector](https://community.obsidian.md/plugins/mcp-tools-istefox) | 本機 in-process MCP server | 約數十個工具：read/write/patch、note property、**on-device 語意搜尋**、Templater、canvas | Claude Desktop／Code／Cline／Cursor／Continue／Windsurf |

> 證據：兩者皆 primary source（repo／plugin store）、三票全票確認。**時間敏感**：預設 port（obsidian-claude-code-mcp 為 22360、istefox 為 127.0.0.1:27200）與工具數會隨版本浮動，用時回查 repo，勿把數字當恆值。

對本 vault 的適用性：這條路是「AI **直接讀寫 vault**」。與本 vault「唯一守門 git push、其餘全自主」相容，但要注意 MCP 直連讓 agent 繞過 git diff review 直接改檔——若採用，寫入層仍應落在能被 git 追蹤、事後可 review 的路徑，維持既有守門不被架空。

## 可直接照抄的 context-injection 契約：hot.md 分層讀取

[claude-obsidian](https://github.com/AgriciDaniel/claude-obsidian)（開源 Obsidian 外掛，自述 Based on Karpathy's LLM Wiki pattern）的具體做法最有借鏡價值——它解決「別的專案要用知識庫時，如何不整包 index 讀進 context」：

1. **`hot.md` 熱快取**：約 500 字的近期脈絡快取，每 session 刷新。
2. **跨專案 CLAUDE.md 指令**：在其他專案的 CLAUDE.md 寫「先讀 `wiki/hot.md`，不夠再讀 `wiki/index.md`」。
3. **MCP 直連降級**：以 MCP server（REST API plugin，或 filesystem transport，用 `detect-transport.sh` 自動選）供直接存取。

合起來是 **「熱快取優先 → 索引降級 → MCP 直連」的三層讀取契約**。

> 證據：primary source（repo）、三票全票確認。

**對本 vault 的直接含意**：本 vault 已有 `wiki/01.index.md`（索引層）與 MCP 可達（直連層），但**缺中間的「近期熱點快取」層**——別的專案要引用知識時，最省 token 的入口目前是整份 index。hot.md 是個輕量、可評估的補強點，正好接上 [[跨專案第二大腦整合模式]] 的「模式 1：context manifest」——manifest 是「指哪些頁」，hot.md 是「先給最近動過什麼」，兩者互補。**尚未拍板採用**，列為可評估項；風險是 hot.md 需維護刷新，與本 vault「零維護成本」目標要權衡。

## 對外發佈的現成工具：Quartz Syncer（面向 C）

[Quartz Syncer](https://saberzero1.github.io/quartz-syncer-docs/)（Obsidian 社群外掛）可在 Obsidian 內選取帶 `publish` property 的筆記，**單向**直發到 Quartz 靜態網站產生器（digital garden）並推到 Git repo，免手動匯出。

對本 vault 的適用性：正對應現有 `cards/`、`topics/` 經 Quartz 發佈的分層——「selective publish（挑頁對外）」是既定設計，Quartz Syncer 是把它工具化的現成路徑。與 [[第二大腦實踐與本-vault-優化]] 的 Digital Garden 節（保持私有 garden、只選擇性公開）一致：發佈是使用者從 wiki 手動撿選的動作，不是 agent 的一環。

> 證據：primary source（官方 docs／plugin 目錄）、三票全票確認。

## 傳統 PKM 的活用共識（橋接，詳見方法論頁）

本輪對「別人怎麼真正用起來而非囤積」的查證，與既有 [[第二大腦方法論比較]]、[[第二大腦實踐與本-vault-優化]] 收斂，此處只留與**整合**最相關的兩點，不重複展開：

- **系統目的是輸出（Express）**：BASB 的 CODE（Capture-Organize-Distill-Express）主張知識庫價值在加工與產出，"You're not building a library, you're building a factory"。→ 對本 vault：只 ingest 不產出（Query 綜合、對外發佈）就是死庫，佐證「好答案回存 wiki」紀律的必要。
- **按行動性而非主題組織對決策支援最相關**：PARA「依當前專案/決策脈絡取用」是面向 D（知識庫作決策底）目前**唯一有據**的原則性連結。

> 證據強度：blog／書級來源（Maggie Appleton BASB 圖解、開發者 15 分鐘 review 儀式、Forte Labs），屬**個人工作流主張、非實證**，作設計啟發用，勿當效果證明。

## 被否決的主張（勿引用）

> ❌ **「編譯式 wiki 能給出比對同一批來源做 RAG 更有深度的答案」**——本輪三票中 2 票反駁（1-2 否決）。「更深」的效果宣稱缺乏證據支持，**不可拿來為 agent 維護式 wiki 背書**。此與 [[LLM-Wiki-生態實作比較]] 既有拍板一致：compiled wiki「全面勝過 RAG」不成立，只在多跳推理場景有 preprint 級證據；RAG 與 wiki 是**取捨**（累積複利 vs 檢索即忘），非誰更強。

## 未解缺口（本輪證據最薄的兩個面向）

- **面向 B（工具間雙向同步）幾無紮實案例**：Obsidian ↔ Zotero／Readwise／自動 pipeline 的雙向同步、raw 自動灌入（如 Readwise highlights → `raw/`）的具體工具與資料流，本輪未撈到通過驗證的實作。既有 [[跨專案第二大腦整合模式]] 的聯邦查詢（qmd）偏「唯讀查詢」而非「同步寫入」，缺口仍在。
- **面向 D（串接另一個 AI 做決策支援）無直接案例**：只能從 PARA 原則間接推得，無存活的直接實作。搜尋撈到 swtestingdojo「agentic OS on Obsidian」用 brain-anatomy 命名（分 PrefrontalCortex 決策層、TemporalLobe 長期模式層）餵 agent 做判斷，但**未通過驗證門檻**，僅記為待查線索、勿逕引。
