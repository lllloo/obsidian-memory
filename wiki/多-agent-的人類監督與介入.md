# 多 agent 的人類監督與介入

同時跑多個 agent 時，人該怎麼盯、什麼時候介入。本頁是 [[平行跑多個-coding-agent-的工具選型]]（選工具）和 [[平行-agent-產出的合併與-review]]（收產出）之間缺的那一段：**跑的過程中，人的注意力怎麼分配**。

> 來源：2026-10-28 deep-research（5 個搜尋角度、23 個來源、105 個 agent）。**方法上的限制**：workflow 只對前 25 條主張做三票對抗驗證，其餘 83 條沒進驗證。下文分兩種強度標註：「**3-0**／**2-1**」是通過對抗驗證的票數；「**主 agent 原文核對**」是事後回原文逐句核對過、但沒有對抗投票。兩者都沒標的屬於抽取階段的摘錄，引用前要再查。

## 一句話結論

人不逐一核准每個動作，而是**設邊界、在關鍵時刻介入**。一人能盯幾個 agent，取決於「每個 agent 能被放著不管多久」除以「每次介入要花多久」。切回時重建情境的成本是主要耗損，例外通知也消除不了它。**不要把容量排滿**：保留餘裕的監督者整體表現較好。

## 一、一個人能同時盯幾個

這是 deep-research 原報告宣稱「沒有答案」的子題。實際上，答案在沒輪到驗證的主張裡。下面每一條都已回原文核對。

### 理論骨架：fan-out 公式（人機監督控制，2005）

- **fan-out ≈ 1 + NT／IT**。NT（neglect time）是 agent 被放著不管、效能還不會跌破門檻的時間；IT（interaction time）是把它拉回正軌所需的互動時間。原文：「fanout is one plus the ratio of neglect time to interaction time」。出處：Crandall、Goodrich、Olsen、Nielsen，*IEEE Trans. SMC-A* 35(4)，2005。**主 agent 原文核對（PDF 逐句）**。
- NT 和 IT 都由「自主程度＋介面」一起決定。所以 **agent 更自主，或介面讓人更快看懂狀況，都能提高上限**。
- 切回注意力有暖身成本：人要先重建狀態，這段期間 agent 的效能還在往下掉，所以必須在跌破門檻**之前**就切回去。
- 不同自主模式的耐放程度差很多。Scripted 模式放 30 秒後仍有約 40% 效能，另外兩種模式已接近零。**主 agent 原文核對**。
- **限制**：研究對象是 2005 年的模擬機器人，不是 coding agent。套到 coding agent 屬於類比，公式結構可借用，數值不可搬。

### 切換成本是主要耗損（MIT，2008）

- 估算一人能監督幾台無人機時，把等待時間算進去，容量預測**最多下降 67%**。等待時間包括認知重新定向、互動排隊、情境意識喪失，其中**情境意識喪失是主因**。
- 即使採用「只在異常時通知人」的 management-by-exception 設計，容量仍比不計等待時間的模型**低 36%**。換句話說，例外通知能減少排隊，但**消除不了切回時重建情境的成本**。
- 出處：Cummings & Mitchell，*IEEE SMC-A* 38(2)，2008。**主 agent 原文核對（摘要原句）**。限制同上：對象是無人載具。

### 不要排滿：保留餘裕勝過最大 fan-out（BYU，2010）

- 實驗為 48 名新手、受試者間設計。雙人合作監督時，每人實際控制的機器人數比單人**少 35% 以上**（p=0.0004／0.015），主任務表現卻沒有下降。也就是說，**fan-out 下降不等於表現下降**。**主 agent 原文核對**。
- agent-based 模擬中，監督者保留約 **50% 閒置容量**時，團隊總表現最高。作者明說這個數值取決於模型參數，屬模擬結果，但結論在不同參數下都成立。**主 agent 原文核對**。
- 出處：Whetten、Goodrich、Guo，〈Beyond Robot Fan-Out〉，IEEE SMC 2010。

### coding agent 的實務經驗值（非實證）

- **Kilo Code 7 位工程師訪談**（廠商部落格，2026-05-26）：多數人同時主動盯（foreground）的 agent 是 **2–4 個**。以跑 20 個以上平行 agent 出名的工程師，foreground 也只有 1–3 個，其餘是 fire-and-forget 的背景任務。另一位工程師說「平均關注 20 個背景 agent 幾乎不可能」。任務切分準則是：一個 agent 任務的產出，要能讓人一次看完、審完。**主 agent 原文核對**。單一廠商的訪談整理，屬經驗值。
- **Simon Willison**（2025-10-05）：「一次只能專注審核並合入一個重大變更」，平行派出去的只限不增加主工作認知負擔的任務；「從自己寫的規格出發的產出，審起來省力很多」。**主 agent 原文核對**。單一作者經驗。
- **Morph 部落格**（廠商，2026-03）：手動協調的實務上限約 8 個。1–3 個靠腦子記得住，4–8 個需要一套系統，超過 8 個就改由 lead agent 協調 worker、人只管 lead。**未核對**。原 URL 已改成另一篇文章，內容取自 Wayback 快照，文末推銷自家產品，屬單一作者經驗值、無量測。

**綜合**：foreground 2–4 個、背景任務另計，這和 fan-out 公式的邏輯一致。背景任務的 NT 很長（跑完才需要注意），所以可以多開；foreground 任務的 IT 很高，所以只能少開。

## 二、何時打斷：監督模式的轉變

- **Anthropic 自家遙測**：Claude Code 使用者愈資深，全自動核准的比例愈高（未滿 50 個 session 約 20%，到 750 個 session 超過 40%），**打斷率也跟著升高**（新手約 5% 的 turn，資深約 9%）。Anthropic 主張：要求核准每個動作「會增加摩擦，卻不一定帶來安全效益」，有效監督的重點是在關鍵時刻有能力介入。**3-0**。限制：只有單一廠商談自家產品；屬相關性資料，沒說明是追蹤同一批人還是跨人比較；打斷率上升可能只是因為資深者接手更難的任務。
- **agent 主動停下來問的頻率比人打斷高**，任務愈複雜差距愈大：Minimal 複雜度 6.6% 對 5.5%，High 複雜度 16.4% 對 7.1%。**3-0**。限制：停下的原因由 Claude 自行分類，作者自己也提醒它不一定停在對的時機。
- **介入時機放在自然任務邊界**：一項 IDE 實地研究（15 位專業開發者、5 天、229 次介入）發現，post-commit 等邊界的參與率是 52%，任務中途介入有 62% 被略過。**3-0**。限制：樣本小，情境是「AI 打斷人」，不是「人打斷 AI」，套用屬類比。另一項 CHI 2025 研究（N=18）方向一致：任務邊界是最有效的介入原則，依隱性訊號觸發則誤報多、打斷工作流。**未經對抗驗證**。
- **經驗法則**（Morph，未核對）：agent 在同一個錯誤上繞約 2 分鐘就直接終止，補上脈絡後從 git checkpoint 重開，不要等它自己恢復，因為失敗的嘗試會污染 context。

## 三、agent 主動升級與核准機制

兩家的設計哲學一樣：**用邊界取代逐步核准**。實作分層不同。

### Codex：sandbox × approval policy 兩層

- sandbox 決定技術上能做什麼，approval policy 決定越界前要不要停下來問人。官方明說這是為了**降低審核疲勞**：在已核准的邊界內，讀檔、編輯和常規指令都不逐一確認。**3-0**，官方文件。
- `approvals_reviewer = auto_review`：已經需要核准的請求（sandbox 越權、被擋的網路請求、有副作用的 app／MCP 呼叫）會先交給 reviewer agent 依風險分級審查。critical 一律拒絕，high 需要足夠的使用者授權。失敗時 fail closed。**3-0**。限制：文件沒定義風險等級怎麼判定；也沒有數據證明這樣真的降低了審核疲勞，還是只把風險移到 reviewer 身上。
- 能力與預設值各版本會變，以當下官方文件為準。舊政策已陸續退場，官方文件也已轉址到 `learn.chatgpt.com`。

### Claude Agent SDK：canUseTool＋hooks

- 工具權限請求和 `AskUserQuestion` 澄清提問都走同一個 `canUseTool` callback，callback 回傳前執行暫停，可以無限期等待。**3-0**，官方文件。
- **人可能晚回時的非同步核准**：`PreToolUse` hook 回傳 `defer`，讓 process 退出，之後用 `claude -p --resume` 從持久化 session 續跑。`PermissionRequest` hook 可以在等待核准時推送 Slack、email 或手機通知。**3-0**。限制：`defer` 只在非互動模式生效，同一 turn 有平行工具呼叫時也會被忽略。
- **陷阱**：已被 allow rule、`acceptEdits` 或 `bypassPermissions` 自動核准的工具，**不會觸發 `canUseTool`**。要攔下每一次工具呼叫，必須用 `PreToolUse` hook。**3-0**。
- 核准點不只有 allow 和 deny 兩種選擇，還可以：改輸入後放行（Claude 不會被告知輸入被改過）、放行並記成規則、附理由拒絕、用 streaming input 整個轉向。**主 agent 未另核，抽取自官方文件**。
- **多 agent 下的缺口**：`AskUserQuestion` 在 Agent tool 生出的 subagent 中不可用，所以 subagent 無法直接向人提問，只能回報給主 agent 轉問。**3-0**。

### approval gate 會退化成橡皮圖章

- 系統愈可靠、核准愈例行，核准率就愈高；幾乎全數核准時，等於系統取得了決策權。建議**記錄人駁回的次數與理由**，當作 gate 是否還有效的指標。出處：軍事 C2 文獻回顧（arXiv 2608.20597，二手引述）。**未經對抗驗證**。
- 這和 Bainbridge（1983）「自動化的反諷」同源：人對很少出事的資訊源，有效注意力撐不過約半小時；加裝告警也一樣，告警長期正常後就沒人盯它。**轉述自部落格，原始實證是工業與雷達監視情境，不是 coding agent**。本 vault 在 [[Agent-維護知識庫的已知失效模式]] 記過同一機制（事後 diff review 的 automation bias）。
- Passi & Singh（Data & Society，2026-07）：human-in-the-loop 可能只是形式。暫停鈕、核准提示、進度報告，只要人缺乏介入所需的知識、可觀察性和控制力，就只是監督的外觀；反過來，要求審核每個動作又會毀掉 agent 的價值。即時監控比事後稽核更難，因為它承襲了資訊過載，又多了時間壓力。**未經對抗驗證**，質性田野研究（計算生物實驗室）。

## 四、卡住、迴圈、偏離的自動偵測

給「不想一直盯著」的人：以下訊號可以交給機器先篩一輪。

- **確定性規則就夠用，成本是毫秒級**。LivePlan 用不呼叫 LLM 的規則式 monitor 偵測 10 種 drift，包括軌跡圖上反覆出現的 self-loop／循環、同一 phase 連續超過 7 步（判為停滯）、重複探索、解完不收尾。**3-0**。限制：preprint；7 步是作者自訂的參數。
- **重複類訊號會誤報**。OpenHands 的 StuckDetector 以 4 組相同的 action-observation 判定卡住，但刻意輪詢也會被誤判（software-agent-sdk issue #762）。
- **迴圈有前兆**：動作熵在迴圈發生前約 40 個 turn 就開始塌縮，線上預警召回率 97.71%，**但偽陽性 42%**。這個訊號抓不到語意漂移，而且需要 log-prob 存取權限。**未經對抗驗證**，作者的 Notion 研究筆記。
- **偵測到 drift 才介入，優於固定週期介入**：LivePlan 讓 SWE-agent 解題率最多提升 15.2 個百分點，每個 instance 多花約 $0.08；每 5 步固定諮詢一次的對照組觸發較多，解題率卻較低。**3-0，但信心 low**：單一 preprint、作者比較自己的系統、單次執行，而且消融有混淆。
- **回饋給「診斷」優於給「處方」**：點出哪裡壞了、或哪一項檢查失敗，比直接叫 agent 怎麼做有效（SWE-PRM 50.6% 對 44.8%；rollback 重跑時附上失敗的檢查項，救回 45% 的失敗，對照組 16%）。**2-1 分歧票、信心 low**：兩篇 preprint，換成開源 PRM 後結論翻轉。
- **能定義可重算結果的任務，就用確定性驗證器**：拿 tool 實際結果重算 agent 宣稱的總數，再加上 coverage check，held-out 偵測率 93%、0 誤報。**3-0，信心 low**：單一作者、窄任務。同一篇的 completion check 抓到 7/7 次 silent abort（agent 無聲中止）。**主 agent 原文核對**。

> 以上全部是「LLM 監督 LLM」的結果。套到「人何時該介入」屬於外推，而且全部是 2025–2026 年未經同儕審查的 preprint。

## 五、審核點放哪裡

沒有研究直接比較不同審核點的效果。以下是間接證據：

- **前段（需求與計畫）**：CentaurEval（人機協作 coding 任務）中，完全自主的 AI 只有 0.67% pass；研究者只修基礎設施故障也只到 2.89%；人類參與策略層後到 31.11%。作者把失敗主因歸於**需求理解與規劃**，不是演算法難度。**未經對抗驗證**，標註 ICML 2026 接收。這支持把人放在 plan 階段。
- **規格先行降低審核成本**：Simon Willison 說，從自己的規格出發的產出審起來省力很多。**主 agent 原文核對**。這和 [[長跑-Agent-的目標定義與計畫工具]] 的「目標分層、驗收判準」是同一件事的兩面。
- **後段（批次事後審）**：Morph 的做法是，規格裡寫明完成定義、讓 agent 自己 commit，等全部 agent 跑完再批次審 diff，避免「審查模式」和「下指令模式」交錯切換。**未核對**。這個做法的邏輯和 fan-out 的切換成本一致，但沒有實測。
- **分開寫與審**：Kilo 工程師另設獨立的 review agent，不讓寫 code 的 agent 自己審。「驗證迴圈讓結果好 2–3 倍」是二手轉述，**勿引用該倍數**。

## 本機做法建議（綜合，非實證）

1. foreground 只開 2–4 個，其餘做成「跑完才通知」的背景任務。用容量的一半當目標，不要排滿。
2. 提高每個 agent 的 NT（能放著不管多久）：動工前寫好規格與完成條件，用 sandbox 和權限規則劃邊界，取代逐步核准。
3. 降低 IT（每次介入多貴）：通知要附上狀態摘要（卡在哪、哪項檢查失敗），讓切回時不必從頭重建情境。
4. 介入點對齊任務邊界（計畫核准、commit、跑完），不要在任務中途插入。
5. 卡住偵測交給規則：同一錯誤重複、同一階段停滯，就自動終止或升級，接受它有誤報。
6. 定期看自己駁回過幾次。核准率逼近 100%，代表 gate 已經變成橡皮圖章。

工具面：[[Orca]] 的 supervised loop 與 worker 契約、[[Herdr-使用方法]] 的五態 agent 偵測與 `agent wait`，都是第 1、3、5 點的現成落地。

## 勿引用

- 「每次 context switch 損失 15–20 分鐘生產力」（Morph 部落格）：沒附出處的二手數字。
- 「驗證迴圈讓結果好 2–3 倍」（Kilo 轉述 Boris Cherny）：二手轉述、沒附數據。
- 「one-class 監測器（ESN＋CUSUM）在 5% 誤報預算下偵測率 0.71，對 silent abort 完全看不到」：以 0-3 被否決。主 agent 回原文核對後，**否決只部分成立**。0.707 確實存在於論文，但出自 Section 6 的**模擬器**而非真實 agent，誤報率是 4.4%；「對 silent abort 看不到」的原文是「omission is invisible to telemetry」，摘要只寫 completion check 抓到 7/7。所以可以引用「模擬器中約 0.71」，不能說成真實 agent 的偵測率。
- 原報告「子題 (4) 注意力管理沒有答案」的結論：是驗證名額用完造成的假陰性，見第一節。

## 未解問題

- 人機監督控制的 NT／IT 能不能在 coding agent 上量出來？例如從 session log 算出「agent 能自主跑多久」和「一次介入花多久」。
- Codex `auto_review` 這類「agent 審 agent 的核准請求」，實際誤放和誤擋的比率是多少？
- plan approval 和事後 diff review，哪個對品質和人類時間最划算？目前沒有直接比較的研究。
- 「偵測觸發優於定期介入」和「給診斷優於給處方」在人類監督者身上是否成立？
- Cursor background agents、Devin 的升級機制，本輪沒有主張通過驗證，這裡未涵蓋。
