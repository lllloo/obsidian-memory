以 deep-research 多來源查證（對抗式驗證）彙整。Tiago Forte 的 **BASB**（Building a Second Brain，含 CODE 擷取流程與 PARA 組織系統）與 Niklas Luhmann 的 **Zettelkasten**（原子筆記＋雙向連結）是兩套最常被並列的互補方法論。Evergreen notes、LYT、Digital Garden 等延伸實踐及其對本 vault 的取捨，見 [[第二大腦實踐與本-vault-優化]]。

## BASB：CODE 四步驟

[官方方法論](https://www.buildingasecondbrain.com/)（2017 年提出、2022 年書中定稿，六個來源交叉印證一致——多屬創始人生態圈，獨立性侷限見下方「侷限與存疑」節）：

- **Capture** 擷取有共鳴的資訊
- **Organize** 依可執行性組織——判準是「這會用在哪個專案」而非「屬於什麼分類」，例如發票該歸入具體專案資料夾，而非通用分類資料夾
- **Distill** 漸進式摘要萃取重點
- **Express** 產出創作或行動

一篇 [zettelkasten.de 的批評](https://zettelkasten.de/posts/building-a-second-brain-and-zettelkasten/)（中等信心，單一來源、帶立場）指出：Distill 的漸進式摘要本質只是逐層畫重點，並未真正把想法抽取成獨立筆記——使用者在此階段始終停留在原始資源內部，只有到 Express 才真正脫離原始資源作為資訊單位。

## BASB：PARA 組織系統

高信心。所有資訊分四類：

- **Projects** 有明確完成定義的主動成果
- **Areas** 無明確終點的長期責任
- **Resources** 未來可能有用的主題
- **Archives** 前三類中已不活躍的項目

> ⚠️ 常見誤植：多篇部落格把第三類寫成「References」而非「Resources」，經對抗式驗證判定為錯誤主張，已排除。

## Zettelkasten：原子筆記＋連結

中等信心。核心是每則筆記只含單一想法，透過筆記間**連結**形成知識網絡，價值來自連結激發的新想法，而非筆記本身品質。

## 兩者的關係：互補而非競爭

[zettelkasten.de 的整合建議](https://zettelkasten.de/posts/building-a-second-brain-and-zettelkasten/)（中等信心，單一來源，未見反駁）：BASB 管資源與專案管理事務，Zettelkasten 是實際知識加工、整合思考的環境。具體整合做法：用 PARA＋CODE 管資源與專案，用 Zettelkasten 的結構筆記取代 BASB 的專案資料夾。

## 學術實證

查證時（2026-07-09）僅見一篇學術來源：IBM Research 對 7 位 Obsidian 使用者的[質化案例研究](https://arxiv.org/pdf/2509.20187)（高信心）發現，**使用者的知識檢索策略會反向影響其建立與維護內容的方式**，並歸納出四種檢索路徑：搜尋欄搜尋、點擊標籤清單、筆記內行內標籤、筆記內連結。樣本小、單一機構單一工具，不宜過度推廣為普適規律。

## 工具實務

中等信心，高度個人化，常見分工模式：Obsidian（本地優先、純 Markdown、可與 Git 搭配同步）+ Notion（團隊共享）+ Logseq（每日日誌、零碎想法）。Obsidian 個人與商業用途目前皆免費（授權政策歷史上曾變動，以[官方定價頁](https://obsidian.md/pricing)為準）。

## AI agent 的呼應：Hermes Agent 雙軸記憶

[[Hermes-Agent]]（Nous Research 自我進化 agent）的記憶架構與上述人類方法論在邏輯上同構（中等信心，2026-07-09 對抗式驗證）：**有界核心記憶**（`MEMORY.md`／`USER.md`，session 級凍結快照，寫爆報錯逼迫手動整理）對應行動導向、低單筆投入的 BASB／PARA；**外接 `llm-wiki` skill**（官方明言複刻 Karpathy 模式）對應深度連結、高單筆投入的 Zettelkasten／LLM Wiki。兩軸各自複利不同種類的知識——核心記憶複利「精選的當下狀態」，外接 wiki 複利「陳述性知識網絡」——呼應本頁前述 BASB 管資源、Zettelkasten 管深度思考的分工。

補充（2026-07-17）：雙軸類比只涵蓋 Hermes 的**知識**分工。其待辦／roadmap 刻意不進有界核心記憶也不進 wiki，而是第三個獨立子系統（SQLite Kanban 任務佇列，見 [[Hermes-Agent]] 的任務管理節）——「工作狀態」與「知識」分開存放，這點人類 PKM 方法論裡對應的是 GTD／PARA 的 Projects 層，而非 Zettelkasten。

> ⚠️ 同一輪查證也駁回了多筆過度延伸的類比，包括「A-MEM／Mem0 等記憶系統明確採用 Zettelkasten 方法論」「Hermes 的 skill 目錄結構與本 vault `.agents/skills` 慣例同構」——AI agent 記憶系統與人類 PKM 方法論的對應目前僅停留在**邏輯結構相似**，不代表兩者有直接技術血緣或官方引用關係。

## 侷限與存疑

- CODE／PARA 多數細節來源集中在創始人本人網站與其愛好者部落格，屬同源生態圈重複轉述，非獨立學術驗證——但概念框架本身穩定未變（[[第二大腦整合的現成工具與做法]] 對 PKM 活用共識的查證同樣落在 blog／書級、標為「個人工作流主張、非實證」，是同一「PKM 主張缺獨立效果驗證」問題的另一輪印證）
- 對抗式驗證駁回了 4 條主張，包括「PARA 第三類是 References」「CODE 是 PARA 的補充系統」「某作者 Obsidian 承載 80% 開發筆記」等具體定義／數字類主張，顯示同類部落格來源的細節不總可靠，引用時宜逐條核實而非整篇採信
- 未解問題：CODE／PARA 是否有創始人生態圈外的獨立效果驗證？BASB 陣營是否正式回應過 Zettelkasten 派「Distill 未產生獨立筆記」的批評？
- 未解問題（AI agent 記憶對照，2026-07-09 補）：Hermes 的自主 skill 生成有無品質把關（已知有背景 skill-review agent 產生非預期副作用的案例，需先確認失敗模式再借鑑）？其「有界記憶寫爆即報錯」機制是否可類推到 wiki 頁面級（頁面過長/索引過肥時），還是只適用其特有的極短記憶檔案場景？
