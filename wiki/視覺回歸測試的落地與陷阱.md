視覺回歸（visual regression，以下 VR）是 [[用測試約束-AI-產碼]] 缺的那一塊：type check、lint、單元測試全綠，但畫面壞掉——AI 產的 UI 碼尤其容易落在這個縫裡，因為模型改的是類別名與版面結構，而那些正是既有測試不斷言的部分。VR 是這層的機械防線，也是 [[不讀碼時該看哪些圖]] 講的「驗收界面」在畫面層的對應物。

本頁沿兩條軸展開。**第一條是目標與範圍**：VR 到底在斷言什麼、該把什麼納進來——這決定它值不值得做。**第二條是一個取捨：渲染環境的控制權放在哪**——VR 的所有技術麻煩幾乎都由這一項推導得出：本地 pixel-diff 把整條渲染鏈（kernel、字型、hinting、GPU、瀏覽器版本）一起納入斷言範圍，你想斷言的是「版面有沒有變」，實際斷言的是「這台機器這一刻畫出的每個像素」。

## 一、目標：VR 的 oracle 是「有沒有變」，不是「對不對」

這是選型前最該先講清楚的一句話，而且有同儕審查的原文可引：

> Snapshot testing is a type of output comparison testing technique that asserts whether the outputs by the current state of the product remain unchanged. That is, **it only detects differences before and after code changes, and ignores whether the current state is correct.** The aim of snapshot tests differs from those of unit and functional tests that define the correct behavior of the products.
> ——Fujita et al., ICSME 2023 (NIER)

由此推導出三件事，全部是機制上的必然：

- **基準圖本身錯了，VR 一樣全綠。** 它比的是「和上次一樣嗎」，沒有任何一處在問「這樣對嗎」。把版面切歪了但兩次都歪一樣，VR 不會有意見。
- **它是變更偵測器，不是驗收關卡。** 「畫面對不對」的判斷永遠發生在**人核可基準圖的那一刻**——這也是為什麼下面第 6 點說治理才是真正的失敗點：核可品質等於整套機制的品質上限。
- **它不能替代任何一層既有測試。** 同一篇研究的實測：1,029 個 repo 只有單元測試、567 個兩者都有、**只用 snapshot 測試的僅 31 個**；而兩者都有的專案，其單元測試數量與只有單元測試的專案幾乎相同（中位數 16.7 vs 16.2，Mann-Whitney U 檢定 p=0.23 無顯著差異）。**snapshot 測試是加上去的，不是拿來換掉什麼的。**

維護成本也有實測錨點：該研究發現 **8.2% 的 commit 會動到 snapshot 檔**。

> **兩點引用限制。** 其一，該研究對象是 **Jest 的序列化 DOM snapshot**（比的是 JSON／DOM 字串），不是像素級 VR；上面的 oracle 定義兩者共通，但 8.2%、31 個 repo 這類**數字不可直接外推到 pixel VR**。其二，LLMShot（arXiv 2507.10062）把這個 8.2% 引成「false positives 或非預期改動佔 commit 的 8.2%」——**回讀原文後確認是誤引**，原句只說「a non-negligible number of commits (8.2%) update the snapshot files」，沒有任何假陽性的成分。引用時以原文為準。

## 二、範圍：三個維度會相乘，預設是全都截

VR 的範圍不是一條線，是**粒度 × 狀態 × 模式**三個維度相乘，這也是它成本失控的唯一機制。

**維度 1：粒度。** 由粗到細三種，愈細愈不容易被無關改動波及：

| 粒度 | 做法 | 特性 |
|---|---|---|
| 整頁 | `expect(page).toHaveScreenshot({ fullPage: true })` | 任何一處高度變化推移下方全部內容，一改全紅 |
| 元素 | `expect(locator).toHaveScreenshot()` | **只有那個元素變才紅**，同樣有「等連續兩張相同」的抗抖動 |
| 元件 | Storybook story ＋ Chromatic／Percy，或 Playwright 內建 `mount()` ＋ 自建 story gallery | 元件庫／design system 的自然單位，與頁面內容脫鉤；`mount()` 回傳 Locator，故元件級 VR 即元素級截圖 |

**維度 2：狀態。** 同一個元件的 hover、focus、error、empty、loading、超長文字截斷——這些正是回歸最常發生、而人工 review 最看不到的地方。走 Storybook 路線時一個狀態就是一個 story；走 Playwright 路線得自己把狀態擺出來再截。

**維度 3：模式（modes）。** viewport、主題（light／dark）、語系。Chromatic 把這些組合稱為 mode，關鍵在它的計價與治理語意：**每個 mode 各自獨立的基準圖與獨立的核可**。所以「桌機／平板 × 淺色／深色 × 兩個語系」不是多 3 個設定，是 **×8**。

**預設值要知道**：Chromatic 預設**替所有元件截圖**，控制方式是 opt-out——`chromatic: { disableSnapshot: true }` 可下在 story、component、project 三層（專案層設預設、個別覆寫）。Playwright 則相反，你不寫 `toHaveScreenshot()` 就沒有。兩種預設方向決定了兩種失控形態：前者是「沒人排除 → 帳單與雜訊一起長」，後者是「沒人補 → 以為有防線其實沒有」。

**收斂範圍的判準**（本節這幾條是綜合推論，非引自單一來源）：

1. **先問這一塊壞掉會不會有人在意**——內部後台的表格對齊跑掉，和結帳頁按鈕被蓋住，不是同一個量級。
2. **能用元素級就不要用整頁**：整頁截圖的紅燈幾乎不帶定位資訊，而定位資訊正是 triage 成本的大宗。
3. **模式維度最貴，先只留一個**：先固定單一 viewport ＋ 單一主題把流程跑順，確認核可紀律真的執行得起來，再往上加維度。
4. **動態內容不進範圍**：日期、隨機值、外部資料驅動的列表，先在測試資料層固定，固定不了就排除——留著它等於自願每輪付 triage 成本。

## 三、兩條路線的機制差異

| | 本地 pixel-diff | 雲端 DOM 重繪 |
|---|---|---|
| 代表 | Playwright `toHaveScreenshot`、BackstopJS | Percy、Chromatic |
| 截什麼 | 你的瀏覽器渲染出的 PNG | 序列化的 DOM ＋ 抓齊的資產 |
| 在哪渲染 | 你的機器／你的 CI | 廠商的雲端瀏覽器 |
| 環境變因 | 全部繼承 | 結構上被隔離 |
| 代價 | 免費、資料不出境 | 付費、綁 CI、資料出境 |

Percy 的流程是：呼叫 snapshot 時捕捉並序列化 DOM → 交給 asset discovery 在 Chromium 裡重放、攔截網路請求把資產抓齊（預設等 100ms 無新請求）→ 送到 Percy 自己的環境**重新渲染**，且預設關閉 JavaScript（*"JavaScript has already executed and modified the page before the DOM is captured"*）。Chromatic 走同一路線（Storybook 導向）。**它們穩定不是因為演算法比較聰明，是因為根本沒在你的機器上截圖。**

## 四、本地路線怎麼用（以 Playwright 為例）

### 起手

```js
await expect(page).toHaveScreenshot();
```

第一次跑沒有基準圖，會寫入 `<spec 檔名>-snapshots/` 並報錯提示。產出檔名長這樣：`example-test-1-chromium-darwin.png`——**browser 名與平台是檔名的一部分**，官方直言「Screenshots differ between browsers and platforms due to different rendering, fonts and more, so you will need different snapshots for them」。用多個 project 時，project 名會取代 `chromium`。路徑可用 `snapshotPathTemplate` 配置。

基準圖**要進版控並在 PR 裡 review**（官方明示 "You should commit this directory to your version control and review any changes to it"）。這件事看似瑣碎，卻是整套機制的關鍵：基準圖沒有人看，VR 就退化成「按 approve 讓 CI 變綠」的儀式。

比對引擎是 [pixelmatch](https://github.com/mapbox/pixelmatch)。斷言前會**自動等到連續兩張截圖相同**才拿最後一張去比——這是內建的第一道抗抖動。

### 穩定化手段（依成本由低到高）

1. **預設已經幫你關掉的**：`animations: "disabled"`（有限動畫快轉到結束並觸發 `transitionend`、無限動畫取消回初始態、截完再播）、`caret: "hide"`（藏文字游標）、`scale: "css"`（每個 CSS 像素一個像素，避免 high-dpi 機器產出兩倍大的圖）。這三個是預設值，不需要動。
2. **`stylePath`**：套一份自訂 CSS 再截圖，用來隱藏動態元素。**會穿透 Shadow DOM 並套用到內層 frame**，是遮蔽手段裡覆蓋面最廣的一個，適合放全域規則（隱藏 iframe、關掉 `transition`、固定 `::-webkit-scrollbar`）。
3. **`mask`**：傳一組 locator，被遮的元素整個 bounding box 覆蓋成粉紅色塊（`#FF00FF`，可用 `maskColor` 改）。適合逐處理的動態內容（時間戳、頭像、金額）。注意**對不可見元素也會套用**。
4. **`clip` / `fullPage`**：把斷言範圍縮到真正在乎的區域。`fullPage` 預設 false；截全頁會讓任何一處高度變化推移下方全部內容，紅一大片而看不出真因。
5. **容差兜底**：`maxDiffPixels`（允許幾個像素不同）與 `maxDiffPixelRatio`（允許的比例，0–1），兩者**預設都不設**；可在 config 的 `expect.toHaveScreenshot` 全域或逐 project 給預設值。

### threshold 與 maxDiffPixels 是兩種東西

- `threshold`（預設 `0.2`）是**逐像素的色差容忍**，量的是 YIQ 色彩空間裡的「可感知色差」，0 嚴格、1 寬鬆。
- `maxDiffPixels` / `maxDiffPixelRatio` 量的是**有多少像素被判為不同**。

分工：`threshold` 吸收抗鋸齒與微小色偏，`maxDiffPixels` 吸收零星雜訊面積。**兩者都吸收不了字形或字距改變**——那是整片像素的位置不同，不是同一個位置顏色略異。這條機制決定了下一節第一個陷阱。

### 更新基準圖的語意（很容易搞錯）

`-u` / `--update-snapshots` 接四種值：`all`、`changed`、`missing`、`none`。

- **不帶旗標** → 等同 `missing`（只補沒有的）
- **帶旗標但不給值** → 等同 `changed`（只更新有差異的）
- 要全量重寫 → **必須明寫 `--update-snapshots=all`**

驗收「這輪到底改了幾張」不要看 `git status` 的檔案數——`=all` 會重寫全部檔案造成 mtime 變動的假象，要用 `git hash-object` 逐張比內容。

## 五、須注意的坑

### 1. 容差救不了字形差（機制決定，非調參問題）

承上：字型換了、字距位移了，差異是位置而非顏色。實務上會出現「能吸收底噪的容差，必然連真實改動一起吃掉」——某專案實測底噪最小值 236px 已大於真實文案改動的 153px，容差區間是空的。中文站尤其嚴重，因為一個字形不同就是整片方塊全差。

### 2. Docker 不是銀彈

網路上大量「用官方 Playwright image 就解決了」的說法**不是官方立場**。官方文件只說渲染會隨 host OS、版本、設定、硬體、**電源狀態（電池 vs 插電）**、headless 模式等變動，處方是「run tests in the same environment where the baseline screenshots were generated」，全篇沒有推薦 Docker。

一手反例：Playwright issue [#35143](https://github.com/microsoft/playwright/issues/35143)——回報者用**同一個 image、同一組雲端 VM 映像（因此 kernel 相同）**，中文文字仍出現細微差異；維護者先猜 font hinting、再猜 kernel，最後回「Really only you can figure out what that difference is」，建議 `maxDiffPixels: 100` 繞過，issue 以 stale 關閉。回報者補充**同一台機器重跑也會出現 1px 差異，成功率約 70%**。

結論：Docker 消除的是「跨 OS」這一維，不保證跨機器逐位元一致。

### 3. CJK 有專屬的前置條件

容器內沒裝 CJK 字型時，中文直接渲染成 tofu 方框（`fc-list | grep -i cjk` 為空即可確認）。要裝 `fonts-noto-cjk`（Ubuntu 另有 `fonts-noto-cjk-extra`）＋ `fontconfig`，並跑 `fc-cache -fv`。但這只解決「有沒有字」，**不解決上一點的 hinting 差異**。

### 4. dev server 產的基準圖不穩定

某專案實測：以 Nuxt dev server 產的基準圖只在同一個 dev server 生命週期內有效，容器或 dev server 一重啟渲染輸出就變、基準圖成批失效（重啟後原本紅的 43 條全綠、原本綠的反而紅）；改用 production build ＋ preview 後，經「殺掉 preview 重啟」與「重新 build」兩道擾動皆全綠，全套耗時也由 4–5 分鐘降為 2.3 分鐘。**單一專案實測（n=1，無外部佐證）**，但機制上合理：dev server 會注入 HMR runtime、CSS 未經打包排序、樣式以動態 `<style>` 插入，這些都不保證跨進程一致。

### 5. 重產前先分辨「本輪改動」與「既有漂移」

同一專案的實測：某次重產前全套 17 紅／86 綠，其中只有 11 張屬本輪改動，另 6 張是既有漂移（把改過的共用元件退回改動前重跑仍紅）。**不分辨就一次 `=all` 重產，等於把既有漂移悄悄烙進基準圖**，那 6 張從此永遠不會再紅。

### 6. 基準圖治理才是真正的失敗點

Chromatic 的模型值得借鏡（即使你走本地路線）：基準圖**只在有人 accept 時才更新**，且**逐分支各自維護**——新分支從分岔點繼承，別的分支 merge 進 `main` 的核可**不會自動流到你的分支**，所以要定期 rebase／merge `main` 回來，否則會看到「已經核可過卻又冒出來」的假陽性。

改寫歷史會讓兩套歷史分岔：`reset --hard` 之後 git 忘了那個 commit，Chromatic 記得。rebase 則是刻意設計成「一律沿用該分支最後一次 build 的已核可基準」，不因不是 git 後代就丟棄。

走本地路線時，基準圖是 repo 裡的檔案，上述問題換一種形式出現：**merge 衝突發生在 PNG 上，git 幫不了你**，只能挑一邊重產。

### 7. flake 的業界處置是「承認它不穩」而非「修好它」

Chromatic 的 Flake Filter：每個測試**渲染多次**判斷變化是真的還是不穩定，判為不穩就自動忽略、**不擋 build**，收在摺疊區仍可 review，可手動 deny 強制失敗，每次 build 重評、恢復穩定就自動歸隊。代價是被自動忽略的仍計入計費快照數。這件事的訊號意義大於功能本身：**連專做這門生意的廠商都不主張能消除 flake，只主張能把它隔離。**

### 8. 動態內容要逐類處理，工具只包一部分

Chromatic 會主動暫停 CSS 動畫／轉場、影片與 GIF，並以 network quiescence（一段網路靜默）判斷可以截圖；但明說 **「Chromatic cannot disable JavaScript-driven animations, so you are responsible for pausing them」**。日期時間、隨機值、排序不穩的清單，都要自己在測試資料層固定，不是靠遮蔽。

## 六、替代與互補：VR 不是唯一的畫面防線

先分清楚問題，才分得清工具——**兩類機制回答的是不同的問題**，不是同一件事的好壞排名。

| | 變更偵測 | 性質驗證 |
|---|---|---|
| 問的是 | 和上次核可的比，有沒有變 | 這個性質成不成立 |
| 要不要事先知道驗什麼 | **不用** | **要** |
| 代表 | pixel VR、ARIA snapshot、DOM snapshot | `toHaveText`／`toBeVisible`／`toHaveCSS`、版面不變量、a11y 掃描 |
| 紅燈品質 | 只說「有東西變了」，位置與意義要人判 | 直指哪個性質壞了 |
| 漏什麼 | 幾乎不漏，但噪音全收 | 漏掉你沒想到要驗的 |

Playwright 官方對這條分界有明確表述：snapshot 適合**整頁與元件的廣泛結構檢查**、變動不頻繁的回歸；assertion 適合**核心邏輯、計算值與需要精確條件**的細粒度測試，並建議兩者組合而非二選一。

**ARIA snapshot（`toMatchAriaSnapshot`）是這張表裡最容易被忽略的一格**：它比的是無障礙樹——角色、可及名稱、層級、連結目標，而**不是像素**。這意味著本頁第五節那一整批坑（字型、hinting、GPU、Docker、dev server）對它**完全不適用**，因為渲染細節根本不進入比較。它抓得到「按鈕不見了、標題層級變了、文案改了、連結指向變了」；抓不到「顏色、間距、對齊、疊層」。

**版面不變量**是另一條被低估的路：與其比整張圖，不如斷言「這兩個元素的 bounding box 不重疊」「內容沒有溢出容器」「這一欄靠右對齊」。這類斷言零環境變因、紅燈自帶語意。專門做這件事的框架（Galen Framework）**已停止維護**（最後 release 2019、repo 最後推送 2022），不建議採用；同樣的斷言用 Playwright 的 `boundingBox()` 直接寫得出來。

**推薦的堆疊順序**（推論，非引自單一來源）：

1. **ARIA snapshot 當主力變更偵測**——AI 改壞 UI 的常見形態（元素消失、結構錯亂、文案錯置）它幾乎都抓得到，而且完全不用付渲染環境那筆稅。
2. **對真正在乎的視覺性質寫斷言**——品牌色、關鍵間距、對齊、不溢出。精準、穩定、可解釋。
3. **pixel VR 只留給「說不出來但不能變」的少數區塊**，並且用元素級或元件級粒度。

換句話說：**pixel VR 是最後一道、而不是第一道**。它的獨門價值在於能抓到你事先列不出來的視覺回歸，代價則是本頁前面那一整節的坑；把能用前兩層表達的東西先搬走，剩下的量少了，那些坑的成本才付得起。

## 落地判準

- **先確認你要的是「變更偵測」而不是「畫面驗收」**——若真正的需求是「這頁做得對不對」，VR 結構上答不了，該找的是人工驗收或設計稿比對。
- **UI 已視覺凍結、且改動頻率低** → VR 划算，因為基準圖不常需要重產。
- **UI 每週在變** → 基準圖維護成本會超過它擋下的回歸，先不要做。
- **中文站 ＋ 只在本機跑** → 可行，但要接受第 2、3 點，且**基準圖必須由固定的一台機器（或固定的 build 產物）產出**。
- **要在 CI 擋 PR** → 本地路線需要先解決「CI 的機器與產基準圖的機器一致」，否則直接評估雲端 DOM 重繪路線，那是它結構上的優勢所在。
