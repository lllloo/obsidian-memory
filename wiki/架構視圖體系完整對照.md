「架構圖有哪幾種」這題的答案取決於問的是哪一條軸。[[不讀碼時該看哪些圖]] 已釐清兩條：**抽象層級**（放大倍率）與**關注面向**（結構／執行期／部署／資料／維運）。本頁補上第三條，並把各體系的清單查全——先前的對照表為求精簡只列格位，漏掉的部分改變了讀法。

## 第三條軸：品質屬性是橫切面，不是視圖

Rozanski & Woods 明講他們**刻意不設 Security viewpoint**，理由是安全性會同時影響幾乎所有其他視圖——功能視圖要管認證、資訊視圖要管存取粒度、維運視圖要管金鑰與更新，「用一個視圖處理它並不合理」（**high**，官網一手全文）。他們為此另造一個與 viewpoint 正交的概念：

> **Definition**. An *architectural perspective* is a collection of activities, tactics, and guidelines that are used to ensure that a system exhibits a particular set of related quality properties that require consideration across a number of the system's architectural views.

也就是說 perspective **不產生新的圖**，它是拿去「套用」在每一張既有視圖上的檢查清單。官方目錄十項（**high**，官網一手）：

| Perspective | 要保住的品質 |
|---|---|
| Accessibility | 身心障礙者可用 |
| Availability and Resilience | 可用性與失效處理 |
| Development Resource | 在人力／預算／時程／物料的已知約束內做得出來 |
| Evolution | 面對部署後必然的變更有多大彈性，與其成本的平衡 |
| Internationalization | 不綁定特定語言、國家、文化 |
| Location | 克服元件絕對位置與彼此距離帶來的問題 |
| Performance and Scalability | 可預測地落在效能規格內，並吃得下增量 |
| Regulation | 符合法規、公司政策與各種規則 |
| Security | 可靠地控制、監看、稽核誰能對什麼資源做什麼 |
| Usability | 互動者能否有效工作 |

**對「該畫哪些圖」的實際影響**：品質需求（安全、效能、可演化性）常被誤當成「還缺一張圖」。這套模型給的答案是不用畫——那些東西的正確落點是回頭審每一張既有圖。少畫幾張圖不代表少考慮，這條分工把「圖清單」與「品質清單」拆開，避免圖無限膨脹。

證據強度分列（**混合**，逐項不同）：

- **C4 七種圖**（**high**，[c4model.com/diagrams](https://c4model.com/diagrams) 一手全文）。這是先前對照表的一處缺漏：C4 不只有四層，官網把它分成 **static structure diagrams（4 種：context／container／component／code）** 與 **supporting diagrams（3 種：system landscape／dynamic／deployment）**，共七種。官網原句仍是「你不需要用滿四層，多數團隊 context 與 container 兩層就夠」。
- **arc42 十二章**（**high**，[arc42.org/overview](https://arc42.org/overview) 一手全文）：1 Introduction & Goals、2 Constraints、3 Context & Scope、4 Solution Strategy、5 Building Block View、6 Runtime View、7 Deployment View、8 Crosscutting Concepts、9 Architectural Decisions、10 Quality Requirements、11 Risks & Technical Debt、12 Glossary。官網對第 5 章的註解是「通常是整份架構文件最長的一節」。⚠️ **十二章裡只有 5、6、7 是視圖**，其餘八章是決策紀錄、品質樹、詞彙表這類文字產物——把 arc42 當「圖的清單」會誤解它，它是**文件模板**不是視圖體系。官網另提供 arc42 canvas，把整個系統壓成一頁。
- **4+1 五視圖**（**medium-high**）：Logical、Process、Development、Physical，加上 Scenarios 作為「+1」，出自 Kruchten 1995 年 IEEE Software 12(6) pp.42–50（本頁以 WebFetch 直取論文 PDF 確認名稱與出處，但取得的是模型摘要而非逐字全文）。關鍵限定來自 Kruchten 原句：「The "4+1" view model is rather "generic": other notations and tools can be used」——**4+1 不綁任何記法**，常見那套「Logical 用 class 圖、Physical 用 deployment 圖」的對應是後人以 UML 補的，不是原文規定。
- **Rozanski & Woods**（**high**，官網一手，含一處內部不一致）：官網正文寫「our catalog of **six** core viewpoints: the Functional, Information, Concurrency, Development, Deployment, and Operational」，但同頁表格列出**七個**（多一個 Context）。兩者不一致，且該站為第二版專屬網站——合理推測 Context 是第二版增補而正文句未同步，但**本輪未取得書的版次說明佐證，屬推測**。
- **RM-ODP 五 viewpoint**（**medium**，Wikipedia，非 ISO 原文）：Enterprise、Information、Computational、Engineering、Technology。它額外要求文件必須寫出**視圖之間的一致性規格**（例如 enterprise 物件如何被用來定義 information 單元）——這是其他體系沒有的機制，而「視圖彼此對不上」正是多視圖做法的頭號失效。
- **SEI Views and Beyond 三 viewtype**（**low，未複驗**）：module／component-and-connector／allocation。書本身確認存在（Clements 等九人合著，2nd Edition 2010，ISBN 978-0-321-55268-6，SEI 官網書目一手），但**該頁未列出 viewtype 清單**，上表這三格出自通用知識，引用前須回查原書。

## UML：官方只分兩大類

UML 常被說成「有十四種圖」，但規格本身的分類只有兩層（**medium-high**，[uml-diagrams.org](https://www.uml-diagrams.org/uml-25-diagrams.html) 全文；該站為第三方整理，非 OMG 規格原文）：

- **Structure diagrams** — 靜態結構，不涉時間：class、object、package、composite structure、component、deployment、profile。
- **Behavior diagrams** — 隨時間變化的動態行為：use case、activity、state machine（再分 behavioral 與 protocol 兩種）、interaction（再分 sequence、communication、timing、interaction overview 四種）。

三個不可略過的細節：

1. **該站自陳其清單含非官方項目**，並就其中數項明講規格未定義：object diagram「UML 2.5 規格根本沒有定義」、manifestation diagram「UML 2.5 未定義」、network architecture diagram「UML 2.5 未正式定義」。故**引用「十四種」這個數字前應回查 OMG 規格**，本輪未取得規格原文。
2. **規格不禁止混用**：原文明說各類圖的邊界並非嚴格強制，可以把 state machine 嵌在 use case 裡；是繪圖工具在限制可用元素，不是規格。
3. **use case diagram 在 UML 2.4.1 被定義為 class diagram 的特化**，而 class diagram 屬結構圖——即這個「行為圖」在規格系譜上掛在結構圖底下。分類本身沒有想像中乾淨。

**與 C4 的關係不是競爭**：C4 的 dynamic diagram 官方自陳「基於 UML communication diagram」，並提供 collaboration 與 sequence 兩種樣式（**high**，[c4model.com/diagrams/dynamic](https://c4model.com/diagrams/dynamic) 一手）。C4 是分層與抽象的約定，UML 是記法；兩者可疊用。

## 企業架構層：問的不是同一個問題

ArchiMate、Zachman、TOGAF、DoDAF 常與上面幾套並列，但它們的對象是**整個組織**而非單一系統，混用會答錯。

- **ArchiMate**（**medium**，Wikipedia；官方規格本輪取不到，`pubs.opengroup.org` 回 **401 Unauthorized**）：核心是三層（business／application／technology）× 三面（passive structure／behavior／active structure）的矩陣，完整框架另加 physical、strategy、implementation & migration、motivation 各層。最新版 3.2，2022 年 10 月發布。與 UML／BPMN 的關鍵差異是**它把概念與記法分離**，靠 viewpoint 機制為不同 stakeholder 產生不同呈現。⚠️ **官方 viewpoint 完整清單本輪未取得**。
- **Zachman Framework**（**medium**，Wikipedia）：1987 年 John Zachman 於 IBM 提出，以 what／how／who／where／when／why 六問切分企業，是**分類矩陣**不是繪圖記法。
- **RM-ODP** 見上，1996 年 ISO 發布，針對大型分散式系統。

判準很簡單：如果問題是「這個 repo 怎麼組起來的」，這一層全部用不上。

## 標準本身：ISO/IEC/IEEE 42010

它**不提供任何視圖清單**，只定義 viewpoint／view 這組概念機制與架構描述應含的內容，讓組織自訂（**high**，[iso-architecture.org/42010](http://www.iso-architecture.org/42010/) 一手）。系譜是 IEEE 1471:2000 → ISO/IEC 42010:2007 → **ISO/IEC/IEEE 42010:2011** → **第二版於 2022-11-30 由 ISO 與 IEEE 聯合發布**。

⚠️ **版本引用陷阱**：該官網首頁至今仍寫「This is the website for ISO/IEC/IEEE 42010:2011... the latest edition」，同頁新聞區卻公告 2022 年第二版已出並說明「將更新相關資訊」。**站點自身不一致**，凡引用 42010 一律標明年份版次。姊妹標準 42020（架構流程）與 42030（架構評估框架）於 2019-07 發布。

## 這對「該畫哪些圖」的淨影響

補查後有三處改變讀法：

1. **C4 的 supporting diagrams 不該被忽略**。先前把 C4 當成「只有四層」，於是 system landscape 這一格從未進入考慮——多系統全景**只有 C4 有**，而那正是「一個組織好幾個 repo 各自在做什麼」的落點。它與 [[不讀碼時該看哪些圖]] 選定的 container 層同屬變動很慢的一端。
2. **品質屬性不該再被當成缺圖**。Security／Performance 這類需求對應的是 perspective 而非新視圖，處理方式是回頭審既有圖。
3. **arc42 不是視圖體系**。十二章裡只有三章是視圖，其餘是決策、品質、風險、詞彙表——這也解釋了為何「新人上手包」裡的**業務詞彙表**在 C4／4+1 都找不到位置，卻正好是 arc42 的第 12 章。
