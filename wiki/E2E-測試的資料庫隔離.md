> [[專案測試流程|總覽]] 第 3 層（最外層）的環境問題。本頁只談**資料庫**，不談 E2E 該測哪些路徑。

**本頁狀態**：內容為通用工程實務的綜合，**尚未在本專案實測**；下面的做法在落地時要按實際環境驗證，尤其是平行 worker 與守衛那兩節。

## 結論

E2E 的資料庫要獨立。這裡的「獨立」指**獨立的 database**，不必是獨立的 DB server——同一台 MySQL 開一個只給 E2E 用的 database 就滿足了。

## 為什麼不能跟開發環境共用

關鍵在於 E2E 收尾**不能靠交易回滾**。第 2 層的整合測試（[[專案測試流程-後端-Laravel]] 的 `Feature` testsuite）可以用 `RefreshDatabase` 把每條測試包在交易裡跑完就退回，因為測試碼與被測碼在同一個進程、同一條連線上。E2E 不是：瀏覽器發出的請求由另一個進程、另一條連線處理，測試端開的交易根本包不住它。

所以 **E2E 寫進去的資料是真的留下來的**。跟開發用的 database 共用會出現三種痛：

- 手上的開發資料被測試的清理動作掃掉，或被測試造的假資料污染到難以分辨
- 測試因為 database 裡剛好存在某筆手動建的資料而通過或失敗，換一台機器就重現不出來
- 完全沒辦法平行跑——兩個 worker 同時造資料就互相踩

第二點是最貴的：它讓失敗變成不可信的訊號，而不可信的測試很快就會被整批忽略，這正是 [[專案測試流程]] 說的「測試寫了但沒人跑，比沒有測試更糟」。

## 獨立到什麼程度

| 情境 | 做法 |
|---|---|
| 本機跑 E2E | 同一台 DB server 上另開一個 database，用專屬的環境設定檔指向它 |
| CI | 每次跑起一個乾淨的 DB 容器，跑完即丟——隔離最徹底，也不必寫清理邏輯 |
| 平行 worker | **每個 worker 一個 database**，開跑前依 worker 編號建立 |

平行那條是硬需求，不是優化。E2E 慢，遲早會想開平行；只要多個 worker 共用同一個 database，flaky 就是時間問題，而且症狀是隨機的、很難歸因到「共用 DB」這個原因上。要開平行就先把 database 拆開。

## 不要用 SQLite

第 1、2 層為了速度改用 in-memory SQLite 是可接受的取捨，E2E 不是。E2E 存在的理由就是驗證**真實堆疊**；換掉資料庫等於在最外層親手拆掉它唯一的價值。

差異不是理論上的：型別轉換、外部鍵約束的實際執行、鎖的行為、分組查詢的嚴格程度（MySQL 的 `ONLY_FULL_GROUP_BY` 這類 SQL mode）在兩者之間都不一樣。用 SQLite 跑 E2E，測到的是一個不存在的系統，而且它會綠。

## 重置點放在套件開始，不是每條測試之間

E2E 昂貴，逐條 refresh database 會慢到沒人願意跑，於是就沒人跑。可行的節奏是：

1. **整套開始前**跑一次 migration，並灌入一份固定 fixture（角色、基礎設定、必要的關聯資料）
2. **每條測試自己造自己要的資料**，並用唯一值（時間戳、UUID）避開撞名，讓同時跑的測試互不干擾
3. 測試之間**不重置**

代價是測試之間有殘留資料，所以斷言不能寫成「列表共有 3 筆」這種依賴全域狀態的形式——要斷言的是**自己剛造的那筆**存不存在、值對不對。這跟 [[專案測試流程]] 的「斷言要具體」是同一條紀律在 E2E 的形態：弱斷言在這裡不只是容忍錯誤，還會直接變成隨殘留量增加而崩掉的 flaky。

**fixture 要固定、可重現**。用寫死的 seeder，不要用隨機 factory 灌初始資料——隨機資料讓失敗無法重現，而 E2E 的失敗本來就最難查。

## 防止跑到正式資料庫

E2E 的清理動作（重建 schema、清表）具破壞性，一旦環境設定檔選錯就是不可逆的事故。靠紀律記得不夠，要有機器擋。

做法是在執行破壞性動作前加一道守衛：檢查目前連線的 database 名稱是否符合約定（例如必須含 `_e2e` 字樣），不符合就直接中止。這條檢查很便宜，而且它擋的是那種只會發生一次、但發生就無法補救的錯誤。

同一個理由，E2E 用的環境設定檔要進版控忽略清單、或至少與正式設定明確分檔，不讓「複製一份改一改」變成預設操作。
