### 入門指南

這張圖清楚告訴你怎麼用 BMAD method，不管你是在 web 上還是在你選擇的 IDE 裡。首先，你有一個專案想法，對吧？你有兩個選擇：可以用 Analyst agent，也就是商業分析師，在開始做 PRD 之前幫你進一步完善想法。我要來示範如何安裝 BMAD method、在 Claude Code 裡設定好環境後啟動 Analyst agent，還有可選的腦力激盪流程，以及如何產出一份產品摘要（project brief），讓後續流程輕鬆許多。

令人興奮的是，現在你可以在 Claude Code 裡、在 IDE 內完成 BMAD method 的一切。如果你願意，你不必再使用 web 和完整的 team stack 了。我自己確實在 IDE 裡全程使用 BMAD method，效果非常好，今天我就要把這個流程展示給你看。快速說一下：我們先有 Analyst agent，然後進到 Product Manager，再到 PO，最後進入開發階段。

花點時間好好理解這個流程，它看起來複雜，但其實是個很簡單的流程圖。這套流程是讓你用 BMAD method 進行 brownfield 或 green field 開發，從發想一路走到在程式碼中實際開發出來。現在你看到的只有 BMAD method 本身。你不需要在本地端 clone 完整的 GitHub repo。

### 完整安裝流程

只有當你想建立自己的擴充包、修改核心系統或為專案貢獻內容時才需要 clone，我非常歡迎那樣做，但你並不需要這樣做。我要示範如何在 Claude Code 裡使用 BMAD method，完全不需要 clone GitHub repo。首先，來建立一個專案。在任何目錄下都可以執行，我建議在 dev 目錄裡操作。我們要輸入 `npx`，然後輸入 `bmad-method install`，使用 BMAD method 版本 4.33.1。

按 Enter 接受。輸入目錄的完整路徑。因為我們在 dev 資料夾裡，輸入 `.` 表示當前資料夾，然後輸入 `/`，再輸入我要建立的新目錄名稱。因為我們從頭開始，沒有任何現有的起始專案，我就命名為 `simple-todo`，這是我們的專案名稱。

這是一個非常簡單的待辦事項應用程式，按 Enter。如果那個目錄還不存在也沒關係。如果你是在做 brownfield 開發，或者你已經用模板開始了專案，只要提供你專案的目錄，它就會把 BMAD method 加入既有的專案。接著這裡是多選，我們就接受預設值，選 BMAD core。BMAD core 是我們展示的敏捷 AI 驅動工作流，按 Enter 就好。然後我們要 shard PRD，也就是生成一份大文件後把它拆成較小的片段。

接受預設值。架構文件也一樣，依照你建立的專案類型，架構文件可能非常龐大，所以你會想把它 shard 成更小的文件，這一切都是自動化的，我稍後會示範。這真的能幫助你最大化 agent 的 context window，讓它們只需載入當下需要的內容，而不是讀完整個巨大的檔案。它們會知道在當下需要載入哪些檔案，有助於管理 context。所以我們選 yes。

現在，這裡有個警告，要注意這也是多選。你可以選擇一個或多個想安裝的 IDE。比如你同時喜歡 Cursor 和 Claude Code，你可以按空白鍵選 Cursor，再按空白鍵選 Claude Code。今天我只在純 VS Code 裡操作，所以我只選 Claude Code。我已經用 radio button 選了 Claude Code，請確保你真的有按空白鍵確認選取。如果你只是把它反白顯示但沒按空白鍵就按 Enter，實際上不會安裝到任何 IDE。

另一個小提示：依照你螢幕的大小，你可能看不到所有選項，只要知道你可以上下箭頭，更多選項就會出現，而且我們也持續在增加更多 IDE 的支援。按 Enter。

現在它在問是否要包含預建的 web bundles。web bundles 在 IDE 裡工作時是不需要的。這個警告主要是提醒我們以免輸錯了目錄。如果有需要，你可以選擇其他目錄位置，或者取消重新開始。這裡我們就選「建立目錄並繼續」。好，往上捲，看看它做了什麼：它安裝了一些 Claude Code 的指令，這些 slash commands 就是我們用來啟動各個 agent 的方式。它也安裝了一些 task commands，非常方便，因為有時候我們想做一些事情，但不一定要啟動一個 agent。安裝完成了，就這樣。

我知道因為我在講解每個選項，花了一些時間說明，但實際安裝有多快呢？我再做一次讓你看看。輸入 `npx bmad-method install`，給它一個不同的資料夾名稱，比如 `demo-one`。Enter、Enter、Enter、Enter，選擇我的 IDE。

### 10 秒安裝示範

Enter、Enter、Enter，完成了。5 秒鐘，你就可以開始用 BMAD method，就這麼簡單。好，來確認我們的兩個專案都在。執行 `ls`，可以看到 `demo-one` 和 `simple-todo` 都在。`simple-todo` 是我們要用的專案，所以執行 `rm -rf demo-one`，刪掉它。

現在我們只剩 `simple-todo`。我要進入 simple-todo，然後打開 VS Code。目前這個專案裡什麼都沒有，只有我們為 agent 安裝的 BMAD 內容、Claude Code 的 custom tasks 或 commands，以及完整的 BMAD core 系統。在繼續之前，我想說一件事——我要感謝每一位花時間請我喝咖啡的人。

### 重要的 IDE 使用說明

我和其中幾位聊過，真的很感謝大家對我、對 BMAD method 和這個社群的支持。如果你想支持的話，可以去 Buy Me a Coffee，搜尋 BMAD code，或者點描述欄的連結，任何金額我都衷心感謝。

如果還沒有，去 Claude Code 官網看看如何安裝，決定要用 $20 方案、$100 還是 $200，然後你就準備好了。順帶一提，我跟很多只用 $20 版本 Claude Code 的人聊過，如果你不需要 Opus 模型，$20 的 Claude Code 其實已經能帶你走很遠，端看你的使用量。好，選擇信任這個資料夾，這是我們第一次在這個專案裡開啟它。

你可以執行 `/init` 指令，但我現在還不打算這樣做，因為這個專案裡還沒什麼東西可以讓它分析。等我們建立了一些東西、有了一些內容之後，再來執行 `/init`。回到圖表，第一個我們要交談的 agent 是 Analyst，因為我們要做腦力激盪。如果你按下斜線 `/`，而且你在安裝時選了 Claude Code，你就會看到所有這些選項。如果你不想用箭頭滾動這個清單，你可以直接開始輸入你想要的 agent 名稱的一部分。

比如 `analyst`，你就這樣開始輸入，它就會把你要的選項反白。或者如果你知道完整名稱，直接輸入，或者用上下箭頭找。好，這裡是 Analyst，選它。這就是在 Claude Code 裡搭配 BMAD method 的操作，就是這麼簡單。你看到安裝只要 5 秒，如果你想讀所有選項，最多 10 秒。這位是 Mary，我們的商業分析師。我知道很多人認為 BMAD method 的精髓在於開發實際程式碼，但我認為 Mary 這位商業分析師可能是整個 BMAD method 裡最特別的 agent。

如果你正在思考要做什麼，或者只有一個模糊的想法，我強烈建議你試試這位商業分析師的腦力激盪功能。

### 最強大的 Agent 揭曉

這個功能超越了軟體開發的範疇。你可以用它做任何類型的腦力激盪，無論是工作上的事，還是生活問題。我試過很多腦力激盪工具，包括 Google 開發的專業工具。例如，Gemini Gems 裡有一個預設的腦力激盪 Gem，但它跟這個根本沒辦法比。好，讓我們來試試。現在我們在跟 Mary 說話，Mary 已經啟動了。你可以輸入 `*help`，看看所有可用的功能。

你可以選擇一個數字、輸入指令名稱，或者依靠模糊匹配，LLM 通常都能猜對。我直接選 5 號，也就是腦力激盪，不指定主題，就輸入數字 5。雖然 Claude Code 支援的 context window 看起來讓你可以一直聊下去都不會被壓縮，但這並不代表你應該這樣做。所以當我們完成 Analyst 的腦力激盪後，它會給我們一份腦力激盪文件，存到一個叫 `docs` 的資料夾，然後我會開一個新的對話。我喜歡每次有輸出文件時就開一個新對話，然後準備繼續。所以即使我要繼續跟同一個 agent 說話，我也會清除 Claude 的 context 或開一個新的 Claude 工作階段，再重新載入 agent 繼續。

好，我們跟 Mary 一起出發了，她首先會問我們四個問題。我要用 Super Whisper 來回答。「這次腦力激盪的主題是什麼？」我想創作一個簡單的待辦事項 app 來展示 BMAD method。這應該是一個非常簡單的 Node.js 後端應用程式，但我真正想腦力激盪的是一些讓它稍微有趣的想法。所以來玩些腦力激盪的遊戲，看看我們能想出什麼。

問題二：「有沒有任何我需要知道的限制或條件？」我剛才說了我們用 Node.js，我希望這是個非常簡單、直觀的小型專案，只是為了展示 BMAD method，使用 Node.js 和 TypeScript，然後送出。

這就是你跟 agent 互動的方式。BMAD method 有個神奇之處：它不像 taskmaster 或其他工具那樣，你只要丟出你的想法，它就替你做所有思考和執行。事實上，你在腦力激盪中會看到的是，它實際上會逼你把想法說出來，它會是你的教練。這就是它的特別之處，它不是讓你把大腦關掉、替你完成一切，而是和你一起工作，激發出你們兩個的最佳狀態。

順帶一提，BMAD method 的核心就是提升你自己、學習，同時也提升 LLM。整體而言，你們兩個加起來比任何一方單獨都更厲害。這就是 BMAD method 的秘訣，這就是秘密所在。

「我們的目標是廣泛探索可能性，還是更聚焦的構想發想？」讓我們來個廣泛探索，放開來想。我想展示你作為這個驚人腦力激盪 agent 的能力，偶爾讚美一下你的 LLM 也沒什麼不好，它肯定也會讚美你的。沒錯，這也是預設值。當我們完成後，它會把我們的腦力激盪整理成一份令人驚嘆的產出文件。這是 BMAD method 最近新增的最酷功能之一，在 V4 初版時甚至還沒有這個功能，我原本以為要到 V5 才會有，但我非常喜歡這份腦力激盪文件的輸出，相信你也會喜歡。

我們還沒真正開始腦力激盪，但開始了。你現在又有四個選項，可以自己挑選技術（有 20 種腦力激盪技巧的清單），或讓 agent 根據你的專案推薦，或進行隨機創意混沌——這個很有趣，永遠不知道它會挑什麼，有時會挑最瘋狂的組合——或者是漸進式創意旅程，從超廣泛的「假如…」類型情境開始，共五種，逐漸聚焦。我只是想展示我們的所有選項，這次選 1 號。

好，來了。你可以看到這裡有相當多的技術，未來還會有更多。有「假如情境」、類比思考、反轉法、第一原理思考、結構化框架（如 SCAMPER 法、六頂帽子、心智圖）、協作技術（來自即興表演界的 Yes-And、腦力書寫、輪流法、隨機刺激），還有用五個 W 做深度探索（這是做根本原因分析的經典腦力激盪技巧）、形態分析、進階技巧（如強制聯想、假設顛覆、角色扮演、時間位移、資源限制、隱喻映射、問題風暴）。有了 Mary 這位 BMAD agent 的加持，她會引導你走過這些流程，幫你想出你可能從未想到的點子。你會看到，透過腦力激盪，我們甚至可以讓一個待辦事項清單變得超級有趣。

如果你選了上面的其他技術，那些也涉及從清單中進行多選，然後逐一執行，通常每個需要 10 到 15 分鐘。

所以這可能是個耗時的過程，但看，如果你正在開始一個真正龐大的專案，或者你有一些有抱負的想法，做這個腦力激盪來想出超有創意的點子是非常值得的，花時間為未來打好基礎。我就隨便挑幾個：社群有人說他們很希望看到六頂帽子和五個 W 在 BMAD method 裡，然後才發現它們其實早就在了。所以就為了他們，我選 6 號「五個 W」，再選 11 號角色扮演，角色扮演總是很有趣。

現在 agent 會記住我們的選擇，逐一帶我們走過每個技術。記住，我們不是要求 Mary 幫我們腦力激盪、替我們想出這些內容，她是要引導我們走過這個練習。這是你自己的私人教練，用來針對複雜、有創意或有趣的想法進行腦力激盪，各位，這值太多了。

你可以付費請專家教你腦力激盪或擔任你的腦力激盪教練，那可能要花上好幾千美元，而你現在免費得到這些，我們全都在 Claude Code 裡做到了，太驚人了。

好，讓我們看看有什麼。太棒了，首先是 6 號選項，也就是六頂帽子，然後是五個 W，再來是角色扮演。這將會產生一些非常有創意的想法。再次強調，這不一定要關於 app，你可以腦力激盪任何事情——也許你想腦力激盪一個度假計畫，或者腦力激盪 10 年後如何退休，或者腦力激盪你的人生方向，或者如何解開人生中的某個難題。這個工具可以用在任何地方，太驚人了。

好，我們要做什麼？白帽。在六頂帽子裡有六種顏色的帽子，第一頂是白帽。「從技術數據角度來看，哪些事實元素可以讓你的待辦事項 app 更有趣？想想看，它可以追蹤什麼樣的數據？大多數待辦事項 app 忽略了哪些指標和資訊？」我自己絕對不會問自己這個問題，現在我已經在想了，從白帽的角度思考這個簡單的待辦事項 app，讓我開始思考一些很有趣的面向。

記住，沒有正確或錯誤的答案，我也不確定自己是否能想出什麼有趣的東西，這不是我們最終要做的產品，我們只是在拋出想法。當所有這些完成後，它會給我們一份報告，幫助我們提煉出有趣的東西，再帶到下一個 agent 去。我覺得它可以追蹤從輸入待辦事項到標記完成之間花了多少時間。另外，把待辦事項的長度或複雜度與完成所需時間做相關性分析也會很有趣。順帶一提，我非常喜歡用 Super Whisper 或 Whisper Flow 之類的語音轉文字工具。

在 Claude Code 的 IDE 裡工作有個很棒的地方：當你逐段完成每個部分時，它會同步為你建立文件。你不用擔心失去對話紀錄，這和在 web agent 上工作時不同——那時你可能會很焦慮，怕工作階段丟失很難找回整份文件，但在這裡，你一邊工作就一邊在建立文件。我們的腦力激盪記錄已經在這裡了。

現在是第二頂帽子，黃帽，樂觀的好處。好，朋友們，走完所有腦力激盪會花太多時間，所以我要快速帶過全部三個技術。好，你看，我們完成了腦力激盪，做完了三個練習。現在來看看它產出的文件，點選「Open preview」。

### 腦力激盪成果回顧

這會給我們輸出結果，並保存我們做過的腦力激盪記錄。首先我們做了六頂帽子，有批判性的疑慮、創意的替代方案，找到了一些有趣的想法，還進入了流程控制的討論。這讓我思考了很多不同的有趣面向，然後我們做了五個 W。

五個 W 非常有趣。第一個「為什麼」是：為什麼複雜度與完成時間的相關性有價值？我給了一個答案：因為人們一貫低估複雜任務需要多長時間。五個 W 的運作方式是，它接著問「為什麼會這樣？」我給了回答，然後再問「那為什麼會那樣？」如此循環，以一種有點惱人但和 AI 一起做很有趣的方式不斷深挖。

然後我們進入第三個技術：角色扮演。這是我最喜歡的，因為 AI 會自己發明某種角色扮演情境，你永遠不知道它會給你什麼。這次它給我的是「不堪重負的自由工作者」，情境是：你正在同時服務 12 個客戶、有 47 個待處理的任務，而你現有的多個待辦事項 app 讓情況更糟。那麼，我們如何智慧地進行分流？讓我看看今天真正需要做什麼，而不是我以為需要做的。客戶工作量平衡、視覺化儀表板顯示各客戶的任務分配以防止過度承諾。想像你真正想推向市場的專案，以及這個腦力激盪 agent 能為你做什麼，這已經超乎我的想像了。

它還給了我們更多，因為我想繼續腦力激盪。我們不只討論了不堪重負的自由工作者，還聊到了「完美主義學生」從待辦事項 app 中能獲得什麼、行政助理、ADHD 創作者等角色。我不一定自己會想到所有這些人物，Mary 這位 Analyst 幫我想出了這些不同的角色扮演情境，我們來回討論，然後它給了我們一個執行摘要。我們做了這一切，但不是全都要用上，我們討論了哪些對我最重要，我們共同找出了一些關鍵洞見：「從任務管理轉變為行為智能」——你的簡單待辦事項 app 成為一個個人生產力研究實驗室，幫助用戶了解他們實際的工作模式與假設之間的差距。告訴我這不強大。

這就是從「讓我來腦力激盪一個待辦事項 app」中一起得出的結果。接下來真正酷的是，它把事情分解成：現在可以做什麼？未來我們可能想研究和做什麼？以及哪些是登月計畫或有創意且有抱負的事情可以稍後再做？再強調一次，這可以用在生活的任何層面，用在個人生活中，用在工作中。

你現在可以看到 BMAD method 有多強大，你甚至不需要在 web 上操作，我們全都在 Claude Code 裡做到了。事實上，這只是 Claude Code 的最便宜的模型。執行 `/model` 可以看到我用的只是 Sonnet，不是 Opus，也不是預設值，就用 Sonnet。隨著時間，你會直覺地知道什麼時候用哪個模型，相信我，即使你不認為自己是一個強大的開發者，或者你剛接觸這個，你也會掌握的，你會越來越直覺地知道要用哪個模型。我的建議是，為了學習，大部分事情都維持用 Sonnet。

好了，這個階段完成了，所有東西都存到文件裡了。在 Claude Code 或任何 agentic IDE 中的工作流程，最重要的事情是：每次有輸出文件時，就開一個新的工作工作階段，不管是要繼續跟同一個 agent 還是換一個新 agent。我們可以停下來、清除 context，或者如果你不想清除想保留對話紀錄，就關掉視窗、開一個新的，重新啟動 Claude。

你可能不知道的是，如果你關掉 Claude 然後意識到還沒完成剛才的對話，你可以按 `/` 然後按幾次上箭頭，或輸入 `/res`，你就可以看到之前的對話紀錄。如果你有多個對話，你會看到一個清單，現在只有一個。選中後就可以回到那個對話，這就是如何回到之前的對話的方式。但我們想開新對話，所以我就再次關掉視窗，重新輸入 `claude` 開一個新的工作階段。

這次我們還是要跟 Analyst 說話，我要展示如何讓 Analyst 做最重要的一件事，也就是產出 project brief。順帶一提，Analyst 完全是選填的，你不一定要做腦力激盪，也不一定要做 project brief，這取決於你的專案複雜度和你對自己的想法有多清楚。如果我們只是要做最簡單的待辦事項 app，我就直接去 PM，讓它建立 PRD 就好了。

### 掌握 Product Manager

你可以直接從 PRD（含 epic 和 story）進入開發，我之後的完整 A 到 Z 示範會展示這個流程，但現在我只想繼續展示在 Claude Code 裡使用的基本路徑。所以現在選 2 號，這會幫我們建立 project brief。你可以看到它載入了 elicitation methods，這是 BMAD method 的另一個重大亮點。

BMAD method 是由 YAML 模板建立的，每個模板基本上有兩個東西：文件類型的大綱架構，更重要的是——我認為這是它比我看過的任何其他方法都更強大的地方，但其他方法也開始學習這些想法了——模板裡嵌入了給 LLM 的指示，告訴它應該如何與你互動。就像我稍早說的，BMAD method 的美妙之處不是你請它做什麼然後它輸出整份文件，而是它真的跟你來回協作，共同想出最好的結果。

所以，它先問我們有沒有現有的腦力激盪結果、市場調查等資料。有時最好先研究市場，看看有什麼東西，再建立你自己的版本，可能加入你自己的特色。市場非常大，不要覺得你必須永遠搶先上市，也許你想做市場調查，看看有什麼，或做競爭分析，看看競爭對手做了什麼不同的事。我們要做的是把腦力激盪結果放進去，說「這是我的腦力激盪結果，用這個來啟動我們的互動模式，建立 project brief 的工作」。這些不是必須記住的確切措辭，你就像跟你的商業分析師說話一樣跟它說。

這樣就啟動了流程。好處是，我們開了一個新的對話，但因為我們把結果存到文件了，我能夠在全新的 context 下使用它，不會被之前的對話污染，只有腦力激盪的輸出。這保持了 context 的精簡。它現在會問我們一些問題，從我們的腦力激盪中提取內容，可能比一般建立 project brief 的速度更快，因為它已經知道執行摘要是什麼了。

我只展示第一個部分，然後完成文件，再繼續到 PM。你可以看到，每完成一個部分，這只是整份 brief 的一個段落，它就從我們之前的腦力激盪中推算出一些東西，我們可以修改或告訴它改變。在每個部分結束時，你會看到多個選項，這些叫做 advanced elicitations（進階引發法）。不管你在跟 PM、Architect 還是這裡的 Business Analyst 工作，每個文件的大多數部分都會提供與正在處理的文件相關的不同進階引發法。

現在，不同於腦力激盪時它問你問題，這裡是 BMAD method 另一個強大面向的用武之地，我之前沒有太多談到這個，但這非常重要——這就是你逼 LLM 表現更好的地方。當你跟任何 LLM 說話，不管是用 BMAD method 還是只用 ChatGPT，如果你想象一個鐘形曲線，你得到的大概是整個 LLM 語料庫的平均回答，不特別好也不特別差。Advanced elicitation 是你真正刺激 agent、要它「做得更好，確保你已經把這個問題過了一遍火，給我最好的結果」的機會。

挑戰範疇，我們可以逼它腦力激盪——就像之前它逼我們腦力激盪一樣，我們現在可以反過來對 LLM 做同樣的事，讓它腦力激盪不同的想法。其實還有更多進階引發法，只是為了不要讓你不知所措，它暫時只顯示一部分。讓它做 4 號和 5 號。等它執行的時候，注意它已經開始建立我們的 brief 了，這是我們的 project brief。再次強調，在 IDE 裡用 Claude Code 做這個的美妙之處是：我們在工作的同時就在建立文件。

它先做了「關鍵假設測試」，這本身就是一個很棒的事情，可以對任何你有的產品想法做這件事：審視所有你的產品想法，真正做壓力測試，確保它們有道理，特別是如果你想先做一個 MVP 來搶先上市。然後我們還做了「探索替代解決方案路徑」。在最後，它綜合了所有內容，根據它自己做的事情給出一些建議。

好，這只是示範，所以我們就直接套用所有建議、更新部分，繼續到 product brief 的下一部分。請訂閱頻道，如果你喜歡這個內容。朋友們，還有更多內容要來，我知道這些影片出來的頻率不如我希望的那麼頻繁，因為我同時也在持續改進 BMAD method。我不是只想炒作新事物或新產品，但我確實想用這個平台把改變分享給你們，而且我花了很多時間實際在這個上面工作。訂閱頻道，開啟通知鈴，這樣當下一部影片出來時你就知道了，因為有時候出片時間不太規律。也加入我們的 Discord。

好，讓我加快節奏。Brief 完成了，我們走完了整個流程，brief 現在準備好交給 PM 了。在做這件事之前，我想讓你看看我們的 product brief，因為我們在 Claude Code 裡而不是在 web 上，它會一直幫我們更新文件。我們有執行摘要、問題陳述、痛點、我們為什麼要做這件事、提出的解決方案是什麼、目標用戶是誰（包括人口統計、我們預期誰會使用這個、他們各自會如何使用以及為什麼對他們有價值）。這非常重要。

如果你只是想把任何產品推向市場，只是想「vibe code」出個東西、丟出去、成為一夜暴富的人，也許你會，但你必須考慮這些事情，你必須了解你的目標受眾。這就是這份 product brief 的美妙之處——它真的能幫你理清很多思緒，確保你在做一個有道理的東西，或者指出你可能需要轉向，因為它實際上不會達到你想要的效果。

為什麼要浪費大量金錢、精力和時間來構建一個不會成功的東西，而你可以預先做這一點點研究呢？所以我們展示了這整份文件，product brief 的重點是真正與它來回工作，產出這份文件，幫助你從最根本的層次理解你要做什麼。

一如往常，即使在 Claude Code 裡，即使我們可能可以繼續跟三個 agent 說話都不會用完 context，我們仍然要開一個新的。所以再次關掉視窗、開一個新的 Claude 工作階段。我要示範另一種方式，就是 `/clear`，這會清除對話歷史並釋放 context，基本上是一樣的效果。你也可以用 `/compact`，但我不建議這樣做。如果你看到 IDE 顯示你快要開始壓縮的警告，這意味著你在同一個對話裡待太久了，可能需要收尾了。有不同的技術來處理這個情況，但一般來說你不會想依賴 compact，它可能會隨機忘記一些重要的事情。

還有其他技術，但基本上如果你遵循我的方法，就是切換並 clear，偶爾你可能忘記，突然看到那個警告，然後就需要應對。現在讓我們跟下一個 agent 說話。如果不確定要跟哪個 agent 說話，可以回去看圖表。我們已經跟 Analyst 說過話了，我們做了可選的腦力激盪，沒有做可選的市場調查或競爭分析，但你可以自己試試，取決於專案類型，但我們確實建立了 project brief。現在要去跟 Product Manager 說話，如果我們有 product brief，就把它給 Product Manager。它其實會問我們，所以如果你有更簡單的專案，或者你已經知道你想做什麼，也許你已經有 project brief 了，你可以直接跟 PM 說話，它只會問你更多問題。

### 建立 PRD

但如果你提供了 brief，它就能快速啟動、更快完成 PRD。取決於你想怎麼工作。再次強調，如果你只是在做一個簡單的 app，你不必走過所有這些，直接去 PM、建立 PRD，甚至可以告訴它你想要一個內建架構的技術 PRD，很快你就能開始寫程式了。有多種流程和工作方式可以使用這個系統，如果不確定就回去看圖表。

回到 Claude Code。按 `/` 後輸入 `pm` 就可以直接進入，或者不確定的話也可以瀏覽清單。Product Manager 要建立的 PRD 也就是產品需求文件。建立 PRD 很重要，我說這份 PRD 最重要的三件事是：第一，它給我們所有的功能性和非功能性需求，以及滿足這些需求所組成的 epic，我們可以看到整個建構計畫的所有內容。

第二，它幫助我們共同確認什麼在 MVP 範疇內，什麼可以拉出去作為 MVP 之後的功能。如果你能讓 app 做到最簡單的版本、能夠達到初始目標，那就能降低風險、減少對產品的投資。也許你想以最少的功能集推出市場測試，這就是為什麼你要做 MVP，也就是最小可行產品。什麼是這個核心的最基本功能？PM 還會留存你其他的想法，如果不在 MVP 範疇內，就會保存起來作為 MVP 之後的 epic，在主要建構之後再處理。

最重要的是什麼？幫助我們維持 MVP 的範疇，提供含 epic 的功能性和非功能性需求。第三件事，也是 BMAD method 的關鍵——在那些 epic 裡，它要建立 user stories，更具體地說，它知道我們是在為非常非常「笨」的 developer agent 建立這些 stories。就像我一直說的，你不能把大腦關掉、100% 依賴它。所以我們要用 advanced elicitation，我們自己閱讀資訊，邏輯地思考 story 的順序是否合理。

如果你看到 story 裡沒有「建立鷹架」、「設置你的專案或帳號，或者你需要的任何東西」之類的步驟，你就知道有問題、有東西被遺漏了。通常那應該是第一個，比如「專案設置」，學會去識別這些東西。也有一些 advanced elicitation 可以幫我們發現這些問題。

好，我們直接輸入 `create PRD`。在此之前，我不只用數字，也可以用 `*` 再輸入指令名稱，甚至可以說出來。注意這裡有兩個 PRD 選項：一個是一般 PRD，一個是 brownfield PRD。

### PRD 進階技巧

Green field 就像你看著一片乾淨的綠色牧場，開闊無限，幾乎沒有任何限制，你的地基很容易打，什麼都沒有，什麼都不阻礙你。Brownfield 則是所有麻煩累積的地方，可能是一個存在了幾個月或幾年的現有應用程式，也許是其他人開發的，也許你理解它，也許它有很多問題。如果你要在這種情況下工作，你就要選 create brownfield PRD，那會有更多步驟，也要提供現有應用程式的 context。

我們選 2 號，一般 PRD。PM 現在問我們，有沒有 product brief 來建立 PRD？這能幫助我們快速啟動 PRD。如果你從這裡開始，沒有 brief，你就說「沒有」，然後開始回答它的問題，或者回去先做一個。我們就直接拖入 brief，說：「給你，就用這個。」Product brief 和 PRD 的一些段落有很多重疊，但它真的會把語言從 product brief 轉換成功能性和非功能性需求，以及我們在 PRD 裡需要的一些其他細節。

好，讓我們看看結果。它理解了我們要做什麼、為什麼要做，給了我們一些目標、詳細的理由、做出的取捨、關鍵假設和需要注意的地方。我們有選項做 advanced elicitation。我非常喜歡這個，就像之前一樣，我們在建立文件時會一段一段地產生每個部分，所以它始終可以存取它已經做的所有內容，保持一個連貫的文件視野，一段一段地建立起來。

現在是第二部分，是需求，包含功能性和非功能性需求，仔細閱讀這個，確認有沒有你需要或不需要的功能性需求。我想展示我最喜歡的 advanced elicitation。讓我告訴你如何找到 BMAD method 裡其他可用的 advanced elicitation：去 `data` 資料夾，裡面有各種 elicitation methods。有解釋推理、批判與精煉、分析邏輯流程、評估與整體目標的一致性、識別潛在風險、從批判視角挑戰、思維樹、深度探討、「事後諸葛」、「如果只是」腦力激盪、敏捷團隊視角轉換（讓不同的 agent 從不同視角查看）、利害關係人圓桌、元提示分析，還有 2025 年新增的先進技術：自我一致性驗證、REWOO（無觀察的推理）、人物角色混合模式、新興協作發現、紅隊對藍隊、創新競賽、逃脫室挑戰等等。

我做了很多關於如何真正做 prompt engineering 以獲得 LLM 最大化效果的研究，這些是我從 Google 和 Anthropic 找到的一些最佳技術。我還研究過多個提示競賽，那裡的專業提示工程師競爭，我看到很多人使用這些很酷的技術，其中一些真的很有趣。讓我選一個比較瘋狂的，我喜歡「事後諸葛假設」（Hindsight is 2020）。我直接點這裡選它。

這個技術會查看你所有的功能性和非功能性需求，然後想象我們已經建立了應用程式，站在未來六個月或幾年後進行分析，LLM 自己進行對話，模擬在董事會會議或其他場合，大家說「如果當初我們這樣做就好了」。讓我們看看結果：「想像是現在 6 個月後，MVP 已上線，回顧這些需求，你可能會說什麼樣的『如果只是』？如果只是我們從一開始就加入了基本的團隊共享功能。非功能性需求一對於有限預算和單一開發者可能不切實際，如果我們沒有在 MVP 中承諾跨裝置同步呢？功能性需求 7 增加了重大的技術複雜性，如果我們從單一裝置開始，在第二階段再加入同步呢？」

這裡發生了什麼？這實際上在幫你找出如何從 MVP 中削減範疇，保持精簡，讓你能真正推出一些東西上市，測試它，然後再分層加入那些功能。這才是真正敏捷的產品開發方式，超強大的。我說套用變更、更新段落，根據這些洞見修改需求。在你這樣做之前，你可以跟它討論，對不同的事情提問，告訴它你想保留什麼、不保留什麼，但我為了節省時間就直接選 1 號。

LLM 不會總是主動告訴你所有事情，我們有 agent 和人物角色的原因是：它不只是幫助 agent 在其專業領域更專注、更好地回應，它也是為了讓你有一個心智模型。當他們在扮演這個角色時，就把它當作真的在那個角色裡一樣跟它說話。

### 掌握 Architect Agent

不管你實際用的是哪個 IDE 或工具，在做架構時你要用你能用的最好的模型。我展示這可以在 $20 版本的 Claude Code 裡做到，但我建議——特別是對於更有挑戰性的架構——用 Opus 或者你擁有的任何強大模型，因為你可能會得到更好的結果。或者在 web 上用 Gemini 做架構，節省你的 credits，然後等我們有了架構之後再進入 IDE。但我確實喜歡在這裡做架構，因為就像你看到的，我們再次一段一段地即時產生文件。

它給了我們一個 sequence diagram、一個高層架構，關於資料庫的設計、錯誤處理方式以及全局安裝和解安裝流程。我們可以對任何這些做替代方案分析、利害關係人輸入、風險評估、資源影響、用戶體驗影響、技術可行性、市場驗證。讀一下它給你的內容，想想這些中有哪些有道理，如果有的話。如果沒有，就繼續下一段。

在下一部分，對它提出的技術提問，確認它知道最新版本是什麼或最佳版本是什麼。你也可以告訴它用 web 確認它挑選的所有技術都是最新的，這會建立一個列出所有具體版本和技術的表格。如果你沒有這份表格、沒有告訴它具體用哪些技術，後來你的 LLM 在開發時，它可能因為看到專案已經建立了某個測試框架就繼續用那個，然後遇到問題，不是試著修它，而是悄悄安裝一個全新的測試框架而你沒有注意到，或者你走開回來後發現多了一個新的測試框架或新的套件。

當我們在這裡建立這個表格並將它 shard 成獨立文件後，之後的開發 agent 會始終知道這個技術棧，不會偏離它。這是一個非常強大的技術，確保所有 agent 使用一致的函式庫、套件和版本。我要繼續完成架構，但記住每一段都要真正使用 advanced elicitation。

讓我直接展示一個快速範例，然後我就快速帶過其餘部分，最後再一起繼續。比如說，在做資料模型的這個部分。這很棒，因為如果它建立了資料模型，之後的 agent 就會始終遵從同一個模型。就像我們的技術棧一樣，你不希望他們臨時產生不同的模型。

假設我不理解為什麼要建立這些，或者不喜歡它們，我要問一個問題。這是你可以做的事之一，不一定需要提示，直接問問題就好：「請解釋你創建的 interfaces，我想知道每個的解釋以及它存在的原因，我們是否缺少任何 interfaces？」Architect 被設定為也非常善於解釋，以非常清晰的方式、以你能理解的程度來說明。

我建議跟這些 agent 聊天，即使你不在專案中途，你可以載入這些 agent，就直接跟他們說話，聊聊你的正在進行的專案。他說了什麼？說了很多。讓我解釋每個 TypeScript interface 並分析我們是否遺漏了任何。

Todo interface 顯然很重要，但它為什麼存在？類型安全。換句話說，interface 讓我們可以定義一個對象的藍圖，這個藍圖說每個 task 必須有 task 字串、completed、completedAt 和唯一的 id。它為什麼存在？類型安全和資料庫映射——這很有趣，這告訴我們它在設置一個 interface，之後也會直接映射到 SQLite，確保本地資料庫中的屬性和欄位始終相同。它還幫助我們定義 API 合約——API 返回待辦事項時，每個待辦事項都保證回傳這些屬性。

如果我們想要待辦事項包含其他東西，現在是添加的好時機，不是等到開發時。這就是為什麼你要真正注意並嘗試理解 Architect 在告訴你什麼。如果你不理解，就問它。如果你讀了還是不懂，就對它做五個 W——問它為什麼這樣做，為什麼那樣做，然後繼續問。你只是透過與 Architect 討論就能學到很多關於軟體實際開發的知識，非常強大。

### Shard 文件

繼續往前，我們不再需要讓 LLM 去看腦力激盪或 brief 的文件了。你在這裡保留的每個檔案都是 LLM 可能選擇載入的潛在 context。你可以加限制，告訴它不要，但有時把這些移到另一個資料夾更好，比如加一個「project references」資料夾，或者直接移出去存放，也許存到線上，取決於你如何組織專案文件。不管怎樣，你不希望它們被載入而污染整個 context。

回到 Claude，用 shard 指令。輸入 `shard`，可以看到有個「task shard doc」的任務。要用 MD tree 嗎？是的，我們要用。好，它說 MD tree 指令可用，如果不可用，它會建議你安裝。現在它問我要 shard 哪些文件，提供我想 shard 的文件路徑，它會用 MD tree explode 指令根據第二層標題自動拆分成更小的文件。

首先 shard PRD，我直接把它拖進去，預設資料夾叫 `PRD`，完成了，就這麼快。我們現在有了 epic 清單，最重要的是 Epic 1——如果有多個 epic 就是 Epic 1、Epic 2、Epic 3——以及所有 stories，因為這就是 Scrum Master 要用來為我們的開發者建立東西的材料。

現在 shard 架構，直接把它拖進去。使用 BMAD method 在 Claude Code 裡就是這麼簡單，不需要跳回 web，非常強大，不管你用 Claude Code 的哪個模型，它執行指令的效果都非常好。架構完成了，只需幾秒鐘。Shard 之後確實非常好用，因為我們有了程式碼規範（包含我們想要的文件和其他內容）、source tree（顯示了我們的專案結構）、tech stack——這三個非常關鍵，我要解釋原因，讓你無論用哪個工具都能理解。

看看 Claude Code 的設定，因為我們用 Claude，看看開發者 agent 有什麼：它有一個指令基本上告訴它，看 BMAD core，找 core config，這就是告訴開發者 agent 每次都要載入哪些檔案。開發者 agent 的工作方式是：Scrum Master 要拿高層 epic 和 story，讀取各種架構文件，一次理解一個 story，然後為開發者建立一個非常詳細的 story，一個較低層的開發者 story。這是一個自包含的檔案，讓開發者擁有建立應用程式所需的所有 context。

### 開發者自定義載入設定

這就是 context engineering 的核心，給 agent 恰好它需要的東西來建立它的那一小塊，對吧？此外，不只是 Scrum Master 會放進去所有它需要的架構和其他來源的資訊，開發者還會始終載入你在「dev load always files」下列出的這些檔案。順帶一提，我不需要自己建立這個檔案，它是在安裝時建立的，但如果你想自定義它，也許有另一個你想讓開發者始終載入的檔案，你可以在這裡加它。

這裡是我們從架構 shard 出來的關鍵文件：程式碼規範、tech stack 和 source tree。花時間進去更新這些，如果有任何變化就修改它們。

### Scrum Master 建立 Story

你可以選擇其中一個，執行 correct course 指令。它會問你一系列問題，分析你走了多遠，判斷最好是回退到某個早期階段、產生新的 stories 和 epics，還是從你現在的位置產生新的未來 stories 和 epics。或者你的改動可能太劇烈，以至於它雖然不應該輕易建議，但確實建議你重新開始。

不只是給你這些建議，它還會幫助你確定哪些 epics 和 stories 需要修改、更改、新增或刪除，讓你可以完成這個轉向，考慮到它，並仍然達到你的最終目標。也許這意味著更新架構，或者更新 PRD，也許你發現了一個新的 API 或函式庫想使用，它可能會把它加入 tech stack。這些都是 correct course 指令的可能結果，在某些情況下可能是救命稻草。當然，最好的方式是避免走到這一步，這就是為什麼你要做很多前期規劃。

現在我們要做的是 1 號：起草第一個 story。如果你知道要起草哪個 story，就直接告訴它。我們知道要做 Epic 1 Story 1，可以說 `*draft 1.1`。

假設你做到一半，是時候做 Story 2.3，因為 2.2 已經完成了，你可以直接說「起草下一個 story」，它會找出下一個是什麼。或者你可以告訴它做哪一個，這會讓流程更流暢，更快開始起草。起草 story 時，它始終會檢查是否有之前的 story；如果有，它會檢查那個 story 裡有沒有需要帶入新 story 的筆記。這些基礎 stories 也常常包含一些步驟，你真的要讀這些 stories，尤其是看看有沒有人工操作的事項——也許你需要設立帳號，或者訪問某個網站並配置一些基礎設施，因為 LLM 通過命令無法對遠端服務做到這件事。也許你需要拿出信用卡付費什麼的。

好，完成了。讓我們看看我們的 story，確認它遵循了正確的模板。它始終會把它放在草稿模式，這是標準的敏捷 story 做法。「作為一個開發者，我想要建立基礎的 Node.js TypeScript 專案結構，讓我有一個穩固的 CLI 開發基礎。」驗收標準意味著什麼條件可以說這個 story 完成了？Tasks 和 subtasks 有時聽起來和驗收標準很相似，應該是這樣的，因為這些是開發者 agent 要一步一步遵循來實作我們 story 的實際步驟。

這是 Scrum Master agent 讀過所有架構文件、找到與 story 相關的資訊後提供給它的。因為我們做的是專案設置，agent 需要知道架構師想出的專案結構，這就是為什麼它把結構貼在這裡——讓開發者 agent 有這個 contextual 資訊，不需要自己去搜尋而讓自己的 context 膨脹。有 placeholders 讓開發 agent 可以放筆記，以及 QA agent 可以放他們的筆記。把狀態改為 approved，我們完成了 Scrum Master 的工作。

### Developer Agent 建立程式碼

關閉 context，開一個新的，因為一如往常，每個步驟之間即使不是必要的，這是更好的做法，能最小化整體 context。現在進入最後直線了。我們的 James，全端開發者已就位。執行 `*help`，你可以直接告訴 James 「開發一個 story」，它會找到設定為 approved 或已在進行中（可能被之前的某個實例留下未完成的）的最高編號 story。或者直接告訴它哪個 story，這樣更流暢、更快。

我說 `*develop story`，然後按空白鍵，把檔案拖進去。現在我們應該終於看到開發者在實作 story 1 了。我們就做第一個 story，然後 commit。說 yes，讓它做想做的事，它在設定 `package.json`，一邊加入我們需要的套件，我們可以確認這些和我們的設定是一致的。

順帶一提，我們可以開啟 Claude Code 的 unsafe mode，讓它全速前進。但現在我就在這裡陪著它，一起工作。不介意直接說 yes continue。如果你想冒險，可以關掉所有安全功能讓 Claude 自由運行。好，快完成了，它建立了一些自己的 internal todos，對應到 story 裡的實際 todos，然後我們應該看到它會逐一勾選它們。狀態設為「ready for review」。

### QA 審查：Quinn

這樣你有兩個選項，我建議兩個都做，但取決於 story 的複雜度。如果是簡單的 story，可能不必要，但自己審查一下——也許手動測試一下功能，看看結果。我要開一個新的 context，退出後輸入 `claude`，再啟動 QA agent，也就是 quality assurance。執行 `*help` 看看 Quinn 的選項。選 1 號，把 story 1 拖進去。

這是全新的 context，它會看著 story 和所有專案的 source code 以及其他更新，真正確認開發做得好不好。這會做一個相當深入的審查。這也是你可能想用 Opus 的地方，也許比開發時更重要，因為這是確保 agent 沒有偏離軌道、在不對的地方放檔案的關鍵一環。

看起來它已經找到一些東西了。這顯然是一個非常小的設置 story，所以 QA 能做的不多，但它確實找到了一些問題，給了我們一些合規性檢查或改進建議。太好了。我只想再次說謝謝。如果你一路撐到這裡看完了影片，你已經遠遠走在了前面。你將成為 BMAD method 的進階用戶，特別是在 Claude Code 方面。
