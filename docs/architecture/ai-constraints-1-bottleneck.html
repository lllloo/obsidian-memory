瓶頸可能不在你以為的地方

產碼速度上去之後，業界處方分四條路線。但在選路線之前有個更前面的問題：「瓶頸已經從寫碼移到 review」這個大家共用的前提，認知與觀測互相矛盾——選錯瓶頸，所有投資都會落在錯的地方。這頁只做一件事：把那個矛盾攤開，給你一個成本近零的自我檢驗，然後標出四條路線各自攔在流程的哪個位置。

01認知與觀測對不上

DORA 2025 的大樣本問卷給了一組彼此矛盾的事實：90% 的技術人員在用 AI、超過八成自認生產力提升，但三成對 AI 產的碼幾乎不信任。同一份報告觀測到 AI 採用同時關聯到交付吞吐量上升與交付不穩定性上升——更多變更失敗、更多返工、更長的修復時間。（相關性，非因果。）

壓力確實落在 review 上。高 AI 採用團隊的 merge PR 數 +98%、review 時間 +91%、PR 平均大小 +154%medium：Faros AI，1 萬名開發者，廠商研究未同儕審查。GitLab 的調查裡有 85% 的人同意「瓶頸已從寫碼移到 review」low：主觀認知調查，非行為觀測。

問題在於另一組觀測對不上：超過九成的團隊仍在批次部署，半數批次含 2–10 個變更、四分之一含 11–50 個low-medium：單一廠商進行中的研究。這兩件事不可能同時成立——如果變更 review 完之後還在排隊，review 就不是約束點，而加快 review 只會把壓力更快推給真正的瓶頸。

獨立印證來自完全不同的方向。2026-02 Thoughtworks 在 Deer Valley 主辦的 Future of Software Engineering 閉門工作坊（Agile Manifesto 25 週年、Martin Fowler 主辦、約 50 位資深實踐者、Chatham House Rule，一手報告 PDF 公開）得出同方向但更廣的結論：

It is the same speed with more frustration, because the bottleneck has shifted from engineering capacity to everything else.

報告點名的「everything else」包含跨團隊依賴、架構審查與專案決策，並提出兩個延伸判斷：code review 正在被拆解成依風險分級的不同處理路徑（risk tiering），以及 decision fatigue 才是新瓶頸——當 agent 產出快過決策者能審核批准的速度，約束就從產能移到決策容量，原本作為協調節點的中階管理者變成核准瓶頸。

這裡的證據強度要誠實

批次那份是單一廠商進行中的研究；Thoughtworks 這份則是閉門群體共識、非量測，且 Chatham House Rule 下無具名歸屬。兩者利益方向不同、獨立同向，合起來足以支持「別預設瓶頸在 review」，但不足以推翻 DORA 的不穩定性觀測（那是獨立的、更大的樣本）。三者其實可以並存——AI 確實對 review 造成壓力（+91% 是實測），但壓力大不等於它是約束點。務實的讀法是：先跑上面那個檢驗，再決定投哪條路線。

02機制根源：verification tax

DORA 基於 1,110 份 Google 工程師開放式回答的質化分析，給了一個比「速度變快」更有解釋力的框架：寫作省下的時間被重新分配到稽核與驗證。因為模型無法表達自己的不確定性、又會用高信心輸出幻覺，工程師被迫把每次互動都當成可能有詐。受訪工程師的原話：

Reviewing [another's] code is so much harder than writing it. AI tools are increasing the rate at which people can churn out code that needs to be reviewed…

這解釋了為何吞吐量與不穩定性會同時上升，也解釋了為何單純加快 review 不會解決問題——review 的成本結構是認知性的，不是流程性的。DORA 對此的總結是：AI 是放大器，會放大高效組織的優勢，也會放大失能組織的問題；測試實踐薄弱的團隊，AI 只會幫他們更快產生技術債。

還有一個分佈上的發現值得單獨記：OSS 專案導入 Copilot 後，生產力提升主要來自經驗較淺的貢獻者，負擔則落在核心開發者身上——他們多 review 6.5% 的碼，自己的原創產出掉 19%medium-high：OSS 行為數據計量分析、非自陳；preprint 未同儕審查。另一份對 Reddit 與 HN 上 15 個討論串、1,154 篇貼文的質化編碼把這個現象框成 tragedy of the commons：個人的生產力收益把成本外部化給 reviewer、maintainer 與整個社群。

從那份討論分析裡萃取出的實際反制手段值得直接參考：PR 行數上限（有團隊訂 500 LOC，超過不審）、要求作者自審後才能送 peer review、同步 walkthrough（「can you walk me through it and explain some of your choices?」）、跨團隊雙重 review。問責規範「It's not AI's code, it's my code」被廣泛認同，有組織寫進年度考核。

03四條路線各自攔在哪

四條路線不是替代品，它們攔在開發流程的不同位置。看清楚位置比比較優劣重要——因為你的瓶頸在哪，決定了哪一條對你有用。

DORA 對 review 流程的四條建議

一手來源、訊號最強的一組（出自 Balancing AI tensions）：

  1. 把 AI 回饋移到 author 端——在寫作階段就攔，比事後丟給 reviewer 有效率得多。
  2. 用 context-aware 的 review agent 自動執行組織標準，人力介入前先過一輪。
  3. 小批次——強迫把大塊 AI 生成拆成可審、可測的單位。
  4. 重新質疑非同步 review 本身：「投資 robust test automation 的 ROI，可能高於優化人工 review。」

第 4 條是這批建議裡最反直覺的。原文還補了一句更根本的——傳統 code review 是一道 quality gate，在 AI 時代值得重新想「這道 gate 的目的本身，是否有其他技術能承擔它的一部分」。

04這些數字別引

本頁範圍內被查證否決的主張，列在這裡避免日後從別處流回來。

  • 各家 AI review 工具的相對抓 bug 率——全為廠商自評，互相矛盾且方法不公開。例如某家宣稱在 50 個 open-source PR 上比對手多抓 50%+ bug，無法交叉驗證。選型請看 signal-to-noise，不看這類數字。
  • review 工具的 false positive 率「成熟工具 5–10%、較弱的 15–30%」——出自部落格彙整，未見一手方法。可當粗略印象，不可當選型依據。

另有一條屬於「方法上要小心」：HN／Reddit 的留言樹用一般網頁擷取工具讀取時，容易錯置歸屬、甚至產生原串不存在的回覆。要引用原句，一律走 HN Algolia API 取結構化資料，或直接開原串核對，不憑摘要轉述。

這頁沒講什麼。四條路線只標出位置，沒有展開。B（用測試約束）在第 2 頁完整展開，一個把它推到極致的實作在第 3 頁。C（約束前移）的可抄措辭層與 D（部署層安全網）都不在這一組裡。

證據標註的規則。沒有標註的主張，其依據是一手來源、原始碼、或同儕審查的研究，可以直接引用。加了灰底小標籤的是弱證據——單一 preprint、廠商自評、單一作者實測、閉門共識——標籤上寫明是哪一種。被查證否決的主張不會出現在正文，全部收在第 04 節。
