哪些能自動產

「自動產生的架構圖」不是一個類別，是一條光譜。同樣叫自動產出，讀資料庫 metadata 的結果可以拿來當依據，掃程式碼推呼叫關係的結果只能拿來探索。差別不在工具好壞，在資料源本身有沒有那個資訊。

可信度光譜

ER 圖：記法不用選，而且理由不是「差異不大」

三個主要工具把 Crow's Foot 寫死在原始碼裡，沒有選項：tbls 的 dot 模板用 arrowtail=crow、SchemaSpy 寫在 Edge.java、Mermaid 官方文件原句是「uses the most popular crow's foot notation」。唯一給選項的 DBeaver 把它做成檢視時的即時切換，不是要提前承諾的決定。

獨佔有機制上的原因：Crow's Foot 的 min／max 兩枚符號，恰好對應 DB metadata 拿得到的東西。tbls 的 detectCardinality 實作可以直接讀——子側看 constraint 含 UNIQUE／PRIMARY KEY，父側看子欄位是否 nullable。整張圖的關係語意可由 metadata 完全推導。

換記法的代價因此很具體：Chen 需要 relationship 實體與屬性語意、UML 需要 association／aggregation／composition 語意，metadata 都給不出，得人手補——圖立刻退回「會過期的手繪圖」，把「唯一可信自動產物」這個性質弄丟。

沒有查到任何量化的可讀性實證（Chen vs Crow's Foot vs UML 的理解度實驗）。「Crow's Foot 較易讀」全部來自 blog 層級斷言。正確說法是「沒有證據顯示差異大到值得花時間選」，不是「已證實差異不大」。

IDEF1X 的美國聯邦標準 FIPS 184 已於 2008-09-02 撤回，現以付費的 ISO/IEC/IEEE 31320-2:2012 存續——標準沒死，但已離開開源工具鏈。

資料流圖：想要的那個工具不存在

data lineage 工具只適用資料工程與 ETL 管線。 OpenLineage 的官方整合清單全部是資料處理／編排工具（Airflow、Spark、dbt、Flink…），無任何 Web 框架整合。DataHub 的 MySQL source 雖標示支援 column lineage，但限定條件是只涵蓋 view 定義推導出的依賴。

換句話說，這些工具答的是「倉儲內表與欄位間的血緣」，不是「一筆請求的資料怎麼流過 controller → service → 幾張表」。不是同一個問題。

DFD 本身沒死，但轉移到了安全威脅建模，而且已有 as-code 形態：OWASP pytm 把模型寫成 Python 檔進版控，./tm.py --dfd | dot -Tpng 重產圖；Threagile 是 YAML 版。卡點是模型仍需人寫、不從碼逆推。

唯一嘗試「從原始碼產 DFD」的 Threatspec（靠原始碼註解標記）最後一次 push 是 2020-12-30。這條路線目前無活躍實作。

四者都無法檢查「圖是否還符合程式碼」。全部只驗語法或模型內部一致性。Structurizr 的 inspect 最接近，但它強制的是 C4 階層規則，不是跟 codebase 對照。

D2 的佈局優勢有個陷阱：最強的 TALA 引擎是 proprietary、closed-source、收費，與 D2 分開安裝，開源部分只剩 dagre 與 ELK。它另外處於矛盾狀態——24,887★、今天仍有 commit，但最後一個 tagged release 是 2025-08-19，近一年未發版。

唯一的 LLM 產圖量測是 MermaidSeqBench（arXiv 2511.14967）：8B 級模型 syntax 91.29%、logic 87.23%、activation handling 79.55%。限制必須一起記——preprint、只測 8B 級開源模型、LLM-as-Judge、只測 sequence diagram，不可外推到 frontier 模型產架構圖。

另一組相關數字指向同一個弱點：LLM 產 DFD 的評測中 correctness 一律低於 completeness——「元素抓得到、語意連錯」。這也解釋了為什麼 ArchAgent 的 F1 0.966 是元素層級比對，元素抓得準不代表關係畫得對。
