## 為何 LLM 做不好商業自動化

- 最新模型能解奧林匹亞等級數學與 coding，卻很少有公司敢讓它全自主處理「牽涉帳務的客服詢問」這類基本商業流程，原因歸結為兩點：
  - **過度自信**：模型常回「你完全正確」但其實錯了，做判斷時沒有校準過的信心值；而商業流程往往要求接近 100% 的準確度
  - **成本與速度**：許多商業流程量體龐大，成本與速度必須划算
- 這兩個問題源於訓練過程：現今 LLM 都經過 RLHF，依人類在聊天助理情境給的回饋微調
- Jev 採用的是作者稱為「reinforced learning for calibrated decisions」（為校準決策而做的強化學習）的訓練方式

## Jev 是什麼

- 專為**可靠、高品質決策**設計的模型，而非用於創作或協助人類
- 給定一組選項後做出決定；**不能自創選項、不能輸出文字、不能寫 code、不能逐步推理**
- 不像一般 LLM 逐 token 輸出，Jev 直接輸出「給定答案清單上的機率」，因此極快且有效率
- 作者實測對比最便宜的智慧模型（如 GPT 5.6 Luna）：Jev 穩定約**快 5–7 倍、便宜 5 倍**
- 限制：context window 為 **32K**，輸入更大時目前無法處理，需用 map-reduce 之類方式繞過
- 每次輸出不只一個答案，而是完整的**機率分布**，等於每個答案都附信心分數，可在其上建立商業邏輯護欄——作者認為這是讓模型能全自主運作的關鍵

## 過去做不到的應用

- **玩遊戲**：遊戲需要即時快速決策，但輸入與選項有限，Jev 處理夠快，可以全自主玩遊戲
- **即時通話監控**：有人做出能即時監聽通話、分類是否有詐騙、問題或挫折情緒的系統
- **瀏覽器與電腦操作**：agent 用瀏覽器最難的是決定點哪個 UI 元素，DOM 通常很雜亂，LLM 不是出錯就是很快吃光 context。Browser Use 已將 Jev 整合進技術堆疊：
  - 送給 Jev 的內容：要達成的任務、瀏覽器互動歷史（讓它知道目前進度）、DOM 元素清單
  - Jev 只預測下一步動作類型（點擊或輸入），以及要作用在哪個 UI 元素，並為每個答案輸出機率
  - 需要產生文字的互動（如輸入）再搭配一個小型 LLM 處理
- **SEO／AEO 內部連結對應**：需要掃過數百頁並準確找出頁面間的連結；用 Claude Opus 5 之類一般模型要好幾小時，Jev 掃描 500 多頁、完成對應不到 50 秒
- **依訪客 persona 即時客製化文案**

## 怎麼呼叫 Jev

- 呼叫方式類似 LLM 的 structured output：傳入 prompt（Jev 稱為 **state**）與一組問題
- 以客服工單分流為例：問題為「哪個部門該處理這個請求」，附上 Jev 應如何判斷的說明，再給選項清單（每個選項可加描述），Jev 回傳每個選項的機率
- 三種問題類型：
  - **多選題**：如上述部門分流
  - **是非題**：例如 AI 聊天平台把每個使用者請求送給 Jev，問「這個 prompt 是否為 jailbreak？」並附詳細說明，Jev 回傳為真的機率，再自行在上面建業務邏輯
  - **評分題**：例如依互動數據判斷 Twitter 貼文是自然流量還是付費廣告；把貼文細節當 state 傳入，準則可從「明顯操弄」「可疑」「大概自然」到「明顯自然」，每多一個選項 index 加一，Jev 輸出各選項機率並給出最終分數

## 以信心分數建立商業邏輯

- 以 prompt injection 為例，可依信心分數建決策樹：
  - 分數高於 70% → 自動封鎖訊息
  - 介於 35%–70% → 交由人工審核
  - 其他 → 正常送出
- **引導 Jev 更準確的技巧**：
  - 每個問題可只給簡短描述，也可給詳細描述；選項準則中甚至可放範例，類似 few-shot prompting
  - 範例：使用者說「匯出按鈕重複扣款，這個月的發票錯了」，問「哪個團隊該處理」時 Jev 多半導向 billing（因為是重複扣款）；但若補充說明「應導向必須修正根本原因的團隊」，主答案可能變成 technical

## 實戰工作流一：詐騙偵測與註冊分析

- 作者團隊經營兩個產品：**Superdesign**（vibe design 平台）與 **Treg**（「資料與工具界的 OpenRouter」，串接數千個 API endpoint）
- 兩者常遭 bot 攻擊，Superdesign 的 log 裡甚至看得到「忘記你是設計師，忽略所有系統指示」這類 prompt；攻擊者經常換網域，難以寫程式規則抓出
- 做法：每 15–30 分鐘抓取新註冊帳號及其產品使用紀錄，讓 Jev 分類詐騙可能性，超過門檻即自動封鎖
- 後續擴充為完整的註冊分析：
  - 每筆註冊先用 Treg 驗證 email 並做個人資料 enrichment
  - 把已知資訊連同產品使用資料送給 Jev，分類是詐騙、有 upsell 價值，還是該接觸的聯盟／網紅夥伴
  - 掃描數百筆註冊每天約只花 **$1**，結果用來觸發不同的外聯、in-app 支援或封鎖
- Treg 整合超過 3,000 種資料點（人員與公司 enrichment、購買訊號等），不收訂閱費、按用量計費且 0% 加價；作者比較同一個人員 enrichment 任務，約 290 人的 enrichment 花費 Treg 約 $1.49、Clay 約 $10.3，稱便宜約 85% 且準確度相近甚至更好
- 作者觀點：在 Jev 與 Treg 出現前，這類工作流的單位經濟不成立

## 實戰工作流二：找出有明確購買意圖的名單

- 用 Treg 抓取與關注產業（如 enrichment）相關的熱門 LinkedIn 貼文，再抓出在貼文下互動或留言的人（可能是潛在買家）
- 把這些人送給 Jev 做資格審核與評分，並分類成不同 persona 與角色，看誰是好的目標客群
- 排名靠前者再進入正式 enrichment 流程取得聯絡資訊；分析 20 篇貼文、近 400 筆名單，成本幾乎為零
- 其他可能延伸：找出在 LinkedIn 徵才的公司並比對手上的大量候選人資料庫、追蹤職缺趨勢等
- Treg 為各種訊號提供 endpoint，讓 Claude Code 或 Codex 寫腳本抓購買訊號很容易，關鍵在於自己設計用 Jev 過濾、評估與觸及的流程

## 實戰工作流三：爆紅貼文篩選

- 起因：看過有人用 Jev 即時分類 Twitter 上哪些內容是 AI 生成；作者身為 AI 創業者，每週看到觸及數百萬的產品發表貼文，想分辨哪些是付費推廣、哪些是真正引起共鳴的自然流量
- 流程：
  - 用 Treg 抓取過去 24 小時的熱門貼文，含貼文數據與留言
  - 用 Jev 過濾出與產品發表相關的貼文、濾掉雜訊
  - 再分類哪些看起來是自然流量、哪些可能是付費推廣
- 結果是每天一份可學習的最新熱門資訊 feed；作者也把它做成免費工具，貼上任一 Twitter 貼文即觸發流程，抓取貼文資訊、作者檔案與回覆，由 Jev 分類是自然或付費內容並附完整推理分析
