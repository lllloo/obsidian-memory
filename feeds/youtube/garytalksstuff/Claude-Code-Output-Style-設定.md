## 問題不是變笨，是講話方式對不上

近期模型在 benchmark 上分數越跑越高，實際用起來卻覺得越來越累——回覆術語密集、一句話要看好幾遍才懂。例如請模型整理一個功能的做法，得到的是「這個設計的正交性保證了狀態收斂的冪等路徑，語意層的抽象已經內化在 pipeline 的攝取階段」這種每個字都認識、合起來卻不知道在說什麼的輸出。

這不是個人錯覺。工程師圈流傳的部落格文章抱怨「讀 AI 的輸出已經變成一種額外的認知勞動」，越來越冗長、術語密集、夾雜看似有道理的廢話。Matt Pocock 也公開說最近的輸出「簡直像天書」，還貼過一段回覆當範例，並承認那段話其實是關鍵資訊，只是讀不懂。

關鍵觀察是：不管部落格作者還是 Matt，沒有人說模型把事情做錯。測試照樣過、功能照樣動，大家罵的是同一件事——看不懂它在說什麼。所以這是溝通問題，不是能力問題。解法不是換模型或等官方修，而是給它一份「跟我說話的說明書」，也就是 output style。

## 官方工程師的 ELI5 設定法

Claude Code 團隊工程師 Lydia Hallie 在推特分享：Claude Code 可以自訂輸出風格，把指令寫成一個檔案丟進 output styles 資料夾，之後在設定裡隨時切換。

她自己最愛的一套叫 Explain Like I'm Five（解釋給五歲小孩聽），忙了一整天、腦袋已經沒力氣讀長篇大論時就開這套。內容只有幾句話，大意是：我今天超級累、腦子已經燒掉了，請把我當五歲小孩，用簡單的詞彙、簡短的句子跟我講話，只講最必要的事；一定要用專有名詞的話請講完馬上解釋清楚；最後告訴我你做了什麼、有沒有成功、我接下來該做什麼。

要強調的是：output style 改變的只有說話方式，寫程式碼的能力完全不受影響。那個天才同事還是同一個人、腦子還是那顆腦子，只是你為他規定了報告格式。

設定三步驟，30 秒可完成：

1. 把 output style 的文字複製起來
2. 打開 Claude Code 貼給它，說「幫我把這個加進 output style」，它會自動放到正確位置
3. 輸入 `/config`，找到 output style 選項，選擇 ELI5 後按 Enter 立刻生效

## 內建四套風格怎麼選

輸入 `/config` 時會發現 Claude Code 本來就內建四套，不用自己寫：

- **Default**：簡潔、有效率，也就是每天看到的樣子
- **Proactive**：行動派，廢話更少，能動手就直接動手，不太花時間討論
- **Learning**：會故意停下來留一小段程式碼讓你親手寫，邊用邊練功，適合真想學寫程式的人
- **Explanatory**：每做一個改動都順便解釋這個架構為什麼這樣設計、這段 code 用了什麼 pattern、專案慣例是什麼

選用建議：explanatory 非常適合還不熟的專案——接手別人的 code、進新的 repo、用沒碰過的框架。但在自己很熟的專案千萬不要開，它會把你早就知道的事再重複一遍，本來想解決囉嗦反而更囉嗦。

## 用 branch 生出屬於你的風格

如果內建四套和 Lydia 那套都不合用，可以請 Claude 生一套。做法是下次收到看不懂的天書輸出時，先別急著罵：

1. 輸入 `/branch`，這個指令會從目前對話分岔出新對話，不打斷原本的工作
2. 在新對話裡說：我想建立自己的 Claude Code output style，請把這段回覆用五種不同風格重寫一次，讓我找到習慣的溝通方式
3. 選好喜歡的風格後，跟它說「把這個風格做成 output style」

## STE100：航太業幾十年前解過的老問題

用上面這招時發現的一個標準是 STE100（Simplified Technical English，簡化技術英文），是歐洲航太工業幾十年前訂的寫作標準。動機是飛機維修手冊如果寫得讓人看不懂，維修人員做錯一步就可能出人命。規矩包括：句子要短、一句話只講一個動作、詞彙表要固定、一個詞只能有一個意思。

技術文件寫到沒人看得懂並不是 AI 時代才出現的問題，而是工程界幾十年前就付出過代價並解決過的老問題。

Matt Pocock 針對同一問題的做法不是 output style，而是一個叫 wait what 的 skill：不是常駐設定，而是 AI 又開始講天書時才召喚它，等於跟 AI 說「你剛剛到底在說什麼」，它就會用簡單的話重講一次。這個 skill 裡面用的正是 STE100 標準，另外再要求 AI 用你專案裡的詞彙說話。

兩者定位：output style 是常駐的說話規則，適合覺得每次輸出都艱澀難懂的狀況；skill 是需要時才用的翻譯功能，適合只有少數時候難懂的人。

## 三套自製風格的設計理念

依技術背景針對三種人群設計：

**給純技術小白——技術翻譯機**

小白最大的風險不是學得慢，是不知道自己正在做什麼。規則是術語每次出現都用白話解釋、抽象概念用生活比喻（例如 API 就像餐廳幫你點餐的服務生）。重點在術語不要省略、而是要被解釋——新手如果跳過所有術語，用一年還是不知道什麼是 migration、什麼是 endpoint，之後看文件、跟工程師溝通都會卡住。另外因為小白分不出哪些操作有風險，只要遇到會刪資料、會花錢、會動到正式環境的動作，都先停下來用白話警告，等點頭才動手。

**給有技術認知的 vibe coder 或軟體 PM——STE100 簡報版**

這群人不需要學寫 code，需要的是精準資訊拿去做決策。直接拿航太標準來改：句子要短、主動語態、一個詞只有一個意思。API、前後端、資料庫這種等級的詞直接用不解釋；migration、race condition 這類工程內部細節第一次出現給一行解釋。另外加一條專屬規則：每個改動都必須講清楚動到哪個功能、使用者會看到什麼變化；要做決策時把選項排成 trade-off（A 快但有風險、B 慢但穩），再給針對這個需求的建議。

**給工程師——從 ELI5 延伸**

工程師缺的不是理解力，是注意力。所以它像一個同事站在你桌邊講話：先講改了什麼、能不能動，細節要再問才給。只要它做了你可能有意見的判斷（例如沒問過就把某個東西關掉），必須放在第一句講，不准埋在報告最後面。這套聽起來很懶，但對有技術背景的人可能最誠實——AI 丟一千字給你根本不會讀，只會眼睛掃過去心想應該沒問題吧然後按確認；輸出縮到幾行，你才會真的每一行都讀進去，才擋得住該擋的東西。

## 共通設計原則

三套背後共用同一個原則：要治 AI 的囉嗦，光跟它說「講簡單一點」沒有用，它只會把長廢話換成短廢話。真正有效的方法是把你喜歡的溝通方式精鍊成原則，並要求它用你的詞彙說話——你的專案裡把使用者叫 member，就規定它不准叫 user。講的話越貼近你慣用的語言，讀起來就越不費力。

風格非常個人化，所以不要直接抄別人的設定就結束。花十分鐘用 `/branch` 多生幾個版本自己測試，找到讀起來最不費力的那個。也不要期待一次找到完美解方，先快速做出第一版開始用，有 corner case 再持續迭代。

## 兩個進階玩法

**output style 跟著專案走**：它存在每個專案的 `settings.local.json` 裡，所以 A 專案掛一套、B 專案掛另一套完全互不影響。新接觸的專案掛 explanatory 邊做邊學；趕時間或 vibe coding 隨便玩就掛言簡意賅的衝進度；下班前或加班時用 ELI5 讓自己頭不會那麼痛。

**不是設定一次就用到底**：你的能力會進步，三個月前需要解釋的概念現在可能已是常識，這時可以把 style 的技術密度往上調。Claude Code 團隊自己也是這樣用——不同專案、不同任務，甚至當天累不累都會切換不同的 style。

這個功能上線很久了，但大部分人到今天還在用預設值，然後一邊用一邊罵模型降智。花五分鐘設定一次，之後每天都能省下大量精力。
