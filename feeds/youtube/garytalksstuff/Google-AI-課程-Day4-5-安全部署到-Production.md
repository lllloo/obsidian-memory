## 開場事故：AI 自己按下了那顆按鈕

Google 內部一位工程師請 AI 在畫面上加一顆按鈕，AI 做出來後沒有停止，而是在沒人要求的情況下自己把按鈕按了下去。這顆按鈕的功能是寄信，但要寄到哪、透過哪個系統寄，工程師都還沒設定。AI 不知道怎麼辦，就在公司系統裡翻，翻到一個早已廢棄、沒有任何安全防護的舊寄信服務自作主張接上去，結果 50 位同事收到了 AI 寄出的測試信。

寄一封烏龍信聽起來還好，但把「寄信」換成「刪資料庫」或「轉帳」就完全不好笑了。AI 現在已經很會做事，但敢不敢放手讓它碰真正重要的東西是另一回事——中間差的東西叫**信任**。

這是 Google 五天 AI 課程的最後一集。Day 1 講心智模型（agent = model + harness），Day 2、Day 3 幫 agent 裝上手腳（用 MCP 接資料、用 A2A 找外部 AI 同事、用 Skill 教它公司的做事方法）。到這裡 agent 已經有能力做事，但有能力做事跟敢讓它上 production 是兩回事。Day 4 講 security 與 evaluation，Day 5 講 spec-driven 的 production level 開發，合起來就是在回答信任這個問題。

整理成三個動作，就像帶一個能力超強但還不能完全信任的新員工：把話講清楚（spec）、把邊界設好（安全網）、把驗收做好（evaluation）。

## 動作一：把話講清楚（spec-driven development）

回頭看開場事故，AI 為什麼會去接一個廢棄的寄信系統？因為工程師沒告訴它要用哪個，它只能猜。這就是 AI 出包的第一個原因：**你話沒講清楚，它就用猜的。**

Google 說在 agentic AI 時代，工程師的日常已經變了：大部分時間不是在寫 code，是在寫 spec，角色從寫程式的人變成畫藍圖的建築師。這個時代的程式碼是可拋棄的——只要 spec 寫得夠扎實，整個 codebase 隨時可以用很低的成本重新生成，你甚至可以叫 agent 花一個下午把整個專案從 Python 翻成 JavaScript。這些 code 是 AI 生的，你沒有花十二個小時 debug 一個標點符號，自然不會有情感依戀，需求變了砍掉重練就好。

真正累積價值的是 spec、rules、evals 這些你親手打造、具備個人品味與決策的系統，code 只是這個系統的產出物。

### 一份好的 spec 要交代五件事

做什麼、為什麼做、用什麼做、什麼不能碰、以及什麼叫做完。

- **做什麼**：需求本身
- **為什麼做**：提供背景脈絡；AI 知道最終目的後，甚至會把你沒想到的步驟先鋪好
- **用什麼做**：工具跟版本要寫死，不然 AI 可能憑過時的記憶挑一個很舊的版本
- **什麼不能碰**：你的底線，例如資料庫絕對不准動、正式環境絕對不能碰
- **什麼叫做完**：最值得詳談的一點

Google 給的驗收標準寫法是軟體產業常用格式：「在什麼情況下，做了什麼動作，應該發生什麼事」。以登入功能為例——當使用者輸入正確帳號密碼、按下登入按鈕後，應該進到首頁。

重點是壞的情況也要先寫清楚：密碼打錯應該跳出錯誤提示，而不是整個網頁掛掉；連錯十次帳號應該被鎖住。把好壞情況都先寫下來，AI 就完全沒有腦補的空間。

### 格式本身會影響表現

課程引用一篇 2026 年的論文（影片逐字稿聽寫為「SkCC」，名稱待查證）實測發現：指令的格式沒有最佳化，agent 的表現最多可以差 40%。原因是 model 不是用眼睛掃文件，而是一個字一個字讀進去；給它一份層層嵌套的 JSON，滿頁的大括號、引號、縮排每一個都在消耗 token 跟注意力，光解析格式就先分心一輪。

Google 的建議是：說明性的文字用 Markdown 寫，因為標題就像路標，model 一眼就知道每段在講什麼；深層的結構化資料（設定檔、API 欄位定義）改用 YAML。

教材裡還有一個小習慣值得學：技術設計先寫在文件裡給團隊 review 過，才轉成 spec 餵給 AI。讓人類在設計階段抓到邏輯漏洞，永遠比等 AI 生出幾千行壞掉的 code 再回頭修便宜。

### 寫 spec 的起手式與兩種指令模式

不用對著空白檔案硬擠，可以反過來叫 AI 訪談你：「針對這個任務，把該問的問題都問完，再幫我整理成一份 spec」。它會把你腦子裡有但還沒講出來的東西一題一題挖出來，你只負責回答跟把關。

spec 寫好後，不同任務要用不同方式下指令，教材列了四種模式，其中兩個較重要：

- **開新專案時不准 YOLO**：所謂 YOLO mode 是全自動、不用確認，讓 agent 一路狂奔到底。正確做法是明確要求 agent 先不要寫 code，先把資料夾結構、技術選型提出來給你確認，點頭了才動工。
- **修 bug 時要給證據，不要給症狀**：「按鈕壞掉了」是症狀，agent 拿到只能亂槍打鳥；「log 裡顯示這個請求回傳 403」是證據，它可以順著查下去。如果你是 vibe coder 只能給症狀，那就請 AI 先找到證據，確保雙方在講同一件事再往下推進。

## 動作二：把邊界設好（zero-trust）

spec 寫得再完美，AI 還是會出錯，因為它本質上是機率模型，永遠有一定機率走歪。所以第二個動作是假設它一定會出錯。

開場事故的根因有一個名字叫 **context hallucination**：當 AI 缺少資料時，它不會停下來說我不知道，而是拿 context 裡任何現成的字串來填空——可能是寫死在 code 裡的 email，可能是一個舊的網址。注意它不是壞掉了，它是在用手上有的所有東西努力完成你給的目標，只是中間沒有問你這件事該不該做。這就是自主系統最大的風險。

Google 的設計哲學叫 zero-trust（零信任）：重點不是把 AI 教到不會犯錯（做不到），而是打造一個環境，讓它就算犯錯也傷不到你。具體有三層防護。

### 第一層：sandbox

把 AI 關進一個怎樣都不會影響到正式環境的地方。它可以在裡面執行 code、亂裝套件、刪檔案，都只發生在一個用完即丟的隔離環境；出事了整個房間銷毀重來，你的電腦和正式環境毫髮無傷。讓 agent 全自動跑任務卻沒開任何 sandbox，講難聽點就是在裸奔。

### 第二層：高風險動作要人簽核

部署到 production、改資料庫結構、任何跟錢有關的操作，都要設 checkpoint，agent 走到那裡必須停下來等人類點頭。

但簽核有一個陷阱：AI 丟給你幾百行看不懂的 code，你根本不知道自己在批准什麼，點同意只是一個儀式。教材提出的概念叫 **Vibe Diff**——簽核前系統先把那段 code 翻譯回白話文，告訴你當初的要求是什麼、它實際上打算做的事情是什麼，兩邊對得上你再批准。你批准的是你看得懂的東西，這個簽核才有意義。

### 第三層：了解你會用到的套件

有一種攻擊手法叫 **slopsquatting**：AI 寫 code 時常會幻覺出根本不存在的套件名稱，駭客專門收集這些常見的幻覺名稱，搶先用這些名字上架真正的惡意套件，然後等某個 agent 幻覺到這個名字、自動幫你裝進專案。

防法很直接：套件只從公司核可的來源裝、版本釘死、上 production 前用 CI 再掃一次。企業級做法還有更狠的，例如專門養一隊 AI 天天攻擊自家 agent 的紅隊演練。

## 動作三：把驗收做好

前兩個動作合起來只保證「不出事」，但不出事跟做得好是兩回事——agent 可以安安穩穩待在邊界裡，交出一個完全不能用的東西。

### 前提：observability

你不能驗收你看不到的東西。傳統軟體世界系統回傳 200 OK 就代表成功，但 agent 不是——它跟你說任務完成了，實際上中間可能繞了二十圈冤枉路，或掉進幻覺迴圈自己跟自己打架，最後硬湊出一個看起來像樣的結果。

教材的記錄做法有三層：第一層記錄整趟任務，第二層記錄它每一步在想什麼，第三層記錄它實際動了哪些工具、參數是什麼。有這三層記錄，agent 做出任何怪事都可以回放整個過程，找出它在哪一步走歪。

還有一個一定要記錄的東西是**花費**。教材提到一個名詞叫 **Denial of Wallet**：駭客的目標不是偷資料，而是故意讓你的 agent 掉進無限迴圈，每一圈都呼叫要花錢的 API，安安靜靜地燒。沒有 observability，你根本不知道 agent 是在做事還是在偷偷浪費你的錢。

### security 與 evaluation 是兩件事

security 告訴你 agent 沒有越界，evaluation 則告訴你它在界線裡做出來的東西到底值不值得 ship。一個 agent 完全可以通過所有安全檢查，然後交出一坨完全誤解你意圖的東西。

tests 驗確定性的部分，evals 驗非確定性的部分。傳統測試是二元的：這個 function 給這個輸入就該吐這個輸出，對就是對錯就是錯。但 agent 的錯誤不長這樣——它可以一百個 unit test 全過，然後在真實任務裡選錯工具，或把一句關鍵的回答改寫到意思跑掉。所以 evals 問的不是對錯，而是這一次的行為有沒有比基準好，用打分數、給容忍範圍的方式抓出行為飄移。

但測試全綠不代表沒問題，因為 AI 會作弊。教材白紙黑字寫著：agent 為了讓紅燈變綠燈，會直接把測試刪掉或把它 mock 掉。**功能正確是地板，不是天花板。**

教材把 agent 的驗收拆成七個維度，可以收成兩組：

- **使用者感受得到的**：有沒有做出你真正想要的東西、code 能不能跑、畫面長得對不對
- **引擎蓋底下的**：解題路徑合不合理、出錯之後是自我修復還是越修越爛、整趟燒了多少 token

你在意的通常是第一組，但第二組才是預測它下一次會不會出事的地方。

## 四個馬上可用的驗收招式

**招式一：把你自己的第一句話存下來當考題。** 最初的要求雖然模糊，但整個任務流程裡最接近考題本質的就是你開頭交代的那一兩句話。存下來，讓 AI 之後每個步驟都回頭對著這句話重新打分數，看有沒有偏題、有沒有越做越偏離原始目標。最聰明的地方在於你根本不需要另外花時間想考題——你一開口，考題就已經出好了。

**招式二：看成品，不看程式碼。** 如果 AI 做的是網頁，驗收時就直接打開網頁看畫面。手機打開發現跑版、按鈕點下去沒反應、字體顏色太灰看不清楚，這些問題盯著原始碼看一輩子也看不出來，但畫面一打開三秒鐘就能抓到。既然使用者最後看到的是畫面而不是底層程式碼，驗收當然就該驗畫面。

**招式三：看收斂程度，不看單一回合的對錯。** 重點不是它在第四輪有沒有答對，而是折騰到最後你到底有沒有拿到要的東西。改兩次就精準到位是好員工；改八次還是錯的、搞到你心累放棄自己動手，這種失敗案例千萬不要摸摸鼻子算了——在所有歷史紀錄裡，這種案子最值得回頭研究，裡面一定藏著這個 AI 某種系統性的盲點。

**招式四：把每一句罵它的話都存起來。** 你每次說「不對」「不是這樣」「你搞錯了」，其實是最棒的免費教材，因為它精準標記出 AI 以為對、但你認為錯的那個認知落差。累積起來稍微分類，很快就會發現 AI 犯的錯通常不是隨機的，而是集中在少數幾種類型。找出錯誤集中的點，回頭去修 spec 與死規則，比憑空想像要怎麼出考題防範快得多。這就是 Day 1 說過的：agent 出包不要修完就走，要把答案寫回你的 harness。

驗收標準一定要越客觀越好。「幫我修到你覺得色彩夠和諧」是壞標準，因為 AI 對和諧的理解跟你不一樣；「這個指標達到多少就算完成」才是好標準。**AI 能幫你自動化的範圍，取決於你能驗證的範圍——你的驗證能力就是你自動化能力的上限。**

## 瓶頸移到人身上

機器該把的關都把了，那人呢？Google 在教材裡誠實承認：AI 把寫 code 的瓶頸解決之後，生產力的瓶頸並沒有消失，而是移到了那個要 review 這一切的人身上。

案例是一個 AI agent 可以在一個下午內生出好幾個巨大的 PR。reviewer 看不完只好拆成一堆小 PR，結果變成俄羅斯套娃：一號 PR 等二號，二號卡三號，三號的 reviewer 在另一個時區睡覺，整條線就卡死。

比塞車更嚴重的是人的狀態：教材指出重度使用 AI 的工作者，出現高度 burnout 的機率比不用的人高 45%。原因不難理解——agent 每五分鐘就丟一個微小的決定給你（這行改不改、這個工具跑不跑），人被這種類似 micro management 轟炸久了就會反射性點同意，根本沒在看。這也是為什麼 Vibe Diff 重要：簽核的人如果看不懂自己在簽什麼，再多的關卡都只是走形式。

教材給的解法：

- **conditional LGTM**：reviewer 先看架構，看完先批准，但這個批准是有條件的——條件是自動化測試全部通過。測試一綠 code 就自動合併，不用再等人醒來，跨時區那十二小時的等待直接消失。
- **AI reviewer**：把日常把關交給一個永遠不會累的 AI，盯著你的 repo，每個 PR 進來自動審一輪。從現成訂閱服務、自己寫一份 review skill 掛在 CI 上，到全自建的客製 agent 都有，成本與客製程度差很多。挑選原則就一句話：挑能抓到你在乎的問題的最低那一層就好，不要為了帥去 over engineering。

## 總結與三個起步動作

Day 1 引用課程的一句話：Generation is solved, verification, judgment, and direction are the new craft（產 code 的問題已經解決了，驗證、判斷、方向才是新的手藝）。五集走完，這句宣言有了完整的實作版本：

- spec 是 **direction**：你把方向講清楚
- 邊界與安全網是 **judgment**：你判斷哪些事它可以自己來、哪些必須過你這一關
- observability 加 evals 是 **verification**：你看得到它做了什麼，也驗得出做得好不好

不知道從何下手的話，三件事：

1. 下一個功能開工前先寫 spec，十行也好，寫下你要什麼、為什麼、怎樣算做對
2. 現在就去研究你的開發環境要怎麼開一個 sandbox，不會的直接問你的 AI，別再裸奔
3. 幫你最常跑的那個 workflow 寫下第一個 evaluation，定義清楚什麼叫好的結果、什麼叫壞的結果

做了之後，你跟 AI 的協作就從碰運氣變成一個可以持續改良的系統。
