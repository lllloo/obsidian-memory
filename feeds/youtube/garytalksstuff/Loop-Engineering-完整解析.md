## 這個詞怎麼紅起來的

六月初 OpenClaw 創辦人 Peter Steinberger 在 X 貼文主張：不該再替 coding agent 寫 prompt，而該設計 loop，讓 loop 去 prompt 你的 agent。差不多同時，Claude Code 負責人 Boris Cherny 也說自己不再給 Claude 寫提示詞，工作已變成寫 loop 讓 loop 來做這件事。接著 Google 的 Engineering Lead Addy Osmani 發長文把這件事整理成一個框架，叫 Loop Engineering。

## Loop Engineering 是什麼

Loop 可以先理解成一個反覆循環的工作方式。

**過去的做法**：你說「幫我修這個 bug」，AI 修一下回你一段，你看完發現測試還是壞的，再說「這裡不對」，它再修，你再看。審核與給修改意見的都是你本人。

**Loop Engineering 的做法**：讓 agent 自己改程式、自己跑測試、自己讀錯誤、自己再改，直到測試過，或連續幾次都沒進展就停下來回報。審核角色一部分由 AI 取代；你不用每輪都自己來，而是一開始就告訴它目標是什麼、可以用哪些工具、怎麼驗證、什麼算完成、什麼狀況要停下來找人。

作者舉的例子：跟 agent 說「幫我做十張 YouTube 封面圖，評分標準四個——能不能讓觀眾一眼看懂影片在講什麼、能不能勾起好奇心、視覺對比夠不夠強、跟影片內容符不符合。做完用這四個標準幫每張打分，把沒過關的挑出來重做一版，改完再用同一套標準重新打分。跑兩輪，最後把分數最高的三張發給我。」這只是一句完整的 prompt，但代表了觀察、執行、驗收、修正四個重複步驟。

**核心轉變**：以往「執行 → 觀察結果 → 再執行並迭代」這個 loop 由人推動；loop engineering 強調由使用者**設計**這個 loop，然後讓 agent 自己推動。目的不是保證一次到 100 分，而是讓 agent 第一次交到你手上的版本是從 85 分開始，而不是 60 分。

## 與 Prompt、Context、Harness Engineering 的關係

- **Prompt Engineering**：強調跟 AI 溝通的技巧——要做什麼、語氣、格式、限制、輸出長什麼樣，講得越清楚結果越符合期望。
- **Context Engineering**：強調在對的時機給到不多不少的正確資訊，讓 AI 有足夠背景知識做事。
- **Harness Engineering**：設定規矩與邊界。像老闆要讓員工有效率工作，不能只叫他努力，還要給辦公室、工具、流程與權限。
- **Loop Engineering**：專注在把 human in the loop 變成 agent in the loop。從「人類審核後給 feedback」，變成人類把自己提供 feedback 的邏輯**標準化**、講清楚，讓 agent 自行 review 並迭代。

## Loop 的兩個端點：Trigger 與 Verifiable Goal

Loop 的形成由兩個問題決定：什麼時候開始、什麼時候停止。

**Trigger（觸發機制）**決定 loop 什麼時候開始，可以是：

- 事件：GitHub 上有人開了 PR，agent 自動開始檢查
- 排程：每天早上跑一次資料整理、每三十分鐘檢查一次任務狀態
- 手動：你今天覺得這件事值得跑就按下去

**Verifiable Goal（可驗證的目標）**決定什麼時候停，可拆成兩個問題：什麼叫做完成？AI 要怎麼檢查自己完成了？

Coding 任務比較好理解：所有測試通過、TypeScript 沒有報錯、lint 沒有違規、build 成功——機器可以檢查。但很多任務沒那麼乾淨：叫 AI 寫一篇文章，什麼叫寫好了？

## 把抽象標準變成可檢查的東西

這是實作時最常見的卡點。兩種常見做法：

**Rubric 評分**：先選定幾個面向（例如風格人設、語法用詞、內容主題），再替每個面向寫出分級定義。以風格人設為例，滿分五分代表完全符合設定的人設、用詞語氣一致；三分代表有點像但偶爾出戲；一分代表根本沒有你的風格在裡面。關鍵在每個分數都要定義清楚評分標準，AI 才有依據可循，而不是隨意給分。

**二元檢查清單**：把品質拆成一串 yes/no 問題——開頭三句有沒有抓住重點？有沒有冗詞贅字？專有名詞有沒有用錯？這種方式比打分數更穩定，也更容易判斷有沒有過關。

不論用哪種，最後都要收斂成一個明確的完成條件，例如「三個面向的 rubric 都達到四分以上」或「檢查清單全部通過」。

## 什麼任務值得做成 Loop

作者的建議是：面對任何新功能，先了解底層邏輯，再思考自己的工作流有沒有可套用的地方。通常一半以上的功能對一般人沒有用武之地，因為這些功能的需求來源大多是 OpenAI 與 Anthropic 的工程師，他們用得到的東西我們不一定用得到。不要盲目跟風。

三個判斷條件：

1. **它是不是會重複發生**。一次性任務直接寫一般 prompt 就好（臨時查一個錯誤訊息、改一段小文案沒必要設計整套 loop）。Loop 對「會反覆發生、每次流程差不多但細節不完全一樣」的任務比較有價值。
2. **完成標準清不清楚**（最關鍵）。你要能講出什麼叫這件事做完了——把網站部署到指定網域且載入時間低於兩秒、修復所有 CI 錯誤直到狀態變綠。抽象或主觀的則用 rubric 或 yes/no 寫驗收標準。
3. **Token 花費你扛不扛得住**。Loop 不是免費的，每跑一輪 AI 要讀東西、想下一步、呼叫工具，可能還要請 reviewer 檢查。原本手動 prompt 三次能解決的事，做成 loop 跑二十輪還沒停，這個帳單會非常有教育意義。

另一種適用情況是快速做 demo：核心 feature 的驗收標準很清楚（例如做一個能搜尋最新新聞的網站），其他細節先不追求完美，用 loop 把主功能跑出來再由人接手調整。

作者坦白說自己還是更喜歡 human in the loop：大多數人不需要一個 AI 不眠不休跑 27 小時，加上成本問題——如果像 OpenAI、Anthropic 的工程師一樣有接近無上限的 token 預算他也會一直用，但一般人沒有，所以 human in the loop 往往更準、更有效率也更便宜。

## Loop 失控的三個問題與三條規則

**問題一：不知道什麼時候該停。** 你說「幫我把這個 app 優化一下」，它改一點跑一下覺得還能再優化，因為你沒定義什麼叫優化——是前端視覺還是後端回覆速度？沒定義終點就變成 token 黑洞。

> 規則一：一定要有 hard stop。最多跑幾輪、最多跑多久、最多花多少 token、三輪沒進展就停下來回報。這些限制聽起來保守，但正是 loop 不失控的關鍵。

**問題二：把不該碰的東西也改掉。** 你說優化效能，它可能開始重構一堆本來不該碰的架構；你說改善 UX，它可能順手把元件拆掉重做；你說修 bug，它可能為了讓測試過改掉一堆旁邊的東西。

> 規則二：要定義邊界。不能只說測試要過，還要說不能刪測試、不能改公開 API、不能動資料庫 schema、不能碰某些核心檔案。

**問題三：Verifier 失效。** Loop 能停下來是因為有驗收機制。目標模糊到不能用時，verifier agent 只能用很主觀的方式判斷，例如問自己「這樣改完看起來是不是差不多了」。

> 規則三：驗收標準盡量變成可以檢查的東西。測試、效能數字、審稿清單都比「看起來不錯」具體；真的很主觀的任務也要拆成 rubric（語氣是否符合、主題有沒有偏、格式有沒有對）。

**額外提醒**：有分數不代表客觀。叫 AI 做任務然後 AI 自己評分就是球員兼裁判。比較好的做法是把產出跟檢查分開——一個 agent 負責產出、另一個負責檢查，或乾脆在關鍵節點保留 human in the loop。否則指標上看測試過了，實際上產品沒變好反而更糟。

## 成本與入門建議

Loop 很迷人，會讓人覺得按一下按鈕事情就自己往前走，但每次自動往前走背後都有成本：讀 context、呼叫工具、跑測試、解讀錯誤、重試，再加 reviewer agent、subagent、多輪驗證，成本會不斷疊加。連 Addy Osmani 都說 loop engineering 還處於早期階段，保持謹慎態度，必須非常注意 token 成本。

想試的話建議從一個小任務開始：範圍小、目標清楚、工具有限、停止條件明確。例如每天整理一次固定資料夾、針對某個測試項目進行修復、針對一篇文章跑固定的品質檢查 checklist。這些不會讓成本失控，但足以體驗 loop 的精髓——怎麼定義目標、怎麼設計驗收、怎麼控制權限、怎麼讓 AI 在正確的地方停下來。

## 作者的總結

Loop 把人的工作往上移。以前你是 prompt 操作者，一輪一輪跟 AI 對話再決定下一步；現在你更像系統設計者，要定義目標、設計驗證、設定邊界、控制成本。

Loop Engineering 的重點不在於 AI 能不能自己做事，而是**你有沒有能力定義一件事應該怎麼被完成**。往更高階推可能走向 software factory：工程師不再只是寫一段程式，而是設計一套可以生產、測試、修正、部署軟體的系統——但作者認為這對一般人現階段還太遙遠。

不論這個觀念有沒有出現，做一個好 loop 的能力都是現在 AI 工作者的必備條件：讓 AI 知道什麼時候開始、什麼叫完成、哪些事不能做、失敗時要停下。最後一句提醒：不要因為很多人在討論就逼著自己去用，最新的方法不一定是最好的方法，能解決你問題的方法才是。
