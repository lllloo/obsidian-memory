## 事件概況

Zeabur 資料庫遭駭客攻破，使用者放在專案環境變數裡的 API Key、資料庫密碼等關鍵資訊外洩，受影響者收到平台通知信。作者本身是受災戶，多個專案在名單內，其中一個專案的 OpenAI API Key 已遭盜刷一兩百美金。

處理原則：受影響範圍不限於通知信點名的那把 Key。**只要曾經把敏感資訊放進 Zeabur 專案，一律當作已外洩處理**。

## 緊急處置一：撤銷並重換所有金鑰

最常見的錯誤是「只在後台建一把新 Key 填回 Zeabur 就以為沒事」。舊 Key 只要沒有在平台後台手動撤銷，駭客仍可繼續拿它刷卡。

標準流程：

1. 到各個 AI 平台後台，把舊的 API Key 徹底撤銷。
2. 建立全新的 Key。
3. 更新 Zeabur 專案的環境變數並重新部署。
4. 確認線上服務已正常吃到新金鑰。

盤點範圍要涵蓋所有曾放進 Zeabur 的憑證，包含 Anthropic、Gemini、OpenRouter 以及資料庫密碼，不能只看通知信提到的那幾把。

換完後立刻檢查各平台的帳單與用量紀錄，找這幾天有無用量突增、異常的呼叫時間、或出現自己平常根本沒用過的模型。**發現盜刷先把用量圖表與帳單明細截圖存證**，之後才有紀錄可以向 Zeabur 申請求償。

## 緊急處置二：開花費上限，並確認速率限制

兩者管的事情完全不同，常被混為一談：

| 機制 | 管什麼 | 擋得住什麼 |
|---|---|---|
| Rate Limit（速率限制） | 速度，例如一分鐘最多幾次請求 | 瞬間高頻濫用把伺服器打爆 |
| Hard Spend Limit（硬性花費上限） | 當月總花費，達標即停止 API | 帳單無限膨脹 |

只設速率限制不夠：即使限制每分鐘 100 次呼叫，攻擊者仍可用慢速持續呼叫好幾天，挑最貴的頂級模型累積出可觀帳單。**能當荷包防線的是花費上限**，兩個一起開風險才控制得住。

## 緊急處置三：關掉 Auto Recharge

自動儲值在金鑰外洩情境下等於「幫小偷開無限暢飲」——餘額一見底系統就自動刷卡續杯，直到信用卡額度被刷爆。

擔心關掉後餘額用完服務中斷，解法是改用 **Budget Alert（預算警報）**：設定餘額低於某金額、或當月花費達上限八成時發 Email 通知，收到再手動儲值。

若業務真的非開自動儲值不可，把每次自動儲值金額壓到最低，並設定每月儲值次數上限，讓最壞情況的損失停在可承受範圍。

## 核心思維：控制爆炸半徑

Blast Radius（爆炸半徑）指的是一旦出事，最壞會波及多大範圍。平時就該做的習慣是**檢查每一把 API Key 的權限**。

常見壞習慣是同一把 Key 到處貼，開發、測試、正式環境全部共用。較好的做法是不同專案、不同環境各用獨立的 Key，且每把 Key 只給剛好夠用的權限——也就是**最小權限原則**。這樣某個小測試專案翻車時，出事的只有那個角落。

延伸到零信任架構：永遠不要假設任何第三方平台百分之百安全，而是從一開始就把「金鑰隨時可能外洩」這個前提設計進系統。第三方何時出意外無法掌控，能掌控的是出事時最多損失多少。

## 六題資安健檢

花五到十分鐘把手上的 API 服務盤點一遍：

1. 舊的金鑰有沒有定期更換？
2. 查過平台的速率限制嗎？
3. API Key 的每月花費上限有沒有設好？
4. 危險的自動儲值是不是還開著？
5. 開發與正式環境有沒有切開？
6. 每把 Key 的權限是不是開得太大了？
