## 又一個新名詞？先別慌

起點是 Peter Steinberger 在 X 上的一句「Are we still talking loops or did we shift to graphs yet?」——上個月才談完 Loop Engineering，這個月又冒出 Graph Engineering。

作者的判斷是：這不是全新的東西。它很像 agents orchestration，用過 n8n 的人也會覺得眼熟——任務拆解、條件分支、平行處理、狀態管理、人工審核，這些在 workflow automation 與各種 agent framework 裡存在很久了。但它也不純粹是 buzzword：Graph Engineering 更像一種思考方式，把原本只存在腦袋裡的分工、路由、context 與驗收機制**畫出來、講清楚**。

它真正要解的痛點是：很多人期待丟一個 prompt 給 agent 就自動完成所有任務，但實際放進真實工作流後會發現，最難的不是叫它做事，而是讓它搞清楚「現在做到哪、下一步做什麼、哪裡要先檢查、做錯了退回哪一步」。沒有這些控制，agent 看起來像自動駕駛，實際上你整路提心吊膽幫它扶方向盤，每走一步就回頭問你「下一步呢？這份資料放哪？這結果可以直接用嗎？」——本來想把工作交出去，最後只是把自己變成**人肉 routing system**。

## 五個概念差在哪

AI 圈一直冒新名詞，是因為同一個核心問題還沒解決：怎麼讓輸出不穩定的 AI 可靠地把整份複雜工作做完。傳統程式輸入與規則不變，執行路徑與輸出就穩定；LLM 同一個 prompt 問兩次可能得到兩個答案，而且講錯話時通常不會自己舉手。**模型能回答只代表它有能力產生文字，不代表結果可以直接交付**——任務只有一步還看得出來，拉長到十步時，前面一個看似合理的小錯就會滾雪球。

這五層本質上都是替 AI 的不確定性加上不同維度的防護網：

| 層 | 管的事 |
|---|---|
| Prompt Engineering | 要做什麼、有哪些限制、成功標準、回傳格式 |
| Context Engineering | 在正確的時間給正確且剛好足夠的資訊——不是越多越好 |
| Harness Engineering | agent 的工作環境：能不能讀檔、執行程式、有哪些權限、能不能跑測試看 log |
| Loop Engineering | 怎麼讓單一 agent 反覆工作與停止：做完檢查、不合格就改、再跑一次直到通過 |
| Graph Engineering | 整體工作怎麼分工、交接、驗收；誰先誰後、哪些可平行、output 送到哪 |

Context Engineering 的例子：叫 AI 寫一封客戶回信，它需要看到客戶的問題、公司政策和語氣要求，不需要順便讀整間公司三年的會議紀錄。

**五者不是競爭關係**。一張 Graph 裡可以包含好幾個 Loop，每個 node 裡的 agent 也都需要自己的 Prompt、Context 和 Harness。Graph 出現不代表 Prompt 沒用、Loop 過時；每一層在解上一層管不到的盲點。前四層主要優化「單一執行者怎麼做好一件事」，Graph 站到制高點解決「多個執行者、工具、傳統程式與人類之間怎麼協作」。

要注意的是：**畫一張流程圖不叫 Graph Engineering**。畫圖只是給人看的，Graph Engineering 要設計的是圖背後一套真能自動跑起來的系統結構——明確告訴系統每一步做什麼、輸入什麼、輸出什麼、下一步往哪走、什麼條件算完成、失敗了退回哪裡。

## 三個零件：node、edge、state

### node

一個獨立的工作單元，也就是流程圖裡的一個方框。裡面執行的東西非常靈活，**不一定是 AI**：可以是一次 LLM 呼叫、一段 Python 腳本、一個資料庫查詢，也可以是一個自帶 Loop 的完整小 agent，甚至需要真人按確認的人工審核本身也是一個 node。

所以 **node ≠ agent**。很多確定性的工作——加總預算、檢查日期格式、驗證網址有沒有缺漏——傳統程式三行 code 就搞定，速度快、成本零、百分之百精準。硬派一個大語言模型去按計算機，除了浪費 token 跟增加出錯機率沒有任何好處。

設計良好的 node 核心就三件事：**清楚的 input、嚴格的 output、明確的完成條件**。例：負責找住宿的 node，input 是日期、人數、地點、每晚預算；output 固定為三個住宿方案，每案必須含價格、地點、取消條款與原始訂房連結。

### edge

節點之間的連線，決定資料怎麼傳遞、下一步往哪走。它代表的是**依賴關係與路由邏輯**，不是單純把兩個方框連起來。

- 依賴限制：住宿與交通方案沒找齊前，行程合併 node 絕對不能啟動。
- 平行觸發：條件齊全時，交通、住宿、景點三個 node 可同時執行。
- 固定路徑：A 做完直接交給 B。
- 條件式分支：檢查通過送去真人確認；不通過就把錯誤訊息退回原 node 要求重做。
- 中途暫停：執行到一半發現必要資訊不足，edge 可以把流程暫停、跳去向人類提問，拿到答案再繼續。

### state

最簡單的理解方式是大地遊戲的闖關卡：上面記錄隊伍資訊、每關收集到的結果、現在第幾關、關主的批改紀錄，每過一關就更新一次。

旅行規劃的 state 會存：旅行日期、人數、總預算、交通候選名單、住宿候選名單、景點清單、合併後的第一版行程、查核抓到的問題清單、最後的人類審批結果。

**每個 node 不需要也不應該看到整個 state**。住宿 node 只讀日期、人數、地點與住宿預算，找完寫回 state；景點 node 只讀同行者興趣與可用時段，產出後寫回。這讓每個 node 的 context 保持乾淨精準，出問題時也立刻知道是哪筆資料被誰寫壞了。

**state 與聊天紀錄的差別**：聊天紀錄像把所有文件、便利貼、草稿一股腦堆在同一張桌上，前面的需求、中間的廢案、最後的定案全混在一起，AI 越讀越眼花。正式的 state 像有標準欄位的 Google Sheet 或資料庫——日期就是日期、預算數字就是預算數字、審核狀態就是審核狀態，有嚴格的讀寫規則，可以存檔、版本比對，出錯時直接倒帶恢復。

三者合起來，AI 系統才真正有方向感：清楚知道自己在哪一站、手上有什麼資料、接下來往哪去。

## 案例：四人東京五天四夜

條件：四個朋友去東京玩五天，每人預算三萬元；有人想逛街買衣服、有人想看美術館、其中一人吃素、還有一人膝蓋不好每天不能走超過兩萬步。

全部丟給一個 AI 也排得出來，但過程中會有不少規劃瑕疵與不細心。換成 Graph 架構：

1. **需求 node**：不急著排景點，先把零散需求規格化——日期、出發地、目的地、人數、總預算、每晚住宿預算、每人的飲食與行動限制、絕對不能接受的雷點。input 是大家七嘴八舌的需求，output 是一份標準結構的旅行規格書，寫入 state 作為後續所有 node 的共通基準。
2. **平行分流（fan-out）**：交通 node 搜尋來回航班、機場到市區路線與交通時間，產出含班次、票價、轉乘方式與購票連結的選項；住宿 node 只拿日期、人數、預算與地點偏好，產出價格、位置、取消條款與到主要商圈的車程；景點 node 依各自興趣與空檔篩選候選景點，含營業時間、建議停留時間與景點間移動距離。這三個任務需要的 context 截然不同、彼此無先後依賴，可完全平行。
3. **合併 node（fan-in）**：綜合班機抵達時間、飯店 check-in 位置、景點營業時間與每天步行步數，把三組獨立資料組裝成完整的五天行程表。
4. **verifier**：合併只代表資料排在一起，不代表行程可行。verifier 依嚴格邏輯全面稽查——交通與住宿 check-in 日期有沒有對上、景點當天有沒有開門、轉乘與移動時間合不合理、有沒有踩到吃素或走太多路的地雷，最後把機票、住宿、門票、交通費精算加總確認有沒有超支。
5. **局部退回**：查核不通過就依條件分支精準退回。例如總預算超支五千、問題出在住宿太貴，系統不需要全盤推翻，只把問題退回住宿 node，要求在同一區域找每晚便宜一千塊的替代方案；改完回到合併 node 更新行程，再讓 verifier 重驗。景點公休就只退景點 node，轉機太趕就只退交通 node——**哪裡出錯就退回哪裡修**。
6. **human approval**：AI 可以窮舉選項、找出時程衝突、自動修正邏輯錯誤，但最終取捨留給人——要不要為省三千塊住遠一點、要不要因為朋友膝蓋痛拿掉某景點、要不要冒險買不能退改的特價票。

第 5 步「verifier 發現問題 → 退回前面的 node 修改 → 重新驗收」這條回溯路徑本身就是一個**局部 Loop**。所以 Graph 和 Loop 不是二選一：Graph 負責宏觀的架構分工、資料流動與全局驗收，Loop 負責微觀的迭代修正，一張大 Graph 裡隨時可以嵌入好幾個局部 Loop。

## Graph 解決的三個問題

**一、context 污染與工具失焦**。所有任務塞在同一個長對話裡：前面是四個人的聊天需求、中間是航班搜尋紀錄、後面貼一堆飯店與景點連結，中間再來回改五六輪——模型的 context 又長又髒，分不清哪些是過期廢案、哪些才是最新決定。工具同理：訂房、地圖、搜尋、算數學、串 API 全塞給同一個 agent，它每走一步都要在十幾個工具裡猶豫，看似全能，注意力卻完全渙散。Graph 的解法是 **context 隔離與工具專業化**：每個 node 只讀自己需要的 state、只配備自己需要的工具，住宿 node 專心找飯店，不用讀景點介紹、也不用知道群組裡吵了什麼。

**二、缺乏可觀測性與無法局部重跑**。單一 agent 一路蠻幹，只要一開始選錯飯店位置，後面的景點順序與移動時間就連鎖崩盤，拿到爛行程也不知道從哪改起——改 prompt？換飯店？整個重來？Graph 架構中每個 node 的輸入、輸出、路由選擇與驗收紀錄都清楚保留在 state 裡，verifier 發現移動時間過長，可以立刻倒回去看住宿 node 當時依據什麼條件挑了這家飯店，然後只重跑住宿這個分支。

**三、把「做完」當成「做對」**。LLM 最大的盲點是特別擅長完成表面任務——叫它查最便宜的機票，它能生出一張以假亂真的班表，但實際上根本買不到那張票。Graph 讓你在關鍵節點設立 verifier 與人工審核節點。驗證器無法百分之百消滅幻覺，但它的價值在於把原本藏在你腦袋裡的驗收標準明確寫成規則，由系統嚴格執行。

## 不寫程式也能做：手動版三步

新手強烈建議先從純手動版本跑起。

**第一步，定義最終交付物與成功驗收標準。** 以旅行計畫為例：目標是產出一份時程可行、符合預算、照顧同行者需求、關鍵資訊都能追溯到原始來源的行程表。具體來說「可行」代表每天交通時間合理、住宿沒超支、景點營業時間對得上——這就是 output 與 success criteria。

**第二步，把工作拆解成必要的 node。** 再次強調 node 不等於 agent，它只是一個獨立工作單元。每個 node 寫清楚五件事：負責什麼、需要什麼 input、交出什麼 output、完成後去哪裡、遇到什麼情況絕對不能放行。例如交通 node 必須交出航班選項、票價、時間與連結；少了來源網址或票價超支就判定不合格、禁止放行。

**第三步，開幾個獨立的 AI 對話視窗，手動扮演這張 Graph。** 一個對話專門查交通、一個查住宿、一個排景點，把整理好的需求規格分別丟給它們，每個對話只專注做好自己的任務，**絕對不要讓任何一個 AI 包辦整份行程**。三份結果產出後，開第四個對話視窗負責合併，依時間、距離、預算與限制條件嚴格審核；發現住宿超支就丟回住宿對話重新推薦，景點時間排不下就丟回景點對話調整，改完再重新合併檢查，最後由自己決定是否採用。

在這個版本裡你就是 routing system：資料由你搬、下一步由你決定，state 可能只是一張表格或幾份文件——但你已經在實踐 Graph Engineering。先手動跑才能看見這份工作到底怎麼運作，流程跑順後再考慮自動化，不要想一步登天。

## 不要對新名詞焦慮

Graph Engineering 其實就是一種讓人跟 AI 更好協作的架構思維，很多人可能一年前就在用了，只是從未被 AI 圈大佬點名。

也絕對不是每項任務都要硬套 Graph——**AI 系統不是越複雜越好**。一次性的簡單任務、一個 prompt 就能搞定的事，千萬別硬拆成七個 node 自找麻煩。作者自承影片舉的旅行案例，其實現在比較前沿的模型就能自己處理，沒必要拆得這麼複雜；但仍可以拿簡單任務練練手，感受一下當流程圖架構師的樂趣。
