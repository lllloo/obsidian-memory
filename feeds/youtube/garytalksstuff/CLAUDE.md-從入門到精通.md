## CLAUDE.md 是什麼

- Claude Code 的 `CLAUDE.md` 與 Codex 的 `AGENTS.md` 功能相同，背後概念通用。
- 開啟對話時，系統會自動讀取檔案內容並注入 Context Window，等於在你下任何指令前，AI 已被強迫讀完並視為最高指導原則。
- 好處是不必每次開新對話重複解釋專案架構與規矩，省下大量溝通時間。
- 影片主張：把這份檔案寫好是使用 AI 時投資報酬率最高的一件事。

## 三個層級與作用範圍

| 層級 | 位置 | 適合放什麼 |
|---|---|---|
| User Level | 使用者目錄下的 `.claude/` | 個人長期偏好，作用於這台電腦上所有 session |
| Project Level | 專案根目錄 | 專案共同規則，通常隨程式碼進 Git 讓團隊共用 |
| Nested Level | 專案底下的子資料夾 | 該資料夾專屬規則（如 frontend 與 backend 各一份） |

- 講者自己的 User Level 設定包含：只用繁體中文輸出、用第一性原理思考、用金字塔原理結構化輸出。
- 若在團隊協作但有不想分享的個人癖好，可用 `CLAUDE.local.md`，它不會被上傳、只留在個人電腦。
- 多層並存時 Claude 不是挑一份看，而是依序疊加：User → Project → Nested。Nested 距離正在修改的檔案最近、最貼合眼前工作，通常對該次任務影響最直接。
- 原則：規則放得越接近實際工作的檔案，適用範圍越精準。

## 用 /init 建立第一版

- 進到專案資料夾、開啟 Claude Code，輸入 `/init`，Claude 會掃過整個專案並產出起始版 `CLAUDE.md`。
- 產出內容通常包含：專案用途介紹、啟動／建置／測試方式、使用的框架、資料夾架構、從程式碼觀察到的開發規範。
- **問題出在它整理得太完整**：Claude 接到任務時本來就會在背景啟動 Explore subagent，自己去掃資料夾、看 `package.json`。`/init` 寫的很多內容是 Claude 不寫也查得到的事實。
- 重複資訊的三重代價：浪費 Token、架構改了忘記更新會被過期資訊誤導、以及佔用 Instruction Budget。

### Instruction Budget

Context Window 決定 Claude 一次能看到多少資料；Instruction Budget 影響的是它在這些資料裡能同時顧好多少條要求。每看到一條指示，Claude 都要判斷這條現在適不適用、跟其他規則有無衝突、這次工作該優先遵守哪一條。看似無害的背景說明也會分掉注意力，塞越多，真正重要的規則越容易被淹沒。

## 做減法：三個刪除判準

逐行檢查 `/init` 產物，對每一條問：

1. **Explore subagent 自己找得到嗎？** 找得到就不要寫。夠格留下的是它翻程式碼也猜不到的隱性知識，或藏得很深的重要資訊。
2. **大部分工作都會用到嗎？** 只跟前端有關的規則（如改完畫面要跑某個視覺測試）就放進前端資料夾的 Nested `CLAUDE.md`，等真的動到前端才讀進來。
3. **過幾個月後還會成立嗎？** 像「目前暫時使用舊版 API」這類要求可能幾週後就失效，留著會讓未來的 Claude 照過期做法工作。

把關夠嚴格的話，`/init` 自動生成的內容大概會被刪到很少。

## 做加法：五個提問萃取隱性知識

不必死背分類，反問自己這五題即可：

1. **有沒有絕對不能搞錯的規定？** 例：網路商店所有對客顯示的價格都必須含稅——Claude 不知道就可能在新頁面顯示未稅價。
2. **有沒有固定的處理方式？** 例：商品價格要先改試算表再同步到網站，直接改網頁數字下次同步就會被蓋掉。
3. **改完一個地方，還有哪些要跟著改？** 例：會員價格調整後，首頁、結帳頁、常見問題、通知信件都要一起更新。
4. **做到什麼程度才算完成？** 例：改完畫面要同時檢查電腦版與手機版；改完購買流程要實際下一筆測試訂單。
5. **遇到不懂的事該去哪找答案？** 例：寫網站文案看品牌語氣指南、退款問題看退款規則。`CLAUDE.md` 只需說明資料放在哪，需要時再去讀。

好的 `CLAUDE.md` 內容通常不多，留下的是：不能搞錯的規定、固定的處理方式、容易漏掉的連動關係、完成前的檢查、其他重要資料的位置。

## 刪掉的內容該搬去哪

- **客觀現狀** → 留給 Explore 機制自己找。
- **只跟某資料夾有關的規則** → Nested `CLAUDE.md`。
- **很長、只有特定任務才用到的流程**（如發布新版本要依序檢查十幾個項目）→ 寫進 Skill，真的要發布時再呼叫。
- **絕對不能犯的死罪** → 用 Hook，不能只靠 `CLAUDE.md` 提醒。例如 API key 不得提交到 Git：模型處理複雜任務時仍可能漏看指示，Hook 則會在 `git commit` 前用程式強制檢查，偵測到疑似 API key 直接擋下。

## 長期維護：新增與修剪

講者形容 `CLAUDE.md` 像花園，維護只有新增與修剪兩件事。只增不減的做法當下合理（每條都是踩過的坑），但檔案終究會肥到把 Claude 的腦袋塞滿。

### 新增：用 /insights 找重複問題

在 Claude Code 輸入 `/insights`，它會分析歷史紀錄產生一份 HTML 報告：

- 回顧你平常怎麼使用 Claude Code（習慣一次給完整規格，還是分幾輪慢慢改）。
- 找出反覆出現的模式（例如是否每次改完都要重新提醒它檢查檔案）。
- 直接根據問題提建議：重複提醒很多次的要求會產出一段可直接複製進 `CLAUDE.md` 的規則；經常重複的工作流程可能建議做成 Skill，甚至建議改用 Hook。

累積一段使用紀錄後值得跑一次，但只加真正需要的規則。

### 修剪：兩種該勇敢刪掉的規則

**第一種：因為模型變強而不再需要的規則。** Claude Code 官方團隊在為新一代模型優化系統提示詞時，一口氣刪掉超過八成的原有規則，而能力完全沒有退步。原因是同一條規則在舊模型上能減少犯錯，到新模型上反而變成限制——過去死板規定「不要做什麼」，如今模型懂得觀察你的工作習慣與偏好，舊規則反倒綁手綁腳。

一般人難以自行判斷模型變強多少，較客觀的做法是參考各家最新釋出的官方 Prompting Guide，比對最新寫法，看看哪些規則已不需要。

**第二種：已跟真實情況不符的規則。** 程式碼早就改了、工作流程也變了，規則就過時了。只要跟 codebase 的事實不符就直接砍掉，避免誤導。

### 健檢 Prompt

因為不可能每週讀一次官方 Prompting Guide、也不可能記得專案每個改動，講者把修剪流程包成一組 CLAUDE.md 健檢 Prompt（Claude Code 與 Codex 皆可用，放在其 Patreon）。流程是：先確認目前使用的模型 → 對照該模型的官方 Prompting Guide → 回頭逐條查證 `CLAUDE.md` 的規則是否符合 best practice。

## 健檢實測抓到的問題

講者拿這組 Prompt 對幾個月前的專案跑健檢，抓到的典型問題：

- `CLAUDE.md` 裡的規則與專案內另外幾份文件互相牴觸 → 建議整段刪掉，只留一行 reference 指向真正正確的那份文件。
- 一整段網頁測試流程（教 AI 開發完怎麼用登入身分測試）寫在 `CLAUDE.md` 裡 → 建議整段搬進 Skill。
- `CLAUDE.md` 與 `AGENTS.md` 難以同步 → 建議在 `CLAUDE.md` 第一行 reference `AGENTS.md`，之後只維護一份檔案，AI 透過 reference link 讀到真正在維護的 single source of truth。

## 收束觀點：Becoming

講者引用凱文·凱利《必然》的核心觀念 Becoming——世界上沒有任何東西是有終點的，一切都在變成下一個版本的過程中。不敢刪除舊規則，往往是潛意識把 `CLAUDE.md` 當成一份已完成的規格書；但 codebase 是流動的、AI 能力也是流動的，這份檔案理應同樣流動：持續寫下新經驗，也定期清掉不再需要的舊限制。
