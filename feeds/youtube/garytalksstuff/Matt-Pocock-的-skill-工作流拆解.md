## 這套專案是什麼

- `grill-me` 是 Matt Pocock 在 GitHub 開源專案裡的其中一個 skill。影片提到該專案已超過 16 萬顆星、被下載 700 萬次。
- Matt Pocock 是 TypeScript 領域頂尖的專家與教學者，這次開源的等於是他自己的 AI 工作流。
- 專案裡是一整套 skill，從寫規格、拆任務到寫測試都有。影片認為只盯著 `grill-me` 很可惜——整包其實是他多年寫程式與 AI 開發經驗的集大成。

### 設計哲學：小而模組化

Matt 這一年幾乎把重心搬到 AI 上，發現比起寫 code 的速度，更難的是**控制 AI 的隨機性**（AI 本質上是充滿隨機性的黑盒子）。

市面上已有 Get Shit Done、Spec-Kit、Superpowers 等框架在做這件事，但他認為大框架的毛病是想把整個開發流程接管過去。以 Spec-Kit 為例，它把寫規格、做計畫到實作綁成一條又重又硬的固定流程，前面一步定歪，錯誤就順著整條線傳染，想改往往整條得重跑。

所以他的 skill 走完全相反的路：**每一個都刻意做得很小、很好改、還能自由拼裝**。這個「小而模組化」的理念是後面所有東西的底層邏輯。

## grill-me：讓 AI 反過來拷問你

被幾百萬人下載的這個 skill，檔案裡只有短短五行字，大意是：

1. 在對接下來的計畫達成共識之前，把使用者往死裡問。
2. 像畫心智圖一樣順著使用者的思路延伸，把每個決定背後會引發的連鎖反應一個個抓出來問到底。
3. 每次只能問一個問題，而且必須附上建議答案。
4. 在整體設計達成共識之前，絕對不准偷偷跑去寫程式。

### 為什麼這五行有效

寫程式的本質是連續做出幾百個微觀決定：防呆怎麼做、斷線怎麼辦、極端資料怎麼處理。把模糊想法直接丟給 AI 憑感覺做（Vibe Coding），等於把這幾百個決定的決策權全部外包給黑盒子；而 AI 為了討好你，通常會瞎掰出一套最難維護的架構——這對生產級軟體是噩夢。

這五行字的唯一目的是**把決策權搶回人類手裡**。要人類面對空白螢幕從零寫出涵蓋所有極端狀況的完美企劃書太痛苦，所以他把「找漏洞」這件苦差事丟給 AI：AI 順著決策樹無情挖出你沒想清楚的盲點、只負責給選項，拍板定案的永遠是人類。透過強制的一問一答，人類才能穩坐架構師的位置。

### 進化版 grill-with-docs

`grill-me` 的罩門是：AI 越熟悉專案，拷問才問得越深，但它每次開工都要重新摸一次專案，而且有些東西翻遍程式碼也查不到（專有名詞定義、當初為什麼這樣決定），導致前半場都在問背景，尖銳問題要等它摸熟才出得來。

`grill-with-docs` 會在每一場拷問裡順手把這些專有名詞與重要決策寫成文件留下來，之後 AI 帶著資料來拷問，一開場就能切進重點。Matt 自己比較常用這個版本。

## to-spec：寫規格書，但禁止寫程式碼

拷問完的共識一關掉對話就蒸發，所以第二站用 `to-spec` 把共識寫成規格書存起來。

Matt 在這個 skill 裡**完全禁止 AI 在寫 spec 時引用或寫任何程式碼**。理由是軟體工程界最大的痛——文件永遠跟不上程式碼更新的速度。比起整體業務邏輯，具體程式碼最容易變動；若讓 AI 把程式碼寫進規格，日後程式碼改了與規格對不上，下次請 AI 照規格修改功能時，它就會被規格書裡過期錯誤的舊 code 搞混，越改越亂。封殺這個選項，是要確保規格書永遠只專注在「這項功能到底要解決什麼問題」。

## to-tickets：按功能拆任務，不按技術層拆

`to-tickets` 把規格書拆成具體待辦任務，裡面蘊含一套專門對付「AI 規劃任務很爛」的方法論。

**AI 的壞習慣**：讓它自己規劃電商網站，它會先把資料庫全建好、再把後端邏輯全寫完、最後才畫前端畫面。最可怕的盲點是在最後一步畫面出來之前你完全無法測試任何東西——第一步資料庫建錯，要等做前端時才發現，前面心血全毀。

**強制改用使用者功能拆分**：同樣是電商網站，切成

- 任務一：只做會員登入，包含登入專屬的資料庫、登入邏輯、登入畫面。
- 任務二：做商品加入購物車，同樣包含完整的資料庫、後端邏輯、前端畫面。

好處是第一個任務做完就能立刻打開瀏覽器測試，而不是蒙著眼寫完幾千行才開始審核 AI 的產出。此外 `to-tickets` 還會排好任務順序，互不干擾的任務可以同時發包給好幾個 AI 平行處理。

## implement：TDD 綁死 AI 作弊的空間

下達實作指令後，`implement` 會照任務清單寫 code，過程中自動用 TDD 引導開發，寫完自己呼叫 Code Review skill 審查。

**TDD 為什麼對 AI 開發特別重要**：AI 骨子裡是個作弊仔。若讓它先寫算錢的程式再補測試，萬一它把「滿 1000 扣 100」寫成扣 200，它為了交差會直接生出一個假測試宣稱「滿 1000 必須扣 200，檢查通過」——拿自己寫錯的邏輯配上一個絕對會通過的測試，你根本抓不出 bug。

TDD 就是用來防作弊：寫任何一行程式之前先把測試定死（滿 1000 就是只能扣 100），此時程式還沒寫，測試一跑必定失敗亮紅燈；紅燈出現後才准 AI 開始寫真正的邏輯，直到轉綠為止。

## Code Review：把爛 code 症狀寫成檢查清單

測試過了會自動觸發審查 skill，它會**開一個全新的 session** 做 Code Review，讓 AI 保持在最乾淨、最聰明的狀態下檢查，避免被寫程式時的記憶干擾。

這個 skill 不是空泛地說「幫我看有沒有 Bug」，而是把軟體工程界公認的爛 code 症狀寫成具體檢查清單，共點名 12 種現象，全部來自經典名著《Refactoring》。影片挑了三個：

| 症狀 | 表現 | 建議 |
|---|---|---|
| Shotgun Surgery | 只想改一個按鈕顏色，卻要打開十幾個檔案修改，改動像散彈槍散落各處 | 把它們重新集中起來 |
| Feature Envy | 一段處理訂單的程式碼老是跑去管庫存的檔案拿資料來算 | 這段邏輯放錯位置，應搬去訂單那邊 |
| Data Clumps | 買家姓名、電話、地址永遠同時出現，卻散著在程式碼裡傳來傳去 | 打包成一個「聯絡人」物件 |

## writing-great-skills：為什麼他的 prompt 這麼短

Matt 的每個 skill 都非常短、非常精鍊，秘密藏在 `writing-great-skills` 這個 skill 裡。核心理念是：**在 AI 面前，你多寫一句廢話，AI 就多一分分心的可能。**

三個原則：

1. **修剪（pruning）**：刪掉所有廢話、會讓 AI 分心的文字，甚至那些你不說模型也知道該怎麼做的指令。這就是 `grill-me` 五行字就寫完的原因——必須確保每一句指令都有實際作用。
2. **指引詞**：一種資訊被極度壓縮、含金量超高的專有名詞。對 AI 說 `Data Clumps`，等於說了「請檢查程式碼裡有沒有總是綁在一起出現的變數，有的話打包成一個獨立物件」。Matt 大量運用這些深植於 AI 訓練資料裡的經典術語，用一個字取代一百字的廢話解釋。
3. **完成標準**：給 AI 一個明確的終點。

## 深模組 vs 淺模組

AI 寫程式很快，但天生沒有大局觀，每次只盯著眼前幾個檔案，為了方便交差最容易寫出**淺模組**。

**淺模組的比喻**：一棟房子裡廚房、客廳、臥室分得很乾淨，但沒有大門——進廚房要走窗戶、進客廳要爬煙囪。溝通成本極高，你得記住五個房間各自的密碼與路線。

AI 寫購物車結帳最愛蓋這種房子：把結帳切成 `計算折扣`、`驗證信用卡`、`建立訂單`、`扣除庫存`、`寄信` 五個小房間，卻沒有蓋一個統一的大門隱藏細節，主程式必須親自處理五間房的資料傳遞。

**為什麼這對 AI 特別致命**：Context Window 有限，結帳出 bug 時 AI 打開檔案發現邏輯散落五處，為了看懂整個流程必須在房間之間瘋狂跳轉；一旦塞進太多瑣碎邏輯超過記憶範圍，它就開始瞎猜，很容易把原本正常的程式碼一起改壞。

**深模組**不是叫你把一萬行 code 塞在同一個大房間不准切分，而是**蓋一扇極度簡單的大門，把複雜的房間藏在裡面**。同樣是結帳，對外只提供一個 `processCheckout`，折扣怎麼算、信用卡怎麼驗全藏在大門背後，主程式敲一次門就辦妥。它具備極強的局部性：出問題時 AI 只要專注讀這一個模組，來龍去脈都在眼前視野裡，不必去別處找線索。

一句話：淺模組讓 AI 迷路並瞎猜，深模組讓 AI 專注並精準打擊。

### improve-codebase-architecture：刪除測試

這個大掃除 skill 不只看語法，而是對程式碼進行**殘酷的刪除測試**：檢視每一個模組並想像「把它直接拔掉、讓主程式自己處理會發生什麼事？」

- 拔掉後天下大亂、原本隱藏的複雜邏輯全炸回主程式 → 這是有在做事的深模組。
- 拔掉後程式碼反而變清爽、原本要跳兩個檔案現在集中在一處 → 這個模組沒有隱藏任何細節，只是多餘的空殼。

Matt 建議把它當日常保養：每隔幾天在終端機叫 AI 跑一次，它會掃描整個專案並在你的電腦上生成一份 HTML 診斷報告，畫出前後的架構對比圖。不用看程式碼，看視覺化圖表挑一個最急迫的建議說「就照這個方案重構」即可。

## 跟 Superpowers 的路線差異

| | Superpowers | Matt Pocock 的 skill |
|---|---|---|
| 形態 | 已組好的自動化生產線 | 隨插即用的樂高積木 |
| 流程 | 寫死的九個步驟，逼你想清楚目標、寫好文件才准動工 | 一個 skill 只解決一個問題，做完就收工 |
| 進入點 | 希望你從頭走完設計、寫計畫、執行 | 手上已有規格（自己寫的、主管給的、別的 AI 產的）可直接跳到 `to-tickets` |
| 產出文件 | 為它自己的下一步量身打造，別人難接手 | 不綁架後續流程 |

影片的判斷：在模型還不夠聰明、容易偏題的年代，保母級防呆流程非常管用；但用到現在這個世代的模型，這套死規矩反而變成累贅。動工前一樣需要釐清目標，差別在於模型理解力已極強，不必像填表一樣被強迫走完九個防呆步驟才能避免翻車。既然不需要重度防呆，把設計與執行包山包海塞進一個巨大流程就顯得笨重——這是 Matt 的做法更適合現在生態的原因。

## 收束：專業底子才是控制 AI 的關鍵

Matt 把深厚的軟體工程底子用在兩個地方：

1. **架構上**：把深模組、爛 code 徵兆這些軟體工程界早已證明有效的老方法融入 skill，用來規範 AI 的行為。
2. **與 AI 溝通上**：把專有名詞直接當成 prompt 的一部分——與其寫一大堆廢話解釋，不如丟一個精準術語，AI 一聽就懂。像老教練給球員的一句話，簡單卻蘊含幾十年經驗。

影片的結論：很多人以為有了 AI 就不需要在自己的領域精進，但 Matt 證明了**只有成為專業領域的專家，你才能真正控制好 AI**。他真正開源的不是幾個 skill，而是在教人怎麼用專業領域積累的思維與語言去駕馭 AI 這個黑盒子。

影片另提到 repo 裡還有三個專門用於 AI 寫作的 skill，走的路線與一般「幫我寫一篇 blog」完全不同，該部分細節未在影片中展開。
