## 問題不在用太多 AI，在每一步都用太貴的模型

新模型接連上線，很多人第一個感受到的不是生產力爆炸而是 Token 額度爆炸：只是叫 AI 研究一個題目、做一份簡報、改幾頁網站，來回幾輪工作還沒做完 Token 就快見底。

同一份任務實測，不降低品質、不偷工減料，只把規劃、執行、Review 分給不同模型，成本就下降了 58%。這就是 Model Routing（模型分工）——讓每一步任務用剛剛好的模型。在改格式、整理資料、跑重複步驟時不用一律派出最強的 AI，就像不會讓公司裡薪水最高的人整天複製貼上、整理表格、改檔名。最貴的判斷力應該留給最容易影響結果、走錯代價最高的地方。

## Model Routing 的兩個維度

很多人把 Model Routing 理解成「選模型」，但那只回答了一半。同一個模型也可以用不同的推理強度工作。

- **模型選擇**：派誰上場——最強、最貴、判斷力最好的模型，還是便宜、快速、適合大量執行的模型
- **推理強度**：叫它用多少腦力——快速回答就好，還是多想幾步、反覆檢查、花更多 Token 去推理

兩者相乘出現四種組合：

| 組合 | 適用情境 |
|---|---|
| 強模型 + 高推理 | 方向不明、走錯代價高：產品策略、系統架構、重要 spec、最後的高風險 Review |
| 強模型 + 低推理 | 需要好判斷但不用想很久：例如三個產品方向要快速初篩哪一個值得研究 |
| 便宜模型 + 高推理 | 方向已定、spec 也清楚，但執行本身有難度：依既有規格補一段複雜邏輯 |
| 便宜模型 + 低推理 | 機械、重複、易檢查對錯：整理資料、分類、摘要、改格式、跑固定檢查 |

## 選模型前要先過的兩道限制

**第一道：公司准用的工具。** 在公司用 AI，第一個問題通常不是哪個模型最強，而是這份資料能不能丟進去。客戶資料、財務資料、法務草稿、還沒發布的產品計畫，不能因為某個模型看起來划算就丟到外部 API。公司批准的若是 ChatGPT Enterprise、Claude Team、Microsoft Copilot，就先從這些工具裡選。

**第二道：任務需不需要特殊能力。** 有些工作取決於特定資料源——Live Web、X、公司內部資料庫、逐字稿資料庫、CRM，或可搜尋歷史資料的系統。任務若取決於最新資訊，能不能連 Live Web 就很重要；若取決於 X 上大家現在怎麼討論，接近該資料源的工具才有意義。重點不是它是不是最強模型，而是有沒有接到你需要的那條資料流。

過完兩道限制才輪到模型本身：方向未定、任務混亂、需要判斷力與 taste 時用日常主力的強模型（規劃影片主論點、拆產品策略、判斷文章邏輯漏洞）；規格已清楚、輸出格式固定、知道怎麼檢查成果、只需大量生產時交給負責做工的模型。

## 為什麼分工能省一半而不掉品質

一份工作裡不同步驟需要的智力本來就不一樣。以做網站為例，開頭要理解客戶是誰、網站解決什麼問題、競品怎麼做、頁面架構怎麼排，這段是在處理未知的方向；定下來後架構、頁面清單、文案原則、資料格式與驗收條件都寫清楚了，後面就變成純執行。

而最花 Token 的剛好是後面的執行——模型要讀 code、寫 code、改頁面、跑測試、修 bug。全程用最貴的模型，等於把最高單價套在輸出量最大的地方。

實測比較三種做法：強模型規劃 + 較便宜模型實作、強模型同時規劃與實作，這兩種最後品質沒差太多；但把 plan 和實作都交給便宜模型，雖然單價便宜，成品品質卻掉很多，來回修改到變成可用產品時花的錢反而跟前面差不多，時間消耗還直接翻倍。

所以真正的成本不只是 API 單價，而是「完成一份可用成品的總成本」，至少分四塊：

1. Token 花多少
2. 跑錯後要重跑幾次
3. 人要花多少時間檢查
4. 方向一開始就走錯的代價

便宜模型沒有 spec 就亂做、最後重跑三次是耗時耗力；最強模型整天被拿去改格式只是亂燒預算。Model Routing 的目標不是把單價壓到最低，而是用合理的成本做出真的能交付的成品。

## 五步流程與交接鏈

落實到工作中是一條流程：Research → Design & Spec → Execute → Review → Fix & Deploy。

但只把任務切成五塊還不叫 Routing，關鍵是把交接設計好，讓每一步的 output 變成下一步的 input，出問題才知道該退回哪一步：

- Research 交出研究資料包，讓 Design 與 Spec 有證據可做決定
- Spec 交出清楚的工作規格，讓 Execute 不用猜
- Execute 交出可以檢查的成品
- Review 交出問題清單和證據
- Fix 按問題清單修完，最後才 Deploy

有了交付鏈，才有辦法逐步判斷每一步需要什麼模型特色、模型要多強、推理要開多深。同一套邏輯也適用於做影片、做市場研究、做內部工具。

### 第一步 Research：拆成一支小團隊

很多人用 AI 做研究只是開一個對話框叫模型「幫我 Google 一下」，搜尋、判斷、結論全壓在同一個模型身上，很容易漏東漏西。建議拆成小團隊：

- 強模型當 Research Manager：定義問題、拆研究子題、決定要找哪些來源，並先講清楚每個結論需要什麼證據
- 成本較低的 Scout Agents 平行搜集：有人找競品、有人找使用者需求、有人找相關技術、有人找法規案例或 GitHub、Benchmark。Scout 不急著下最後結論，只把來源、重點、可疑點整理回來
- 資料回到 Research Manager，由強模型去重、找矛盾、補缺口，整理成能拿去決策的報告

這樣把開頭和結尾留給高品質高單價的模型，中間大量、可拆分的資料搜集就可以做替換。

### 第二步 Design 與 Spec：最值得開高推理

Spec 白話講就是交接文件，要清楚到換一個模型、換一個人、甚至隔兩週後的你自己回來看，都知道要交什麼、怎麼判斷做完。一份好的 spec 至少要交代：網站有哪些頁面、每一頁服務誰、資料從哪裡來、設計原則是什麼、success criteria 是什麼，還有什麼事情不能做。

這段用強模型並開較高推理強度，因為那些你自己還沒想清楚的地方都需要在這裡被抓出來。好的寫法會具體到像「首頁三秒內要讓第一次來的 SaaS 創辦人理解產品賣點」「案例頁要看得到導入前後的差異」「手機版不能把主要 CTA 擠到打開後的第一個畫面外」。

### 第三步 Execute：可驗收才適合交給便宜模型

規格清楚後負責做工的模型才適合大量上場。把頁面、文案整理、資料轉換、code 與測試準備拆成一個個獨立工作包，每包講清楚輸入是什麼、要交什麼、不能碰什麼、完成怎麼判斷。

規則固定、容易驗收的工作用低推理強度（產品資料轉 JSON、補 metadata、依既有元件套版、整理 CSV）；spec 已很清楚但技術難度較高的工作，可以讓成本較低的模型提高推理強度。

判斷標準很簡單：**你能驗收的事情，才適合交給比較便宜的模型大量做。** 成果好壞容易檢查（格式對不對、連結能不能打開、測試有沒有過、欄位符不符合規格）就很適合 Routing；反過來如果你自己都不知道什麼叫做好，便宜模型做得再快也只是快速產生一堆你不敢用的東西。

### 第四步 Review：當成 Investigation 而不是抓錯字

先決定要查什麼、需要什麼證據、什麼條件才算過關。網站要查的可能包括速度、SEO、accessibility、broken links、事實與引用有沒有亂寫、表單能不能送出。

接著讓多個 Checker 分頭調查：A 測速度、B 找 broken links、C 檢查引用與事實、D 測 accessibility、E 看手機版與主要流程。Checker 只回報證據、失敗項和可疑點，不負責宣布網站能不能上線——五個 agent 同時當法官，最後通常只會得到五份互相矛盾的判決。

所有調查結果回到強模型手上，由它判斷問題嚴不嚴重、哪些要退回修改、哪些可以接受、哪些需要人來決定。一般初檢可用成本低的模型；當證據互相衝突，或問題涉及安全、法規、商業決策，再拉高推理強度甚至直接交給人。

### 第五步 Fix 與 Deploy：附帶升級條件

Review 把問題講清楚後，局部改 code、補格式、重跑測試與部署都可用成本較低的模型，因為方向已確定，它只需照著問題修。

但有一個條件：如果修改時發現問題不是實作錯、而是 spec 本身就錯了，就不要叫便宜模型硬修，直接升級回強模型重新處理方向。

## 成本實算

以下數字不是要背價格（價格一定會變），重點是看懂成本結構——哪一段 Token 量最大、哪一段 output 最多、哪一段最值得 Routing。

假設做一個中型行銷網站，各階段用量：

| 階段 | Input Token | Output Token |
|---|---|---|
| Research + Planning | 30 萬 | 4 萬 |
| Execute | 30 萬 | 15 萬 |
| Review | 12 萬 | 3 萬 |
| Fix + Deploy | 10 萬 | 5 萬 |
| 合計 | 82 萬 | 27 萬 |

**方法 A：全程使用同一個最強模型**（Input 每百萬 10 美元、Output 每百萬 50 美元計）
82 萬 Input ≈ 8.2 美元，27 萬 Output ≈ 13.5 美元，總成本 **21.7 美元**。

**方法 B：Model Routing**
Research 與 Planning 仍用最強模型（方向最重要）約 5 美元；Execute 交給中階模型約 2.1 美元；Review 換成另一個中高階模型約 1.35 美元；Fix 與 Deploy 回到中階模型約 0.7 美元。總成本 **9.15 美元**。

同一組任務從 21.7 降到 9.15 美元，少掉 12.55 美元、約 58%。

這組算式也解釋了為什麼執行階段最值得 Routing：**Output Token 通常比 Input Token 貴，模型寫得越多價差越明顯。** 所以不要只看 Input 單價便宜多少，要看這一步最後會輸出多少東西。

當然 Routing 不保證每個任務都能省一半——spec 寫得很爛、或便宜模型根本做不了這份任務，只要重跑一次就可能把省下的錢和時間全部填回去。

## 沒有全套訂閱也能用

Model Routing 不要求把所有模型湊齊，而是先弄清楚每個角色需要什麼能力。實際要把不同模型串起來，可以看 OpenRouter 這類平台——把它理解成 AI 模型的總機，把不同模型放進同一個按量計費的 API 入口，再接到支援它的 agent 或客戶端。

但要注意：OpenRouter 只是把模型接在同一個入口，不會自動替你把工作拆好；不同模型對 tool use、特殊參數與資料政策的支援也不完全一樣。正式拿來處理公司或客戶資料前，要先確認隱私設定與實際相容性。

## 做成一張表才叫系統

挑一個最常重複的工作流程，列出每一步的 input、output、錯誤代價、驗收方式、模型層級、推理強度，最後再加一個**升級條件**：出現什麼問題時，便宜模型必須停下來把工作退回給強模型或交給人處理。這張表做出來，Routing 才不會只是一句概念，而是可以直接執行的系統。

## 核心觀念：Compute Allocation

比起 Model Selection，更準確的說法是 Compute Allocation（算力分配）。就像不會拿一張高階顯示卡只用來玩小畫家，OCR、摘要、分類、固定格式整理也不需要每次都叫最強模型上場，然後再抱怨 Token 太貴——那不是模型定價的問題，是把算力放錯位置。

成熟的做法不是今天哪家模型強就全部換過去、明天換另一家。模型會變、價格會變、平台政策也會變，真正要建立的是一套架構：任務可以拆、模型可以換、資料權限清楚、驗收標準存在、出錯可以回退。這樣才不會每次模型榜單一更新整個工作流就要重做。

AI 讓執行越來越便宜之後，重要的是知道怎麼定義問題、怎麼拆工作、哪裡值得花錢、哪裡必須驗證，以及哪一個決定不能直接交給 AI。
