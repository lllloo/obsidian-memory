## 問題場景

兩種人都會撞上同一堵牆：vibe coder 用 AI 寫 side project，前三週爽到不行，第四週只改一個小地方、另一個頁面就掛掉；工程師剛進公司接手別人幾千行的 codebase，商品資料從哪抓進來不知道，改這裡會不會弄壞別的頁面更不知道。兩者的共通點是被逼著用 AI 進入一個自己不熟悉的 codebase。結果 vibe coder 覺得 AI 還不夠格而放棄產品，工程師覺得模型能力不夠而把 AI 打回冷宮。

影片的主張：問題從來不是 AI 不夠強，而是用它的方法錯了。

## Greenfield vs Brownfield

- **Greenfield（綠地）**：什麼都沒有的空地。全新專案沒有歷史包袱，架構怎麼設計、檔案怎麼命名、用哪套 pattern 全由你決定。這是 AI 最好發揮的場景——沒有既有規則要遵守，你叫它怎麼蓋它就怎麼蓋。網路上「用 AI 三十分鐘做一個 App」講的都是這種。
- **Brownfield**：已經蓋滿東西的土地。你接手的是一棟別人蓋好、而且已經有人住在裡面的房子，裡面有寫好的 code、既有 pattern、沒解掉的 bug，以及一大堆你看不到但牽一髮動全身的水管跟電線。

**關鍵提醒：Greenfield 不會永遠是 Greenfield。** Vibe Coding 狂寫一個月後，若過程中沒有有意識地維持乾淨架構，專案就已經變成 Brownfield 了——因為裡面大部分的 code 你根本沒讀過。這就是為什麼照著網路教學做都很順，一碰真實專案就嚴重水土不服：教學教的是在空地上蓋新房，你每天要面對的卻是在別人住的房子裡拆牆改管。

## AI 為什麼會埋地雷

假設你跟 AI 說「幫我加庫存狀態的篩選跟編輯功能」，它幾秒鐘生出一大段 code，畫面看起來也沒錯，你開心送出 PR，隔天 QA 說訂單頁掛了。

這句話在 Greenfield 完全沒問題，但在 Brownfield 等於把一個從沒進過你家的裝潢師傅丟進廚房，叫他直接搞個流理台出來——完全沒先講你家的設計風格與裝潢理念，於是 AI 自己看著辦：

- 不知道專案已有一套 React Query 的 pattern 在管 API，自己發明了新寫法。
- 不知道專案早就有共用的 Table 元件，又自己重刻了一個。
- 最糟的是，它為了拿商品資料去改了 `useProducts` 這個 hook，但訂單頁也在用它；改了資料格式後商品頁修好了，訂單頁卻爆了。

AI 的每一步看起來都合理，但它是在一個完全不認識的房子裡憑感覺做事——表面省了時間，實際是在別人的專案裡埋地雷。它手藝可能比你好、React 寫得比你熟，但它不認識這棟房子的管線、不知道哪面是承重牆、哪根水管接的是樓上鄰居。

**Brownfield 用 AI 的順序：先把它當成幫你讀專案的資深同事，等兩個人都把房子看懂了，再把它當成照著這棟房子規矩施工的師傅。順序絕對不能反——先看懂，再動手。** 大多數人犯的錯就是把順序反過來，甚至直接跳過「看懂」。

## 兩種走法

同一套流程有兩條路，取決於你對 AI 的熟練度與信任度，沒有標準答案：

| 走法 | 做法 | 適合誰 |
|---|---|---|
| AI 輔助開發 | 主導權在你：自己開瀏覽器、自己翻檔案、自己把 code 貼給 AI。AI 是放大鏡，真正走進每個房間的人是你 | 平常主要用網頁版 AI，或對 AI 寫的 code 還沒那麼放心 |
| 純指揮 agent | 用 Claude Code、Cursor 這類讀得到整個專案的 coding agent，幾乎不碰檔案，只負責出一張嘴，讓 agent 自己探勘、讀、交報告回來驗收 | 對 agent 信任度較高 |

流程分兩階段共五步：前半段「看懂它」，後半段「安全的動它」。

## 第一階段：看懂它

### 第一步：搞清楚畫面長在哪個檔案

**AI 輔助**：與其跟 AI 玩猜猜看，最土炮但百分之百準確的方法是打開瀏覽器開發者工具，對著要改的畫面點右鍵、檢查，找出一個獨特特徵（特殊的 class name、按鈕文字、測試標籤），拿它回編輯器全域搜尋，立刻定位是哪個檔案在渲染。找到後把檔案丟給 AI，請它分析畫面結構：引入了哪些子元件、各自渲染什麼、有沒有哪些看起來是全站共用而非本頁專屬的元件——**只分析，不要修改任何 code**。

**純指揮**：直接對 agent 說畫面上商品列表是哪個檔案在渲染、分析元件結構、標出哪些子元件是全站共用的，這階段只做分析、不要改任何 code。

兩條路的指令都強調「只分析，不要改」，因為這階段的重點在探索。這一步的價值是把「我怕改壞」的恐懼變成一張看得見的地圖：你會清楚知道自己站在這棟房子的哪個房間，還有哪些元件是全站共用的資產——那些資產以後可以重複用，但絕對不能亂改。

### 第二步：梳理 data flow

前端最容易出事的地方從來不是畫面，而是資料。

**AI 輔助**：先打開 `package.json` 看它用哪套狀態管理工具（Redux、Zustand、還是 React Query），接著找對應的 store 或 hooks 資料夾，回到畫面元件找出觸發資料變動的動作（`dispatch`、`mutate`、`setState`），最後把畫面元件與狀態檔案一起丟給 AI，請它用白話文解釋這條 data flow：商品列表的資料從哪個 API 來、用哪套工具在管、管理員編輯庫存時資料怎麼從畫面流回 server、中間經過的 function 依序列出。

**必做的一件事**：請 AI 特別標出這個 hook 有沒有被商品頁以外的地方用到。注意網頁版 AI 看不到整個專案，你得先在編輯器全域搜尋這個 hook，把搜到的檔案一起貼給它才答得出來。

**純指揮**：同樣一段話交代 data flow 的問題，而「還有誰在用這個 hook」agent 讀得到整個 codebase，直接就能答。

### 額外招式：叫 agent 畫一張架構導覽圖

講者每次接手陌生專案都會用、也是純指揮這條路上他最喜歡的一步：探勘做完後補一句——把剛剛探勘到的結果做成一頁 HTML，把專案的頁面結構、共用元件、data flow 畫成一張架構導覽圖，要能直接用瀏覽器打開。

幾分鐘後你就拿到一張地圖：哪些元件是共用的、資料從哪流到哪、哪一根水管後面接著別的頁面，一目了然。這頁 HTML 就是這棟房子的建築藍圖。

## 第二階段：安全的動它

從第三步開始，兩條路合而為一。原因是前兩步的本質是**勞力活**（讀 code、找檔案、追資料流），勞力活可以外包，你信任多一點就外包多一點；接下來兩步的本質是**決策活**——決定什麼東西絕對不准動、決定一段改動夠不夠格進這個 codebase。決策活沒有外包版：不是 agent 做不到，它可以幫你起草，但起草跟拍板是兩回事，改壞了被 QA 找麻煩、隔天踩到地雷的是你。

### 第三步：給 AI 帶著既有規則的需求

這是 Brownfield 跟 Greenfield 差最多的地方。**你給 AI 的不能是一個空需求，而必須是一個帶著既有規則的需求。**

不能只說「幫我加一個庫存篩選」，要把前半場學到的規矩全部寫進去變成它的邊界，例如：

- 動手前，先讀負責商品資料的 hook、共用元件資料夾、型別定義檔。
- 沿用專案既有的 React Query pattern。
- 重用現成的 Table、Modal、Select 元件，只准用 Tailwind。
- **絕對不要動到**全域的 routing、權限控管，以及任何被商品頁以外用到的共用 hook。

那句「絕對不要動」就是把前半場看懂的東西變成 AI 的 guardrail，也是整套流程裡最關鍵的一步。

**Clean Code 的觀念澄清**：在 Brownfield 裡，Clean Code 不是你自己覺得漂亮的寫法，而是**跟前人一致的寫法**。所以 guardrails 的第一條永遠是「照著這個專案原本的樣子寫」——沿用前人的 coding style 本身就是最高優先的 Clean Code。

### 第四步：拆成小步，每一步親自 review

規格給對了不代表 AI 第一次就會寫對，所以不要讓它一次生出整個功能。順序大致是：

1. 只提出元件結構跟資料流的規劃，先不要寫 code。
2. 確認方向對了，再讓它只去改商品資料的 hook、加上庫存篩選的參數。
3. 改完你也 review 完，再讓它做篩選的畫面。
4. 最後才做編輯庫存的彈出視窗。

一次只做一小塊，每一塊都在你眼皮子底下進行。

**Brownfield 專屬的 review 重點**（跟 Greenfield 不同，不是只看有沒有 bug）：

- 這段改動有沒有偏離專案既有的寫法？
- 命名習慣、資料夾結構、抓資料放的位置跟前人一不一致？
- 有沒有偷偷改到共用的檔案？
- 有沒有重複造輪子，自己又刻了一個早就存在的元件？

可以直接請 AI 用資深前端工程師的角度先做一輪：有沒有偏離既有的 React Query 寫法、有沒有動到共用元件、有沒有漏掉 loading 與 error 的狀態處理。**但 AI 的 review 是初審，終審永遠是你。** 在 production 環境下，除非你已經很熟這套 codebase、或這套 codebase 已有很好的 harness 與 context 管理，否則重要決策建議都先不要外包給 agent。

### 第五步：客觀驗證沒改壞別人的功能

這一步勞力活回來了，兩條路又分岔。分三個部分：

**1. 先跑專案本來就有的測試。** 很多人完全忘記專案裡早就有一整套測試，這是最快最省力確認有沒有壞到既有功能的方法。

- AI 輔助：動手前自己跑一次確認都是綠燈，動完手再跑一次。
- 純指揮：交代 agent 動手前先跑一次既有測試並回報結果，之後每完成一小塊改動就再跑一次，讓跑測試變成它的固定動作。
- 專案根本沒測試？現在就是叫 AI 補幾條關鍵測試的最好時機。

**2. 看懂別人的 error log。** Brownfield 的經典坑是很多專案有自己一套包裝過的錯誤紀錄機制（custom error logging）：包裝過的 logger、一組統一的 error code、或固定要送去某個後台的格式。在公司裡這叫**部落知識**——老鳥都懂，但沒寫在任何文件裡。而且這不只是公司的事：AI 幫你生 side project 時常常也順手建了一套 error handling，你根本不知道它存在，結果後來隨手寫的 `console.error` 根本沒進到那個系統。

與其瞎猜，不如請 AI 讀 logger 檔案並回答三件事：錯誤最後被送到哪裡、一筆 log 長什麼樣子、有沒有規定一定要帶哪些欄位，然後示範這次的功能要沿用同一套 logging 該怎麼寫。重點是**錯誤處理要說專案本來的語言**：隨手丟一個 `console.error`，這筆錯誤上線後根本不會被任何人看到；照既有格式帶上對的 errorCode 與 metadata，它才會出現在該出現的地方，之後 debug 才找得到線索。

**3. 回歸檢查（regression）。** 直接對付「訂單頁掛掉」事件：明確檢查加了這個元件之後，其他用到同一個 hook 的地方是不是還正常。

- AI 輔助：前半場已經讓 AI 標出那個 hook 還被誰用到，拿著那份清單一個個回頭驗。
- 純指揮：一段話交代——我動了商品資料的 hook，列出專案裡所有用到它的地方，逐一確認我的改動有沒有改變它原本的行為（回傳型別、參數、預設值有沒有變），既有測試若有覆蓋到這些地方就告訴我該跑哪幾個。

## 整條線走一次

同樣是「幫我加個庫存篩選跟編輯」這句含糊的需求，走完一輪後你做的是：

1. 先分清楚這是 Brownfield，知道自己在別人的房子裡改廚房。
2. 選好走法——自己拿放大鏡逐間看房，或指揮 agent 畫出建築藍圖——總之拿到那張地圖，標出那根危險的共用水管。
3. 把既有規矩（含 coding style）全部寫成規格與 guardrail。
4. 讓 AI 一小塊一小塊地寫，每一塊都用資深的眼光親自 review。
5. 用既有測試、看懂的 log、回歸檢查，客觀證明沒有弄壞任何人的東西。

同一個需求、同一個 AI，差別只在於這次是先看懂再動手，而不是閉著眼把整包 code 丟給它。

## 收束觀點

AI 越強，前面那些分岔的步驟會越來越往純指揮那邊收斂，總有一天不會再有人手動貼檔案給 AI。身為 AI 原生工作者，很重要的能力之一是：被丟進一棟完全陌生的專案時，你要知道自己現在需要 agent 幫你探索並帶著你理解，而不是直接擼起袖子幹活。

反過來說，如果開新專案時就已經有很好的 harness 與 context 管理，這些問題其實都不存在，真的只需要出一張嘴。講者認為「有能力搭建專案架構、做好 context 管理」是 vibe coder 晉升 agentic engineer 的關鍵里程碑之一。
