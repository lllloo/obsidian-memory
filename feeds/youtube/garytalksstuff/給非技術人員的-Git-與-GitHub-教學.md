## 這支影片要解決什麼

沒有程式背景卻迷上 vibe coding 的人，一定遇過 Claude 或 Cursor 突然問「要不要 commit？」「要不要開個分支？」「要不要發個 PR？」——這些術語背後全都指向同一個東西：Git。影片用一個「Gary 做記帳軟體」的情境，把概念一路串起來。

## GitHub 與 Git 的差別

- **GitHub**：可以先簡單理解成程式碼專用的 Google Drive，在雲端儲存與管理程式碼的網站，有權限的人隨時能查看甚至一起編輯。
- **Git**：幫你在本機端管理程式碼版本的工具。

為什麼不能像 Google Drive 那樣直接把資料夾拖上去？因為 GitHub 主要用於協作與追蹤程式碼進度，**它不收單純的檔案，只接收已經做好版本紀錄的專案**。所謂版本紀錄，就像以前寫報告會留下「報告 v1」「報告最終版」「報告打死不改版」那種修改歷史，而幫資料夾建立這套紀錄系統的工具就是 Git。

**沒有 Git 的下場**：AI 幫你加新功能時不小心把原本好好的程式改壞了，你根本不知道它動了哪些檔案，也不知道怎麼恢復到上一個正常狀態。有 Git 就不一樣——不管 AI 怎麼亂改，你隨時能把程式回溯到之前正常的樣子。

所以在把專案放上 GitHub 之前，Claude Code 通常會先問要不要設定 Git，或直接幫你跑 `git init`。這行指令的意思就是告訴 Git：請開始追蹤這個資料夾裡的所有變動。

## commit：存檔，不是上傳

當你有「這個功能終於能跑了，我想先建立一個版本紀錄，萬一之後 AI 又改壞可以退回來」的念頭時，對應的就是 **commit**。

- 比喻：像玩遊戲打大魔王前先手動存檔。
- 價值：幫程式碼建立一個絕對安全的檢查點。做了 commit，這份正常狀態就被永久封存，就算 AI 發瘋把程式碼全刪或改得亂七八糟，都能瞬間還原回 commit 當時的狀態。

**最重要的觀念：commit 不是上傳，也不是把東西放到 GitHub 上。** 它只是單純在你自己的電腦裡幫目前狀態留一份紀錄。所以 Claude Code 問「要不要 commit」時，其實是在問「現在這個好好的狀態，要不要先存個檔、買個保險？」

你也可以主動說：現在這版測試都沒問題，幫我 commit 一下，並在訊息裡寫清楚這次改了什麼。

## push 與上傳前的金鑰陷阱

想把電腦裡存好的進度上傳到雲端，對應的動作叫 **push**。commit 跟 push 完全是兩回事：commit 在自己電腦裡存檔，push 才是真的推送到雲端的 GitHub。

**push 之前所有 vibe coder 都要知道的事**：如果專案裡藏著串接金流的 API 金鑰，它跟著程式碼被 push 上 GitHub，等於把家門鑰匙公開貼在網路上，任何人都能撿去用。程式改壞了還有救，**金鑰一旦外洩流傳出去就真的救不回來**，只能整把作廢重新申請，就像信用卡被盜刷只能掛失補發。

解法是 `.gitignore` 檔案，作用單純：告訴 Git 這些特定檔案不要追蹤、絕對不要上傳。你不用自己記哪些該擋，直接跟 Claude Code 說「幫我確認 env 檔、密碼還有各種金鑰或機密檔案都已經放進 gitignore 裡面，絕對不要 commit 上去」即可。

**第一次 push 會看到的字眼**：

- `remote`：遠端的地址，相對的是 `local`（你電腦本地的資料夾）。
- `origin`：通常指你在 GitHub 上的那個專案資料夾。
- `main`：這個專案目前的官方正式版。
- 所以 `push 到 origin main` 白話就是：把現在寫好的正式版本傳送到雲端的那個專案資料夾裡。

## clone 與 pull：協作的基礎循環

- **clone**：朋友想一起共同編輯這個專案時要做的動作。注意它跟 GitHub 網頁上的 **Download ZIP 完全不同**——Download ZIP 抓下來的只是一包純檔案，裡面沒有被 Git 追蹤的紀錄，改了也沒辦法同步回 GitHub。用 clone 抓下來才等於正式加入這個專案，只要被加成協作者，之後的修改上傳回去都很輕鬆。
- **pull**：把 GitHub 上最新版本的程式碼抓下來、同步到自己的電腦。

合作的基礎循環：第一次加入專案用 `clone` → 平常同步別人的最新進度用 `pull` → 自己改好東西存檔用 `commit` → 想把進度送上雲端用 `push`。

## branch：隔離風險的實驗沙盒

在 Git 的世界裡，所有專案一開始都有一條主線 `main`，代表穩定運行中的程式碼。開 branch 的目的很單純：**讓正在開發中、還不穩定的功能，跟已經寫好、很穩定的功能徹底分開，井水不犯河水。**

**既然有 commit 可以退回，為什麼還要 branch？** 因為 AI 寫比較複雜的大功能時通常不會一次寫對，而是反覆試錯、修改好幾次。一直在 `main` 上讓它改，試錯期間你的程式就會長時間處於半壞掉的狀態；這時若朋友突然想看你的作品，或你發現畫面上有拼字錯誤要緊急修正，就會非常尷尬——作為專案門面的 `main` 現在根本跑不動。

**比喻**：專案資料夾是一張神奇辦公桌，branch 是桌子旁邊的平行時空切換按鈕。按下 `main`，桌上呈現穩定版本；按下新功能 branch，桌上瞬間變成開發中的草稿。草稿真的被 AI 改爛，最壞就是把這個 branch 刪掉切回 `main`，而 `main` 毫髮無傷。

**實務講法**：這個時代不必逼自己學會 git 指令，但要知道這些名詞在幹嘛，才能直接跟 AI 說——先幫我從 main 開一條新的 branch 專門做這次的資料庫功能，之後所有改動都 commit 在這條 branch 上，絕對不要動到 main。

## worktree：讓多個 agent 平行工作

branch 的致命傷是**你終究只有一張辦公桌**，同一時間只能顯示一個平行時空。硬要兩個 AI 同時在這張桌子上做事（一個看資料庫藍圖、一個看 UI 設計稿），它們會搶顯示狀態而大打出手——你明明在開發資料庫的 branch，裡面卻混進了修改 UI 的 commit，整個 Git 狀態變得非常混亂。

**worktree 就是直接再買第二張實體辦公桌**：跟 Claude Code 說要開一個新的 worktree，它會在你電腦裡生出一個全新的實體資料夾。兩張桌子連通同一個 Git 記憶庫，所以可以讓 Agent A 在第一張桌子負責資料庫的 branch、Agent B 在第二張桌子負責 UI 的 branch，各司其職、平行開發效率拉滿、完全不互相干擾。

影片點出的時代差異：以前工程師不太會用到 worktree，一個人一次專心做一件事就好；但 vibe coder 很可能同時開兩三個 AI Agent 平行工作，而不是排隊等一個做完才換下一個，這時就一定會需要 worktree。

## PR 與 merge

- **PR（Pull Request）**：可以想成一份**改動提案**。branch 上的功能寫完，正式合併進 `main` 之前先開 PR 送到 GitHub，讓大家一起審核這次改動合不合理。開 PR 也能請 AI 代勞：跟 agent 說「幫我把這條 branch 開一個 PR，內容說明這次做了什麼功能、改了哪些檔案、還有要怎麼測試它」，它就會把提案整理得讓 reviewer 一看就懂。
- **merge**：大家檢查過沒問題後，把這次的程式碼變動正式合併回主線 `main`。在 GitHub 網頁上按下 Merge 按鈕，雲端的 `main` 就更新了。

**新手最容易誤會的地方**：合併發生在雲端網頁上，**你電腦本機裡的 `main` 並不會自動跟著變**。很多人以為在 VS Code 或 Cursor 裡看到的程式碼就是 GitHub 上最新版本，其實你看到的永遠是本機目前的狀態。所以每次有新功能被合併進 `main` 之後，一定要切回本機的 `main` 並叫 agent 再執行一次 `pull`，手動把雲端最新版本拉下來，下次開新 branch 才是從最新進度出發，而不是活在過時的舊版本裡。

## conflict：Git 在等你下產品決策

當你跟朋友剛好改到同一個檔案的同一個地方，或兩個 AI Agent 動到同一段核心邏輯，Git 就會跳出 conflict 警告——它發現同一段程式碼出現兩個完全不同的版本，不知道該聽誰的。

現在 Claude Code 這類工具遇到 conflict 會自己判斷處理。Git 會在檔案裡留下特殊標記，把兩邊打架的程式碼上下並列，AI 分析兩個版本各自想做什麼後，通常用三種方式合併：

1. **二選一**：判斷出朋友那版才是最新邏輯，或你原本的寫法有 bug 剛好被朋友修好了，就捨棄舊寫法只保留正確的一邊。
2. **兩邊都留**：Git 比較死板，只要同一行被兩個人動過就判定為衝突。例如 Gary 在清單最後一行加了「理財分類」、朋友也在最後一行加了「日常分類」，Git 以為是衝突，但 AI 看得懂這只是在新增不同項目，就把兩個都保留湊進同一個選單。
3. **打掉重練幫你改寫**：兩人改的邏輯硬拼在一起程式很可能出錯，AI 看懂雙方目的後乾脆把那段重寫一遍，用新寫法把兩邊功能順順接起來。

**但 AI 終究不知道你的產品規劃。** 如果雙方改的邏輯在產品邏輯上互相衝突，AI 就會卡住不知道該選哪種方法。這時 vibe coder 要做的不是自己下去改程式，而是**給出明確的產品決策**，例如：幫我解掉這個 conflict，分類列表的邏輯以朋友的為主，但把我的「理財分類」移到右邊的進階選單裡。把取捨方向與規則講清楚，AI 就會挑最適合的合併方式。

## AI 改壞了怎麼救

| 情境 | 動作 | 說明 |
|---|---|---|
| 還沒 commit | `restore` | 一鍵讀檔回到上一次的存檔點，就當作剛剛 AI 亂寫的事完全沒發生過 |
| 已經 commit | `revert` | **不是**偷偷刪掉歷史紀錄，而是新增一個反向的 commit 去抵消前面那次錯誤的改動 |

`revert` 在協作專案裡特別安全，因為所有人都能在歷史紀錄裡看到「有加錯東西、然後又被抵消掉」的完整過程，不會覺得某段進度憑空消失。

這些指令都不用硬背——發現 AI 改壞時直接說「剛剛這次的改動我不要了，請幫我回到上一個正常的版本」，AI 會自己判斷現在的狀態，決定該用 `restore` 還是 `revert`。

## 收束：你只要有能力指揮

Git 對非技術背景的人像一堆難背的火星文指令，但你只要能把這些概念對應到它幫你解決什麼開發問題，就會非常好理解。不必今天就逼自己變成 Git 專家，但要聽得懂：當 Claude 或 Cursor 問「要不要 commit / 要不要開 branch / 要不要發 PR」，它其實是在問——這次開發你要不要先存檔？你要不要開個空間來隔離風險？你要不要把寫好的東西交出去給別人檢查？聽得懂這些判斷，用 AI 開發就會踏實很多。
