## 問題：時間都卡在來回修正

不管用哪個 model，產出總有些地方沒想清楚——漏掉 corner case、邊界沒處理、跑起來一堆 bug，然後你回頭說這裡不對那裡要改，改完又冒出新問題。作者認為 vibe coding 的時間其實全部卡在這上面。

他的解法是 cross model review：讓 Claude 跟 Codex 彼此自動 review，找出各自的盲點。作者本來是 Claude 死忠用戶，後來覺得它降智轉去用 Codex，用久了發現 Codex 也有缺點，於是想通「幹嘛非得二選一」，兩個都要、各取所長。

## 兩個模型的分工

作者的配置是 Claude 當主力（大部分討論與實作計劃），Codex 當 reviewer 專門挑錯。他的形容是：

- **Claude** 像班上第二名的學生，合作愉快、討論細心，丟一個想法它能理解你，有時還給驚喜；但偶爾粗心，有些細節沒顧到、狀況想得不夠周全。
- **Codex** 很無聊、對話沒什麼火花，但就是穩，尤其處理後端複雜邏輯時特別可靠，該想到的都幫你想到。

作者強調兩者職責沒有對錯、單純看個人偏好，也完全可以反過來讓 Codex 主導、Claude review（Codex 還比 Claude 便宜不少）。他的原則是：**reviewer 這個位子要找那個無聊但永遠不出錯的人**，把關要的是穩不是有趣。

**為什麼不讓 Claude 自己再檢查一遍？** 因為模型訓練時的側重點不同（例如 Codex 做前端常給出讓人吐血的設計，Gemini 或 Claude 在這方面較好）。更根本的是：一個 model 寫出來的東西，它自己讀起來一定都很合理，因為它是用同一套腦袋、同一套假設在檢查自己，必然有盲點。就像你自己寫的東西讀三遍還是有錯字，拿給別人一眼就看到。

## 從人肉橋樑到系統

最早的做法完全純手工：Claude 寫完 plan 整份複製貼到 Codex 請它 review，把 feedback 複製回 Claude 請它修改，改完再貼回 Codex 複查，來回好幾輪直到兩邊達成共識。

作者沒做嚴謹的 A/B test，但體感是程式碼架構變乾淨、技術債變少、後期修 bug 頻率非常低。

問題是**他自己成為了生產力瓶頸**。一條線還好，但多功能並行開發要用 worktree，同時三四條開發線在跑時，每條線的 plan 都要手動跑好幾輪 review，全部卡在複製貼上的速度，光切換上下文就快瘋了。而且他會偷懶——plan 比較小、看起來簡單就瞄一眼跳過 review，結果出包的偏偏就是那些「應該沒事」的東西，省下的五分鐘後面要花一兩個小時擦屁股。

結論是：**人的紀律靠不住，與其逼自己每次都記得，不如把這件事做成系統，讓它每次都自動發生，完全不依賴當下想不想做。**

## 出版社比喻

作者用出書流程說明系統的三個角色：

- **作者**負責寫稿 → 對應 Claude
- **門口守衛**只認一件事：稿子上有沒有蓋「審核通過」的章，沒蓋就不准送出這道門 → 對應 stop hook
- **審稿人**跟作者來回討論，作者要嘛改掉、要嘛拿出理由反過來說服審稿人，兩人都同意了審稿人才蓋章 → 對應 Codex
- **審核通過的章** → 對應寫在檔案結尾的一段文字，作者稱之為 marker

老闆（你）從頭到尾只會看到最後那份定稿，中間的爭吵與修改過程完全不用管。

## 兩塊組件

**第一塊：stop hook（守衛）**。這是 Claude Code 的機制，每次 Claude 想收工、要把控制權交還給你之前就會被觸發。觸發時它有兩個選擇：放行讓這輪正常結束，或擋下來並塞一段訊息回去，讓 Claude 不結束、把那段訊息當成新指令繼續做事。**這個能擋下結束、還能塞提示詞回去的能力，就是整套系統成立的關鍵。**

它在這套系統裡做三件事：

1. 掃這一輪有沒有寫出一份 implementation plan
2. 有的話，翻到該檔案結尾看有沒有審核通過的 marker
3. 沒有 marker 就擋下這次結束，塞一段話回去叫 Claude 去跑 codex review skill

所以 stop hook 只負責攔，不負責審。

**第二塊：skill（審稿方法論）**。Claude 被攔下來後會讀這份 skill，skill 指示它調用 Codex CLI tool 請 Codex 幫忙 review，直到 Codex 放行後再回頭在檔案結尾蓋上 marker。

**為什麼拆成兩塊？** 單純解耦。攔截失敗或攔截後行為異常就修 stop hook；review 品質不佳就改 skill 裡的方法論，兩者各司其職。中間靠 marker 這個暗號接起來：守衛只認 marker，看到就放行；而 marker 只有 skill 審過了才蓋得上去。

## 完整流程五步

1. Claude 寫完一份 plan，想結束對話
2. 觸發 stop hook，一掃發現檔案尾巴沒有 marker，擋下
3. Claude 收到 stop hook 預設好的指令，啟動 codex review skill，呼叫 Codex 請它 review
4. 兩邊一輪一輪過招，該修的修、該反駁的反駁，直到雙方有共識且 Codex 回覆通過
5. Claude 在檔案尾端蓋上 marker

作者的任務就是掛在那邊等它們自己討論完畢，然後進入實作。

## 通過標準：共識，不是輪數

**標準不是「來回討論滿三輪就算過」，而是兩個 model 真的達成共識。** Codex 不能為了想趕快結束就隨便點頭放水，Claude 也不能為了想趕快過關就假裝問題不存在。每一個爭議 Codex 都要明確表態：要嘛被說服、承認你說得對，要嘛堅持並講清楚它到底在堅持什麼。有爭議就繼續吵，沒有達成共識就不准收工。

作者一開始的版本設過「最多三輪」的上限，後來發現這個上限會逼出很糟的結果：到了第三輪不管問題解決了沒，它都會為了結束而假裝沒問題。這完全違背初衷，所以他把上限拿掉，只認共識這一個標準。

## 收斂的關鍵：從頭到尾只開同一個 Codex 對話

已知風險：丟一份其實已經很好的實作計劃給 AI，它總能挑出一兩個漏洞——要嘛是它沒有足夠 context 而把某些設計決策當成 bug，要嘛是過度追求完美導致 over engineering。底層原因是大型語言模型有 sycophancy 傾向，你給它什麼任務它都使命必達，請它 review 它就會想辦法找出幾個問題。

**這套流程能收斂而不無限拖下去，關鍵在於從頭到尾只開同一個 Codex 對話，不是每輪都重開新 session。**

- 每輪重開新 session：每次都是冷啟動什麼都不記得，每輪都可能挑出一堆新的、不重要的小毛病，永遠挑不完也永遠改不完，變成過度設計沒完沒了。
- 同一個對話：它記得上一輪講過什麼，所以第一輪就把主要問題一次抓出來，下一輪是來驗收改對了沒，往共識收斂而不是重新發明一堆新問題。

缺點是第一次若漏看可能漏掉關鍵 bug，但作者認為這樣已能解決 80% 的問題並省下大量時間——他要的是 Codex 一次抓出真正重要的問題，不是陪他玩到天荒地老。

具體怎麼做作者說有點枯燥，可以直接問你的 AI，他也把 codex review skill 放在 Patreon 文章裡。

## 具體案例

假設叫 Claude 規劃一個電商網站的下單功能，它給你一份寫得漂漂亮亮的 plan，其中一條寫著「這個功能必須保證不會超賣，同一件商品不會賣給兩個人」。聽起來很完整，但仔細看整份 plan 從頭到尾都沒寫具體處理方法——只剩最後一件時兩個人同時按下下單，那一瞬間到底要怎麼處理？誰先搶到？另一個怎麼被擋下來？

原因可能是 Claude session 的 context 過長導致遺漏細節，或是模型處理這種 corner case 本來就容易粗心。換 Codex 或另一個模型用第三方角度客觀審核，就有更高機率發現這個盲點。

## 往上拉一層：這是在建自己的 harness

作者強調他做的不只是「找第二個 AI 來審稿」，而是根據自己的使用習慣替自己建一套 harness——包在 AI 外面的那一整套工作環境，包含你給它的限制、流程與工具。就像老闆幫員工搞個舒服的辦公室、零食區、休息區，目標是提高工作效率。

回頭看這套流程的三個元件：

- **stop hook** 是強制約束，逼流程一定要走完，不給偷懶空間
- **skill** 是工作方法，定義審核的流程與方法
- **marker** 是兩者之間的握手暗號

Cross model review 只是這套 harness 裡的一塊。**同樣的思路可以拿去包任何一件「你本來就會做，但常常會偷懶跳過」的事。** Harness 不用複雜，就像好產品不用花俏，可能非常低調簡單，但只要能解決生活中不起眼的小摩擦就很有感——作者這個 stop hook 只是解決來回複製貼上的小問題，就足以大幅提高工作效率。

作者最後的框架轉換：當 AI 一直產出不夠好的東西，與其每次自己跳下去手動救，不如回頭問「我的系統為什麼會讓這種東西過關」，然後從系統層面把漏洞封殺掉。

對 solo developer 這件事特別重要——沒有同事幫你 code review、沒人幫你把關、所有的洞都得自己扛。但你可以建一套系統，讓它扮演那個永遠不會累、永遠不會偷懶的同事，24 小時在後面幫你守著。一個人也可以有一整個團隊的把關。
