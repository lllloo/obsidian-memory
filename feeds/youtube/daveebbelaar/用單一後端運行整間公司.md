## 核心主張：被低估的不是 AI，是管線

作者 Dave Ebbelaar（AI 工程師、Data Lumina 創辦人，該公司年營收七位數）觀察到社群過度聚焦在 coding harness、模型版本、要用哪些 skill，卻忘了「先想清楚該建什麼」。他認為真正的 low-hanging fruit 是**用自訂軟體取代工具、用自訂腳本串接工具**——這在兩年前不具經濟效益，現在因 AI coding agent 而變得划算。

值得注意的是：這套跑遍全公司的系統**本身用到的 AI 非常少**。

他以客戶經驗佐證這點：做過大量 LLM pilot，有些上線跑了三年，但也有不少失敗——失敗原因不是技術不到位，而是 use case 本身不值得。很多案子如果一開始只是「把兩個系統接起來、完全不用 AI」，對客戶的幫助反而更大，不會拖到三個月後才發現方向不對或預算燒完。

## 兩種自動化類型

公司裡能自動化的事情，本質上只有兩類：

- **觸發式（trigger-based）**：Stripe 進來一筆新付款要寫進 Airtable 或會計系統；有人透過 Calendly 預約通話，要在 CRM 準備好一筆 deal 給業務；表單送出觸發 onboarding flow。
- **排程式（scheduled）**：每週一早上 9:00 產出 pipeline 報表；每晚同步訂單。

隨著公司越 AI-first、越 data-driven，這兩類需求只會越來越多。

## 管線稅（plumbing tax）

要自己做哪怕最簡單的自動化，前置成本包含：

- 一台伺服器讓程式跑
- 自訂後端與 API（例如 FastAPI）
- 部署策略 / CI/CD（push 後自動部署）
- 認證、API key 與 secret 的安全管理
- webhook endpoint 本身
- 測試、除錯與驗證的方法

這就是過去十年 Zapier、make.com 這類工具的價值所在——它們替你付掉管線稅：OAuth 登入或貼 API key、選觸發器、拉兩三個步驟，自動化就成了。作者自己公司過去幾年也是這樣做，理論上 Python 寫得出來，但不值得。

轉折點在於：**管線稅現在付得起了，而且只要付一次**。第一次要把左邊那一整排東西建好會花時間，但如果結構與 design pattern 設對，之後每個新工作流大約 99% 的工作已經完成——「我現在要接 Calendly 而不是 Stripe，一樣進 Airtable」就只是一個 prompt 的距離。

作者坦言這件事他拖延了很久，直到幾個月前才動手，事後認為是最好的決定。

## Bottom-up vs. top-down 的 AI 轉型

- **Bottom-up（個人層）**：一個人透過 Claude Code、Codex 等 harness 變快。即使能把任務丟到背景跑，本質仍是 user-centric——人要坐在鍵盤前。
- **Top-down（公司層）**：從公司的系統、流程、人與資訊流動出發往下設計，部分流程甚至可以完全不需要人在迴圈裡。公司（至少初期）跑**一個**集中式後端，所有人與團隊接上它，靠 trigger 與 schedule 在沒人在場時自行運作。組織夠大時才談拆分。

完整的 AI 轉型兩者都要：一邊用 coding agent 提升個人產出，一邊持續把工作卸載給這個在背景執行的後端。

## 架構原則：event-driven

系統核心是 event-driven 架構：**任何事情發生時先把 event 持久化**，寫進資料庫。這帶來狀態可查（是否已執行、是否需重試、有無錯誤），也留下一份可回溯的 ledger。

作者強調整套設計是 technology-agnostic：所有元件名稱都可替換，任何語言都能實作；他選 Python 生態只是因為自己是 AI 工程師、資料科學背景。

## 實際技術堆疊

- **來源系統**：Stripe、Calendly、自家網站等，透過 webhook 與 API call 接入
- **網域**：Cloudflare
- **部署**：一台 Hetzner VPS（規格拉大），整間公司一台就夠；上面跑 Docker Compose stack、Grafana dashboard
- **安全**：防火牆保護，只能透過 VPN 加專用 IP 位址存取
- **入口層**：Caddy 負責 HTTPS 與網域設定，並放行特定 IP
- **中央層**：FastAPI + Celery
- **佇列**：Redis queue 承載 event-driven 的排隊，Celery worker 取件執行
- **可觀測性**：Grafana 儀表板 + Sentry（應用錯誤記錄）
- **資料庫**：Supabase（此部署用雲端版，亦可自架），同樣設嚴格 IP 規則
- **外部服務**：Stripe、Slack、Close（CRM）、其他 LLM API

作者形容這只是冰山一角，而且幾乎全部屬於一次性的管線稅。

## 六大元件分類

系統跑的東西可歸為六類：intake（進料）、state（狀態）、execution（執行）、integrations（整合）、operations（維運）、delivery（交付）。

作者刻意示範**檔案結構**而非逐行程式碼，理由是：實作與程式碼已經不是 secret sauce 了，**架構才是**——理解架構後就能交給 AI coding agent 用任何語言實作。

## 案例一：課程購買的觸發式工作流

Data Lumina Academy 有數千名使用者，免費產品與付費課程之間有自然的 ascension path，後端要處理註冊、付款、email、CRM 狀態與提問。以六週的 AI 工程課程 Gen AI Accelerator 為例：

1. 使用者在網站購買，付款發生在 **Polar**（性質類似 Stripe 的金流商）
2. Polar 依設定送出 webhook（訂單／購買建立時），打到自建後端的 `api/webhooks/polar.py`
3. 事件先持久化進資料庫（經 FastAPI endpoint → Redis queue）
4. Celery worker 取件，執行對應 workflow

workflow 本身放在 workflow 資料夾下、各自一個子資料夾，內含 `__init__.py` 與一份 **workflow schema**。這份 schema 是關鍵：整個 code base 極度剛性（rigid），統一 schema、嚴格驗證，因此 AI agent 每次新增自動化時**不需要自己決定檔案放哪、用什麼 pattern**。作者說這套結構已經打磨三年，也是所有客戶專案的核心。

Gen AI 產品購買 workflow 的節點串接（node config 中每個節點都指向下一個，並帶有描述）：

1. **normalization**：正規化輸入
2. **Drip**（email 行銷平台）：更新狀態、打 tag、寄出 onboarding email
3. **Circle**（課程平台）：邀請成為 academy 成員並套上產品 tag
4. **Close**（CRM）：建立記錄，追蹤從免費到付費的所有帳號
5. **Airtable**：記錄銷售
6. **Slack**：往專用頻道發通知，例如有人購買產品時通知本人

由於節點之間就是純 Python，中間可以放任何處理。

## 案例二：每日營收同步的排程式工作流

用 Celery worker 執行 cron job，**每天早上 7:00** 跑一次 sales sync：把 Data Freelancer 與 Gen AI Accelerator 兩個課程的資料同步整合進 dashboard，用來追蹤日／月營收數字。視覺化端用的是 Airtable 的 view。

作者指出這實質上讓後端同時變成自家的 data platform／data layer——排程拉資料、送進視覺化工具。
