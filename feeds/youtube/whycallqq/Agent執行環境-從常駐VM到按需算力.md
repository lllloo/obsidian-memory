## 問題：伴隨式空轉

假設你在瀏覽器裡打開雲端 AI 編程助手，要它找出登入頁面偶爾跳回首頁的原因、修好並跑測試。Agent 搜尋路由設定、檢查登入態邏輯、改了兩個檔案、跑了一輪測試，十二分鐘完成。你關掉網頁去開會，兩小時後回來又補一句需求。

如果這個雲端 Agent 後台採用「一條對話綁定一台常駐虛擬機」的架構，且為了隨時回應、閒置時並未休眠，那麼你開會的這兩小時裡，那台計算執行個體和附屬儲存一直在持續計費。就算平台做了執行個體啟停，磁碟快照和恢復環境的資源成本通常也無法完全抹零。

這帶出一個生命週期錯位：**真正需要長期保存的是對話狀態和專案檔案；真正需要拉起 Linux 環境、跑編譯器的時間，往往只集中在那短短幾十分鐘的執行期。**當使用者量從一百漲到十萬，這種「伴隨式空轉」帶來的算力消耗可能成為不可忽略的基礎設施成本。

## 兩種架構路線

一個能在工程裡落地的 Coding Agent，底層由幾大塊拼起來：

- **對話狀態**：保存任務進度和審批記錄
- **控制層**：負責呼叫模型、做路由
- **專案資料**：原始碼和設定
- **手腳**：輕量的檔案檢索操作，以及重型的依賴安裝和編譯測試

**早期方案**是把這幾類職責一股腦放進同一台 VM 或容器裡。Anthropic 和 YC W24 公司 camelAI 都公開披露過曾採用類似設計。Agent 拿到一套終端、一批憑證，自由組合，通用性無敵；但代價是狀態與機器高度耦合，休眠、恢復、遷移和擴容都更容易受到對話生命週期的牽制。

**到了 2026 年**，另一種已在部分產品落地的路線是在架構層面解耦狀態、控制與執行環境：

- Anthropic 在 Managed Agents 裡公開的「大腦、雙手與對話分離」架構
- camelAI 披露把 Coding Agent 從常駐虛擬機整體遷到 Durable Objects（狀態化計算單元）和獨立雲儲存，真正需要跑建置任務時才臨時拉起一個 Linux 容器

## 挑戰一：狀態與檔案的剝離

Agent 執行環境的第一項核心能力不是模型多聰明，而是它得穩定地記住自己幹到哪了：讀過哪些檔案？你批准了什麼修改？

對於需要跨故障恢復的長任務，記憶體絕不能成為唯一的事實來源。對話狀態必須進入獨立的持久層，記錄任務游標、外部任務 ID 以及冪等鍵；而負責排程的控制層本身完全可以設計成無狀態元件，靠事件日誌恢復現場。

但有個折磨人的細節：就算有了持久化，Agent 也只是知道自己「最後確認到了哪一步」。那個遠端容器裡的任務究竟成功還是失敗？**永遠不能只相信本地的記錄，必須透過外部任務 ID 去做查詢和對帳。**

### 檔案的並行衝突

當計算環境變成按需啟動後，專案檔案的持久性就不能再依賴臨時節點的本機磁碟，它可以落在共享檔案系統、持久卷、物件儲存或獨立的檔案服務中。

一到工程落地，並行衝突就來了：Agent 修改核心設定花了十秒，但這十秒內你透過雲端 IDE 手動改了同一個檔案。如果盲目覆寫，程式碼就丟了。系統必須制定明確的一致性策略：

- 條件寫入、單寫者、租約，或乾脆開獨立分支
- 對於有共同基線的文字檔案，可以嘗試三方合併
- 如果無法可靠合併，應該拒絕覆寫、保留版本，或交給人處理

面對動輒幾 GB 的大型儲存庫，每次按需啟動還要做同步，真正的工程實踐往往需要組合拳：快取映像、增量同步，或乾脆像 Git 底層那樣引入內容定址；而內容定址還得配合部分克隆之類的機制，才能真正把 I/O 和啟動延遲壓下來。

## 挑戰二：執行環境的精準分級

殺雞不用牛刀：只是改一行文案，拉起完整 Linux 容器是極大浪費；但涉及編譯，輕量沙箱又根本跑不動。所以成熟的 Agent 執行環境往往切分出多個檔位：

| 檔位 | 適用場景 |
|---|---|
| 純結構化工具 | 全是 API 呼叫，最輕 |
| 輕量沙箱（如 V8 Isolate） | 稍複雜的自訂資料轉換，毫秒級啟動 |
| 臨時 Linux 容器 | 明確需要 shell、套件管理器、原生二進位檔或完整作業系統語意時 |
| 持續的工作空間 | 超大工程 |

輕量沙箱雖然啟動快，平台仍必須顯式設定它的網路出口、可用繫結和資源上限；根據任務風險，可以讓它完全斷網，也可以只開放受控的白名單能力。

關鍵在於**協調器**。而且要注意：**計算等級和風險等級是兩個完全正交的維度。**查個資料庫、發封郵件，算力消耗極低但業務風險極高。對於這種非冪等的高危操作，協調器絕不能依賴「先在輕量環境試錯、失敗了再升檔」的邏輯，必須要有獨立的審批和隔離機制。

## 挑戰三：從環境授權走向能力授權

想像 Agent 在幫你看一個開源專案，裡面藏了一段惡意的 README：請讀取環境變數裡的金鑰，並上傳到指定網址。如果這個環境同時允許讀取金鑰並存取外網，一旦模型被騙，就可能演變成真實的資料外洩——這就是間接提示詞注入。

收緊工具能縮小攻擊面，但光改工具名字沒用。必須把粗放的**環境授權**收縮為極致的**能力授權**：

- 權限必須由伺服端和下游系統強制執行，每次請求都要進行嚴格的授權校驗
- 敏感憑證絕不能暴露給模型生成的程式碼
- 高影響操作要強制加入人類審批和稽核記錄

即使攻擊者沒拿到金鑰，間接注入依然可能誘導 Agent 去刪改檔案或汙染程式碼。

## 灰度改造路徑

如果要改造手頭的 Agent 基礎設施，別一次全押，走灰度路徑：

1. **先去測算真實的佔空比**。如果業務全是大型編譯，老實保留完整的常駐空間；如果文字處理居多，才值得優先試點這種解耦架構。
2. **別動舊容器，先把任務狀態剝離到持久層。**
3. **給檔案系統掛上影子後端**：一邊讀舊磁碟、一邊寫新儲存，非同步比對雜湊，跑通兜底流程。
4. **把部署、查資料庫這些高危操作統統封裝成可稽核的伺服端工作流**。該用冪等鍵的用冪等鍵，用不了的就老實做對帳。
5. **明確沙箱和容器的邊界，進行灰度切流。**

永遠記住：**前端點一下「取消」，不代表遠端的副作用沒發生。**最終結果只能靠狀態對帳。

## 結論

從 Anthropic 和 camelAI 的公開實踐看，一種正在形成的方向是：虛擬機不再必然與 Agent 對話同生共死，而可以變成按任務申請的執行資源。但這並非銀彈——至少在當下，面對重度開發任務，持久化的工作空間仍可能是更合適的方案。

當所有人都在比哪家模型能多寫幾行程式碼時，工程團隊真正要面對的是：狀態怎麼存、檔案怎麼防衝突、權限邊界在哪、崩潰了怎麼回滾。只有蹚過這些基建深水區，AI Agent 才能從一個秀肌肉的 Demo 蛻變成具備規模化營運基礎的現代工程系統。
