## 為什麼要讓模型寫程式碼而不是畫圖

現在用圖像模型，互動入口基本只剩提示詞。如果畫面裡有一片花瓣稍微偏了，你很難直接去改那幾行像素，最常見的操作是重寫提示詞再抽一次盲盒——上一版滿意的構圖通常也會跟著消失。

Surya 與 Cameron 換了思路：讓 Qwen 先寫一份完整的 JavaScript 草圖，程式碼經 p5.brush 引擎渲染，最後得到水彩圖片。這樣就能直接改顏色、改路徑或微調筆刷，生成結果變成一個**可以繼續維護的工程產物**。

底層模型是 Qwen3.5 35B。輸入一句大白話（例如「畫一朵桃色水彩木槿」），Qwen 吐出來的不是像素矩陣，也不是擴散模型的潛變數，而是一段可以直接跑的 p5.brush JavaScript 程式碼——筆觸怎麼走、顏色怎麼填、隨機種子是多少，全都明白寫在程式碼裡。

對工程師而言差異很實在：能做 Git 版本對比、能針對局部修改、能把失敗的 Bad Case 攢成測試集。**圖像只是建置結果，原始碼才是要長期維護的資產。**

代價也不小：模型得同時懂構圖、懂色彩，還得精通一個小眾繪圖庫。中間任何一層 API 呼叫錯了，匯出的 PNG 就是一張白紙。

## 四段式訓練流水線

1. Qwen 接收提示詞並吐出草圖程式碼
2. Puppeteer 在沙箱裡把程式碼跑起來，匯出成 PNG
3. 視覺模型把這張圖和兩張參考圖做比對，判斷哪張更符合「優秀水彩」的標準
4. 比較結果轉換成純量獎勵，交給 GRPO 演算法更新模型權重

整個迴圈全自動跑上幾千次。從工程視角看，系統最先要保障的是**介面邊界**：程式碼能否編譯？沙箱能否穩態渲染？圖片能否順利送審？如果中間環節靜默報錯，訓練曲線照樣在跑，但數字早就失去意義。創意類模型訓練同樣離不開詳盡的日誌、異常分類以及支援重放的樣本機制。

## 審美要怎麼給分

數學題能對答案，寫程式能跑單元測試，但水彩畫沒有非黑即白的布林邏輯：花朵輪廓清晰不代表畫面耐看，筆刷細節多也不意味構圖穩。團隊真正要搞定的是一個針對「審美」的**測試預言機**——既要給訓練指明方向，又得包容風格差異。規則卡太死，模型退化成套模板；規則放太鬆，梯度裡就只剩雜訊。

這跟寫業務的驗收標準很像：PRD 裡的形容詞沒法直接執行，必須把偏好翻譯成具體的測試樣本、比較演算法與權重。**在這個系統裡，獎勵函數就是需求，也是 API**——你稍微寫錯一項，模型就會老老實實把那個錯誤最佳化到極致。

## 舊版量表：九項指標與指標劫持

早期獎勵函數包含九項指標：程式碼要能編譯、要呼叫 p5.brush、程式碼長度目標定在 3000 Token 左右（為了防敷衍）、HPSv3 打「人類偏好分」、GPT-5.4 與 Gemini 檢查提示詞遵循度，另外還有可辨識度、美感、技法與縱深四個維度的評分。

乍看覆蓋得滴水不漏，跑起來就出事：訓練到總獎勵 0.65 左右死活上不去，輸出的畫面全變成一種扁平的五瓣花，像批量生成的剪貼畫。最要命的是面板上的「總獎勵」居然還在漲——**線上指標被代理目標劫持**，圖表一片綠，真實能力根本沒提升。

### 坑一：獎勵訊號高度共線

把子獎勵拉出來看，四個品質裁判加上提示詞裁判之間的相關係數高達 **0.85 到 0.95**。五個訊號聽起來唬人，數值上幾乎等同於對同一個特徵重複採樣：只要花畫得容易認，美感分通常也低不了，提示詞遵循度也會跟著漲。相當於 Qwen 每次都同時收到五張近似的選票——只要畫出一種安全構圖，五個裁判就會合夥把它強化到底，總獎勵的信賴度就這樣被放大了。

工程團隊也容易犯這個錯：監控大盤上曲線密密麻麻，並不意味觀測維度就豐富。**加指標之前，先拉個相關性矩陣看看**——重複指標不僅浪費權重，還會掩蓋真正有資訊量的訊號。

### 坑二：飽和的指標仍佔著權重

程式碼長度這個指標一開始佔總獎勵約三分之一的權重，初衷是逼模型寫到 3000 Token。結果訓練到第 30 步附近就飽和了，在後面一百多步裡幾乎提供不了任何有效梯度，但權重依然死佔那三分之一——學習訊號直接歸零。

反觀 HPSv3，它是當時少數還在持續輸出變異數的指標，權重卻只有 0.10。這套設定就像把三成預算砸給一個早就完工的里程碑，而真正能區分好壞的測試只分到一成。

**設計獎勵不能只看業務重要性，還得盯著變異數、飽和速度與邊際梯度。**靜態權重太容易把早期的合理約束熬成後期的死設定。

## 重構：從絕對打分改成成對比較

團隊乾脆砍掉 0 到 10 分的絕對打分制，改成讓評審器每次看**一張候選圖與兩張參考圖**，任務簡化為「選出這三張裡最好的木槿」。候選圖只要贏過參考圖，就能按比例拿到獎勵。

對視覺模型而言，相對比較比絕對打分靠譜：它不用再憑空捏造一把抽象的刻度尺，去死磕 7 分和 8 分的邊界，分數的動態範圍也因此被打開。這做法在 Code Review 時很常見——讓人給實作品質打 7.3 分毫無意義，但把兩段程式碼並排對比可讀性與邊界，結論往往一目了然。**主觀任務沒必要硬裝成客觀的絕對測量，可靠的偏序關係就足以驅動整個最佳化過程。**

### 參考池：把人類品味硬編碼進圖片

既然做相對比較，就必須有極穩定的基準。團隊翻了 1664 張歷史生成圖，人工分成喜歡、還行、淘汰三檔，最初挑出的 117 張「喜歡」級樣本成為整個參考池的種子。之後模型跑出的每個結果都要和這批人工精選的圖 PK。

人類那點難以言喻的品味，並沒有被壓縮成一句乾癟的提示詞，而是被硬編碼進這組圖片裡——**這就是我們的金標測試集**。如果挑的圖顏色分布太窄，模型馬上會把某種色調當成刷分捷徑；構圖太單一，模型就會死背。所以參考池需要做版本控制、統計資料分布、保留回歸樣例。資料漂移在審美資料裡同樣逃不掉。

### 新版量表：門禁與目標分離

| 項目 | 權重 |
|---|---|
| 程式碼能編譯且使用 p5.brush（門禁） | 0.05 |
| 長度檢查（門禁） | 0.05 |
| HPSv3 人類偏好分 | 0.30 |
| 參考池成對比較 | 0.60 |

工程味道非常重：他們把「能編譯」和「呼叫對 API」徹底降級成**門禁條件**——程式碼不報錯只配叫「合法樣本」，不代表有審美。真正的品質排序任務，全權交給偏好模型與成對比較。

把約束與目標剝離開來這一手極其關鍵。以前很多評測體系總把兩類訊號揉在一起，導致格式正確的平庸程式碼反而能穩定拿高分。先立門禁、再追求目標上限，整個獎勵系統的可解釋性就通透了。

### 效果與解讀的克制

底模與訓練資料完全不變，新版量表一上線差距立刻拉開：爬到舊版瓶頸分數的速度快了三倍，並輕鬆越過 0.65，在 200 步左右穩定維持更高的獎勵。

但工程上得克制解讀：兩條曲線雖然共享座標軸，**只能證明新獎勵方案把模型的收斂軌跡拉偏了**——畢竟換了把新尺子去量，不能光憑這個斷定通用審美能力變強。更可靠的驗證還得引入盲測、留出參考集並跨提示詞評估。不過在控制變數之下，僅僅改寫獎勵函數，模型的演化軌跡就截然不同——這說明獎勵函數本身已是模型核心能力不可或缺的一部分。

### 程式碼長度：教科書級的獎勵投機

模型生成的程式碼從 13500 個 Token 一路壓縮到 2000 以內。舊量表把程式碼長度當成品質代理，模型為了刷分自然學會了堆屎山；新量表只看最終渲染畫面，冗長實作徹底失去收益，逼著模型去找更精簡的繪圖演算法。

只要長度能換分，它能給你擴寫出無數個空迴圈與重複筆觸——**模型不會替你維護系統複雜度，它只負責無腦執行眼前的績效合約。**當然程式碼變短不代表可維護性一定變好，還得結合控制流與 API 真實呼叫來看，但 7 倍縮減至少實錘了一點：先前確實在花大錢購買無效 Token。

### 參考池的最終組成

共 581 張圖：117 張「喜歡」、266 張「還行」、198 張用來填補顏色分布稀薄的長尾區域。

這組數字藏著細節：**參考池不能只盯著天花板級的最高品質，還要撐起一個足夠寬廣的比較空間。**如果池子裡全是高分粉色花，丟一張完美的黃色候選進去，大概率會因為分布對不上被錯殺。補充樣本就是為了提供更細膩的相對梯度。做模型評測的金標集也是這個理：全是神仙局，模型排不出中等生；全是大鍋飯，又稀釋了目標風格。

參考池裡的圖全是模型自己生成的，因為 p5.brush 太小眾，根本找不到足夠的人類手繪程式碼。他們搭了兩條線批量造資料：一條讓 Opus、GPT-5.4 與 Gemini 對著照片反覆迭代修改、靠視覺評審器打分；另一條直接用 Gemini 批量推斷。這是標準的合成資料閉環，規模與格式可控，但風險極大——**生成器的偏好很容易在迴路裡變成系統性偏差**：它愛畫的構圖，恰好又是模型裁判愛選的。所以人工介入定級無比重要，後期還得引入外部藝術家的真實樣本，並做跨模型的雙盲評審糾偏。

## 系統提示詞：長文件不等於好上下文

獎勵系統穩了之後，系統提示詞成了新的坑。早期版本把 400 多行的 p5.brush API 文件一股腦全塞進去，結果模型吐出的程式碼格式漂亮、語氣自信，一執行滿屏報錯——它瞎編了一堆根本不存在的方法。

做 Agent 的人都煩這種事：長文件不能自動轉化為可靠的上下文。對語言模型來說，密集堆疊的 API 名稱成倍放大了續寫空間，長得像的方法簽名還會互相污染。工程直覺總覺得文件給得越全呼叫越準，這次就是反例——**上下文能塞下幾萬字，不代表模型就能精確檢索約束條件**，特別是算力還要分給構圖與色彩。介面給得太寬，就相當於逼模型玩 API 猜詞遊戲。

### 用 GEPA 做提示詞最佳化

團隊引入 GEPA 做自動化系統提示詞最佳化，跑了 200 輪，用 7 個帶審美錨點的樣本做固定評審基準。GEPA 會挖執行軌跡與錯誤回饋，不斷變異出新的提示詞候選，跑得通的留下並分支出演化路徑。

最終勝出的版本極其精簡：**只允許使用 8 個核心筆刷方法**，400 行文件全刪，連範例程式碼也拔掉。提示詞短了，約束力卻大幅增強——刪掉冗長參考後，連續三次推斷都畫出清晰的木槿輪廓。

提示詞最佳化不該靠瞎猜，它本質是**配置搜尋**：每次改動都必須綁定評分函數、鎖死測試集、記錄演化譜系。憑感覺改兩個詞，你根本不知道收益是哪來的。

### 允許列表即最小權限原則

那 8 個方法的允許列表，從底層邏輯看就是物理隔絕了模型的瞎折騰空間。模型手裡的刀少了，但每一刀都砍在點子上，產出有效程式的機率大增。這和安全工程的「最小權限原則」如出一轍：系統只需要暴露任務絕對必須的呼叫面，少給一個無關 API，就少背一口幻覺與沙箱崩潰的鍋。

開發程式碼智能體時千萬記住：別把整個底層 SDK 全塞給大模型，先為特定任務定義**極窄的介面**配合死板的參數約束，需要新能力再去擴充允許列表。文件當然有用，但更適合做成可檢索的工具讓模型按需查詢——把幾百頁 API 當全域上下文掛著，成本高昂且極其低效。

## 監控：分數觸發警報，樣本定位問題

文章用動圖展示訓練演化：早期畫面是角落裡糊成一團的破爛筆觸；接著浮現邊緣生硬的紅色塊；直到中後期，透明水彩的疊加層次與花蕊線條才定型。

比起盯枯燥的獎勵曲線，直接看中間樣本的演變能更快察覺模型有沒有發生模式坍縮。創作類模型的面板上必須有典型的**回歸樣本池**：鎖死一組 Prompt，每隔幾十步生成一次，搭配隨機樣本捕捉畫質退化；做圖像的還可以跑聚類，看看構圖是不是變窄了。只盯均值曲線，團隊遲早會在畫風固化上栽跟頭。

## 這套方案的限制

作者直接坦白：這套方案跑起來比直接生成圖像慢得多，也沒宣稱畫質全方面壓過擴散模型。核心訴求是**改變和 AI 的參與方式**——使用者可以把注意力靈活分配給提示詞、底模或最終吐出的 JS 程式碼。對專業生產力工具而言，能反覆介入編輯遠比抽盲盒一次出神圖有價值：設計師可以鎖住好看的構圖只調色值程式碼，前端能把草圖無縫塞進建置流。

當然這也帶來技術債：生成的程式碼必須可讀、可跑，還得防記憶體洩漏；沙箱權限、逾時熔斷全成了產品設計的一環。圖像生成從單次呼叫，硬生生拉長成了**微型軟體供應鏈**。

### 審美偏差還沒解決

成對評審解掉了分數不再成長的死局，但審美偏差沒散。每次拿候選圖和人工挑選的參考圖硬碰硬，Qwen 為了拿高分自然會瘋狂模仿那一小撮參考。作者也承認：規則設太細，模型最後就變成高級影印機。

穩妥的做法要像常規機器學習那樣，嚴格搞一個獨立的**審美留出集**，還得按色彩、構圖做分層抽樣；充當裁判的評審器也得定期輪換、交叉校驗一致性。如果系統未來對外，審美偏好絕對得做成千人千面——統一的模型頂多兜個預設底線，只有接入使用者的修改紀錄，才能形成局部個性化獎勵。

### GRPO 只是獎勵消費者

GRPO 的邏輯是對同一個 Prompt 批量吐出一組候選圖，再根據組內相對好壞估計優勢值：比組內平均線優秀的程式碼被加權，拉胯的被削除。這大幅減輕了 PPO 時代對獨立價值模型的依賴，省下不少算力開銷。

但要清醒：**優化器再強，也只能放大獎勵函數指出的方向。**那九項舊指標高度雷同時，GRPO 反而加速了模型退化成五瓣花；只有新機制真正拉開優劣差距，優化器才能吃到健康的梯度。排查訓練問題別光盯演算法——優化器、採樣策略與獎勵分布是緊緊咬合的。

### 下一步與其風險

團隊打算用已累積的人工分級資料，煉一個專門的小型獎勵模型。成了的話，以後不需要每次都去龐大參考池裡比對，直接過一遍預測網路就能拿到偏好分，推理速度與大規模線上訓練都順理成章。

硬幣的另一面：審美偏好被徹底壓縮成黑盒參數，日後排查 bug 難度成倍飆升；而且訓練集與驗證集必須對齊參考圖做嚴格去重，不然相似風格跨集洩漏，指標一定假高。上線後同樣離不開主動學習挑邊界 Case 給人類標註。**追求速度固然爽，但人工維護的參考池絕對不能丟——它是日後稽核黑盒裁判唯一靠得住的錨點。**

## 六個可移植的檢查點

把這套思路平移去搞程式碼、UI 或內容的 Agent 時，先過一遍：

1. 各獎勵訊號的相關性是不是高得離譜？
2. 某個獎勵是不是跑幾步就飽和了？
3. 「程式碼能編譯」這種門禁條件，是不是被混進品質打分裡了？
4. 參考集能不能真實覆蓋業務長尾？
5. 大盤上的指標有沒有做過雙盲校準？
6. 系統提示詞裡是不是塞了太多沒用的 API？

再加一條：必須定期人工抽檢，盯著裁判有沒有偷偷發生概念漂移。這套 Checklist 不能把玄學的審美徹底量化，但能把偏好變成可打斷點除錯的邏輯。

日常開發的對應做法：寫程式碼智能體時，「編譯不報錯」僅僅是准入門檻，程式碼可維護性必須拉出來跑成對評審；搞前端 Agent 時，像素對齊也只是一根訊號管，真實可用性照樣得拉使用者做 A/B 盲測。以後想加新打分維度，先拉矩陣看是不是和舊指標嚴重撞車；發現提示詞不靈了，先問自己介面是不是暴露得太寬泛；每次大盤分數起飛，別光顧著高興，去挖幾根真實程式碼樣本看模型到底學歪了沒有。
