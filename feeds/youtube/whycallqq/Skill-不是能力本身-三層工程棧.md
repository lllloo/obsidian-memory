## 問題：讀懂了說明，卻交不出活

常見情境：Agent 讀懂了說明、知道每一步該怎麼做，能寫大綱、能列步驟、能把中間檔案編得有模有樣；可真要它交付一個能打開的 PPT、跑通一輪測試，或改完一個真實專案，它就卡住了，等來的永遠是半成品。

問題不在於 Skill 沒用，而在於**經常把一份 Skill 誤會成完整的能力**。Agent 真正幹活靠的從來不是單薄的一層，而是三層工程棧疊在一起。

影片用三個專案拆這件事：

- **Matt Pocock 的 Skills 合集**：8 月 5 日 X 貼文稱 skills.sh 上的安裝計數已達 1350 萬，並稱該儲存庫曾進入 GitHub Star 排名前 20。截至 8 月 6 日，skills.sh 頁面顯示 51 個 Skill、約 1390 萬安裝量，儲存庫約 20.6 萬 Star，按 Star 降序約在第 23 位。
- **Cloudflare Computer**：要給 Agent 一個能保存檔案、執行指令、隔離任務的工作區。
- **open kimi ppt**：開發者把 Kimi PPT 的公開實作逆向成非官方 Skill，讓 Agent 生成 PPTD 與 PPTX。

## 第一層：Skill 是作業手冊，不是執行保證

按 Agent Skills 規範，一個 Skill 的最小單位就是一個目錄，裡面必須有一份 `SKILL.md`（寫名字、用途、具體操作說明），旁邊可放 `scripts/`、`references/`、`assets/` 等輔助資源。所以 Skill 不能簡單說成 prompt，它更像一份可複用的作業手冊：模型什麼時候該用它、該按什麼流程做、遇到邊界怎麼處理，都可以寫進去，甚至能帶腳本讓 Agent 在需要時執行。

但有個前提經常被忽略：

- 手冊裡寫了腳本，不代表腳本一定能跑
- 目錄裡放了素材，不代表宿主有權限讀取
- 說明裡要求開啟瀏覽器，也不代表當前環境真的有瀏覽器

規範還有一個重要機制叫**漸進式披露**：對話剛開始時模型通常只看到 Skill 的名稱和一句用途描述，等任務匹配上以後才載入完整的 `SKILL.md`，腳本、參考資料和素材則等真正需要時再繼續讀取。這讓你裝幾十個 Skill 時不用一次把所有說明塞進上下文，但它也提醒我們：Skill 解決的是「怎麼把知識交給模型」，不是「怎麼保證模型擁有全部執行條件」。

### Skill 已經開始像軟體套件

Matt 的 Claude 外掛清單列出 25 個正式推廣的 Skill；若直接數整個 `skills/` 目錄，可以看到 35 份 `SKILL.md`，多出來的部分包括仍在開發或未正式推廣的內容。（這組固定 commit 數據不能和 skills.sh 頁面顯示的 51 個混用。）

它有版本、有發布範圍、有不同客戶端的元資料——像軟體套件；但它又不像傳統框架，因為它不一定接管你的程式碼，也不一定提供完整執行能力。Matt 在 README 裡強調這些流程應該小、可修改、可組合：

- **TDD Skill**：不會幫你安裝測試框架，也不保證測試能跑。它把實作迴圈定義為先寫失敗測試，再寫剛好能通過的最小實作，重構放到後續程式碼審查階段。
- **除錯 Skill**：不會憑空製造日誌，也不會替你擁有生產環境權限。它先要求 Agent 建立一個能穩定變紅的回饋迴圈，再重現並最小化問題；接著提出 3 到 5 個可證偽假設，用定向觀測縮小範圍；修復後補回歸測試、清理除錯程式碼，並總結這次問題為什麼漏過了。

所以 Skill 的價值不是把模型變成某個神奇外掛，而是把高手腦子裡的操作順序、判斷標準和踩坑經驗，寫成模型可以呼叫的**程序性知識**。團隊規範、排障習慣、程式碼審查標準本來就很難靠一次提示詞穩定傳遞。

但很多安裝頁面說的「一條指令獲得某種能力」只說對了一半：你確實獲得了一份能力說明書、拿到了腳本和模板，但能不能照著做，仍要回到執行環境那一層檢查。影片的判斷是——**Skill 擁有能力的實作材料，但沒有執行保證**。腳本要跑得動、依賴要裝得上、工具要拿到授權、輸出還要有驗收標準，這些都不是 `SKILL.md` 單獨能解決的。

## 第二層：執行環境決定能不能跑

Cloudflare Computer 目前仍是 Preview，官方文件說得很清楚：API 不穩定，適合實驗、探索和原型，還不適合生產。這個邊界很重要——它不是成熟的生產承諾，而是在嘗試回答更底層的問題：Agent 到底需要什麼樣的電腦？

設計思路是把 Durable Object 裡的 SQLite 當作權威檔案狀態，再透過 `workspace.runtime.exec()` 暴露一個統一執行入口。Agent 不只是拿到一個 shell，而是拿到一個帶檔案狀態、執行後端和隔離策略的工作區。

按截至該期核查時的 main 分支，統一入口背後列出三種後端：

1. **真 Linux 容器**：檔案透過 FUSE 映射進去，可跑真實二進位檔，也有真實網路
2. **在 Worker 裡跑 just-bash**：啟動更輕，但不是完整 Linux
3. **直接跑隔離的 JavaScript 模組**：適合更輕的執行場景

（Cloudflare 8 月 3 日的發布說明只把執行環境概括為 Isolate 和 Container 兩類，所以三種分類是當前儲存庫口徑，不是發布時就固定的分類。）

### 持久化不是免費的

複雜之處在於：檔案由誰持久化、哪個後端可以連網、指令怎麼取消、執行失敗後檔案怎麼回收、結果能否重放——這些都不屬於「模型聰不聰明」，而屬於「模型有沒有一個地方把想法變成動作」。

Cloudflare 自己的基準：在 1 vCPU、6 GB 記憶體的容器環境下，完整安裝一個包含 854 個 npm 套件、36675 個檔案的專案：

| 檔案系統 | 耗時 |
|---|---|
| tmpfs | 34.3 秒 |
| ext4 | 63.9 秒 |
| computerd 的 FUSE | 124.7 秒 |

這不是獨立跑分，也不能直接推出所有任務都會這樣慢；它更準確說明的是：持久化、同步和隔離不是免費的。當你讓 Agent 擁有一個「不會跑完就清空」的工作區，你也在為這個工作區的工程特性付成本。

檔案系統設計文件還提到，當前約 10 GB 的容量與宿主 Durable Object 共享，目標是支援 agent-scale workspace——這份文件標註的是 target design；某個 monorepo 是否適合放進去要看實際體積和檔案類型，公開文件並未直接排除大型 monorepo。

所以執行環境這一層，決定的不是 Agent 會不會說，而是它能不能真的執行、保存、恢復和隔離。

## 第三層：應用層定義什麼叫做完

open kimi ppt 把第三層講透。先說明身分邊界：這是非官方專案，作者明確說它來自對 Kimi Slides 公開實作、PPTD 格式和網頁編輯器前端行為的逆向分析，沒有得到 Kimi 或 Moonshot AI 的官方認可；公開協定一旦變化，它往往也要跟著升級。專案方展示過用 DeepSeek 生成 PPT 的案例，並認為低成本模型也能做出像樣的成品，不過儲存庫沒有提供與 Kimi Slides 的獨立盲測，所以這只能作為專案演示，不能寫成客觀品質比較。

真正值得拆的是它的應用層工作流。這個 Skill 不是只寫一段 prompt 讓模型生成投影片，而是把 PPT 拆成一個可執行流程：

1. 先規劃內容
2. 再生成 PPTD
3. 再校驗格式
4. 再匯出頁面圖片
5. 再做視覺複檢——發現遮擋、溢位、對比度或排版問題以後繼續修

PPTD 可以理解成給 Agent 寫投影片的 DSL，用 YAML 描述主題、版面、元素位置和頁面內容，比直接操作 OOXML 簡單得多，也比把整頁做成一張圖片更容易二次編輯。預設交付不是只有一份中間檔案，而是完整的 PPTD 專案和可打開的 PPTX。

這就是三層的分工：

- **執行環境**回答「能不能跑」
- **Skill** 回答「知不知道怎麼做」
- **應用層**回答「怎樣才算做完」

對 PPT 來說，只生成文字大綱不算做完，匯出一個打不開的檔案不算做完，版面錯位但沒人檢查更不算做完。

### 格式可移植，不代表能力可移植

這份看似可移植的 Skill，完整匯出卻需要 Node.js 18 以上、Python、Chromium 瀏覽器，還需要存取 Kimi 官網與其靜態資源網域。本機編輯器確實只監聽 `127.0.0.1`，但這不等於全程離線——PPTD 內容會透過本機橋接到公開的 Kimi 網頁編輯器裡處理，遠端字型、圖片和編輯器資源也會按頁面需要連網載入。

所以同一個 Skill 複製到另一台機器上，Agent 可以正常讀懂它，卻未必能跑出同樣結果。這是本期最關鍵的反轉：**格式可移植不代表能力可移植；流程能複用不代表交付能重現。**

## Skill 是供應鏈輸入

一個常被忽略的坑：Skill 本身也是供應鏈輸入。官方客戶端實作指南提醒過，專案級 Skill 有機會來自不可信儲存庫，客戶端應該考慮做信任檢查後再載入。

這條提醒不是形式主義，因為 Skill 不只是介紹自己，它還能指導 Agent 讀取檔案、執行腳本、存取網路。規範裡的 `allowed-tools` 目前仍是實驗欄位，不同客戶端支援也不同，所以不能把它當成完整權限沙箱。

裝 Skill 的動作更像引入程式碼依賴：**要看來源、要鎖版本、要審腳本、也要限制權限。**越是能自動執行的 Skill，越不能只看 README 裡寫得漂不漂亮。

## 評估 Agent 的三個字：跑、做、驗

別只問模型夠不夠強，問這三件事：

- **跑**——看執行環境：可持久化的檔案系統、可安裝依賴的執行後端、必要時可用的網路和瀏覽器、出錯後的恢復能力，以及任務之間的隔離
- **做**——看 Skill：流程要寫清楚、所需上下文要夠、異常分支要有處理辦法、團隊規範要能固定下來、多個 Skill 之間還要能組合
- **驗**——看具體應用：交付格式、完成標準、失敗定位、二次編輯，以及視覺、型別、測試或業務規則都要進入交付檢查

三問少一個，Agent 都有翻車風險。模型越強只是把上限推高；執行環境、流程和驗收才把上限變成真正能交付的工作。

## 往後看

Agent Skills 大概率會繼續增長，但真正有用的註冊表不能只展示安裝量，它還應該告訴你：這個 Skill 需要什麼執行環境、會呼叫哪些工具、需要哪些網路網域、產物怎麼驗證、在哪些客戶端和版本裡測過。更成熟的 Agent 平台也不會只比模型排行榜，它們會比工作區、權限、日誌、重放、成本控制和驗收機制。

真正的競爭正在從「能不能生成」轉向「能不能可靠交付」。對程式設計師是好事——當大家不再把 Agent 當聊天視窗，而是當一個可執行系統來設計，軟體工程裡那些老經驗（依賴管理、執行隔離、可觀測性、權限控制、測試回饋、產物驗收）又會重新變得值錢。

影片最想留下的一句：**Skill 不是能力本身，它是能力的施工圖。**沒有執行環境，施工圖落不了地；沒有應用驗收，落地也不等於交付。
