## 問題：錢沒花在寫程式上

- 有工程師統計 Coding Agent 的 token 消耗：讀檔 30–40%、搜尋程式碼庫 10–20%、跑命令看輸出 10–20%，真正寫／改程式碼只占 4–10%——「以為雇了程式設計師，實際雇了個昂貴的圖書管理員」
- Agent 循環內部大量是判斷題：選哪個工具、命令危不危險、上下文留不留，卻一直按「生成文章」的價錢付費
- 九月中旬 Jev 在 X 上刷屏，做的就是把判斷題的價錢打下來

## Jev 是什麼

- 9 月 15 日 TypeSafe AI 發布，定位為 System One 決策模型
- 輸入兩樣東西：一段狀態（如當前對話與工具結果）＋ 一組類型化問題；回傳選項、機率與置信度
- 三種題型，一次請求內所有問題並行回答：
  - **Choice**：從給定清單選一個，附每個選項的機率
  - **Score**：在自訂量表上打分
  - **Noul**：是非題，回傳為真的機率
- 快與便宜的來源：傳統 LLM 逐 token 生成，即使答案只有一個詞也要走完生成流程，再解析、校驗、格式錯還要重試；Jev 直接放棄文字生成，用並行取樣一次算出全部答案，延遲 70–500 毫秒
- 訓練方法 RLCD（校準決策強化學習）：不優化人類愛看的回答，而是優化機率的誠實度——說九成把握就該有九成對
- 價格：每百萬輸入 token 約 0.42 美元（字幕原文為「四分二美元」，確切數字待查官方定價），輸出免費
- LangChain 官方部落格說法：分類任務最快 200 倍、最便宜 400 倍；準確率 67.8%，與 GPT-5.6 Terra 打平，單次成本約七十六分之一。這些是廠商口徑，講者提醒先打折聽

## 路由的成本陷阱：KV 快取

- TypeSafe 內部設計文件開頭問：如果 LLM 沒有 KV 快取，你會怎麼設計 coding agent？
- 文件算帳（上下文 X、生成 Y、工具回讀 Z）：
  - 全程用貴模型：25Y + 5Z
  - 先切便宜模型再切回：3X + 20Y + 8Z
  - 會話一長 X 變大，切換反而更貴，因為大模型要把整個上下文重讀一遍。按文件典型比例，全程用貴模型只有切換方案三分之二的價錢
- 「路由等於省錢」在長會話裡不成立。路由成立的前提：切換後不必重新載入舊上下文，或新會話本來就很短
- Jev 正好踩在這個前提上：做路由判斷時只看當前這一輪的幾百字，不背整個會話歷史，所以它的路由是真省錢
- 文件另一觀察：compaction、子代理、會話重啟這些機制的彆扭，都源自同一根源——狀態被綁死在一份共享上下文裡

## 子任務 token 分布：大頭在閱讀側

| 子任務 | 占比 | 特性 |
|---|---|---|
| 讀檔內容 | 30–40% | 最大的桶，全文視圖常被反覆讀 |
| 搜尋與探索程式碼庫 | 10–18% | grep 結果噪聲遠多於訊號 |
| 命令輸出 | 10–20% | 堆疊與日誌冗長 |
| 系統提示 + 工具定義 | 5–12% | 固定開銷，會話中反覆計稅 |
| 寫程式碼本身 | 4–10% | — |

- 想省錢要讓模型少讀廢話，催它打字更快沒用；許多團隊盯著輸出側優化，方向一開始就偏了
- 外部佐證：微軟 fastcontext 專案分析 GPT-5.4 軌跡，讀檔與搜尋占 56% 的工具呼叫輪次，吃掉主 agent 近一半 token

## 實戰一：模型路由

- LangChain 提供 `ModelRouterMiddleware`：Jev 先判斷訊息難度與類型，再從路由池挑最便宜夠用的模型；機率與置信度留在 agent 狀態裡可查
- 社群專案 `hermes-jev-skills` 更完整：路由池按「難度三檔 × 工作類型五類」排成網格（程式、寫作、研究各有候選），每輪決策 0.4 秒
- 兩個關鍵設計：
  - **shadow 模式**：先只記錄不切換，跑一天看日誌，可靠再開
  - **失敗開放**：Jev 掛掉、逾時或置信度低就沿用當前模型，永不阻塞對話
- 帶「生產、刪除、支付」等風險詞的輪次永遠不往最便宜檔路由

## 實戰二：上下文篩選與壓縮

- 盲壓很難贏過定向壓縮：知道接下來要查什麼，壓縮就容易得多
- Jev 做法：對上下文每一輪問一個 Noul「這段留著有用嗎」。Hermes 實測 71 輪對話 0.95 秒選完，與「按時間保留最近」對比 11 比 4 勝出
- 進階版對每塊內容打四檔分：不顯示／小摘要／長摘要／全文——等於替上下文裝可調節閥門，這次查詢要多少細節放多少，其餘留在會話外、不進 KV 快取、不再重複計稅
- **跨會話交接**：Hermes 測過讓 Jev 寫摘要再交接，召回率反而下降。最後上線方案是「全量對話 1,200 詞 + 找回舊會話的入口，配兩次搜尋」，召回從 58.7% 提升到 75%
- 反常識結論：保留原文加檢索入口，比精心壓縮的摘要更能打

## 實戰三：技能／工具選擇

- 工具定義全塞系統提示是隱形稅：占上下文、還拖累判斷品質（模型本就不擅長高基數的工具選擇）
- Hermes 用 Jev 做技能選擇：377 個技能 2.8 秒挑完；寒暄類輪次直接本地免費放行
- TypeSafe 文件更激進的構想：系統提示只放每個技能的一句話簡介，需要時再動態載入完整 schema。上下文不被污染、成本近零，可內建幾百個工具、幾千份文件，用時才付錢

## 實戰四：安全護欄

- Claude Code、Codex、Cursor 的自動模式裡都藏著一個在命令執行前判斷危險性的分類器，但一直閉源、看不到也改不了
- LangChain 推出 `AutoModeMiddleware`：用 Jev 在工具執行前檢查 bash 呼叫，有風險直接攔下；單次檢查 0.00006 美元、毫秒級延遲
- **安全感知路由**構想：碰不到敏感檔案的子任務可路由到便宜很多的模型；涉及生產環境、支付、刪除的，策略上永遠走可信模型
- 權限判斷從一刀切的人工確認變成可程式化策略：危險命令被攔、低風險操作放行，人不必盯每個確認框，長任務完成率也跟著提升

## 三條實戰經驗（來自 Hermes 文件）

1. **寫清必要與加分**：問題裡多寫一句「什麼是必須的、什麼只是加分項」，準確率直接翻倍。例如選技能時寫清「完成任務必需」還是「僅僅相關」
2. **閾值分檔**：高置信自動執行；中置信請求確認或升級到強模型；低置信轉人工。閾值寫在程式碼裡可審查可調——改儀表板標籤與刪資料庫，門檻天差地別
3. **候選數上限**：單個 Choice 最多 255 個候選，超過先粗篩再精選；若機率攤得很平，代表候選描述區分度不夠，回去改描述

## 限制與風險

- 「Jev 不會幻覺」只在窄義成立：它不會回傳 schema 之外的答案，但會自信地選錯合法選項（該選 technical 的工單選了 billing，格式沒問題、錢照樣退錯人）
- 只給數字不給理由，需要稽核留痕的場景要自己補一層
- 所有跑分都是廠商自測，尚無大規模第三方複現
- 英語是主場，中文內容要用自己的資料先測再上線
- 早期存取階段的模型不要押成架構地基：Jev 可被替代，但「決策層」這個設計思想會留下

## 生態與趨勢

- 瀏覽器自動化專案 `jev-ultrafast`：每步決策 0.4 秒，在 Google Flights 從蘇黎世訂到倫敦全程 7.1 秒
- Pydantic AI、LangChain 已接入；社群 48 小時內做出 MCP server 與開源復刻
- 正在成形的架構：一個貴模型負責真正難的問題，一群便宜的決策模型與程式碼負責判斷、檢索、路由、護欄；每次判斷都被記錄、評估、稽核，成為工程上的一等公民
- 評估 Harness 水準可能只看一件事：環路裡每一步，它有沒有問過「這一步真的需要大模型嗎」

## 落地建議

- 別一上來就圍繞 Jev 重構 agent
- 找一個現在靠慢 LLM 呼叫撐著的判斷點，或一個老是寫錯的正則；給 Jev 最小的狀態與明確的候選，把它的機率與現有結果並排記一週
- 證明配得上這個分支後，再把更多判斷交過去
- 核心一句話：生成很貴、判斷很便宜，別把兩件事交給同一個模型做
