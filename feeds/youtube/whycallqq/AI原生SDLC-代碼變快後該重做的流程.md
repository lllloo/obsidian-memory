## AI 原生 SDLC 是什麼

AI 原生 SDLC 是一套圍繞 Agent 重寫的軟體交付流程：人與 Agent 從需求開始協作，經過設計、實作、測試、部署與維護，每一步留下可追溯的輸入與輸出，關鍵風險仍由人判斷。Anthropic 將這條鏈路概括為 Plan、Design、Build、Test、Deploy、Maintain 六個階段，並為各階段保存意圖、規格、計畫、測試與事故紀錄。

重點在於讓工作流本身能被 Agent 讀取、執行與驗證：需求寫清楚 Agent 才能計畫，驗收條件寫清楚測試才能判斷，生產訊號接回來下一次任務才有依據。模型只是執行層，流程才是系統的骨架。

### 與「AI 助手」的差別

多數人現在仍把 AI 當更聰明的程式碼補全工具——寫函式時問一句、報錯時貼日誌、評審時讓它解釋一段程式碼。這有價值，但沒有改變交付的主要結構。

AI 原生 SDLC 讓 Agent 參與一個有邊界的任務閉環：讀規格、提出計畫、在受限環境裡修改、執行檢查、提交證據、等待人或規則批准。兩者差別落在**責任交接**上：助手給的是建議，工程師自己把建議帶進流程；流程成員要對明確的輸入產出明確的工件。

### 三份工程工件

- `intent.md`：這次要解決的使用者問題與邊界
- `spec.md`：輸入、輸出、約束與驗收條件
- `plan.md`：準備修改的模組與執行順序

測試結果、部署紀錄與事故複盤留在後面，成為下一次任務的上下文。這些檔案不需要長——一個退款入口的意圖可以只寫清角色權限、金額上限、稽核要求、冪等語義與回滾方式。文件在這裡記錄決策、不重複程式碼，讓人和 Agent 站在同一份事實上工作。

## 為什麼生成變快不等於交付變快

GitLab 提出過一個衡量單位叫「**被接受的變更**」：改動經過環境準備、自動檢查、人工複核、上線觀察與責任確認後，被團隊接受進入系統。使用者不為 PR 數量付費，業務也不為程式碼行數付費。

AI 原生 SDLC 的總成本包括需求澄清、生成、環境、驗證、評審、修復、治理與維護——程式碼生成只是其中一項，而且正在變得更便宜。團隊若只盯生成速度，很容易忽略後面耗時更久、出問題代價更高的環節。

Agent 可以並行處理多個任務，但 CI 執行器、測試環境、人類評審與發布窗口都有固定容量。生成端一旦跑得比驗證端快，待審 PR、待跑測試與待確認的風險就會排隊。更麻煩的是速度會**同時放大好需求和壞需求**：原先含糊需求要幾天才造成返工，現在可能在半天內變成一批看似完整的改動。

### 三家公司的實測數字

**Amplitude**（公開複盤，公司自述數字）：接入 AI 開發工作流六個月後，PR 數量提高到三倍，PR 週期從 5.2 小時降到 44 分鐘，前端 CI 從約 30 分鐘縮短到 3–4 分鐘，月度 Bug 報告從 715 降到 319。整條交付管線都在擴容——候選改動增加，驗證與評審馬上會頂在前面。

**Stripe 的 Minions 系統**：這些 Agent 每週產生並合併超過一千個完全由 Agent 撰寫的 PR，但仍由人類評審。它們執行在隔離且預熱的開發環境中，確定性執行 Git、Lint 與測試，還能從三百多萬項測試中選擇與改動相關的檢查。隔離環境減少任務互相污染，預熱減少啟動等待，相關性選擇控制執行時間。結論很直白：高吞吐的 Agent 背後，站著一套高吞吐的環境、測試與審查系統。

**Spotify 的 Honk**：已生成超過 1500 個合併到生產環境的 PR，部分遷移任務節省 60%–90% 的時間。他們也記錄了限制——上下文不完整時 Agent 會交出無法合併的結果；程式碼庫缺少統一標準時同類錯誤會反覆出現；缺少自動化測試的區域，驗證仍要回到業務團隊手裡。Agent 能替你做重複勞動，卻無法補上團隊沒有結構化記錄的知識。

### 四個常見瓶頸

1. 需求不清楚時，Agent 會高效實現錯誤目標
2. 驗證不足時，通過編譯的程式碼也無法證明業務正確
3. 環境與上下文混亂時，任務會卡在依賴、權限與歷史約定裡
4. 治理缺位時，團隊無法放心讓 Agent 接觸高風險操作

## 怎麼做

### 意圖：先寫一份足夠短的說明

要回答五件事：服務誰、使用者在什麼場景遇到問題、改動允許碰哪些模組、哪些行為絕對不能發生、怎樣算任務完成。驗收標準要能被測試或人工觀察，不要只寫「體驗更好」「效能更高」。

「優化退款流程」太寬，可以改成：營運角色可在 30 天內發起退款、金額不得超過原支付金額、重複請求只能生效一次、所有操作要寫稽核日誌、失敗時提示人工處理。

### 計畫先於程式碼

別急著讓 Agent 直接改倉庫，先讓它交一個計畫：哪些服務會受影響、準備改哪些檔案、依賴哪些介面、打算跑哪些檢查、最大風險在哪裡。計畫偏了，工程師幾分鐘就能拉回；程式碼改完才發現方向錯，清理成本高得多。Plan 階段的價值就是把昂貴的返工提前到最便宜的時候。

小改動的計畫可能只有十幾行；涉及資料遷移、權限變更或跨服務協議時，計畫應該補上灰度方式與回滾步驟。

### 上下文工程

把最有價值的資訊從聊天紀錄與個人記憶裡拿出來，放進能檢索、能更新、能引用的地方：服務邊界、介面契約、領域詞彙、程式碼規範、依賴關係與安全規則。

實務上可以從一份服務地圖開始：這個服務依賴誰、哪些 API 對外承諾相容、核心資料怎麼流、哪些測試覆蓋關鍵路徑、哪個團隊負責。再把倉庫級規則寫進固定檔案，讓 Agent 每次執行都能讀取。

### 環境可複現與隔離

上下文還包括環境：依賴版本、啟動腳本、測試資料、臨時憑證、模擬服務、日誌入口與網路限制，最好能用程式碼或設定複現出來。否則 Agent 可能在本機跑通一份偶然成立的結果，到 CI 或生產預覽環境又失敗。

每個任務盡量在獨立工作區與短時憑證裡執行，避免多個 Agent 覆寫同一份狀態，也避免測試意外存取真實資料。**先讓一次任務可以穩定複跑，再談同時跑一百個任務**——可複現性是規模化自動化的最低門檻。

### 把正確性定義在更早的位置

Agent 很擅長寫出「像樣」的實作，也能補一批表面完整的測試。團隊要在更早的位置定義正確性，尤其是**業務不變量**：訂單金額不能重複扣、租戶之間不能互相讀取資料、庫存不能變成負數、遷移前後關鍵欄位要保持一致。

測試要分層：改純函式時快速單元測試就夠；改服務介面時需要驗證契約；觸及支付、權限、資料遷移時，再加完整鏈路與人工批准。

### CI 按風險分流

系統可以根據改動檔案、依賴範圍與標籤選擇不同檢查路徑：文案與樣式改動走快速檢查；公共 API 變化跑契約測試；支付、權限、刪除與資料遷移進入更嚴格的佇列並要求部署前人工確認。同時要盯 CI 的排隊時間、失敗重跑與測試穩定性——它們都會影響 Agent 的有效吞吐。

### 評審轉向證據判斷

Agent 產出的 PR 可能更長、更密集，逐行讀完並不經濟。一個可評審的 PR 應該自帶證據：關聯哪條意圖與規格、影響了哪些介面、跑過哪些測試、哪些檢查還沒覆蓋、風險等級、如何發布、出問題怎樣回滾。

低風險任務可由規則與抽樣評審覆蓋；高風險任務需要業務負責人、安全負責人或資深工程師參與。人類評審沒有退出流程，它從**逐行朗讀**轉向**證據判斷與風險批准**。

### 能力與權限分開

Agent 可以有讀取倉庫、執行測試、建立草稿 PR 的權限；合併主幹、修改基礎設施、存取生產資料、觸發支付操作則應放在更嚴格的規則下。權限越高，所需的日誌、審批與回滾能力就越強。

Anthropic 的安全實踐提到確定性檢查、Agent 審查、權限隔離與重要節點的人類門控。放到一般團隊就是：最小權限、短時憑證、完整稽核、高風險人工批准。每一次工具呼叫都應留下誰發起、做了什麼、依據是什麼、結果如何的紀錄。

### 生產訊號回寫

部署完成後任務還沒結束。使用者行為、錯誤率、延遲、業務指標、告警與事故複盤，都會告訴團隊這次改動的假設是否成立，需要回寫到規格、測試與知識庫。

以退款入口為例：上線後除了看介面成功率，還要觀察重複請求、人工介入比例與異常金額。如果發生一次重複退款事故，修復程式碼只是第一步；更重要的是補上冪等測試、調整審批條件、更新任務範本。

## 該用什麼指標推動

別拿程式碼行數或 PR 數量當核心成績。更有參考價值的是：一項變更從提出到被接受需要多久、CI 與評審各等了多久、線上缺陷與回滾率有沒有變化、高風險任務的證據是否完整。GitLab 所說的「每個被接受變更的成本」可以作為團隊討論效率時的共同單位。

落地時從一個**邊界清楚、測試較全、回滾容易**的任務類型開始，例如依賴升級、靜態規則修復、文件同步或低風險遷移。連續跑幾週，記錄 Agent 缺了哪些上下文、哪些檢查最常失敗、評審者把時間花在哪裡。試點的目的是用真實任務找出下一筆基礎設施投資該放在哪裡。
