7 月 28 日發布的 MCP 新規範移除了協議層的會話功能（初始化握手、session ping、獨立的 GET 端點），官方統稱為「無狀態協議核心」。舊版 TypeScript SDK 一週下載量超過四千萬，改版消息一出，社群分成「要重寫」與「終於」兩派。影片作者逐行比對 RC diff 與遷移指南後的結論：**大多數人無需驚慌，只有少數人需要真正動手，唯一判斷標準是你的程式碼有沒有碰過 session**。

## 改了什麼

四項機制調整：

1. 徹底移除握手機制，版本與能力資訊直接嵌入每個請求以實現自描述
2. 退役會話標頭 `Mcp-Session-Id`，改用**顯式句柄**處理跨呼叫狀態
3. 取消伺服器主動發起請求的能力，反向請求改為多輪往返
4. 能力發現改為名為 `server/discover` 的普通 RPC 呼叫；伺服器必須支援，客戶端可選擇不預先呼叫直接發請求，遇到版本不支援會回傳帶支援版本列表的 `-32022` 錯誤碼，換版本重試即可

取消 ping：正常的請求往來即可證明服務存活。

動機很現實：舊架構水平擴展有瓶頸，伺服器為每個客戶端記帳極易滋生 bug；新架構下網關無需解析 body 即可路由，負載平衡也能輕鬆輪詢。官方砍掉 session 的三大理由是——黏性會話阻礙水平擴展且實例崩潰後需重新握手、各端獨自管理狀態極易引發記憶體洩漏、客戶端對 session 的語義理解從未統一且斷線後鮮有恢復機制。

附帶收益：以前工具列表會隨會話變化且每次連線都要重拉，現在配合 `ttlMs` 與 `cacheScope`，多個代理可以複用快取，大幅減少重複的 `tools/list` 請求。

改版節奏極其謹慎：5 月 21 日鎖定 RC 並預留 10 週驗證期，7 月 28 日正式發布。四個 Tier 1 SDK 在發布窗口內陸續跟進——TS 與 Python 已升到 v2、Go 發布 1.7 正式版、C 處於預發布、Rust 還在 beta。

## 你屬於哪一批：官方千服調研

對一千個開源伺服器的調研結果：

| 比例 | 情況 | 遷移成本 |
|---|---|---|
| 90% | 應用層從未引用過 session id | 幾乎只需升一次 SDK |
| 3.5% | 只有 SDK 路由樣板中的 ID 映射表 | 會被新版傳輸層自動消除 |
| 2.8% | 只設定了無效產生器 | 刪掉一個建構參數 |
| 2.5% | 把 session 當作**儲存鍵** | 最高，通常要重構架構 |
| 0.7% | 在網關層執行黏性路由 | 需人工介入 |
| 0.5% | 認證與 session 強綁定 | 需人工介入 |

把 session id 當儲存鍵在老專案裡屢見不鮮——當年圖省事的寫法，如今面臨最高昂的遷移成本。整體遷移代價因此呈現「幾乎免費」或「要重構架構」的**雙峰分布**。自查只需十分鐘一條 grep。

## 狀態的新載體：顯式句柄

官方以購物車為例：建立購物車時回傳一個類似 `bsk_a1b2c3` 的 ID，後續所有加購與結帳操作都要附帶該字串。這個句柄本質上只是普通的工具參數，**模型不僅可見還能對它推理**。協議本身並未強制規定句柄概念，但這已是 GitHub PR 編號、Stripe 客戶 ID 等主流遠端服務廣泛採用的推薦設計模式。

使用句柄有一條鐵律：**持有不等於授權**。句柄會進入聊天紀錄與子代理提示詞，任何拿到該字串的人都可能發起呼叫。因此：

- 有認證機制時，必須每次校驗句柄與身分的配對
- 無認證時，句柄本身即充當令牌，必須具備 128 bit 以上的高安全熵並限定生命週期
- 過期後要提供明確報錯，引導模型重新建立

## 危險點一：推送式互動硬失敗

過去伺服器依賴 SSE 流反向發起請求來取得確認、取樣或目錄，新協議中這條通道被**物理移除**。當客戶端協商進入 2026 時代後，舊寫法會直接在本地拋出型別化錯誤，因為舊式請求無法送上新協議線，且**沒有任何寬限期**——比其他廢棄特性的 12 個月寬限期生效更早。

替代方案是 **MRTR**：伺服器回傳一份問題清單，由客戶端作答後帶著答案重新發起嘗試。所有互動式工具都必須優先改用這種寫法，優先級高於所有廢棄遷移事項；來不及改的建議先固定在舊時代版本。

MRTR 細節：`tools/call`、`prompts/get`、`resources/read` 等核心多輪請求的方法名未變，但請求與結果結構新增了 `input_required`、`inputResponses` 與 `requestState` 欄位。`tools/call` 最常見，協議並未對輪數設上限（TS SDK 預設提供十輪兜底）。`roots` 與 `sampling` 已進入廢棄期——2026 時代的連線上 MRTR 是唯一通道，想繼續使用也必須先改寫法。`sampling` 因安全原因被廢棄，但 `elicitation` 得以保留並透過 MRTR 重獲新生。

協議探測通常由客戶端發起（Python v2 預設自動探測），伺服器不支援則會拒絕，客戶端隨後依協商結果回退至舊版握手流程。測試矩陣必須全面覆蓋「客戶端單方面升級到新時代」的場景。

## 危險點二：requestState 是敵意輸入

`requestState` 允許伺服器在 MRTR 中打包狀態，客戶端必須在**不查看、不修改**的前提下逐位元組原樣回顯。但規範明確指出：由於這個 blob 要經過可能被竄改或重放的客戶端往返，它本質上是**攻擊者可控的敵意輸入**。因此開發者必須：

- 用 HMAC 或 AEAD 做完整性保護加密封印，驗簽失敗直接拒絕
- 嵌入認證主體資訊與短 TTL——協議本身不提供超時機制，超時控制必須靠 TTL 自行實作

TS SDK 提供了封印工具，但**那僅僅是簽名而非加密**，絕對不要把機密資料放進去。

## 危險點三：狀態安全完全由開發者負責

規範要求伺服器端驗證 `requestState`，但各 SDK 的預設保護有差異：**Python 預設啟用封印，TS 雖提供工具卻需顯式設定**。自行設計業務句柄的話，身分綁定、過期處理、防列舉全都要親力親為，實作品質的參差直接決定業務安全邊界。

稽核清單必須增加三項檢查：句柄的安全熵是否充足、防重放機制是否到位、句柄與身分的配對關係是否經過嚴格校驗。

## 一線踩坑實錄

作者篩選出含報錯資訊、根因與解法的 A 級案例：

1. **Lambda 第二次呼叫崩潰**：首次呼叫成功，熱呼叫報錯「manager 只能執行一次」。典型的生命週期複用錯誤——社群排查 Mangum 原始碼後發現它每次呼叫都會重新進入生命週期。解法是把 app 建構邏輯放進 handler 內部，避免在模組層級建立全域實例
2. **MRTR 破壞延遲統計**：`mcp snoop` 維護者發現一個實際耗時 6 秒的操作被記錄為兩次總計 1 秒的呼叫，因為多輪重試導致請求 ID 變化，不僅欺騙依賴 ID 關聯的工具，還丟失了人類回答問題所消耗的時間。用他的話說，**錯誤的關聯比不關聯更具破壞性**——所有依賴 MCP 流量監控的工具都該重新稽核底層假設
3. **TS codemod 的靜默失效**：把 `e.code === 401` 當鴨子型別判斷，程式碼能編譯過，卻會導致許多錯誤路徑無法被正確捕捉。官方建議改用型別化錯誤分支
4. **Python httpx2 的 TLS 校驗**：pydantic 官方部落格指出 TLS 校驗已改用系統信任庫而不再依賴 certifi，這代表在缺乏系統 CA 的極簡容器中會突然握手失敗，且沒有任何 import 錯誤提示
5. **CIMD 的精確比對要求**：中繼資料中的 `redirect_uris` 必須包含連接埠且精確一致。曾有真實互通 bug——客戶端漏寫連接埠被授權伺服器直接拒絕，這種靜默故障直到使用者嘗試登入才被察覺

真實遷移回饋：Glama 的網關營運者在 HN 上指出，大量 bug 的根源其實都在持久化狀態；同一帖裡提前數月完成遷移的開發者表示系統可靠性提升、問題率下降；還有一個老專案移除黏性路由後每個請求增加 15–30 毫秒延遲，但整體表現依然平穩。作者提醒：這類具備明確報錯、版本號或原始碼行等可驗證細節的證詞可以拿來說服團隊，但別輕信互相抄襲、虛構引語又夾帶廣告的 SEO 洗稿文。

## 不必恐慌重寫的理由

- Roots、Sampling、Logging 這類廢棄能力，官方至少提供 12 個月過渡窗口
- 舊伺服器能否繼續無縫使用，取決於客戶端與 SDK 是否保留版本協商回退；新客戶端遇到舊伺服器且探測失敗時會自動回退至舊版握手
- **升級 SDK 與啟用新協議是兩個完全獨立的決策**：TS 預設保持舊版協商、需顯式開啟新協議；Go 的新客戶端預設協商最高共同版本、伺服器端需開啟無狀態；Python 預設自動探測
- TS 與 Python 的 v1 仍將獲得至少半年的關鍵修復支援；7 月 28 日當天不會有任何服務被強行關停

## 現在該做的三件事

1. **稽核 session 依賴**：用官方提供的 grep 清單搜 `Mcp-Session-Id`、`initialize` 以及舊傳輸類的名稱，十分鐘定位現狀
2. **在測試環境安裝新版**：TS、Python、Go 已有正式版，C 與 Rust 可用 RC 或 beta；TS 專案可配合官方 codemod 升級，再人工處理工具無法自動轉換的標記程式碼
3. **嚴格按相容矩陣驗證**：不只測新舊客戶端與伺服器的連通性，還要覆蓋工具發現、錯誤回應、OAuth 認證、長任務、超時處理、請求取消與負載平衡

特別注意：**舊客戶端遇到純新伺服器會硬失敗**，遷移期間新伺服器最好提供一個能同時相容新舊協議時代的端點。Cloudflare 並行跑新舊兩條車道的做法更穩妥——傳統車道負責拒絕新會話，待舊會話自然排空後再拆除。作者建議的順序是先 grep 自查再做排期，**審計結果明確之前切勿盲目改程式碼**，恐慌式衝刺往往導致最高昂的浪費。

## 核心框架：狀態在哪裡，責任就在哪裡

過去許多問題被隱藏在傳輸層隱式關聯的 session 之中；現在狀態被剝離成兩部分——一部分搬進模型可見的**顯式句柄參數**，另一部分放進在客戶端往返傳輸的 **requestState blob**。這種轉變把授權與隔離的責任更直接地暴露出來：句柄會不會被猜到、狀態會不會被竄改、快取會不會跨使用者串接，全擺在明面上。

以列表快取新增的 `cacheScope` 參數為例：如果把按使用者過濾的目錄錯誤標記為 public 共享，共享網關就會把使用者 A 的目錄送給使用者 B——**責任邊界已從協議層轉移到設定層**。同時 TTL 僅是新鮮度提示，絕不能視為安全承諾。

這個分析框架同樣適用於未來的更新，看任何協議變更時先問三題：

1. 狀態搬去了哪裡，新的責任方是誰
2. 信任邊界是否改變（本次把客戶端回顯的資料一律視為敵意輸入）
3. 原有的觀測假設是否依然成立（MRTR 打破了「請求即操作」的假設，很可能影響現有監控）

## 為未來的廢棄移除做準備

- 2027 年 7 月 28 日只是**最早**的移除節點，特性不會當天自動消失，具體時間取決於維護者決策——但遷移規劃不能因此延後
- 各 SDK 目前已在輸出廢棄警告，現在就該把它納入 CI 門禁，避免積壓到 2027 年才集中處理
- 授權側規範收緊已有預告：目前回應中若帶 `iss` 欄位則必須驗證，官方還計劃未來拒絕缺少 `iss` 的回應，建議現在就按最嚴格口徑實作
- DCR 機制已進入廢棄名單，過渡窗口結束即具備移除資格，新專案應直接採用 CIMD
- Tasks 功能從實驗性轉為正式擴展，但各 SDK 對擴展機制的支援度不一（C 已實作、Python v2.0.0 尚未包含），現階段必須依具體 SDK 獨立驗證。這種擴展機制促使各家廠商爭奪生態地盤，很可能成為下一個競爭焦點

兩個尚未補齊的顯著缺口：檔案與二進位傳輸仍停留在草案階段（一線開發者抱怨客戶端目前僅支援 base64，嚴重汙染上下文窗口）；token 膨脹問題——官方最佳實踐的範例顯示全量載入約需 15 萬 token、漸進式發現僅需 2000 左右，但這尚未成為所有客戶端的標配。

押注方向明確：擁抱無狀態部署、關注擴展生態、採用 CIMD。協議層不再管理狀態，代表**句柄要自己鑄造、封印要自己簽名、安全邊界必須自己劃定**。
