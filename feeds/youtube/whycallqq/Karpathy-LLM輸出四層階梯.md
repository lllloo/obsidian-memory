## 背景：瓶頸從寫換到讀

- 10 月 2 日 Karpathy 發推，開頭一句：我們接下來會花越來越多時間去「理解」語言模型寫出來的東西。一天內四百萬瀏覽、三萬九千讚、五萬四千收藏
- 訊號：AI 寫得越來越快、人讀得越來越慢，瓶頸換了位置
- Karpathy 背景：OpenAI 創始成員、特斯拉前 AI 總監、創辦過 Eureka Labs；今年 5 月 19 日加入 Anthropic 預訓練團隊帶隊，方向是用 Claude 加速下一代模型預訓練
- 他提出過 vibe coding 與今年 2 月的 agentic engineering（不再親手寫碼、指揮 agent 幹活、人負責監督）。監督的前提是看得懂——模型一次吐五百行方案、掃兩眼就簽字，監督就成了擺設。四層階梯就是他的解法，一層比一層好讀

## 第一層：受控語言寫作（ASD-STE100）

- 讓模型用 ASD-STE100 解釋問題。這是 1979 年起源於歐洲航空工業、專給飛機維修手冊用的受控語言規範：
  - 詞典只批准約 900 個詞，每個詞只有一個意思
  - 程序性句子最多 20 詞、描述性句子最多 25 詞
  - 必須主動語態、不省略冠詞、同一個東西永遠用同一個名字
  - 目標是任何國家的機務人員讀一遍就能做對動作
- 用來約束模型可直接卡掉車軲轆話與模糊措辭
- Karpathy 也承認太硬，做法是鬆一檔：提示詞寫「按 ASD-STE100 的八成嚴格度回答」——保留短句、主動語態、一詞一義，放開詞彙表
- 社群把它做成 Claude Code skill，把規範逐條變成檢查規則
- 有工程師觀察：含糊的語言讓模型聽起來自信又不用負責；平實寫法逼模型把話說死，說錯時你能立刻看出來——這比文筆重要

## 第二層：圖表

- 與其讓模型寫，不如讓它畫：系統架構、狀態流轉、呼叫關係，一張圖的吸收速度與逐段讀文字不在一個量級
- 做法：問題結尾加一句「畫一張圖說明」，讓它產 Mermaid 流程圖或直接寫 SVG
- Karpathy 5 月講過：人腦約三分之一區域在處理視覺；文字是窄管子，圖是寬管子

## 第三層：HTML 網頁

- 讓模型把回答寫成 HTML 檔，在瀏覽器打開；LLM 前端能力已能做出帶動畫、帶互動的頁面
- 呼應今年 5 月 Claude Code 團隊工程負責人 Thariq 的長文〈HTML 是新 Markdown〉：他幾乎不再手寫 Markdown，方案、評審、報告都讓 Claude 輸出 HTML。該文 48 小時破千萬瀏覽，Karpathy 當時在評論區附議「在問題結尾加一句把回答組織成 HTML」
- 五個月內 HTML 從個人偏好變成階梯裡正式一級：比文字強、比圖強，但上面還有一層
- Thariq 論點核心是**閱讀率**：超過一百行的 Markdown 沒人讀（他自己也不讀）；同內容排成有導航、標籤頁、摺疊區的網頁，人才會真的看完。看沒看完決定審核品質——格式決定資訊是否真正進入大腦，好不好看只是順帶

## 第四層：客製講解影片

- Karpathy 最看好的一層。提示詞原話大意：「給我做一個 3b1b 風格的影片講解，主題隨便定，用我的 ElevenLabs 金鑰配音」
- 3b1b 即 3Blue1Brown，背後是開源動畫引擎 Manim；模型可生成 Manim 程式碼渲染數學軌跡動畫，再接語音合成配解說
- 沒有付費金鑰時，讓模型幫你找可用本地算力跑的免費替代方案；他表示這條路現在已真能走通

## 點睛：用完即丟的軟體製品

- 智能與程式碼越來越便宜，便宜到可以要求以前不合理的東西：大型、客製、用完就丟的軟體製品——為一個人的一個問題現場寫互動網頁、現場渲染講解影片，看完就刪
- 以前軟體是要維護、要進倉庫的資產；現在可以是一次性餐具，唯一目的是幫你省大腦頻寬
- 講者認同：這一年許多「讓 AI 隨手寫個小腳本、跑完就不再打開」的行為早已開始，Karpathy 只是替它命名

## 社群接力

- 中文圈：有網友當天出長文解讀，稱四層方案為「降維輸出」，每上一層理解成本降一個量級，附中英雙語階梯圖
- 英文圈：有網友寫成可貼進全域 `CLAUDE.md` 或 `AGENTS.md` 的設定，寫死規則：
  - 每句一個指令、最多 20 詞、主動語態、說清楚誰做了什麼
  - 先給答案再給細節
  - 超過三步驟的流程必須附 ASCII 圖
  - 說「解釋成 HTML」就輸出單檔互動頁面
- 有人稱讚「八成嚴格度」這個鬆緊口設計：既能讀，又不會每句都像航空手冊

## 反對意見

- HN 討論受控語言 skill 時有工程師指出：單靠提示詞約束，模型寫著寫著會漂移、規則失守，除非把檢查做成 git hook 等級的強制流程
- HTML 層的老問題：token 開銷是 Markdown 的 2–4 倍；git diff 全是屬性噪音；同事想改一個字都難
- 最尖銳的批評（來自 5 月那場爭論）：真正的問題可能是內容臃腫，一份沒人需要的五百行方案換成 HTML 也救不了。講者認一半：格式不能減少廢話，但能讓廢話現形

## 容易讀漏的正題

- 開頭那句才是正題：工作正往監督與理解的層面爬升。agent 做的越多，人越像審核員，審核員的閱讀頻寬就是整條流水線的吞吐上限
- 讓模型一天寫完一週的活、再花三週檢查，提速是假的
- 四層階梯的本質：把同一份資訊重排成人類吃得下的樣子

## 實用框架：這份輸出給誰看

- 給下一個 agent、給 git 看 → Markdown 與 JSON，結構乾淨、diff 可讀
- 給人快速判斷 → 第二、三層（圖與網頁），犧牲一點 token 換閱讀率
- 要教會一個人真正理解概念 → 上影片
- 隱藏維度是**驗證成本**：層越高畫面越漂亮、逐字核對越難（影片裡錯的公式比文件裡難發現十倍）。高層製品要可拋棄，錨點永遠留在底層可驗證的文本

## 三條今天就能用的提示詞

1. 解釋任何複雜概念時，結尾加「按八成 ASD-STE100 嚴格度回答：短句、主動語態、一個概念一個名字」
2. 接手老倉庫、審查 AI 大改動、排查看不懂的報錯——這三種場景直接讓它畫圖，先圖後文
3. 任何超過一百行的方案或報告，讓它輸出成單檔 HTML，用瀏覽器打開再看

講者自己已在用，尤其第二條：接手別人程式碼先出圖再讀碼，省時實在。

## 趨勢判斷

- Karpathy 5 月給過影片之上的答案：由模型直接生成的互動式動態內容
- 講者較保守的判斷：未來一年輸出格式會變成與模型名稱一樣的顯式參數，IDE 與命令列工具會內建渲染層，依場景切換文本、圖、網頁、影片；人退到更高位置做判斷與取捨
- 對程式設計師來說，練提問的優先級可往後放，先練讀：會問 AI 的人很多，會讀 AI 的人很少
