## 三種典型用錯姿勢

社群拿 Jev 做瀏覽器 agent（7 秒訂完機票）、壓縮 Claude Code 上下文、給 Codex 當監工、在一張 3090 上復現，但踩坑的人比看文件的人多：

1. **一次只問一個問題**：帶著聊天模型習慣。Jev 的問題在同一份狀態上並行評估，13 個問題塞一次請求，成本只有分開呼叫的十幾分之一——少問等於多花錢。
2. **把大問題整個丟給它**：如「分析這條訊息並給出最佳處理方案」需要慢推理，Jev 答不好、答案飄；應拆成原子問題。
3. **閾值亂設**：只想知道哪個選項最好時取最高機率即可，不需設置信度閾值；Noul 回傳 0.5 代表對錯各半，有人當成「中等程度」用，路由邏輯全錯。

## Jev 瞄準的場景

- Agent 真正花時間的是大量小判斷：該點哪個按鈕、要不要重試、這段上下文還值不值得留、工單轉哪組、使用者是否發火。
- 共同點：高頻、範圍明確、答案空間封閉。
- 現行做法是讓幾千億參數的生成模型逐 token 寫出答案，再用 regex、try/catch 把答案摳出來——大炮打蚊子還要收彈殼。

## 系統一模型是什麼

- Jev 是 TypeSafe 的旗艦模型；官方稱這類模型為「系統一」，出自 Kahneman《快思慢想》：系統一是直覺（快），系統二是推理（慢）。
- 一般大模型在模擬系統二、產生像人寫的文字；系統一模型理解自然語言，輸出**型別化的決策與機率分佈**，無文字生成、無需解析，程式拿到回傳值直接 if/else、排序、路由。
- 官方目標：有軟體屬性的 AI——結構化、可靠、可觀測、可測試、快、便宜。
- 訓練走第三條路：RLHF 訓出聊天模型、RLVR 訓出推理模型，TypeSafe 用 **RLCD**（面向校準決策的強化學習），要求機率是真的機率——說八成把握，大量預測中就該對八成左右。RLHF 共同發明人 Diogo Almeida 是 TypeSafe 聯合創辦人。

## 三個原語與 API

- **Choice**：從一組選項選一個，回傳選項、機率分佈、置信度。
- **Score**：依自訂等級打分，回傳分數與分佈。
- **Noul**：判斷一句話成不成立，回傳 0～1 機率。
- 三種可在一次請求混用，所有問題共享同一份狀態、並行且互相獨立評估；多塞問題回應時間幾乎不變，上下文也不打架（對比一般大模型一次問十件事，問到第五件就開始忘前面）。
- 請求範例：`POST v1/systemone`，body 三個欄位：
  - `state`：被評估的內容
  - `model`：`jev-latest`
  - `questions`：問題定義
- 客服訊息例子，一次問三件事：
  - `department` 用 Choice（帳單／技術／銷售）→ 選中帳單，機率 0.84
  - `is_urgent` 用 Noul → 機率 0.999
  - `frustration` 用 Score（三級，平靜到非常憤怒）→ 1.035
- 官方有 Python 與 JavaScript SDK。

## 三條心法

### 一、一個問題只問一件事（原子問題）

- 每個問題都應是高手幾秒內能拍板的判斷，如「這條訊息急嗎」。
- 複雜判斷拆成原子問題，在程式裡加權組合。文件例子：評估創業專案別問「好不好」，分開問市場規模、技術可行性、差異化，再用自己的公式合成。
- 優先級變了改程式碼權重即可，不必重寫 prompt、也不必祈禱模型理解意圖。

### 二、問題往多了問（投機扇出）

- 一次請求把可能用得上的問題全塞進去，即使有些答案只在特定分支才用得到，由程式決定用哪個、沒用的忽略。
- 官方 cookbook 實測：13 個問題合併一次請求，成本是分 13 次呼叫的十幾分之一、速度快 10 倍、答案完全一樣（因每題獨立評估）。

### 三、答案說是什麼，置信度說要不要執行（置信度路由）

- 官方建議分三段：
  - 高置信度：自動執行
  - 中置信度：讓使用者確認或收集更多資訊
  - 低置信度：不動，轉人工
- 閾值要與操作風險掛鉤：查餘額這類讀操作過 0.5 就執行；審批轉帳 0.9 以上才放行，中間區間必須人工確認。
- 風險偏好寫死在程式碼裡系統才敢上線；低置信度硬執行就是線上事故來源。
- 完整機率分佈都會回傳，想換自己的統計口徑也有資料。

## 官方 Agent Skill

- 倉庫 `typesafe-ai/skills`，600 多 star，MIT 授權。
- Claude Code 兩行指令安裝：`marketplace add` 再 `plugin install`；其他 agent 用 `npx skills add`。
- 最值錢的原則：agent 寫問題的水準普通，**問題與閾值要集中放在一個檔案**，方便人審查和手改。
- 坑：Skill 版本舊了，agent 會瞎編請求欄位，記得更新。

## 社群專案盤點

1. **jev-ultrafast**（Browser Use 官方開源，8 千多 star）：DOM 結構化後交給 Jev，一次請求同時判斷操作類型與目標元素，只有要填字時才呼叫生成模型。Google Flights 蘇黎世到倫敦演示 7.1 秒跑完，瀏覽器協定呼叫從 1092 次降到 101 次。專案方自承單任務單設定、不代表普遍可靠，但展示了分工：Jev 負責選、語言模型負責寫、程式負責執行。
2. **fast-jev-compaction**（4 千多 star）：處理 coding agent 上下文膨脹。傳統壓縮讓 LLM 重新摘要，一旦漏掉檔案路徑或錯誤訊息，後續 agent 就沿錯的上下文走；此專案把完整對話交給 Jev 逐項判斷每個舊工具呼叫要不要留——文字原樣保留，工具紀錄按機率保留、截斷或刪除，壓縮變成一組並行判斷、不再有摘要生成。附 Claude Code 插件與 npm 套件。
3. **Foreman**：Codex 寫程式，Jev 當監工，判斷活幹完沒、測試夠不夠、有沒有跑偏；動作仍由 Python 策略決定。延伸問題：幹活的模型該不該自己判斷活幹完了？
4. **SemIf**（原名 OpenJev）：用開放模型在一張 3090 上實作類似語意判斷介面，聲明與 TypeSafe 無關。
5. **NanoJev**：基於 Qwen3 0.6B 加決策頭，一次前向輸出完整機率分佈，訓練程式與資料集全公開，附迷宮與貪吃蛇演示。
6. **BLUFF**（講者自己的專案）：撲克 roguelike 遊戲，AI 對手用 Jev 即時分析玩家行為並建立畫像，玩家可故意示弱誘導誤判；內建自動駕駛艙，候選動作皆帶機率。

## 冷水與限制

- 拿 Jev 取代大模型做分類省錢，是理解偏了；更貼切的說法：它像「有語意理解能力的 if」——語言模型負責生成、決策模型負責判斷、普通程式碼握著權限、閾值與最終動作，三者各司其職。
- 只接受文字輸入，不支援圖片、音訊、影片。
- 英文是主訓練語言，中文可處理但官方明說精度不同，非英文場景要自己測。
- 校準是統計意義上的，單次判斷照樣可能錯。

## 何時值得用 Jev：三條件同時滿足

1. 判斷高頻發生（一天成百上千次），省下的延遲與成本才看得見。
2. 答案空間封閉：選項可列舉、是非題，或等級分明。
3. 需要機率做路由，例如低置信度轉人工。

官方用例地圖大致是這形狀：agent 護欄、語意程式碼檢查、模型路由、RAG 重排序。需要長推理或生成內容的工作回到生成模型。

## 上手管道與價格

- 官方：`console.typesafe.ai` 註冊取 API key，網頁 Playground 可直接貼文字試。
- 價格按輸入 token 計，每百萬 token 0.042 美元，輸出免費。
- 速率限制動態調整，目前每秒 25 萬 token、每分鐘 1200 次請求。
- 官方申請排隊中可走 OpenRouter、Vercel、Cloudflare、Netlify 四個平台；OpenRouter 最簡單（有人儲值 10 美元就跑起來）。
- 本地研究可看 SemIf 與 NanoJev。

## 總結

- Jev 把 AI 判斷變成有型別的函式呼叫：機率是回傳值，程式碼是你的編譯器。
- 決策模型會不會成為 agent 標準元件，取決於更多獨立評測與真實任務中的錯誤成本；但社群已把這方向從概念寫成能跑的程式碼。
