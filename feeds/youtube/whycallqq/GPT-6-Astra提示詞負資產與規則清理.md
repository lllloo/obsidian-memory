## 事件背景

2026-09-05，OpenAI Codex 團隊工程師 Eric Provencher 在 X 發表長文〈重新思考 GPT-6 Astra 的 Skill 和提示詞〉，獲三百多萬閱讀、一萬六千人收藏——收藏數是按讚的兩倍，在技術內容中比例罕見，顯示多數人的第一反應是「先存下來，回家慢慢刪」。

核心主張一句話：過去一年為程式碼 Agent 累積的提示詞，現在可能全是負資產。

## GPT-6 Astra 的發布與數據

2026-09-03 發布，過程並不順利：當天下午 ChatGPT、Claude、Grok 三家同時當機，晚間 Astra 上線後付費用戶進不去，Altman 親自道歉，Codex 工程負責人承諾付費用戶每多等一天就補償一次額度重置。

模型數據（影片轉述）：

- Terminal-Bench 4.0：57.9%，上一代 Sol 為 37.3%，單任務成本還低約 9%
- OSWorld（電腦操作）：40 分鐘完成 Sol 需 75 分鐘的工作，分數高近 7 個點
- FrontierMath 第四檔 98%、ARC-AGI 3 為 99.9%
- ExploitBench：跨 13 個 Chrome 版本的 20 個高危 V8 漏洞，100%
- 數學上把質數間隙的一個上界從 240 壓到 186（240 是人類數學家不久前才刷新的紀錄）
- 安全測試：舊模型在無護欄時有 48% 情況會越過授權目標亂來，Astra 為 0%

但在 Artificial Analysis 綜合指數上 Astra 為 61.2，低於 Claude Fable 5.1 的 65.7——它強，但非全項碾壓。文章講的是行為變化，與跑分高低無關。

## 為什麼舊提示詞成了負資產

過去兩年的教學共識是「規則寫得越細，模型越聽話」：配 AGENTS.md、裝一堆 Skill 檔案、每一步都盯著它走。這套打法在弱模型時代確實有效，但 OpenAI 官方文件也承認：Astra 對 Skill 與 AGENTS.md 裡的指令**更敏感**，寫得亂、寫得矛盾的檔案會直接拖垮它的判斷。

文中值得抄下的一句：每次模型發布都值得重審這些假設，Astra 這次尤其重要。

## Skill 檔案的三個坑

裝越多 Skill 越好，恰恰是最大的坑：每個 Skill 的名稱與描述都要進上下文，裝多了 Codex 會自動壓縮這些描述，模型看到的是殘缺資訊，選錯 Skill 成為常態；描述之間還會互相打架、爭寵，每條都在誘導模型選自己。

由於用 Codex 產生 Skill 時呼叫的就是官方 skill-creator，官方寫法直接決定了使用者倉庫裡 Skill 的品質下限。官方為此改了 skill-creator 的三條規則：

1. **描述越短越好，但觸發時機必須寫清楚**。以資料庫為例，寫得爛的描述會讓模型一碰到資料庫就呼叫；好的描述限定「只有做遷移時才啟用」。
2. **漸進式揭露**。讀 Skill 本身就佔上下文，還會把你推向壓縮；根檔案只做路由，指向詳細文件與腳本，用到才讀。
3. **別寫保姆級食譜**。舊模型需要一步步教，現在的模型能理解模糊語義，瑣碎步驟只會綁住它。

另有一個易忽略的點：倉庫裡的 Skill 會被別人 Agent 中的其他模型讀到，為 Sol 寫的指令可能正好限制住 Astra。

## AGENTS.md 該怎麼重審

這個檔案每次進倉庫都會載入，每一條規則都值得重審。

- 反例一：改一個拼字錯誤，卻要求它先通讀整個倉庫文件——純屬燒上下文。
- 反例二：舊模型偷懶不跑測試，所以寫了催促規則；Astra 自己會跑會檢查，催促規則留著只會讓它重複測試、浪費 token。
- 反向操作：在 AGENTS.md 裡主動**放權**，例如明寫「本地測試用一次性環境、不碰生產，模型可以自己跑、自己修、自己重跑，不用每步都申請批准」。

## 決策邊界畫太死的副作用

以前模型會亂來，大家習慣用很重的語氣限制它（如「凡是改檔案前必須先問我」）。Astra 的特點是判斷力強且嚴格守規則，副作用是：邊界畫太死，它會在你希望它繼續推進的地方停下來——把一年前為防止犯錯寫的護欄，原封不動當成今天的行動上限。

刪留標準只有一個：**這條規則防的那個問題，今天的模型還會犯嗎？**

## 持續性反轉與意圖即授權

Sol 習慣一口氣跑很久，Astra 更謹慎，做完第一版實作就回來確認。官方解釋是它被訓練成更主動的協作者，答案可能改變結果時會先問，答完支線也不會丟主線。

官方給的解法是一段提示詞，核心一句：**把使用者的意圖當成授權，朝著目標持續推進，別停在半成品上**。並建議讓模型拿不準時先做完能做的部分，拿著具體成果再來問，別空手來問。

使用者下指令時同理：把「實作 → 執行 → 檢查結果 → 修復失敗」這個閉環一次說清，並告訴它探索到哪一步可以停；不說，它就預設第一版算交差。

## 主流誤區：提示詞當補丁

大家把提示詞當補丁，模型每犯一次錯就往上糊一條，越攢越多，從來沒人刪。這模式在弱模型時代成立，但提示詞本質上也是程式碼——是程式碼就有技術債，就要有版本管理。模型換代相當於執行環境大版本升級，舊補丁輕則失效，重則干擾新邏輯；為 5.6 寫的防呆規則，到 6 身上就成了天花板。

Provencher 的建議很直接：把這篇文章丟給 Astra，讓它審你專案裡所有的 Skill 和 AGENTS.md，用新模型清理舊規則。

## 開發者該知道的硬變化

- 工具呼叫可非同步：模型等結果時繼續工作，介面把工具設成 async 即可
- 跑到一半可插話改需求；WebSocket 模式下已完成的工作不會丟
- 推理強度可在對話中途熱切換，快取不失效
- Codex 有實驗功能：跨上下文視窗記筆記，取代以前粗暴的壓縮，數週後會變成預設
- 遷移清單：`temperature`、`top_p` 等舊參數直接刪掉（Astra 不再支援）；工具呼叫必須走 Responses API

文件裡另有兩個細節。一是寫作風格：官方承認 Astra 愛用列表、表格與 Markdown，還會跨會話重複同樣的口頭禪，想要乾淨文風得自己在提示詞裡壓；官方示例提示詞甚至點名 delve 這類 AI 腔詞彙、以及「It's not X it's Y」句式，要求模型別用。二是安全：系統會在後台非同步監控模型的跑偏行為，必要時觸發警報——這直接關係到你敢不敢放權。

## 可立即執行的清單

1. 打開專案，數一下裝了多少個 Skill；描述超過兩行的，要麼改短要麼刪掉
2. 把 AGENTS.md 逐條問：這條規則防的問題，新模型還會犯嗎？答不上來就刪
3. 任務提示詞補上完成標準：跑通、驗證、修完才算完
4. 把該文連結丟給 Codex，讓它自己審一遍規則檔案，你只 review 修改建議

## 三條可複用原則

- **上下文是預算**：每條進上下文的規則都在花錢、擠佔真正有用的資訊；描述被壓縮就是預算超支的直接後果
- **約束換成目標**：少寫禁止做什麼，多寫「做完的標準長什麼樣」；強模型吃的是判斷力，你餵邊界它就只會停
- **把規則審計列進流程**：每次模型升級就像依賴升級一樣，過一遍提示詞倉庫

作者收尾：模型越強，你寫的規則越該少而準；提示詞工程師的護城河，正在從「會寫規則」變成「會刪規則」。
