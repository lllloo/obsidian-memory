## 起點：分數很漂亮，倉庫裡卻沒有推理引擎

J-Space Cognition Suite 公布了一組非常漂亮的分數，V4-Pro 載入套件後有些項目甚至跑出比引用的 Fable 5 還高的數據。但把它固定提交的程式碼拉下來完整讀過一遍後，事實更骨感：

- 倉庫裡**沒有模型推理引擎**，沒有所謂 Jacobian Lens，也不存在對模型激活值的讀寫。
- 唯一的 Python 控制器**連模型 API 都不會呼叫**，它只做兩件事：讀寫本地狀態、檢查輸出文本。

一套不碰權重、不控制採樣參數、甚至自己都不執行 Benchmark 的程式碼，怎麼讓任務成功率飆升？答案只能從 **Harness 層**去挖。任何越過程式碼直接下結論說「模型能力進化了」的說法都站不住腳。

## 工程定性：這是 Prompt 協議，不是模型端點

執行目錄結構一目了然：

- `SKILL.md` 充當入口
- 九個 Markdown 模組提供操作規則
- 三份參考資料解釋概念與給範例
- `jspace.py` 是**可選**的控制器
- `verify_suite.py` 純粹用來檢查套件自身完整性

安裝過程極朴素：把 `j-space` 目錄拷進宿主的 Skills 路徑，宿主再把入口指令餵給模型。說白了，它是**一套 Prompt 協議加一個本地狀態控制器**：既不是代理模型的端點，也不接管任何工具的執行。

這個分類很重要——它意味著我們評估的對象是一個 **Agent 的工作流**，而不是底層基礎模型的升級。

## SKILL.md 與九個模組寫了什麼

`SKILL.md` 做的第一件事是強行給模型灌輸一套「工作空間」設定，接著讓模型執行五步自檢，再把任務分發成 fast、full、loop 三種模式。有意思的是，**原始碼裡根本沒有這三個模式的解析器**——`jspace.py` 實際能認的命令只有 `note`、`seam`、`ship`、`resume` 四個，所謂自動選擇全靠模型讀完指令後自己去悟。模組載入也由宿主或模型自己完成，程式碼裡不存在隱藏的底層調度器。

它改變模型行為的邏輯其實和系統提示詞差不多：先立人設，再定規矩，告訴你什麼時候該計畫、檢查、回檔。它確實能影響推理軌跡，但驅動力依然只是**上下文**。

九個模組剝開包裝就是三類流程約束：

1. **共享狀態管理**（capacity、broadcast）：要求模型腦中只保留核心概念，其餘細節記到帳本裡。
2. **證據邏輯順序**（deep-reasoning、empirics）：逼模型在下結論前補齊中間推導橋樑，推不動就去做差分測試。
3. **任務節奏把控**（directed-focus、markers、self-monitoring）：一旦發現目標漂移、陷入死迴圈或想提前交卷，就觸發糾正動作。

另有 shorthand 與 introspection，規範內部表達與交付前的自我審查。這些檔案**清一色全是自然語言協議**，沒有實作任何高階搜尋演算法，也沒去動解碼器。這套規矩靈不靈，全看模型聽不聽話。

## 最有工程價值的核心：五行狀態帳本

`jspace.py` 把任務的持久化狀態釘在五個區段上：

| 區段 | 職責 |
|---|---|
| Goal | 完成條件 |
| Core | 全域約束 |
| Verified | 檢查點 |
| Open | 尚未解決的問題 |
| Next | 強制只允許有一個明確的下一步動作 |

這些資料寫進當前工作區的 `WORKSPACE.md`，同時把最近的狀態備份到 `history.json`。為了防止寫崩，用了臨時檔加上 `os.replace` 的原子替換操作。

這是一個極輕量的**任務狀態機**。它解決 Agent 的一個致命痛點：在漫長的工具呼叫鏈之後，模型不用再死摳那點可憐的上下文記憶，可以直接去讀這本結構化的帳。對於防止狀態漂移，這套機制實打實管用。

## 四個控制器命令

**`note`**：修改帳本。第一次建帳必須同時交出 Goal 與 Next；Core 區段只認前兩個活動項；提 Open 問題必須寫清楚 `settled-by`（立下規矩：這事到底怎麼才算完）；關閉問題時必須附帶新的檢查點；Verified 記錄要求最嚴，必須同時提供 `check` 與 `by` 兩個欄位，原始碼裡甚至寫了正則去查 `by` 裡有沒有包含「全部」「邊界」「樣本」「檔案」這些範圍詞。

> **硬傷**：正則只能確認你乖乖填了格式，看不懂你的結論對不對。就算寫了個錯得離譜的結論，只要帶上合適的範圍詞，依然能混進 Verified。控制器能逼你把證據寫規範，但代替不了語義上的真偽驗證。

**`seam`**：讀一遍帳本，把當前的 Next、Verified 與 Open 數量塞進歷史紀錄，最多存 20 條，形成一個**死鎖偵測器**：

- 連續三次 seam 看到的 Next 連標點都沒變 → 警告動作卡死
- Verified 數量一直不動 → 提醒沒產出新結論
- Open 的坑越挖越多 → 警告問題堆積
- 閒置超過半小時 → 直接把完整帳本、前提與八條底線規則甩你臉上

這是非常廉價但聰明的漂移偵測：它在旁邊敲黑板說「你好像卡住了」，但不會幫你分析任務，更不會替你生成新計畫。`resume` 做的是類似的重新載入。

**`ship`**：像一個針對文本的 Linter。交付前跳過 Markdown 標題、表格與程式碼區塊，專職掃正文，查內部符號洩漏、狀態標記有沒有清乾淨、有沒有連續重複的廢話，順手查宣稱的「已驗證」有沒有交代覆蓋範圍。查出毛病後**依然回傳成功狀態**——原始碼註解寫得明明白白：它只是個匯報員，不幹保安的活。

`verify_suite.py` 查的也只是目錄對不對、路由在不在、模組骨架全不全。整個倉庫的 18 個單元測試全都圍繞控制器邏輯，CI 跑的只是不同系統下的完整性檢查，**沒有任何一行測試程式碼呼叫模型**，更別提跑公開 Benchmark。

## 第一性原理：不碰權重憑什麼提分

在 Agent 的世界裡，任務結果至少是四層邏輯共同作用：

1. **模型**：出主意、寫程式碼
2. **Harness**：管上下文與工具介面
3. **執行環境**：管權限與逾時
4. **評分器**：終審裁判

J-Space 只在 Harness 層做文章，偶爾用控制器帶節奏。它實際上在對沖三類過程損耗：**忘掉約束條件、半途而廢提早交卷、撞牆後原地死迴圈**。

所以基礎模型確實沒變聰明，但系統成功率提高了——這完全符合軟體工程常識：資料庫還是那個資料庫，但加了強一致性的事務協議，線上故障自然就少了。基於程式碼審計，結論只能走到這步；再往上拔高說模型進化了，屬於證據不足。

## 判斷：工程干貨真，機制敘事必須降維看

J-Space 真正的價值，是把頂尖 Agent 玩家的操作手感沉澱成一套可落地的標準協議：五行帳本、強約束的 Next、隨時落地的檢查點、發現不對勁立馬提示恢復——簡直是為長程複雜任務量身訂做。

它最大的敗筆是為了蹭前沿論文熱度，硬套了個 J-space 的殼。Anthropic 論文裡測的是底層的中間激活表示，而這個倉庫既沒有 Jacobian Lens，也沒有任何探測網路內部狀態的探針。明明是個優秀的 Agent 執行規程，卻要搞一套高深莫測的敘事。評價必須分開：**工程思路非常值得借鑑和測試，包裝的機制敘事必須降維看待**。

## 那高分是怎麼跑出來的

做過長程評測的人都知道，這類榜單極其偏愛**有流程紀律的系統**：寫程式碼要跨過幾十個檔案還記得最初的需求，用工具失敗要能平穩落地並恢復狀態。J-Space 的帳本與檢查點正好治這些毛病。

但過程中它用極冗長的指令逼模型多做驗證，無形中必定增加大量工具呼叫與 Token 消耗。拿一個光板基線去和這套全副武裝的協議打，**雙方手裡的彈藥預算早就不一樣了**。分數高確實說明產品體驗變好，但歸因必須嚴謹：我們不知道究竟是哪個模組立了功，也不知道把 Token 與重試次數拉平後這分數還剩多少。沒有消融實驗，這種打包總分只能看個樂。

更要命的是那份公開報告**缺少可複現的執行鏈**：Benchmark 倉庫裡只有 README、授權與引用聲明，既沒有評測腳本，也沒有任務清單，更別提環境鎖定檔或逐題的原始 Log。README 雖給了幾個 temperature、top_p 參數，但找不到一條能把它跑起來的真實命令；表裡甚至還保留著不同廠商原始的 Harness，Kimi 的對比數據也是在完全不同的條件下測出來的。

態度很直接：它可以作為一個有意思的工程觀察紀錄，但在拿出真金白銀的證據之前，**沒資格排座次，更不能拿來證明因果關係**。

## 公平對照實驗該怎麼設計

嚴格拆成五組：

| 組別 | 設定 |
|---|---|
| A | 直接跑官方的死基線作為參照 |
| B | 塞進一個等長的中性 Skill，單純控制上下文長度這個變數 |
| C | 只餵 J-Space 的指令，但把 Python 控制器關掉 |
| D | 只保留五行帳本與恢復命令，砍掉花俏的 J-space 設定 |
| E | 全副武裝的完整套件 |

五組必須死死鎖定同一個模型快照、同一套工具 Schema 與系統提示；沙箱環境、網路狀態、逾時限制、最大 Token、採樣參數、甚至重試次數全都要絕對一致；題目版本與評分器也得鎖死；每道題還得打亂順序跑至少五次。只有這麼摳細節，才能真的算清楚提示詞、外部記憶與完整協議各自榨出幾滴油。

看結果要盯三類指標：

- **主指標**：預先註冊好的任務成功率。首選報告 Pass@1；允許重試就老實報 Pass@k，絕不能把這兩者混在一起。
- **過程指標**（解釋收益從哪來）：約束遺失率、過早結束率有沒有下降、驗證器揪出多少真 Bug、失敗回檔的成功率。
- **資源指標**（最容易被藏起來）：Token 消耗、牆鐘時間、工具呼叫次數、重試次數，甚至人工接管次數，都得一筆一筆算清楚。

每跑一次 trial 都要留完整案底，拿任務做配對差值統計、給出信賴區間。同時回答**效果、機制與成本**的 Benchmark 報告，才有真正的工程決策價值。

## 看高分表的六個問題

1. 它測的是純模型，還是模型外面套了一層厚厚的 Harness？
2. 分母算的是任務數，還是跑的 trial 次數？
3. Pass@1、Pass@k 與後備降級，有沒有偷偷混著算？
4. 不同模型比較時，執行環境、工具與計算預算是不是同一起跑線？
5. 倉庫裡能不能找到固定的提交紀錄、可執行的程式碼命令，以及失敗任務的完整軌跡？
6. 報告有沒有放上基線數據、等長安慰劑對照與消融實驗結果？

兩個隨手可查的招數：拿題目總數反推圖表裡的百分比小數看能不能除得盡；順著對比數據去翻原始出處。缺了任何一項不代表造假，但結論的含金量必須打折——**沒法重放的排名，充其量是個專案方觀察日誌**。

## 總結

J-Space 裡確實有實打實的工程干貨，核心價值是把 Agent 的工作記憶、檢查點與恢復紀律乾淨俐落地外化了。但它的證據缺口大得漏風：公開倉庫只證明了這套規矩能跑通，根本沒法證明那個華麗的分數就是這套規矩帶來的。

路線很清晰：把可執行的評測設定、完整執行紀錄、失敗日誌與消融數據全放出來，讓社群複現，爭議自然平息。在此之前，它是一套非常值得拿來實操的優秀 Harness，但不是模型能力突然覺醒的鑰匙。
