## 問題：擴容 Agent 容易，擴容注意力很難

寫程式時最廉價的擴容資源就是 Agent——開一個 Codex 改頁面、再起一個做 Code Review、旁邊還掛著開發與測試服務，帳面吞吐量拉滿。但人的注意力先「爆了顯存」：得切著終端輪流查崗，誰還在跑、誰卡了授權、誰早就跑完了。視窗一過十個，看名字全成了擺設。

傳統終端只能吐字元日誌，根本看不懂裡面的 Agent 是什麼執行狀態，於是只能手動輪詢：點開、掃一眼、再切走。單次幾秒鐘，累加起來極其消耗心智，真正被摧毀的是思路連續性。Herdr 要砍掉的就是這筆隱形的調度開銷。

## 定位：給 Coding Agent 重新發明的 tmux

Herdr 保留真實的偽終端、窗格與持久化會話，同時「認識」裡面的 Agent。接入後 Codex 還是原生介面、Claude Code 也照舊，測試腳本該怎麼跑就怎麼跑。

生態上的分工：

- tmux 與 Zellij 管理會話與版面配置
- 圖形化平台適合審批流與環境隔離
- Herdr 切中中間這層：給終端補齊 Agent 狀態感知、CLI 控制與本地 API

整個程式就一個 Rust 二進位檔，不強制帳戶、沒有雲端面板、沒有遙測資料。影片作者認為這種邊界感克制得恰到好處——它沒有妄想一口吞下整套開發工作流。

## 五個核心物件

由上而下的層級模型：

| 物件 | 角色 |
|---|---|
| Session（會話） | 管整套執行期，日常一個預設 Session 足矣，要硬隔離再建具名的 |
| Workspace | 直接對應一個程式碼倉庫 |
| Tab | 像瀏覽器標籤，是專案裡的特定視圖（如把 agents、dev、tests 實體隔開） |
| Pane | 真實的偽終端，能跑任意指令 |
| Agent | Pane 中被辨識出來的編碼行程 |

關鍵區分：測試腳本只算 Pane；而 Codex 既是 Pane 也是 Agent——前者管字元流，後者管生命週期。介面會把底層狀態一路向上冒泡到 Tab 與 Workspace，開的專案再多也能一眼定位到卡住的節點。

## 架構：C/S 模式與持久化的真實邊界

典型的 C/S 架構——伺服端死死握著 PTY、子行程與視窗版面，用戶端只管算繪畫面與透傳輸入。正常 Detach 時關掉的只是用戶端，後台的 Agent、測試與開發服務照跑，甚至允許多個用戶端連進同一個會話。

但必須明確：**伺服端才是狀態的唯一真神**。Herdr 伺服端一停，子行程全得陪葬。下次啟動雖能恢復目錄、版面與焦點，但舊行程回不來了。官方整合能存下 Agent 的原生 Session ID 幫你接回對話，卻沒法「穢土轉生」你的建置行程。實驗性的 Pane History 也只是存螢幕文字的緩衝。

工程上得清醒：「持續執行」這四個字很容易誤導人，**行程、版面、對話這三者的持久化完全是兩碼事**。

## 狀態追蹤：五種狀態與向上聚合

真正省時間的是側邊欄的狀態追蹤：

- `working`：Agent 還在幹活
- `blocked`：卡住了，等授權或輸入
- `done`：有點像「未讀訊息」——Agent 後台跑完變回可用但還沒切過去看，介面高亮成 done；一旦點開就回落成 idle
- `idle`：閒置
- `unknown`：系統也拿不準，**千萬別當成成功或失敗的訊號**

這些狀態會向上聚合：就算把某個工作區藏在後台，只要裡面出現堵塞，Workspace 層級也會亮起紅燈。關鍵在於讓人的注意力跟著事件走，而不是每隔幾分鐘去當一次賽博保安。

## 狀態偵測機制與它的代價

偵測分兩步：先抓 Pane 的前台行程；碰到支援的 Agent，再去掃終端底部畫面，透過 Screen Manifest 比對已知的 UI 特徵。這招不強求每個工具都乖乖寫 Hook 就能低成本接入，Codex、Claude Code 與 OpenCode 都能直接跑。

代價也很清楚：

- Agent 偷改提示介面 UI，舊規則可能當場抓瞎
- 在裡面再套一層 tmux，前台行程的判斷也會失效
- 官方整合能靠原生 Session ID 兜底

真遇到誤判，敲一行 `herdr agent explain` 就能查清是靠哪條規則命中的。面對 `unknown`，作者不建議盲信自動化——老老實實切過去看現場最穩。

## 部署與遠端開發

裝好後在專案根目錄敲一下 `herdr`，預設會話就拉起來了。滑鼠能直接切窗格、拉大小，鍵盤派也能用類似 tmux 的前綴鍵無縫過渡，沒多少新快捷鍵要背。

遠端開發直接走原生 SSH，程式碼與 Herdr 伺服端留在遠端。SSH 斷了後台任務照樣跑，網一恢復連上去、Pane 還在原位。它對窄螢幕也做了適配，拿手機終端連上去應急沒問題——不是要在手機上 Review 大段 Diff，而是點個確認、看眼部署結果。需要桌面端能力時，本地跑個 Herdr 當瘦用戶端連過去也行，連本地剪貼簿的圖片都能直接傳進遠端會話。

## 實務組織方式

作者個人實踐：一個活躍倉庫配一個獨立 Workspace，專案裡再按職責切 Tab。

- `agents`：程式碼生成與 Review
- `dev`：掛熱更新的開發伺服器
- `checks`：編譯與跑單元測試
- `deploy`：盯發布流

這樣切換 Workspace 時，目錄、Pane 甚至 Agent 狀態全套帶走，才是無損的「上下文切換」。

也別把什麼行程都塞給 Agent 管：基礎服務、測試與日誌最好獨立執行。Agent 跑完關掉，開發環境還得留著除錯；程式出 Bug 就去 checks 看報錯、去 dev 刷頁面，互不干擾。一套穩固的基礎目錄結構，比背幾十個花俏的快捷鍵管用。

**典型高效陣型**：一個會話塞兩隻 Agent——Builder 負責改程式碼、Reviewer 鎖成唯讀模式，旁邊掛開發伺服器與測試輸出。Builder 改完，Reviewer 直接接手看 Diff；只要 Reviewer 拋出 blocked 就說明碰到系統邊界，這時人再介入拍板，乾等純屬浪費算力。審核任務必須嚴格限制檔案範圍、測試腳本與寫入權限。

## 硬邊界：Workspace 不做檔案隔離

Workspace 只管邏輯組織，不管檔案隔離。兩個 Pane 只要指著同一個目錄，照樣會讀寫衝突。遇到大需求就乖乖切分支或上 Git Worktree；Agent 之間的交接老實走 Commit 與 Patch。

**Herdr 提供的是容器，Git 管的是紀錄，只有你才是負責最終驗收的那個人。**

## CLI 才是控制面的真正入口

- `layout` 指令一鍵拉起 Workspace、Tab 與 Pane
- `pane` 指令管測試與服務
- `agent` 指令負責啟動、Prompt 透傳與等待

用腳本拉起這些物件時 CLI 會回傳 JSON，拿到穩定的 ID 再操作。**千萬別去猜新開的 Pane 是編號幾，也別拿當前焦點盲發指令。**

有了它就能寫外部協調器：動態拉一個 reviewer、分發限定任務，然後等 `idle`／`done`／`blocked` 的訊號。普通腳本沒有 Agent 狀態，就用 `pane wait-output` 抓關鍵字；是 Agent 就等它嚴謹的生命週期。

**但凡能等語義狀態，就別在腳本裡硬寫死 `sleep 30`**——機器負載稍微一抖，靠時間猜狀態的流水線分分鐘崩盤。這是 Herdr 最大的工程價值。

## 控制邊界與安全債

- Pane History 會把 Prompt 與裸原始碼實打實寫進磁碟
- 跑出異常時，Token 與敏感環境變數同樣會在日誌裡裸奔
- 裝外掛等於拿當前系統權限去跑不受信任的程式
- 升級用戶端前最好對齊後台伺服端版本，否則重啟伺服端會讓跑到一半的 Pane 行程灰飛煙滅

能力邊界也要認清：沒有「全域共享記憶」，多個 Agent 之間還得靠檔案與 Git 互傳上下文；沒有產品級的任務相依圖，搞不定複雜的組織級審批流；沒有完整的事件追蹤；並行一上去，CI 與發布佇列照樣塞車；狀態偵測該誤判還是會誤判。**面板能幫你降噪，但替不了你劃定任務邊界。**

## 適用判斷

- 日常只開一個 Shell 單打獨鬥 → 別折騰，現有終端夠用
- 活在伺服器上、早就掛好 tmux、斷線重連 → 也用不上換工具
- 開始跑兩隻 Agent 加一個長耗時任務 → 狀態管理的陣痛已經開始
- 要同時拉起多隻 Agent、留 Pane 看測試盯服務保遠端、關心誰在幹活誰在等授權、還想寫腳本把它們全盤控死 → 值得試

作者的判斷：多 Agent 時代，程式設計的瓶頸必然會從「生成能力」轉移到「調度品質」上。
