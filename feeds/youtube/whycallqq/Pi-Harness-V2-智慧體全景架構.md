## 出發點：真正拖垮生產系統的不是模型

很多團隊做智慧體時注意力都在模型、提示詞與工具數量上，但進入生產環境後，最容易把系統拖垮的往往是更樸素的事：機器重啟了、剛才那次工具呼叫完成沒有？並行任務搶佔資源怎麼辦？使用者中途補發的訊息模型看見了嗎？

一個支付 Agent 明明只發起一次付款，客戶卻可能被扣兩次——不是模型變笨，而是第一次付款已經成功、成功回執卻丟在機器重啟之前。換成部署工具就是重複建資源。對當前執行期來說，這次呼叫既像成功了又像沒發生：重試可能重複扣款，不重試則任務永遠卡死。

**Agent 的可靠性從來不是要求系統永不失敗，而是要求系統在失敗後仍然知道自己做過什麼。**

本影片討論的是 Pi 倉庫中 Harness V2 的**設計文件**，不是當時已完整可用的生產執行期。該版本已落地純狀態還原器與部分儲存能力，但執行迴圈、輸入佇列、工具恢復等仍在工作包中。

## 架構歸類：Event Sourcing 特徵

Harness V2 帶有明顯的 Event Sourcing 特徵：保留追加式的執行事實，並透過歸約計算重建編排狀態。影片作者強調這是他自己的架構歸類，**不是官方標籤**。

目標設計中一個 Session 被嚴格定義為四個部分：

1. 對話樹（Conversation Tree）
2. 並行通道（Lanes）
3. 通道操作日誌（Lane Operation Logs）
4. 全域事實（Global Facts）

不容妥協的原則：**不要把恢復任務所需的編排狀態只保存在記憶體裡**。執行期當然可以有記憶體狀態，但必須存在足夠的持久化事實，讓新行程能重新推導出完全一致的狀態。

## 對話樹與操作日誌必須邏輯隔離

- **對話樹**存語義內容：訊息、模型文字、工具啟用變更、壓縮摘要等
- **操作日誌**記錄底層執行事實，例如規範中持久化的 `step_attempt`（步驟嘗試）

執行紀錄絕對不能進入模型上下文、對話轉錄或分支查詢。至於底層是存在不同的資料庫表，還是寫在同一個 JSONL 檔裡，那是儲存實作的問題。

為什麼要隔離？把「是否重試過」這類內部狀態直接塞進 Prompt，可能干擾模型對使用者意圖與執行狀態的區分。隔離之後既避免編排細節污染模型上下文，又讓恢復器能依據結構化紀錄判斷進度。

## Lane：克制的並行模型

多 Agent 並行常被當成萬能解藥，但 Harness V2 的路線非常克制。頻道是整個 Session，而每一條 Lane 就是一個獨立的工作流分支，有自己的操作日誌與輸入佇列。不同 Lane 之間可以並行、走不同的模型分支。

但 **Lane 不是萬能的分散式鎖**：它解決的是單個執行期內部的並行與順序問題。對同一個 session，系統仍假設只有一個 Writer 在單點寫入；如果多個行程同時搶佔寫入，那是更上層的一致性機制該解決的，框架本身不打算製造無謂的複雜性。

## 最硬核的部分：工具呼叫崩潰的三段恢復

一條 prompt 被受理，和模型真正開始生成是兩碼事。設計要求：

1. 系統先持久化「任務已受理」紀錄
2. 呼叫外部工具前，先寫一條包含**預先分配 ID** 的 `tool_started` 紀錄
3. 效果發生後，再用同一個 ID 把結果寫進樹裡

依當機點落在哪裡，恢復策略完全不同：

| 當機時機 | 日誌狀態 | 恢復策略 |
|---|---|---|
| 準備呼叫工具，`tool_started` 還沒寫就崩了 | 意圖尚未確立 | 認定上一步還沒產生外部動作，直接重走一遍正常流程 |
| 啟動紀錄已寫入，拿到結果前斷電 | 結果條目缺失 | **最危險的薛丁格視窗**——外部效果發生沒發生不知道，絕對不能盲目重發請求，只能依歷史策略決定 |
| 結果條目已寫入，推進下一步前掛了 | 首尾閉環 | 必須跳過該工具，絕不能再執行一次 |

**把含糊的「好像成功了」變成這三種精準狀態，就是設計的精髓。**

## 薛丁格視窗該不該重試

規範規定：只有歷史紀錄和當前工具宣告**都**明確標為安全時，系統才會自動重放。

如果這是付款工具，狀態未知時框架不會自動重放。業務層應根據外部服務的契約選擇：

- 用同一個幂等鍵安全重試
- 或透過訂單號、資源 ID 查詢最終狀態
- 只有無法自動核實時，才進入人工複核

### 對照 AWS Lambda Durable Execution

AWS 預設是 at-least-once（至少執行一次），未完成的步驟在恢復時可能重跑。因此：

- 副作用在本地資料庫 → 去重標記與業務寫入必須在**同一個 ACID 交易**內
- 發布訊息 → 可用交易 Outbox，但下游仍需去重
- 呼叫第三方 API → 必須依賴對方的幂等協定

另外，Events 提供即時觀察、Hooks 負責可改變執行的擴充點、日誌與追蹤走獨立的 Telemetry 通道，三者職責嚴格分開。

## 使用者中途插話：為什麼不能直接插進歷史

Agent 執行長程任務時使用者突然補發一條訊息，若直接插進歷史紀錄中間：

- 公共前綴會在插入點提前結束，從該位置開始的模型快取無法複用，可能明顯增加延遲與輸入成本
- 更關鍵的是，轉錄會錯誤地暗示上一條模型回覆「已經看見」這條後來才到達的訊息，破壞時序邏輯

因此目標設計不把後到的內容直接插進歷史中間：

- `steer`、`followUp`、`nextRun` 先持久化為佇列項
- 執行中的訊息或設定寫入則記錄為 **Deferred Write**
- 它們在各自的消費時機或 Checkpoint 被**追加到上下文尾部**

如此同時保住因果順序與快取前綴。

## 後台執行的 Provider：Deferred Handle

某些模型 Provider（例如 Responses API 的 background 模式）支援後台執行，可能需要幾十分鐘產出結果。Harness V2 為這類 Provider Response 設計了持久化的 Deferred Handle：系統讓當前 Lane 掛起，之後無論誰來接管，都能按持久化控制代碼查進度。

設計規定每次 `resume()` 只 fetch 一次，失敗也不會自動發起新請求替代原任務。注意這針對的是 Provider API；如果是普通的後台業務工具，業務層還得自己設計類似的查詢協定。

## 用量帳本與對話條目分離

模型請求失敗、因溢位重試、被丟棄的回覆，都會產生 Token 費用。規範計畫把使用量帳本（Usage Ledger）與對話條目分離，讓獨立帳本完整保留 Harness 實際收到並成功持久化的用量，失敗請求的消耗也能被單獨統計。

但也要客觀承認：它仍不能覆蓋 Provider 未回報用量、或回傳後立即當機等不可消除的視窗，最終核算仍要與供應商的帳單對齊。

## Reducer：確定性的純歸約

在這個版本中，Reducer 已實作為確定性、無寫入的純歸約函式。它讀取有界的操作日誌、樹條目與設定，歸約出當前執行到哪一步、哪個工具沒結果。

在目標實作中，當 `resume()` 完成、再次掛起或關閉該 operation 時，系統將重新執行 reduction，並與 live state 做 **fixed-point 自檢**。

未來工作包中計畫引入 **Manual Drive**，讓測試能在每一個受控的持久化寫入、Provider 請求、工具執行、Hook 或計時器邊界前暫停。重啟 Agent 不再是靠 if-else 猜歷史，而是靠純函式算出確定性的固定點。

## 落地建議：三步演進

如果任務是單輪問答、純讀無副作用，完整的持久化執行期絕對是過度設計。但如果業務是跨回合審批、程式庫修改或雲端資源維運：

1. **堵漏洞**：在底層資料結構上，給副作用工具的 Payload 明確加上 `operationId` 欄位，並利用查詢介面核實狀態
2. **拆狀態**：把中途使用者插話改用佇列追加，分離獨立的成本帳本
3. **上引擎**：引入 Reducer 還原狀態，並在 CI/CD 中加入確定性的「崩潰—重開—恢復」測試；對高風險業務再補充行程強殺或基礎設施故障演練

## 核心啟示

Harness V2 最值得借鑑的，是它對外部世界不確定性的敬畏：模型必然會抽風、工具必然會逾時、容器隨時會銷毀。**卓越系統的使命，是在災難發生前就把「接受了什麼」「允許重試什麼」寫進不可變的事實裡。**
