## 真正的分水嶺不是啟動變快

大家都在聊 Codex CLI 啟動變快了——Charlie Marsh 公開說重構生命週期後啟動快了差不多 25 倍。但更該盯住的是：OpenAI 把決定 Agent 能不能「真正動手幹活」的底層機制開源了。

官方叫它 **Codex Harness**：卡在模型與真實系統中間的 Runtime，負責準備上下文、管理工具呼叫、執行沙箱與審批策略。哪些高危動作需要人來點「同意」，全看宿主應用怎麼設定。

Agent 接入系統後，真正的難點不再是「生成程式碼」而是**流程控制**：它看了哪些檔案？拿了哪些上下文？出了 Bug 怎麼恢復？高危操作誰來批？以前程式碼補全寫錯了還能逐行 Code Review，但一個能呼叫工具的 Agent 翻車，影響範圍會順著憑證與介面一路擴散。

## 倉庫結構

開源入口在 `openai/codex`（不是單獨的 codex-harness 倉庫），採 Apache-2.0 授權。核心分塊：

- `codex-rs/core`：承載核心業務邏輯，想搞懂 Agent 迴圈重點看這裡
- `app-server`：對外的客戶端協定
- 官方 SDK：程式化整合的入口

`codex-core` 的 README 寫明它支援多個 Rust UI 服務，往下還能看到 session、tools、sandboxing、MCP 呼叫以及上下文壓縮這些模組。要注意：**Harness 與整合層開源了，但模型存取與託管服務仍是獨立的**。

## Harness 在 Pipeline 裡的位置

平時聊 Agent 很容易簡化成「Prompt + 模型」，但工程落地上這只占整個 Pipeline 很短的一截。模型接到請求、輸出工具呼叫意圖後，任務才剛開始：讀檔案、敲命令、抓日誌、處理 Token 權限、應對逾時，最後把結果塞回下一輪對話。任何一環斷了，Agent 就只能停在 Demo 階段。

OpenAI 對 Harness 的定位就是幹這些髒活累活：維護會話狀態、跑沙箱、走審批、讓任務跨回合串聯。**模型負責提建議，Harness 是調度與約束這些建議的 Runtime**——模型說「我想跑個命令」，能不能跑、在哪跑、跑完什麼結果，全靠 Harness 與背後的策略說了算。

### Thread 與 Turn

App Server 的文件把兩個概念分得很清：

- **Thread**：長期會話，例如修一個長期的 PR、處理一張線上工單
- **Turn**：一次具體的請求回合，必須有明確的開始、進度、工具流水、結束狀態與報錯日誌

很多內部自建的 Agent 工具把歷史紀錄與任務佇列全糊在一個聊天框裡，平時看不出來，等你想查「這行 DB 變更是誰授權的」或想恢復一次中斷的任務時就傻眼了。把 Thread 與 Turn 拆開，就是把「長期上下文」與「單次執行流水」解耦，後續做鑑權、計費與排障才會清爽。

## 工具設計與權限

給工具分類千萬別只標個「讀」或「寫」：讀日誌可能會漏 Token；跑個單元測試可能會寫快取或呼叫外部 API。最可靠的分級是綜合看**副作用、資料敏感度、能不能回滾**。OpenAI 把這些權限全交給宿主應用，哪些動作要人工批由你自己定。

每一個寫操作工具都得做好：入參校驗、最小權限控制、冪等設計、落日誌與明確的異常返回。建工單要防重複，發版命令得帶上審批單號。**Agent 能幹多大的事取決於你給了多少能力；系統的風險上限，直接由你設計的工具邊界決定。**

### 審批閉環

OpenAI 給的 Relay 範例演示了完整閉環：Agent 發現異常，透過 MCP 工具查資料；當它想做「重新訂艙」這種寫操作時，系統直接拉起人工審批；點完同意，業務介面同步刷新。

搬到日常開發完全一樣，只是對象變成 PR、資料庫或發版單：Agent 去讀建置日誌、寫草稿隨便它搞；但凡涉及改資料庫、輪換金鑰，必須進 Approval 流程。審批卡片上得寫清楚要動什麼資源、影響面多大、參數對不對；能回滾就把回滾按鈕也亮出來，不可逆操作在 UI 上必須標紅示警。它防不住所有風險，但能給高危動作留下追責證據。

## 嵌入既有系統，別做成聊天框

OpenAI 建議把以前的 Dashboard、IDE 與工單系統都留著，把 Agent 嵌進去。排查線上事故時，值班同學需要看大盤趨勢與告警時間線，Agent 可以在旁邊幫忙順邏輯、查受限日誌，但主戰場還是原來的監控面板。

狀態回饋也很關鍵。PR 38788 裡 Codex 啟動時會明確告訴你是在「恢復會話」還是「衍生會話」，草稿也會保留；旁邊的 composer 改動能把游標與貼上狀態平滑遷移過去。使用者等 Agent 跑的時候最怕對著乾轉的 Loading 圖示發呆——進行到哪步、卡在哪、能不能取消，本來就該是產品介面的一部分。

## 那個 25 倍要怎麼看

Charlie Marsh 說重構生命週期後 Codex CLI 啟動快了約 25 倍。工程師得看具體指標：它指的是行程拉起、首屏渲染、你能敲鍵盤了，還是模型回包了？不同指標對應不同的最佳化路子。

翻 0.148.0 的 Release 紀錄與 PR 38642 能找到線索：TUI 還在初始化時，使用者就已經能開始起草 Prompt——系統先給一個臨時輸入框，後台再慢慢跑初始化設定，最後把文字狀態無縫接管。

從開源程式碼能確認 Codex 把「**首屏可互動時間（TTI）**」大幅提前了。但客觀來說，靠現有公開資料算不出這個「先顯示輸入框」的做法對那 25 倍貢獻了多少，也不能證明後台所有載入邏輯都等比例縮短了。

## 三層整合梯度

OpenAI 給的分層建議：

| 場景 | 建議入口 |
|---|---|
| 一次性腳本或 CI 任務 | `codex exec` |
| 需要程式碼調度、串流消費 | SDK |
| 帶複雜 UI 的內嵌 Agent | App Server |

這套梯度讓團隊用極低成本試錯，不用一上來就硬啃複雜的聊天 UI 與多使用者並發。

### codex exec

天生適合腳本與 CI：進度打進 stderr，最終結果扔進 stdout；配合 `--json` 輸出串流事件，或用 `--output-schema` 鎖死 JSON Schema，下游業務接起來很順滑。

初次試水建議從**做 PR 風險摘要**開始：把 Diff 與測試日誌餵給 Agent，讓它吐出受影響模組與補充測試建議。一開始先給唯讀 Sandbox，別一上來就讓 Agent 自動合程式碼。先跑幾週，看準召回率與人工採納率，等輸出夠穩健再慢慢放開寫權限。

### App Server 與網路邊界

走雙向 JSON-RPC 2.0，天然支援管 Thread、跑 Turn、接串流事件，人工審批介面官方也留好了。但有一點必須卡死：**網路邊界**。

App Server 預設走本機 stdio，官方明確說 TCP、WebSocket 目前還是實驗性功能，不建議直接上生產。非要跨機呼叫務必套上 TLS 並加 WebSocket 認證；純裸跑 `ws://` 只配活在 localhost 與 SSH 隧道裡。當前處於 Rollout 階段，非回環位址的監聽可能會預設放行無認證連線，千萬別裸露在公網上。工具端的權限校驗也得重新做，別完全輕信上游傳來的鑑權。

## 可觀測性

沒有可觀測性，Agent 很快會淪為一個你不敢碰的黑盒。當業務方跑來說「Agent 把庫刪了」，你必須能精確定位到那一次 Turn：它讀了什麼上下文？呼叫哪個版本的工具？誰點的人工確認？最後寫了哪條紀錄？

所以每個 Turn 都要掛唯一 ID，把模型請求、工具入參、審批結果與報錯堆疊全串在一根線上。CI 場景保留原始的 JSON Lines，線上產品直接把核心事件打進稽核日誌。這不只是防甩鍋，還能幫你抓出那些瘋狂重試、消耗巨額 Token 的無效邏輯。

## 用什麼指標評估

別光拿「今天又生成了多少行程式碼」自嗨，要看業務結果：

- 做 PR 摘要的，看人工採納率與漏報率
- 做故障排查的，看 MTTR（平均恢復時間）有沒有降
- 如果上了 Agent 反而增加老員工幫它擦屁股的時間，那就是負最佳化

效能也要拆開算：行程拉起、首屏渲染、首次可輸入，分別看 p50 與 p95。Codex 的互動改動提醒我們——讓使用者「體感上能開幹」的時間，往往比後台服務啟動完畢更重要。

## 落地路線圖

把 Agent 請進研發流程是跨部門的系統工程：產品定審批節點，領域專家定資料源，平台組護航工具鏈，安全團隊卡權限。Prompt 寫得再好，也贏不過拉胯的上下文與沒做兜底的工具。上了 Harness 也不等於多了個數位勞動力——模型照樣會幻覺，介面照樣會逾時，工程上要做的還是那些基本功：攔截非法入參、做好介面冪等、長任務支援 Cancel 與 Resume、死守最後一道人工審批關。Harness 的價值是提供一個安放這些工程約束的標準底座。

穩妥的上手順序：

1. 挑一個「唯讀、好驗證、不碰線上資料」的活兒
2. 拉三五十個歷史 Case 跑離線評估，覆蓋刁鑽的邊界場景
3. 定義好 JSON Schema 格式，算出真實省下的工時
4. 再考慮接進 CI 或大盤頁面——這階段決策權留給人，資料全保存
5. 跑通了再去碰低風險的寫操作，補齊最小權限、冪等鍵與回滾機制
6. 確實需要保持上下文再上 Thread；確實需要 UI 即時互動再接 App Server
