本片基於 AI 研究者 Hanako（@hanakoxbt）於 2026-08-01 發表在 X 的長文《Eval Engineering》，講 Agent 自動合併程式碼前必須建好的評估體系。影片作者聲明：只講能追到原始出處的研究所支持的結論，個別 2026 年新數據未能追到原始實驗，講到時會標註。

核心矛盾：Agent 寫程式碼越來越快，審查程式碼的人還是原來那幾個，人成了整條流水線的瓶頸。「不敢讓 Agent 自動合併」是本能，但說不出不敢的原因就是工程問題——門要讀證據才能放行。

## 第一道門：裁判可不可信

LLM-as-a-Judge 的早期依據是 2023 年 UC Berkeley 的 MT-Bench 論文：GPT-4 當裁判與人類評估者的一致率超過 80%，接近人類彼此之間的一致率；人工評一條要幾分鐘，API 評一條可能只要幾分錢。但二次傳播多半只記住 80%，忽略論文同時列出的三類偏差。

Hanako 引用的一組 2026 年基準數據（影片標註為未能追到原始實驗的部分）：

- GPT-5.2 與 Gemini 3.1 Pro 當裁判時，把 75%–84% 的勝率判給自己模型家族的輸出
- Claude Opus 4.7 反著來，把自己家族的勝率壓到 10.6%–41.2%
- 同一批 Agent 輸出、一個字都沒改，兩個裁判分別打 93.3% 與 39.5%

有獨立研究支持的部分：2024 年一項研究證實模型能認出自己的輸出並系統性偏愛它；冗長偏差也被反覆量化——回答越長得分越高，與多出來的字數有沒有資訊量無關。

安全使用的三條規則：

1. 優先用**不同模型家族**的裁判，降低自我偏好與相關錯誤的風險
2. 高風險判斷組**評審團**，讓多家廠商的裁判一起評；另一項研究算過帳，跨廠商評審團比單個強裁判更準，成本還低好幾倍
3. 凡是**能客觀驗證的交給程式碼**，別交給裁判——測試過沒過、檔案在不在、狀態改沒改都有確定答案

一個被污染的裁判比沒有裁判更糟：它把猜測洗成數字，系統再照著數字自動行動。

## 第二道門：分數能不能改變行為

很多團隊的評估停在儀表板上，分數漲了跌了、開個會發個週報，然後什麼都不變。Hanako 稱之為「溫度計」——溫度計只報數，恆溫器才會根據溫度去開關空調。

評估工程要把評估搬進 Agent 的**執行時**，讓每個裁決都對應一個結構性動作：

- 證據落地不夠的輸出 → 拒絕這次交接
- 結構校驗失敗 → 堵住這條流程
- 疑似編造的分支 → 隔離起來，不許合進主線
- 只有被外部驗證過的完成，才有資格結束一次執行

關鍵區分：Agent 停止呼叫工具只是**回合結束**，回合結束和**任務完成**是兩回事，差別只有外部檢查知道。現實中常見 Agent 在報告裡寫「遷移完成」，狀態檢查一看腳本中途就逾時了。別問它做完沒有，去看系統狀態到底變沒變。

Anthropic 今年的工程部落格給出相近原則：能用確定性檢查的優先用確定性檢查，無法客觀驗證的部分再考慮模型評分。Tau Bench 這類基準也是同一思路——直接查資料庫的最終狀態。

## 第三道門：為什麼要評路徑

只看最終答案打分會出這種事故：Agent 用一條完全錯誤的路徑撞出了正確答案，沒人發現，直到一個月後路徑塌了。

評估要分三層：

| 層 | 看什麼 |
|---|---|
| 端到端 | 任務成沒成 |
| 軌跡 | 路徑乾不乾淨——迴圈、冗餘呼叫、白走的步驟都藏在這 |
| 元件 | 具體哪個檢索器、哪個工具、哪個子 Agent 壞了 |

指標三個就夠：

- **事實忠實度**：答案裡的每個說法能不能在工具真實回傳的內容裡找到出處
- **工具參數準確率**：呼叫對工具沒有、參數填對沒有
- **任務完成率**：對著真實訊號評，對 Agent 自己的聲明打個折

三個裡面事實忠實度最會藏——Agent 寫得乾乾淨淨、順手編了一個匯率，儀表板上所有品質指標都是綠的，直到有客戶按這個匯率真的下了單。

對合併那道門而言，**軌跡比答案更能預測風險**：同一份程式碼差異，三步乾淨走完的和四十步瞎撞撞出來的，風險完全不同。

## 第四道門：測試從哪來

坐在工位上想出來的測試只能防你想像得到的失敗；真正貴的失敗都帶著時間戳躺在日誌裡。撈四種執行紀錄出來：

- 順利跑完的 → 當作正常基線
- 使用者改了說法或糾正了 Agent 的 → 這次糾正就是一份免費的標註
- 工具回傳了空、或同一個查詢用同樣參數呼叫了兩次的
- 外部依賴逾時的 → 專門看 Agent 在「世界說不」的時候怎麼辦

每條紀錄寫四行：Agent 做了什麼、哪裡好哪裡壞、鍋在 Agent 還是在依賴、這個測試要保護什麼能力。

一個要提前說的坑：**日誌只告訴你 Agent 做了什麼，從來不告訴你它該做什麼**。標準答案得來自測試、紀錄、規則或人。

## 第五道門：裁判和評分標準怎麼管

裁判是軟體，軟體就有版本。裁判悄悄升一次級，前後兩個月的分數就沒法比了——鎖死版本號，每個分數都帶著版本一起存。

評分標準壓成一句話：**某個可以獨立觀察的結果發生了，才算過**。別獎勵答案的形狀——長度、關鍵字、引用數量、與參考答案的相似度，一概不給分。把裁判當最佳化目標往死裡調，Agent 會學會一件事：讓自己看起來對。這就是古德哈特定律，只不過迴圈裡多了個模型。

用裁判之前先測裁判：餵它一個明顯正確的結果，再餵一個貌似合理的錯誤結果；任何一個判反了，壞的是評分標準，先別急著怪 Agent。

另一個坑：很多人覺得讓模型自己檢查一遍總比不檢查強。DeepMind 在 ICLR 2024 的一項研究發現，至少在他們測試的推理任務中，**沒有外部回饋的自我糾偏並不可靠**，有時還會把正確答案改錯。注意前提是「沒有外部回饋」——有測試結果、有工具回傳、有真實狀態是另一回事。

評估集規模：原作者給了偏保守的經驗數——至少 500 條再認真看聚合分數，但別把 500 當成業界標準。真正關鍵的是用例有沒有覆蓋真實失敗、以及分數穩不穩定。跑一輪的時間要短到沒人需要為它安排行程；比一杯咖啡還慢的測試，遲早會變成季度儀式。

## 第六道門：按什麼標準開門

很多方案的思路是建一個信心分數、設個閾值、過了就放行。但信心度是整個決策裡最弱的一個變數。真正強的變數是：**這次改動要是錯了，糾錯要花多大代價**——也就是爆炸半徑。按它分三條車道：

| 車道 | 例子 | 開門條件 |
|---|---|---|
| 可逆又局部 | 一條文案、一個測試、有覆蓋的獨立函式 | 先開，錯了大不了回滾 |
| 可逆但影響面廣 | 共享工具函式、資料庫結構的新增、一堆呼叫方依賴的東西 | 確定性檢查全過 + 軌跡乾淨才開 |
| 難以逆轉 | 資料庫遷移、刪除操作、生產寫入、資金操作 | 預設不允許自動合併，必須保留人工確認 |

門打開之後，讀證據的順序也有講究，優先級由高到低構成一條證據鏈：

1. **確定性結果**——測試、型別、結構定義、沙箱執行，這裡面沒有模型參與
2. **這版 Agent 的評估軌跡**——路徑乾淨的改動風險天然低一檔
3. **歷史紀錄**——這個 Agent 在這塊程式碼上的改動以前被回滾過多少次，回滾率就是它的信用分
4. **模型自評**——可以參考，永遠別採信；它缺乏獨立性，也最容易被輸出方式影響

開門動作要慢：先跑**影子模式**——門給每個改動打分但一個都不合併，統計它和人類評審的分歧率；壓不下去，門就一直關著。

影片作者自己的標準：低風險、可回滾、測試完整的改動敢開；資料庫遷移、刪除操作、生產寫入不敢。判斷標準只有一條——它錯了以後，我能不能安全撤回來。

## 兩句補充提醒

- 測試套件全綠，產品照樣可能垮：測試會收斂到測試自己，慢慢偏離真實需求
- 評估未必都變成一個叫「評估工程師」的職位，但會成為一個獨立職責。模型是租的、按月付費、隨時調價；你攢下的**測試集與裁判設定**才是自己的
