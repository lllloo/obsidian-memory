## 問題：驗收的真空地帶

Agent 現在看著範例就能寫 WebGPU 著色器，一句提示詞換一段 WGSL。但典型失敗是：Agent 寫完、CI 測試全綠、放心合併，結果頁面一片黑——程式碼確實編譯過了，畫面卻全錯，因為從頭到尾沒有機器確認過它「畫沒畫對」。

中間卡著兩道牆：

- **CI 那道**：持續整合的容器通常是純 Headless 環境，沒 GPU、沒視窗。本機開發還能開瀏覽器肉眼看 Canvas，伺服器不長眼睛。
- **Agent 那道**：AI Agent 能敲程式碼、跑指令、看日誌，但它沒有視窗，看不見自己畫了什麼。

兩道牆一疊，驗收成了真空地帶。

## 業界舊解法：Golden Image

圖形學的經典套路是把一張正確渲染的圖存下來當參考答案，程式碼一改就重新渲染一張，兩張圖逐像素做 Diff，誤差超標就報錯。Babylon-Lite 和 luma.gl 都是這麼做。

但前提是要有人搭環境、存參考圖、調閾值，全是手工膠水活。現實中 Shader 驗收長期靠人肉盯螢幕。

## vgpu 是什麼

2026-08-27，Vercel 在 X 上發文，把原本用在官網發布 Shader 的 vgpu.sh 開源：

- 倉庫 `vercel-labs/vgpu`，MIT 授權，npm 套件名 `vgpu`，當時為 0.3.1 版
- 官方主推四大特性：面向 Agent 設計的 WebGPU 函式庫、可跑在瀏覽器或 Node.js、支援 CPU 沙箱與 CI 渲染、能建可重用的 `.wgsl` 模組
- 野心包含 3D 場景與 GPU 張量，但本篇只盤它怎麼回答「畫對了沒有」

## 核心矛盾：能編譯 ≠ 畫對了

編譯通過只說明語法沒毛病、Binding 對上了。顏色算錯、座標系搞反、混合模式寫瞎，編譯器根本不管——它只保證 GPU 能跑這段程式碼，跑出什麼鬼畫符它不關心。

以前這個落差靠人眼填，現在寫程式碼的是 Agent，驗收的也必須是機器，這中間缺失的校驗層必須用工程手段補齊。

## 機器驗收畫面的三個硬條件

1. **渲染環境要是確定性的**：同樣的程式碼每次跑出的結果必須一致，不然 CI 就是在擲骰子。
2. **輸出要能讀回像素**：渲染結果不能停在螢幕上，必須變成程式能拿到的資料。
3. **要有標準答案用來比對**。

這三點正好對應 vgpu 的設計：多執行時兜底、Target 提供 read 方法、內建像素比對相依套件。缺任何一環，Agent 生成的程式碼就沒法自證清白。

## 最小核心程式碼

從 `vgpu/node` 匯入 `init`、`target`、`draw`、`frame`：

```
init   → 拿到 adapter 和 device，吐出一個 Gpu 控制代碼
target → 建 256x256、格式 rgba8unorm 的目標
draw   → 傳入 WGSL 原始碼
frame  → 顯式 pass，先 clear 再 draw
read   → 像素陣列直接回到程式手裡
dispose
```

所有入口都把 Gpu 傳在第一位，沒有隱藏的全域狀態黑盒，背後也沒有任何隱式場景圖。

最核心的是 `read` 這行。傳統瀏覽器 Canvas 畫完直接上螢幕，人眼看見了，但程式想拿像素資料非常折騰——很多測試方案就死在這：能跑出畫面，卻取不出結果，斷言無從下手。渲染一完像素直接進記憶體後，要存 PNG、做快照 Diff、算誤差指標當 CI 門禁都隨你發揮。**沒有能讀回的輸出，就不存在能斷言的結果**，這是整個閉環的地基。

## 三種執行時各攔一類 Bug

| 執行時 | 環境 | 攔什麼 |
|---|---|---|
| 本體 | 瀏覽器，畫面進 Canvas | 驗使用者實際畫面 |
| `vgpu/node` | 背後掛 Dawn，Headless 離屏渲染 | 驗 CI 伺服器連通、執行時崩潰 |
| `vgpu/mock` | 純確定性軟體模擬，不碰真 GPU | 死磕邏輯正確 |

scene、client、core 也各有分工。編譯錯、執行時崩、邏輯算錯精準攔截，比一句籠統的「測試失敗」高效得多。

## CI 閉環

一條 `pnpm test:render` 搞定，跑起來就三步：編譯 Shader、Headless 渲染一幀、做快照比對。官方例子跑完整個畫面驗收只要 842 毫秒。

相依套件裡 `pixelmatch` 負責逐像素 Diff、`pngjs` 負責讀寫圖片，加上 Mock 適配器就成閉環：編譯攔語法錯、離屏渲染攔崩潰、像素比對攔畫面全黑。

## WGSL 變成真模組

以前寫 Shader 就是往 TS 裡塞一坨字串，純靠複製貼上維護，改個 binding 忘了同步就出 Bug。vgpu 把 `.wgsl` 變成真模組：

- 像 TS 一樣能 import/export，檔案內匯出函式、結構體，其他檔案直接引用
- 官方標準庫 `@vgpu/wgsl-std` 備好了 hash、noise、color 這些常用輪子
- 建置時做反射，剔除無用程式碼並輸出壓縮原始碼（官方例子壓縮完僅 397 位元組）

最有價值的是**類型反射解決了 Binding 漂移**：過去 Shader 裡的 Binding 和 JS 側綁定是兩套人肉帳本，這邊改了那邊忘改就執行時崩潰或暗中畫錯。現在 WGSL 是唯一事實來源，綁定資訊直接從原始碼反射生成，兩邊不再靠人肉對齊——讓工具鏈推導另一半，對 Agent 而言出錯率直接砍半。

README 還有個硬指標：一個完整全螢幕特效 gzip 後體積可壓到 25KB，且這個預算由 CI 強制執行（影片作者註明這是官方口徑、未實測）。多數專案沒人管 Shader 體積，vgpu 劃了紅線、超標 CI 就掛，配合 Tree Shaking 自動幹掉廢程式碼。

## Agent First 怎麼落地

- CLI：`npx vgpu docs` 查文件、`npx vgpu examples` 搜程式碼並把例子拉到本機、`npx vgpu check` 本機校驗
- 倉庫裡 `agents.md` 是操作手冊、`llms.txt` 給大模型引路
- 提供免 token 的 OpenAPI 3.1 介面，MCP 節點掛在 `vgpu.sh/api/mcp`，本機也能 `npx vgpu mcp` 起服務

串起來的流程：Agent 領到寫 Shader 任務 → 查 docs 摸清 API → 搜 examples 抄個底座 → 寫完跑 check → 跑渲染 → 讀像素做比對。全程不需要瀏覽器、不需要彈窗、不用人類幫看一眼，它自己就能閉環驗證對錯。vgpu 的預設讀者是 Agent，人類反倒成了次要使用者。

## 邊界與冷水

**單拎出來都不是新發明。** Golden Image 測試 Babylon-Lite 玩了多年；Headless 渲染 Dawn + SwiftShader 早就輕車熟路，llvmpipe 配 xvfb 也是老一套；ExecuTorch 專門切這套後端就是為了規範和確定性；逐像素比對 luma.gl 和 ThorVG 都有。vgpu 真正的價值是把這些散裝膠水活打包成跨執行時 API，並配齊 Agent 介面。

**Mock 跑綠不等於真機畫對。** 軟體後端和實體硬體的差異是實打實的：浮點精度、MSAA 取樣、混合順序全都不一樣；在 Mock 上調好的比對閾值換個後端可能全線報錯。Mock 的定位是防邏輯回歸，跨裝置一致性要麼上真機矩陣、要麼放寬容差。（影片作者的立場：有邊界的機器驗收也比沒驗收裸奔強，但 Mock 綠了就閉眼發生產等於拿使用者當白老鼠。）

**快照比對的深層前提是要有可信的標準參考圖。** 第一張圖通常還是得靠人眼審核或用真機跑一次——人的判斷並沒消失，只是被推遲到「建參考圖」這一步，所有 Golden Image 方案都繞不開。更麻煩的是效果一升級舊參考圖就成了絆腳石，還得人肉重定版。機器驗收只砍了日常回歸成本，首次確權的代價一分不少。

**編譯器層面的暗坑。** 同一段 WGSL，Tint（Chrome 和 Dawn 用）能跑，Naga（wgpu 和 Firefox 用）可能直接報錯；社群真出過案例——叢集光照在 Chrome 好好的，Firefox 直接拒。vgpu 的編譯期反射只改善 Binding 漂移，保證不了語義在所有編譯器裡等價；CI 過了 Dawn 不代表 Firefox 使用者打開網頁不花屏。

## 可外推的通則

不寫 Shader 也適用。想搞 AI 輸出驗收，繞不開靈魂三問：

1. 環境是確定性的嗎？
2. 輸出能轉成資料讀回嗎？
3. 有標準快照做比對嗎？

前端元件的截圖測試、PDF 排版 Diff、資料報表的數值快照，全是一個模子。缺任何一環，AI 程式碼就得靠人肉抽查，抽查不到就是 Bug。日後評估 Agent 框架，拿這三點去套比看炫技演示靠譜得多。

過去幾十年開發工具都是給人設計的——文件給人看、報錯給人調。現在 Agent 入場，這個假設反轉了：文件要有 `llms.txt`、測試要有 CLI、結果得能被程式讀回。生成端提速十倍，驗收端跟不上就會卡死在人肉 Review 上；選工具多看一眼它給 Agent 留的入口，決定了它在 AI 工作流的壽命。
