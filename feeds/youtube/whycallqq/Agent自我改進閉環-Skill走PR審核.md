## 問題：回饋的壽命只有一個 session

花三個月調教 AI 編程助理、教它專案規範與命名習慣，開了新 session 就全部歸零。多數人把這當成模型的宿命，Warp（做 AI 終端的團隊）不忍。

Warp 內部有個跑在 Claude 平台上的程式碼審查 Agent，工程師用一段時間後開始抱怨「評論沒用、輸出品質差」。最初的做法很常規：手動改提示詞，看到一次失敗案例就往 prompt 補一句。短期有效，但撐不住——提示詞越改越長、越改越亂，沒人說得清這份 prompt 到底在教 Agent 做什麼。維護 AGENTS.md 之類的上下文檔案有幫助，但治不了本。

病根在於**回饋的壽命**：對 Agent 說的每一句糾正只活在當前 session，session 一結束經驗歸零。

## 自我改進閉環：兩個 Skill

Skill 指的是寫給 Agent 看的說明書檔案，流程、原則、注意事項全是純文字。

- **基礎 Skill**：負責幹活。以程式碼審查 Agent 為例，裡面寫著怎麼讀 PR、按什麼標準提意見。
- **改進 Skill**：自己不幹活，只當觀察者。按固定節奏執行，把累積的人類回饋撈出來，對照 Agent 當時的表現找出落差，提出一個修改建議——改的是**基礎 Skill 這份檔案本身**，改了哪幾行、為什麼改，一目了然。

## 為什麼一定要落在檔案上

檔案能進 git；進了 git 就有 diff、有 review、有版本歷史，出問題還能回滾。把 Agent 的知識塞進提示詞，它隨 session 蒸發；存進資料庫，它黑箱難查；寫成檔案，它就是團隊資產，走和程式碼一樣的工程流程。

Warp 創辦人 Zach Lloyd 的區分：**Skill 寫的是流程，相對穩定，改動要慎重；記憶是 Agent 推理時隨手寫的，一直在變**——兩樣東西別混在一起。

## 真實案例：issue 分揀 Agent

Warp 開源倉庫有個 issue 分揀 Agent，有人提新 issue 時 GitHub Action 就觸發它：分析複雜度、打標籤、給修復方向。某次它漏了 `ready to spec` 標籤（意思是貢獻者可以基於這個 issue 開始寫產品與技術方案）。一位維護者發現後沒有自己動手補，而是直接在 issue 下留一條評論，寫清楚兩件事：他期望什麼、依據是什麼。

這條評論成了一次自我修改的原料：

1. 改進 Skill 跑在 Warp 自家排程平台 Oz 上，是個定時任務
2. 透過 GitHub 認證，執行 Skill 自帶的 Python 腳本，把近期帶回饋的 issue 拉下來，整理成 JSON 再讀回上下文（腳本打包在 Skill 裡，常用操作做成工具，別讓 Agent 每次現場寫程式碼）
3. Agent 從評論識別出具體訊號，提出一個最小改動：issue 描述了真實問題，哪怕介面方案還沒定，也應該打 `ready to spec` 標籤
4. 它開一個 PR，只改基礎 Skill 裡的幾行，PR 描述寫明是哪條回饋觸發了這次修改
5. 人類工程師審查、批准、合併，下一次分揀 Agent 就帶著新知識上崗

## 回饋必須假設會出錯

Warp 的最佳實踐寫得很直白：**假設回饋一定會出錯**。有人會提錯誤需求，有人帶著個人偏好亂指揮；Agent 若照單全收，說明書很快變成垃圾場。

做法是給 Agent 足夠的上下文做合理性檢查、篩選誰的意見算數，並在過濾或最終審核環節始終留一個人。

回饋的**品質比數量重要**：一條資深工程師寫的具體回饋（例如指出某類全域變數的命名約定），比一百個按讚倒讚值錢得多，因為按讚不說原因。同時採集回饋要零成本——入口直接放在 PR 和 issue 評論區，順手寫一句就行。Zach 的判斷是：摩擦一高，訊號就斷。

## 改進能否自動確認，取決於任務類型

- **任務可驗證**（例如改完程式碼能跑測試）：先搭驗證環境、產生參考語料，讓 Agent 的輸出與參照物對比、修、再對比。harness 搭好之前別急著讓 Agent 自己調自己——沒有裁判的訓練只會跑偏。
- **任務不可完全驗證**（例如程式碼評論的品質）：靠黃金輸出集加領域專家審閱，別把回饋大門向所有人敞開。

先問任務能不能自動判分，再決定回饋迴路能自動到什麼程度。

Anthropic 的 Agent 評估指南把這套講得更完整：自動化評測做回歸、人類評審做校準、線上監控兜底；三種評分器搭配使用——程式碼檢查快且客觀，模型評分能抓模糊地帶，人評是黃金標準也最貴。

## Skill Doctor

Warp 開源的 Skill Doctor 做的就是中間那層：拿本地真實的 Agent session 記錄，按效率與程式碼品質打分，篩出失敗的 session，**只從失敗證據裡提修改建議**，每條建議都帶著具體 diff。改動還要過受保護分支的閘門：必須通過狀態檢查、必須有人審，程式碼一變審批自動失效——這套機制管了人類工程師十幾年，現在原樣拿來管 Agent。

## 核心觀點：瓶頸在回饋迴路，不在模型

很多人覺得 Agent 表現不好是模型不夠強或提示詞寫得不夠好，但多數團隊的瓶頸在回饋迴路上：你給 Agent 的糾正散在聊天記錄、口頭抱怨、PR 評論裡，沒有任何機制把它們沉澱下來，模型再升級這個漏洞還在。本質上這是組織知識管理的問題，AI 只是載體——你的團隊怎麼對待一個重複犯錯的實習生，就怎麼對待 Agent：寫下來、流程化、有人審核。

一句話帶走：**把 Agent 的每一次改進，當成一次程式碼提交來管理**。拆開是四個動作：

1. **可 diff**：任何變化都是檔案上看得見的幾行修改，反對整段重寫
2. **可審**：走 PR、走 CI、走分支保護，人有一票否決權
3. **可回滾**：改壞了 `git revert`，下一分鐘就恢復
4. **有證據**：每條修改背後掛著觸發它的失敗案例，不接受拍腦袋的最佳實踐

這四個動作沒有一個需要發明新工具，git 和 CI 早就準備好了。

## 落地三步

1. 挑一個抱怨最多的重複性 Agent 任務，把流程寫成一份 Skill 檔案——寫原則，別寫死規則（告訴它關注重複程式碼，比列兩百條命名規範有用）
2. 把回饋入口放在工作現場：PR 評論、issue 評論，零額外操作
3. 配一個定時執行的改進 Agent，每週看回饋、提一個最小的 PR；先小步跑通再談推廣

Warp 自己也是從一個程式碼審查 Agent 開始，慢慢鋪到規格撰寫、審查、分揀，每個 Agent 帶自己的閉環。

## 對未來的推測

- Skill 檔案會成為團隊的重要資產，像今天的 CI 設定與架構文件一樣進新人培訓材料
- 改進 Skill 會高度複用：Warp 發現程式碼審查 Agent 的改進器與其他 Agent 的改進器結構幾乎一樣，寫一次處處能用
- 團隊差距會從「誰買了更強的模型」轉向「誰的回饋迴路轉得更快」——模型大家都能買，累積幾千條高品質回饋的 Skill 庫買不來
- Warp 已在把這套循環產品化：跨全團隊的 Agent session 自動跑改進，指標可自訂為測試覆蓋率、任務遵從度，再配看板盯合併時長、每個 PR 的成本與品質分

作者收尾：Agent 不會自己變好，除非你給它一條可沉澱、可審核、可回滾的改進通道。
