## 核心命題

2026-08-26，DHH（Ruby on Rails 作者、37signals 老闆）上 Lex Fridman 播客聊了五小時。他的日常是辦公室擺著四五台小主機，每台跑約三個 AI Agent，加起來約 16 條並行工作流。

但他的結論與「炫耀算力」相反——原話是「迴圈裡的那個人才是極限，機器還有餘量，人先跟不上了」。訪談開場不久他就說得很直接：**瓶頸很少出在實現上，出在人的頻寬和溝通上**。

## 八個月的爬坡時間線

- **2026 年 1 月**：DHH 撰文說自己離「90% 程式碼由 Agent 來寫」還很遠，當時認可的是監督式協作——Agent 幹活、他看結果、需要時給指導。
- **4 月**：Gergely Orosz 採訪時，他的工作區是兩個模型並行（一個快、一個慢但更強），中間夾著 Neovim 和 LazyGit 做 Review。Gergely 形容這種狀態像穿上一套機甲。
- **8 月**：四五台機器、16 條 thread。

## 兩處被誤傳的說法

網路上傳播最廣的說法有兩處不準確：

1. DHH 的原話是 about 16 threads（16 條線程），不是嚴格意義上的 16 個 Agent。
2. 很多文章說他自己開發了叫 Herdr 的排程平台——不對，那是他換用的**現成工具**。他自己給的定義非常樸素：帶 Agent 通知的 tmux。

這套工作流沒那麼神秘，全是現成零件拼的。

## 實體架構

- 每台小主機配一個 GL.iNet Comet（IP KVM），透過 HDMI 和 USB 直接接管機器；系統掛了、SSH 斷了、卡在 BIOS 都能遠端救回。
- 機器之間用 Tailscale 組網（底層 WireGuard），不用暴露任何公網埠。
- 用 mise 管理這些 Agent 工具鏈——因為 Agent CLI 更新極快，版本、環境、權限全都要管。

值得留意的推論：Agent 數量上去以後，**Agent 的執行環境本身也變成了基礎設施**。

## 第一層瓶頸：可觀測性

機器就緒後的下一個問題是「16 個 Agent 誰在幹活、誰在等你」。過去用 tmux 得逐個視窗切過去看，Claude 看一眼、Codex 看一眼，換台機器再看一遍——DHH 說這套很快就不行了。

Herdr 解決的就是這件事：終端由背景服務持有，闔上電腦 Agent 照樣跑；每個視窗有狀態（working / blocked / idle / done），不用再巡視，它直接告訴你誰需要你。

## 第二層瓶頸：排程與非同步任務

DHH 在 3 月就把 Basecamp 改造成 Agent 可以存取的系統，做了新的 API 和 CLI，讓 Agent 能看專案、建 todo、發訊息、傳檔案、排日程。

8 月的訪談他講得更明白：**chat 不是理想的 Agent 協作方式**，因為聊天會誘使人乾等，非同步的任務工具才合理。互動模型從「發 prompt 等回覆」變成「派任務、非同步執行、出結果、人來決策」。

影片作者的判斷：多 Agent 的排程器最終會長得像 Jira 和 Basecamp、像 issue 佇列，不會長成一排聊天視窗。

## 上下文成本與 Plan 作為狀態載體

Agent 一多，上下文就變成真金白銀的成本。DHH 提到 token 仍然稀缺，好的架構能讓 Agent 不用每次都重新學一遍整個程式碼庫。

他有個做法很有啟發：一個模型生成一份詳細的 8 步計畫，token 用完以後由另一個模型順著這份計畫接著幹——**Plan 變成了跨 Agent、跨上下文傳遞狀態的載體**。這本質上就是分散式系統裡的狀態持久化：軟體工程沒有消失，只是換了個地方出現。

## 最值錢的失敗案例：局部正確、整體崩壞

Basecamp 5 開發初期，他們讓設計師直接用 Agent 實現需求，結果發現 Agent 有個危險性質——**你讓它幹什麼它就真幹什麼**，不會像資深工程師那樣提醒你「九成的效果其實只要一成的複雜度」。

於是單個 PR 看都合理，合起來架構碎了，效能問題、安全問題、技術債一起湧進來。

後來 37signals 立了規矩：Agent 可以先把東西做出來驗證設計，但**高風險改動進主庫前必須過資深工程師**。DHH 自己的總結是「想寫出高品質的程式碼，還是得花不少功夫」。

## 第三層瓶頸：Review 數量爆炸

Omarchy 的 Quattro 階段三個月合併了 1000 多個 PR，訪談時還有約 400 個在排隊。DHH 早就不逐個看了：Agent 先做第一輪篩選，他只做最終的 merge 或 no merge。

Review 的數量爆炸了，人的時間沒有變多，**判斷力就這樣成了稀缺資源**。這個邏輯反直覺：程式碼產得越多，能看懂程式碼、能拍板的人越值錢。

## 三種並行故障

DHH 講了三個都值得記下來的故障：

1. **局部正確的 PR 合起來毀掉架構**——上下文一致性出了問題。
2. **多 Worker 協同時的並行寫衝突**——Amabot 的主協調 Agent 踩到了另一個 Agent 的工作，破壞了對方的成果。
3. **生產速度超過下游系統的消費速度**——8 個 Agent 做 QA 找出 28 個真實問題，約 12 秒內全部提交到 GitHub，平台直接把這個 Bot 判定成 spam 封號。

上下文一致性、並行控制、限流與背壓——全是分散式系統的老問題，換了個片場重新上演。

## Amabot：把事件流壓縮成決策流

Amabot 目前沒有公開原始碼，資訊全部來自這次訪談。它大致是一個協調者，掛在隔離的 VM Worker 上面，DHH 稱這個設計為 brains and hands（大腦和手分開）。

運作方式：Amabot 定時掃 todo、issue 和 PR，讓 Worker 執行，再讓 Agent 做 Review 篩掉垃圾，彙總成一封 HEY 郵件寄給他——內容是「這裡有 12 個 PR，該合併還是該關閉」。

效果是把 100 個 Agent 事件壓縮成 10 個人類決策。

## 瓶頸遷移路線

把八個月串起來會看到一條清晰的路線，每一層瓶頸被解決，壓力就被推到上一層：

| 階段 | 瓶頸 | 解法 |
|---|---|---|
| 一 | Agent 的等待時間 | 多 Agent 並行 |
| 二 | 不知道誰在等你 | Herdr 這類可觀測性層 |
| 三 | 任務與上下文管理 | 非同步任務佇列、計畫、隔離環境 |
| 四 | Review 數量爆炸 | Agent 初審 + 協調者摘要 |

留在最頂上的，是那些沒法外包給機器的問題：該做什麼？架構對不對？這個 PR 該不該合？要哪種取捨？DHH 把這叫 vision、taste、judgment。

## 反常識的兩條

- **Agent 跑得越快，DHH 能維持的 thread 反而越少**——因為極限從來不在機器那邊，在人消費輸出的速度上。
- **資深工程師從 Agent 拿到的增益比初級工程師大得多**（4 月 Gergely 就點破了）——因為資深的人有能力判斷輸出能不能上生產。

DHH 的原話：很多組織本來就不缺實現能力，卡住他們的是想法、視野和品味。Execution 變廉價了，judgment 在漲價。
