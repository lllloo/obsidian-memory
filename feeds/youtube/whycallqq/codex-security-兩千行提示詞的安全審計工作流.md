OpenAI 於北京時間 2026-07-29 凌晨首次在 npm 發布 `@openai/codex-security`，到 7-30 已連發四個版本，Apache 2.0 授權，版本號已到 0.1.3。影片作者的核心感受：這個倉庫裡最值錢的東西，是**兩千多行用自然語言寫成的安全稽核方法論**——把資深安全工程師審程式碼的全過程一步步寫成提示詞。

## 背景與時間線

傳統 SAST 工具最大的痛點是誤報：掃一遍倉庫扔回幾百上千條告警，大量是低危、重複或沒什麼價值的發現，安全工程師的時間耗在分診上，真正要命的漏洞反而淹沒在告警海裡。現代工具已加入跨檔案與資料流分析，但看不懂真實部署語義，人工分診依然是大頭。

- 2025-10-30：OpenAI 首次公開內部專案 Aardvark（Codex Security 前身），當時小範圍私測
- 2026-03-06：以研究預覽形式公開發布，面向 ChatGPT 付費檔與企業使用者，首月免費
- 2026-07 月底：CLI 與 TypeScript SDK 開源

OpenAI 自報的內測數據（30 天內、外部 beta 使用者的 120 多萬個提交）：識別出 792 項 critical 級發現、10,561 項 high 級發現；critical 級只出現在不到千分之一的提交裡；整體檢測誤報率下降超過五成，重複掃描同一倉庫精度持續改善，有案例噪音直接降了 84%、嚴重程度被高估的發現下降超過九成。並給 OpenSSH、GnuTLS、PHP、Chromium 等專案報了漏洞，共取得 14 個 CVE 編號，包括 GnuPG 的堆疊緩衝區溢位、Gogs 的認證繞過。

## 最反直覺的發現：倉庫裡沒有掃描器

沒有規則庫、沒有模式比對引擎、沒有資料流分析器。倉庫分兩層：

- **外層**：一萬兩千行 TypeScript，負責命令列、鑑權、成本控制、狀態管理
- **內層**：一個打包好的 Codex 外掛，內含 **13 個 Markdown 技能檔**（全是提示詞，加起來兩千多行）外加三十來個 Python 腳本，負責讀寫掃描狀態與校驗產物

真正的掃描邏輯就寫在這 13 個技能檔裡。掃描的主技能檔只有 42 行，它是個調度員；真正的稽核智慧分散在各階段技能裡，用自然語言寫成。

## 四階段掃描流水線

**第一階段 — 威脅建模**：智能體先通讀倉庫，回答五個問題——什麼資產和權限是重要的、信任邊界在哪裡、哪些輸入是攻擊者可以控制的、程式碼必須守住哪些不變量、哪些失敗模式最要命。產出一份倉庫級威脅模型文件並快取給後續階段。

**第二階段 — 候選發現**：拿著威脅模型逐檔案審程式碼，每個疑點記進 JSONL 格式的候選帳本。每條候選必須寫清三樣東西——攻擊者控制的輸入源、被破壞的安全控制、危險的匯聚點（即 source-control-sink 三元組），類別明確時附上 CWE 編號、定不了可留空，位置要精確到行。技能檔明確寫：**發現階段只管技術上講得通，不管最終定級**；通用的「需要更多驗證」式廢話、可維護性抱怨、同一根因的重複變體統統不許進帳本。

**第三階段 — 驗證**：候選漏洞必須先過驗證這關，技能檔給驗證方法排了明確的階梯：

1. 能寫崩潰 PoC 的，先寫 PoC 打一遍
2. 記憶體安全類的，上 valgrind 或 ASan
3. 鏈路不清楚的，用 gdb 批次處理模式跑一段非互動式除錯
4. 有現成測試框架的，補一個最小的針對性測試
5. 有真實介面的（HTTP、CLI、檔案解析器），直接透過介面端到端重現
6. 全都走不通，才退回靜態程式碼追蹤——而且靜態追蹤要寫明證據缺口，到底缺了哪一環

幾條硬規則：沒有真的驗證就不許假裝驗證過；信心度按**驗證方法**校準，不按漏洞類別聽起來有多危險；每條候選都必須留下可稽核的驗證紀錄，哪怕結論是被排除；建置失敗、依賴缺失不算反證，只能記錄下來換靜態方法。這等於把資深安全研究員的工作習慣變成強制流程。

**第四階段 — 攻擊路徑分析**：給每個漏洞編一個完整的攻擊故事——從哪個入口進來、穿過哪些信任邊界、到達哪個匯聚點——然後做一件關鍵的事：**找反證**。技能檔列了一張反證清單：這條路是不是只在內部可達、是不是需要管理員權限、是不是攻擊者根本碰不到。把最強的反面證據擺上桌逐條評估，過了反證這關再用一張機械化的定級矩陣定嚴重度。

誤報就是這麼被壓下去的：能動態重現的附上 PoC 或執行日誌，重現不了的寫清靜態證據與證明缺口。

## 主流水線之外的生命週期技能

- `diff` 掃描：專看 PR 與提交的增量
- `triage`：消化存量告警，把 SARIF 檔案、Jira 工單裡的舊發現逐條過一遍
- `fix`：生成最小補丁
- 漏洞報告技能：寫正式的 writeup
- 加固建議技能：從掃描結果反推架構層面的改進

從發現到修復到復盤，整個安全閉環都有對應的提示詞模組。

## 工程護欄（對做 Agent 產品最有參考價值）

- **成本控制**：原始碼裡有個成本追蹤器，每 100 毫秒輪詢一次會話檔案即時讀取 token 用量，內建一張**精確到奈美元級別**的定價表，含 gpt-5.6 系列四個模型標識，輸入／輸出／快取價格分開算。可給掃描設美元上限，花超了直接中止、報錯退出
- **輸出契約**：三個最終契約檔（`scan-manifest`、`findings`、`coverage`）必須過 JSON Schema 與交叉一致性校驗，報告與 SARIF 都從它們派生。例如 `findings.json` 裡漏洞 ID 必須是 `csf_` 加 24 位小寫十六進位；少一個必填欄位，這次掃描就不算完成
- **狀態管理**：掃描歷史存在 SQLite 工作台，批次掃描支援斷點續掃。倉庫提供 Dockerfile 與一份加固過的 Compose 設定——鏡像用非 root 使用者執行，Compose 丟掉全部 Linux capabilities、禁止提權、再載入 seccomp 規則。餵一個 CSV 就能把整個組織的倉庫挨個掃過去，是為 CI 與批次場景設計
- **超時**：外掛的 MCP 工具超時設成 86400 秒（24 小時）。深度掃描模式會反覆做多輪獨立發現再去重合併，一次要跑很久，這個超時應該是給它留的（官方沒有明說）。多輪取樣的目的是對抗大模型的輸出方差，技能檔說得很直白：一個候選在多個 worker 裡重複出現只是搜尋證據，不等於它可以被報告，該走的驗證一步都不能少
- **誤報回饋**：使用者標記過的誤報保存在工作台資料庫，後續掃描會把相關紀錄匯出交給驗證階段參考，系統還要重新確認原來的排除理由在當前程式碼下是否成立。影片作者判斷：這可能幫著減少重複噪音，但官方說的五成改善不能全算在它頭上
- **CI 整合**：產出的 SARIF 報告能上傳到 GitHub 的程式碼掃描面板，可按嚴重度設門禁、高危漏洞直接卡住流水線

## 一個主流誤讀

很多人第一反應是「OpenAI 把安全掃描的核心技術開源了」——這只對了一半。**模型能力還在 OpenAI 雲端**，開源的是本地 CLI、SDK 與工作流，兩者都處於 beta，跑掃描受帳號權限限制。

作者的解讀：這暴露了 Agent 時代產品價值的分布——**模型是發動機，工作流才是整車**。兩千多行提示詞加上 schema、收據、狀態機、成本熔斷，合在一起才構成一個能用的產品。傳統 SAST 廠商的核心資產是規則、查詢與靜態分析引擎，即使能做跨檔案跨函式的資料流分析，也很難理解真實部署與業務語義；而這套 agent 工作流的上下文是先建的、驗證是動態的、定級是帶反證的——模型變強當然有幫助，但真正起決定作用的是**流程把模型框住了**。

需要說清楚的限制：這套階段劃分在概念上可以遷到別的模型，但當前開源實作綁定 Codex 執行時與 OpenAI 的模型，換模型之後的效果沒有公開驗證過。作者判斷 OpenAI 敢攤開的底氣在於「工作流易學、模型難追」。另一個市場訊號：2026-02-20 Anthropic 發布 Claude Code Security，消息一出好幾家安全公司股價當場下跌。

## 可搬走的五條方法論

1. **上下文先行**：先建威脅模型再找問題，任何沒有上下文的判斷品質都上不去
2. **候選與判決分離**：發現階段只負責提出技術上講得通的疑點，定級和排除交給後面的獨立階段
3. **動態驗證優先於靜態推斷**：能跑 PoC 就不猜、能呼叫介面就不讀程式碼猜行為，信心度永遠跟著證據強度走
4. **每個結論都要配反證**：主動尋找能推翻自己的證據，擺上桌面評估
5. **把關鍵中間產物落盤**：三個最終結構化契約用 JSON Schema 與交叉一致性校驗，其他帳本、清單與報告也有明確的格式與路徑約定——**模型的不確定性被工件之間的契約鎖死**

這五條沒有一條是安全領域專屬的。做程式碼審查 agent、法律合約審查、財報分析、醫療文獻篩查，骨架都一樣：把領域專家的檢查清單寫成技能檔、用 schema 與收據約束模型輸出、用預算與熔斷控制成本。

## 落地建議

- 先跑標準掃描，別一上來就開深度模式——標準掃描是單遍流程、通常成本更低，先看它在自己倉庫上的輸出品質再決定要不要加深
- 在 CI 裡務必設成本上限，`maxCostUsd` 這個參數就是幹這個的；掃一個 monorepo 的帳單可能超出想像
- 認真寫倉庫裡的 `SECURITY.md`，這套系統會把它當作權威輸入，寫的信任邊界與部署假設越具體，掃描結果越準
- 存量告警別扔給人工硬啃，用 `triage` 技能把 SARIF 檔案與歷史工單餵進去，讓它按程式碼證據重新排隊
- AI 給的補丁先跑測試再人工審。補丁契約裡寫了最小改動原則，但合併前的最後一道閘永遠是人

存取限制提醒：CLI 與 SDK 目前處於 beta，執行掃描需要相應存取權限，部分全庫掃描還可能需要 Trusted Access；沒排上隊的可以試 Codex 外掛版（有獨立入口），或直接讀原始碼把工作流設計搬回自己的專案。

## 三個判斷

1. **安全工具的形態會變**：從賣規則庫變成賣工作流加模型推理，傳統 SAST 廠商會被迫接入 agent 能力。GitHub 那邊的 CodeQL 加 Copilot Autofix 已在做檢測加修復建議的閉環，不過只覆蓋部分查詢
2. **倉庫裡的文件會變成高槓桿資產**：這套系統會主動讀取 `SECURITY.md` 與 `AGENTS.md`，寫得越具體掃描品質越高——以後給倉庫寫安全說明文件，等於在給 AI 安全員寫交接材料
3. **人不會退出這個流程**：AI 生成的補丁合併前還是要人審，尤其是生產系統的核心程式碼。開源維護者可申請 Codex for Open Source 計畫，入選者能拿 6 個月 ChatGPT Pro，符合條件的專案還可能獲得 Codex Security 的存取資格

收尾：Agent 產品的差距不在模型的跑分上，在於有沒有把領域專家的方法論變成**可執行、可校驗、可稽核**的工作流。
