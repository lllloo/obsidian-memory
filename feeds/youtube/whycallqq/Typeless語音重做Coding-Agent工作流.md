## 痛點：Agent 做得越快，越怕背景說漏

- 用 Claude Code、Cursor、Codex 最崩潰的往往不是 Agent 不做事，而是它飛快輸出後才發現一開始就理解錯。
- 案例：發版後才出現的 bug，Safari 較易重現，多刷新幾次偶爾恢復；舊登入邏輯不能刪，這次只允許排查、不能直接重構認證模組。
- 多數人只會打一句「幫我查一下 Safari 登入偶發失敗，可能和 refresh token 有關」，Agent 能跑，但從此全程靠猜，繞幾輪仍抓不到重點。
- 複雜任務的第一個錯誤常不是程式寫錯，而是**人把自己知道的東西省略了**。

## Karpathy 的語音習慣與表達成本

- Andrej Karpathy 分享過：覺得用鍵盤交代不清背景時，會切成語音自由講約十分鐘，不急著排版、不怕顛三倒四；他的觀點是模型有時只是需要更多資訊才懂你想做什麼，但人懶得全打出來。
- 作者認為重點不是語音比鍵盤高級，而是**表達成本**：一些零碎資訊看似不值得專門寫，漏掉卻會讓方向跑偏，例如「這只是猜測不是結論」「先調查不要直接改程式」「舊程式雖醜但現在不能動」。
- 這些資訊常不在 codebase 裡，只存在於當下處理問題的人腦中。
- 作者強調：語音工具降低的是表達與整理的摩擦，**工程判斷仍在人手上**。

## 實測：系統聽寫 vs Typeless

- 同一段口述（昨天發版、Safari 登入偶發失敗刷新恢復、懷疑 refresh token 但未確認、看過 Google Provider 設定與 Better Auth、不知是 token 更新時序還是 Safari 本身問題、舊登入邏輯因行動端依賴不能刪、這次不要重構、希望先分析原因／蒐集證據／排查路徑）。
- **系統聽寫**：只把聲音轉成文字，事實、假設、約束、目標全混在一起，Agent 還得自己判斷哪些可信、哪些是猜測、哪些不能做。
- **Typeless 整理後**成為較適合交給 Agent 的任務說明，關鍵在三點：
  - **保留背景**：發版時間、Safari、刷新後恢復等定位問題的重要上下文。
  - **保留不確定性**：仍寫成「可能和 refresh token 有關，但尚未確認」。「幫我驗證一個可能原因」與「修復 refresh token 問題」是完全不同的任務。
  - **提取工程約束**：舊登入邏輯因行動端依賴不能刪。若遺漏，Agent 很可能選看起來更乾淨的方案——直接重構認證模組。
- 中翻英：思考用中文，但變數名、錯誤訊息、Issue、技術文件多為英文；確認內容後可把中文任務說明轉成英文，方便與程式碼對照。實測「可能」「不要改」「僅限於」這類邊界詞在譯文中都有保留。

## 規格預檢：Ask Anything

- 說得多不等於有效資訊多，可能講很久仍沒提版本範圍、沒定義什麼叫完成。
- 發送前加一道預檢，類比提 PR 前先跑 lint：選取任務說明，按 Typeless 的 Ask Anything 快捷鍵，要求檢查是否明確包含——目標、已確認事實、未確認假設、檔名、介面名、版本、時間範圍、權限邊界、禁止事項、驗收標準；**只列出缺失或含糊項目，不要自行補全**。
- 能力邊界：它能檢查「有沒有寫出」檔名、版本、權限，但無法確認檔名是否真實、版本範圍是否正確、權限是否已核准——這些由人核實，或讓 Coding Agent 讀完專案後再問。
- 因此先不讓 Agent 改程式，補一句：先閱讀相關程式與歷史紀錄、不要修改檔案，指出任務說明中哪些問題會改變排查方案。
- 分工：Typeless 做輸入前的**靜態檢查**，Coding Agent 做進入專案後的**動態追問**。

## 研究佐證

- **HIVE preprint**（今年，研究語音轉寫與鍵盤錯誤對模型的影響，累計約 55 萬次評分生成）：輸入多一些「嗯」「啊」通常沒想像中致命；更傷結果的是原問題的**詞與邏輯關係在壓縮、重排、改寫時被破壞**。例如「我懷疑 refresh token 有問題」被整理成「refresh token 有問題」，任務就從沿此方向排查變成按既定結論修復。
  - 作者的判準：評估語音輸入不只看順不順，還要看有沒有守住事實、假設與邊界。
- **Anthropic 分析約 40 萬次 Claude Code session**：使用者展現的領域知識越強，session 達到「驗證成功」的比例越高。作者特別說明這不能證明長 prompt 更好，也不代表有因果關係，但至少顯示人對問題的理解仍影響 Agent 被帶往何處。
  - 剛接手專案的人只看到一條錯誤；經歷過幾次發版的人會想到灰度範圍、舊版相容、登入狀態遷移、快取、埋點與回滾路徑——這些常是經驗判斷而非程式碼。
  - 語音不會憑空產生專業知識，只是降低門檻，讓人更願意說出已知的事。
- **OpenAI 介紹 Codex 團隊工程實踐**：把應用介面、日誌、指標與追蹤都變成 Agent 可查詢的上下文，Codex 因而能重現問題、操作 UI 並驗證修復；文中觀點是對 Agent 而言，執行時無法取得的知識等於不存在。

## Voice Spec Loop 六步

1. **倒出**：先把現象、背景、猜測與不能碰的地方說出來，亂一點沒關係，先別漏。
2. **整理**：用 Typeless 處理重複、改口與口語順序，變成方便檢查的文字；多看一眼邊界詞有沒有失真。
3. **預檢**：用 Ask Anything 檢查是否缺目標、版本、權限或驗收標準；只找缺口，不讓它代編答案。
4. **追問**：讓 Coding Agent 讀 codebase，提出真正會改變方案的問題。
5. **確認**：由人核對檔名、介面、版本、數字與權限，特別留意「可能」「不要」「僅限於」「暫未確認」。
6. **執行**：這時才讓 Agent 擬計畫、改程式、跑測試、驗證結果。

- 角色分工：Typeless 降低表達與整理摩擦；Coding Agent 讀專案與執行；**人負責事實、邊界與拍板**。
- 看似多幾步，其實是把後面的返工提前變成一次便宜得多的檢查。

## 鍵盤與語音的分工

- 仍會切回鍵盤的情境：檔案路徑、Shell 參數、正規表達式、必須一字不差的函式名——錯一個字元都可能出事。
- 解釋舊邏輯為何不能動、上次發版改了什麼時，打字容易把整段背景壓成一句，此時更適合開口說。
- 作者的總結：鍵盤管「每個字元要對」，語音管「來龍去脈別漏」，是分工而非輸贏。
- 涉及公司程式碼、客戶資訊與敏感資料時，須先遵守所在組織的安全要求。

## 結語與建議

- 以前寫程式慢，很多問題在實作過程中被迫想清楚；現在 Agent 很快給出看似完整的實作，理解偏了返工也更快，因此值得在任務定義上多花兩分鐘。
- 建議找一個稍複雜、腦中有背景但打字解釋嫌麻煩的真實任務試一次（不要用「把按鈕改成藍色」測），觀察第一輪後還要糾正 Agent 幾次才拉回原方向。
- Typeless 免費版每週 8,000 字額度，Pro 版無限字數、更高準確度與團隊管理（影片含聯盟連結業配）。
- 工具之後一定會換，但事實、猜測與邊界都得由人講清楚。
