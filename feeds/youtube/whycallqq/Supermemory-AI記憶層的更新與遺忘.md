## 問題：會話之間的失憶

- Claude Code、Cursor、ChatGPT 等工具的會話彼此斷開，專案結構、程式碼規範、命名約定每次都得重講。
- 「上下文窗口都一百萬 token 了，全塞進去就好」是最大誤區：塞越多模型越抓不住重點、帳單越難看；關鍵資訊埋在長上下文中段時準確率明顯下滑（lost in the middle）。
- 真正解法是讓系統知道該記什麼、該忘什麼。

- 曾任 Mem0 AI 工程師、Cloudflare 開發者關係，後輟學到舊金山；2025 年 10 月拿到 260 萬美元種子輪（Susa Ventures 領投，個人跟投含 Jeff Dean、DeepMind 的 Logan Kilpatrick、Cloudflare CTO）。

  - monorepo：`apps/` 放文件站、網頁應用、Raycast 插件、記憶圖譜 playground；`packages/` 放各框架 SDK（Vercel、LangChain、LangGraph、OpenAI、Mastra）。
  - 創辦人提交 800 多次，典型創辦人驅動的開源專案。

## 核心主張：記憶不等於 RAG

- RAG 檢索文件片段、無狀態、對所有人回傳一樣結果；記憶追蹤的是**關於人的事實**，而事實會變。
- 官方例子：三月說「我住紐約」、七月說「剛搬去舊金山」——RAG 會把兩句都撈出來讓模型猜；Supermemory 讓新事實覆蓋舊事實，同時保留時間線。

## 三個關鍵設計

### 一、會更新：時序事實圖譜

- 每條記憶帶時間戳，可更新、擴展、被推翻。
- 背景常駐引擎（官方稱 dynamic dreaming）持續重讀文件與記憶、調和矛盾、把過期狀態重寫成新狀態。
- 記憶的難點不是存，是改。

### 二、會遺忘：臨時事實有有效期

- 例如「我明天有考試」，考試結束就失去價值；系統為這類臨時事實加有效期，到期自動作廢，雜訊不沉澱成永久記憶。
- 多數團隊在卷「記得更多」，這個專案在做「忘得乾淨」。

### 工程細節：fail-open 透明代理

- 請求經過 Supermemory 時，若記憶服務出錯，原始請求原封不動轉發給模型供應商——記憶掛了、聊天不掛，可靠性優先於功能。

### 三、主動供給：使用者畫像

- 傳統記憶靠搜尋，每遇新問題現查一次，約 300 毫秒且常查不準。
- Supermemory 為每位使用者自動維護兩層畫像：
  - **靜態層**：長期穩定事實（如資深工程師、用 Vim、偏好深色模式）。
  - **動態層**：近期狀態（如正在做鑑權遷移、在調限流 bug）。
- 每次會話開始一次呼叫約 50 毫秒，畫像直接注入系統提示詞，模型開口前就知道你是誰。
- 本質像把使用者資料預先快取，但難點在於快取內容由機器自己提煉與更新。

## 基準成績（廠商自報）

- **LongMemEval**（跨會話長期記憶與知識更新）：第一，Recall@15 達 95%。
- **LoCoMo**（長對話事實回憶，含多跳、時序、對抗樣本）：第一。
- **ConvoMem**（個人化與偏好學習）：第一。
- 效率：達 95% 召回時只往上下文加約 720 token，上下文佔用壓縮 99.4%。
- 記憶檔案系統 SMFS：在 xAFS 基準 110 題上，Claude 的 token 消耗從 7200 萬降到 2400 萬（省三分之二）；Codex 也省 1.75 倍。

## 本地部署與整合

- 一行指令安裝、單一 binary、零設定，首次啟動有互動精靈。
- 模型可選 OpenAI、Anthropic、Gemini、Groq 或任何 OpenAI 相容端點；Embedding 預設本地 bge-base，不需 API key。
- 完全離線可接 Ollama，gpt-oss 20B 就跑得不錯；資料不離開本機。
- 資料全放當前目錄的 `.supermemory` 資料夾，備份遷移即複製貼上。
- 本地服務跑在 6767 port，API 與雲端完全一致，改一行 baseURL 即可上雲。
- 官方開源插件：Claude Code、Cursor、Codex、OpenCode、OpenClaw；裝完每次會話自動帶入偏好與專案背景，重要事項自動存下。
- MCP server：一行設定接進 Claude Desktop、Windsurf、VS Code，只暴露三個工具：
  - `memory`：存與忘
  - `recall`：查
  - `context`：會話開頭注入畫像
- 連接器：Google Drive、Gmail、Notion、OneDrive、GitHub 即時同步；PDF、圖片、影片、程式碼檔可直接搜，程式碼按語法樹切塊。

## 競品比較

- **Mem0**：部署量最大，走「抽取 + 檢索」路線，向量庫加可選圖譜；2026 年 4 月更新演算法，LongMemEval 衝到 93.4%。
- **Zep**：開源 Graphiti，雙時序知識圖譜，每條事實帶生效與失效時間，舊事實只作廢不刪除，全程可溯源；3 萬 star、Apache 授權。
- **Letta**（前身 MemGPT）：把作業系統記憶體管理搬進 agent，模型自己決定什麼留在上下文、什麼換出。
- **LangMem**：綁在 LangGraph 生態。
- 共識：記憶需要獨立一層，分歧在實作。Supermemory 的差異：
  1. **維運成本**：Zep 自架要養 Neo4j 或 FalkorDB；Supermemory 本地版是單一 binary、資料在一個資料夾。
  2. **主動供給**：Mem0、Zep 主力是查詢觸發；Supermemory 把畫像做成一等公民，會話開頭主動交出。
  3. **輸入面**：競品主要吃對話；Supermemory 直接吃檔案與 Gmail、Notion 即時同步。
- 代價：每一步都過 LLM，寫入成本與延遲高於純向量方案（有第三方論文實測每個操作都涉及模型呼叫）。

## 冷水：基準分數都是自報

- Supermemory 自報 95%、Mem0 自報 93.4%、Zep 在不同口徑下報過 71.2% 與 94.7%。
- 有論文把各家數字放進同一張表：同一套 LongMemEval，Supermemory 換三個答題模型跑出 85.2、84.6、81.6——分數跟著設定走，不跟著品牌走。
- Supermemory 開源評測工具 MemoryBench；選型唯一標準是用自己的真實對話歷史實測。

## 觀點：窗口越大問題越貴

- 等上下文窗口到一千萬 token 並不會自然解決記憶問題：注意力會被稀釋，從百萬 token 找三週前的一句話像從一本書找註腳，且全部歷史每次都重新計費。
- 記憶是獨立系統層，值得單獨設計、優化、度量；指望模型順便解決記憶，就像指望作業系統順便幫你備份。

## 評估任何記憶系統的三問

1. **會不會更新**：系統知不知道新事實推翻舊事實？
2. **會不會遺忘**：沒有衰減機制的記憶庫三個月後變垃圾場。
3. **給不給得動（主動供給）**：是等你搜，還是會話開始就把畫像交出去？

套完就知道它是搜尋引擎還是記憶系統。

## 展望與建議

- 講者判斷未來一兩年記憶層會成為 AI 應用標配元件（類比今天的向量資料庫），但定位不同：向量庫解決找文件，記憶層解決懂使用者；延伸方向含 agent 間共享記憶、多模態持續沉澱、機器人視覺記憶。
- 建議：花十分鐘跑起本地版，感受畫像注入前後差別，再想產品中哪些該記、哪些該忘。好的記憶系統贏在會忘記。
