## 這包設定檔在解決什麼

剛上手 Claude Code 或 Codex 時，最卡的通常不是不會用，而是它不聽話：講過的事下次就忘、說不要動的檔案照樣動、要它先驗證，它說「驗證過了」其實沒驗。作者 Dustin 認為這是還沒把「默契」寫下來給它看，於是把自己每天在用的設定整理成免費、開源的 starter kit，內容包含 CLAUDE.md 模板、rules、skills 與 hooks。

## CLAUDE.md：每一輪都會被注入的最高默契

CLAUDE.md 在每一輪對話都會注入提示詞，模型會一直記得，是你與模型之間最高層級的默契。

### 撰寫原則

- **盡量精簡**：每一代模型都吸收大量使用者知識與慣例，舊模型需要提醒的事，新模型可能不需要；多寫的規則既耗額度，又會約束行為。
- **用正向敘述**，不用負向語氣約束。
- **給脈絡**：說明理由，模型遇到模糊狀況才能靈活處理。
- **不寫有時效性的內容**。
- **減法原則**：如果拿掉這一行模型不會犯錯，這一行就不該加。

### 模板中的範例規則

- **不可逆操作**：覆寫或刪除檔案前，先確認有沒有版本控制或備份，否則是不可逆操作。語氣不是「你不能覆寫／刪除」，而是附上理由；且拿掉這行模型很可能直接動手，所以必須保留。
- **別輕易採信回報**：派子代理時多半用較便宜、低階的模型做雜工，其回報有時被曲解或不完整；主 agent 輕易採信就會導致後續大幅漂移。規則要求對子 agent 回報、工具腳本回報都先驗證，確認對方真的有這個工具、真的有證據。

### 安裝方式

把 repo 連結丟給 Claude 或 Codex（Codex 會提醒檔名要改成 `AGENTS.md`，性質相同），請它問你問題、掃描工作資料夾，依模板產出屬於你的 `CLAUDE.md` 或 `AGENTS.md`。

## rules：用 frontmatter 決定何時載入

rules 的層級等同 CLAUDE.md，都是會注入對話的長期提示詞，差別在可以用 frontmatter 選擇載入情境：

- 指定檔名樣式：例如與 Python 相關的 rule，只在讀到 Python 檔時載入。
- 指定 path：只跟某資料夾相關的 rule，只在該路徑載入。

套件內附的 rules 包括派子代理規則、諮詢類事務的風險界限規則等。

### 判斷風險的兩個維度

作者特別推薦的一條：用「可逆或不可逆」與「可驗證或不可驗證」兩個維度判斷風險。

- 寄出一封信不可逆，風險較高，應請使用者確認；寫一份內部備忘錄寫錯可改，風險較低。
- 改一份檔案量小、人可親自檢查，屬可驗證；改資料庫裡一千筆 entries 則難以驗證，風險較高。

這些規則可以請 AI 用白話解釋，再依需要選配進 CLAUDE.md 或 rules。

## Skills：溝通、對外文件、收工與決策

### 讓模型說人話

- **ASD-STE100**：源自航空業維修／操作手冊的標準化簡單英語規範，因為從業者背景、教育程度、母語各異，英文要寫得直白。作者認為現在模型大量強化程式能力後變得不說人話，打 `/asd` 呼叫此 skill 即可把難懂文字改寫得好懂，較適合英語使用者。
- **ISO 24495**：有中文版本。與 ASD-STE100 的差別是：ASD-STE100 規範用詞與句構，ISO 24495 規範整篇輸出的邏輯與語氣，兩者可互相搭配。
- **explain**：把你當成沒有相關背景的高中生重新解釋；用短句、常用類比、先說結論、不堆砌資訊、不用表情符號。

### polite：對外文件的禮貌模式

模型寫給自己看要說人話，寫給外部的人還要顧及語氣是否粗魯。作者常嫌 Claude 語氣高傲，逐步教它後做成此 skill，經多次迭代後趨於穩定。內含三種禮貌模式及各自特色與適用情境：

- 溫暖、富同情心
- 正式商務
- 正式商務加親切感

適合常需產出對外交付物或寫信的人。

### 收工 skill

每個對話視窗做完一份工作時一定會跑：找出剛剛做了什麼、寫工作日誌、git commit、git push，最後回報做了哪些事。

### neat-freak：檔案之間的事實同步

多檔案管理時常只改了 A，忘了改與 A 連動的 B，例如 A 檔寫「對帳單已記」、B 檔仍是「未記」。AI 日後讀到過期或不同步的資料會做出錯誤決定，事實偏移越來越嚴重。此 skill 核對整個資料夾的文件是否不同步並協助更新，附有盤點腳本。

作者說明套件中有兩支 skill 不是自製：neat-freak 出自網友卡茲克，另一支出自一位不知名網友。

### first-principles：重大決策前的純邏輯檢查

作者幾乎每天用，源自 Elon Musk 分享的第一性原理思考，加上自己的優化。流程：

1. 先問這個需求該不該存在；刪不刪沒影響就刪掉。
2. 確定需求必要後，深挖問題本質。
3. 挑戰所有先入為主的假設與猜測。
4. 找出哪些不是猜測、而是雷打不動的事實。
5. 依事實與無法被挑戰的假設重組邏輯鏈，給出明確判斷方向。

適用於「這課程該不該做」「該不該做這個產品」「要不要進一步宣傳」這類需要純邏輯、而非陪你發散的重大決策。

### 其他 skill

- **info-diet**：檢查瀏覽器讀過的網站、網頁與文章，判斷資訊是否偏頗、是否每天吃進太多不健康的資訊。
- **phantom-pushback**：減少模型的說教感與「自己紮稻草人再打」的行為（作者認為 Opus 特別嚴重）。例如只要求把報價單付款方式從一次付清改成兩期，模型卻補一段「分期會延後收款日」的提醒。作者認為這源自訓練時要求模型別一味迎合使用者，導致過度緊張。
- **review-loop**：長文件（草案、計畫書）的分輪審閱收斂工作流。
  - 為每段標上特殊 ID，記錄每輪變動；追蹤哪些已改、哪些未改、哪些已核准。
  - 產出一個臨時網頁儀表板（在 Claude 裡是 Artifact），每段有「修改／提問／討論／核准」按鈕。
  - 已核准的部分之後不再給你看但會記錄；已修改的部分顯示差異；提問與討論繼續開展，逐步收斂。
  - 解決的痛點：長文件一次給十點，看到第三、四點就累了，後續展開成 1-1、1-2……，前面要改的沒改、歷史變更與新要求混在一起，最後東漏一塊西漏一塊。

## Hooks：純程式碼閘門，沒有選擇性遵守

CLAUDE.md 與 skill 本質上仍是餵給模型的提示詞，在上下文太長等極端狀況下可能被忽略。hook 則完全由程式碼構成，每次遇到特定情境一定會經過這道閘門。

### claim-guard

兩種檢查：

- **宣稱已驗證**：偵測到輸出含「已驗證」「測試通過」「已跑通」等關鍵詞時，檢查模型是否真的呼叫過測試／驗證類工具；沒有就擋下並指出它在說謊。模型若確實沒做就回頭補做，若有做就給出理由與證據。
- **宣稱不存在**：偵測到「不存在」「找不到」「沒有證據」等關鍵詞時，檢查是否真的用過搜尋或檢查工具；沒有代表是憑空推斷，要求拿出證據或補做。

作者認為這在自動化與品質之間取得良好平衡：長時間自動化時模型要在 loop 裡走很多段，若中途常謊稱驗證通過或謊稱找不到，會嚴重影響品質；裝了閘門就能自動偵測並要求補做，不需人工介入。

### no-emoji-guard

作者不希望文件出現 emoji 或顏文字，把所有顏文字做成列表；模型每次寫檔時掃一遍，掃到就直接擋下要求修改。重點不是提醒模型該不該寫，而是發現就擋、要它重做。

### 為什麼自然語言規則不是萬靈丹

上下文過長、模型注意力流失時，就會開始不守規定、忘東忘西。絕對不能漏掉的事，應寫成純程式碼邏輯的 hook，相對安全且不會遺漏。

## 怎麼開始

把 repo 連結丟給 Claude 或 Codex，請它用白話文解釋，並評估、討論哪些適合你裝，適合就直接裝上。使用中有問題或新想法可以到 repo 開 issue。作者希望這套 starter kit 幫 Claude Code、Codex 等 coding agent 使用者快速建立簡單的 harness，再往上發展更個人化的設定。
