## 核心問題：規則越加，模型反而越不聽話

長期使用 Claude Code 的人常發現：加越多規則、越多約束給模型，模型卻沒有越聽話，反而常常忘東忘西。根源在於沒有維護一個讓模型能專注的環境。

當約束資訊越長越大，模型每次對話都被默默塞進這些內容，上下文很快被塞滿，導致兩個症狀：

- 不遵守你設下的規則
- 才幾輪對話，表現就迅速下滑（注意力缺失、隨機遺忘細節）

## Harness 五層：模型專注的環境

Harness（韁繩）指的是讓能力很強但不受控的模型能在約束裡協作的整套環境。會佔用上下文的五層資訊：

- **CLAUDE.md**：約束模型的最高默契檔，每次對話都注入給模型
- **rules**：與 CLAUDE.md 同等級的規則，但可設定只在進入特定檔案／資料夾才動態載入
- **hooks**：完全按事件觸發的閘門（鉤子）
- **memory**：模型自己記下、關於專案的臨時記憶
- **skill**：特定情境下主動調用或被動呼叫的技能組

兩個作用範圍：

- **user level**：這台電腦每個資料夾啟動 Claude Code 都會遵守
- **project level**：只有在特定資料夾開啟 Claude Code 才需遵守

## 重整目標與 prompt 技巧

最終目的：**精簡上下文佔用，但維持原有規則的效果不變**——不能砍了之後喪失效果。作者強調「請用這個目的為最高原則執行本計劃」。

下 prompt 的關鍵技巧：

- **把最終目的講到最清楚**：就算中間過程寫得不夠詳細，只要模型知道你最後想要的成果，它會自行補全過程。
- **拆細步驟、建任務列表**：大計劃要求「步驟拆分越細越好」，模型會產生 to-do list（checklist），方便盯進度、避免跳步。
- **不懂就用工具問**：要求模型「調查時遇到不清楚的點要確認意圖」，觸發 ask question 工具（選擇題），避免它腦補細節。
- **派多個 sub-agent 協同**：大任務提醒模型派出多個 sub-agent，避免全部塞進同一個 agent 的上下文。
- 搭配 **plan mode**（CLI 用 `Shift + Tab` 切換，App 直接點選）。

## 為什麼用 sub-agent

單一 agent 有上下文視窗限制；大量資料若全給一個 agent，一樣塞滿上下文導致漏步驟、總結錯誤。所以派出多個 sub-agent 分頭調查，並界定好各自的調查範圍（user level 設定、project level 各專案設定、memory 等）。

## 主動協作：揪出 agent 之間的盲點

作者強調與模型協作要主動思考其任務編排是否合邏輯，而非放著讓它跑：

- **跨 agent 重複問題**：單一 agent 能發現自己資料內的重複，但第一個 agent 與第二個 agent 之間的重複它不會自動發現。因此要求模型「互動比對」，找出 agent 彼此間的重複。
- 發現編排不放心時，隨時把訊息補進去；模型會在下一次工具呼叫時把要求一併納入考量。

調查階段最後派出 4 個只看資料、只分析的探索型 agent，回報後又謹慎地多派一個 agent 去複查兩個待確認的點。確認出：哪些 hooks 是設過但從未觸發的多餘項、哪些東西真的吃上下文、哪些重複該不該動。

## 規劃階段：上網查最新最佳實踐

進入規劃階段後，要求模型上網搜尋官方文件與他人最佳實踐。重點原則：

- 設定類的東西**一定要上網搜最新資料**——設定日新月異，模型訓練時的預設知識可能與現況不同。
- 去重要「去蕪存菁」而非「去菁存蕪」，需參考官方偏好：模型喜歡看到哪些規則、哪些東西是多餘的。

上網查證後修正了幾個關鍵假設，例如：

- 原以為會佔上下文的某項其實是零成本、不用動。
- 原以為某 skill 沒有 description 無法觸發，實際上是有的。
- 確認哪些 hook 真的重複需移除、哪些規則可下放到只在部分路徑載入。

## 精簡原則：只留關鍵規則

作者觀察到模型記規則時很「廢話」：會把例子、前因、問題發生的時間、故事都記進去，這些默默佔領上下文。最佳實踐是只放關鍵規定（要做什麼、不做什麼）。

精簡原則（part b）：砍掉日期、事件、人名、故事、多餘的觸發條件與舉例，留下關鍵的觸發條件、起始約束、要不要做、精確且最小化的引數。

## 細部執行步驟

模型排出 30 個任務的細步驟，依序執行：

1. 先做零風險的精簡
2. user level（所有專案共用）內容精簡
3. 規則的精簡
4. 把默契檔裡的內容移到只在固定路徑才載入的規則檔（path scope，按需載入）
5. 精簡 hooks 裡過於冗長的注入文字
6. 處理個別 skill（作者有 100 多個 skill）：description 是否冗長、是否夠精準、是否重複
7. 修剪閒置、沒用到的資訊
8. 逐條審查每條規則的必要性
9. 語義向量去重
10. 最後排一個驗證

## 每步派「不繼承上下文」的獨立 agent 驗證

不要全部做完才驗證，而是**每個小任務做完就派一個獨立 sub-agent 即時驗證**。關鍵技巧——驗證用的 sub-agent 必須**不繼承上下文**：

- **不繼承上下文的 sub-agent**：只收到單獨要求，不知道主 agent 做了什麼，最適合審查——只看結果、只用標準評判。
- **繼承上下文的 sub-agent**：知道主 agent 的脈絡，適合多版本／多方向開發，但不適合審查（會「球員兼裁判」、合理化前面的做法）。

### Ctrl + O 抓包：驗證不能被引導

按 `Ctrl + O` 可看到 sub-agent 收到什麼指令、回傳什麼結果。作者藉此發現危險問題：主 agent 送給驗證 agent 時，特別指定「只檢查這三個地方」，這是**引導式檢查**——如果模型原本漏改了第四、第五個地方，被指定範圍的審查員根本不會發現。

修正：驗證 sub-agent 不應帶任何提示（不告訴它哪些必留、哪些該砍），只給最後的原則（砍掉冗餘約束、行為不變、精簡 context）。並要求之前已驗證過的全部回來重做。修正後的審查明顯更犀利，額外抓到問題。

## 逐條審查：拿掉這條規則會不會犯錯？

官方文件原則：每條規則都很珍貴，要想「如果這條規則拿掉，模型是不是會犯錯」：

- 會犯錯 → 規則留著
- 拿掉無關緊要（模型本來就會做）→ 不該留

因此加一個步驟：用獨立 sub-agent 逐條檢視做完後的所有檔案，每條獨立問「拿掉模型會不會犯錯」。提醒模型所有改過的範圍都要審查，包括容易漏掉的 memory。審查報告拿回後再判斷是否採納，有些建議會被駁回並說明理由；不認同可強制要求修改。

## 第二層保險：語義向量去重

擔心模型在讀大量規則時上下文塞滿、漏掉「意思相同但文字不同」的重複，於是加第二層：**語義向量**。把文字的意思轉成數學向量，計算兩句話雖文字不同但語義的相似度（類比：搜尋引擎搜「睡不著怎麼辦」也能找到「失眠解方」）。

- 對大量文件，請模型給整個 harness 的內容都上語義向量，比對出語義相近的 pairing，再人工確認是否真的重複。
- 實作上改用 Gemini 最新的 embedding 模型（比模型原本不認識的指令碼又好又快）：找出環境變數裡的 API、寫一個高效率指令碼一次處理 50／100／1000 條（作者帳號 rate limit 很高）。跑完確實抓到一些重複並去重。

## @import vs 純路徑實測

模型不確定 `@import` 是否會把引用的檔案文字也一起自動載入上下文。作者實際做實驗：留著 `@import`，用 `/context` 看上下文清單是否出現該內容，把結果貼回給模型。

結論：`@import` 確實浪費——那些東西不用每次都載入，卻用了會隨時載入的 `@import` 語法。於是改成純路徑。

## 移除多餘路由

模型也移除沒必要的內容，例如「沒必要在 CLAUDE.md 裡加的路由」——不加也不會犯錯，就拿掉。

## 成果：設定減 36%、每次新對話省約 4,000 token

- 整體設定精簡了 **36%**，過程中還會回報進度（如「目前精簡了 34%」）。
- 省下的 token 總共約 15,000；平均每次開新對話省約 **4,000 token**。
- 這 4,000 不只在對話開始送一次，後面每次對話都會送。

### 快取計價

- 一小時內的對話走快取計價，約原價 10%。
- 對話多次（如十次）後，這 4,000 token 最終也會算原價。
- 兩次對話間隔超過一小時，快取失效，token 全部重算。

比起省額度，更重要的是：省下上下文空間、解決衝突點、精簡冗長處，模型更容易遵循規則，也不容易在衝突時做出隨機決定。

## 結語

使用 Claude Code 不是開起來用就結束。協作過程中模型的「桌面」會被放上許多東西：要它讀的文件、幫它裝的工具、給它的說明書、要它記的小本本。維持桌面有序、整潔，不只為了省額度，更是為了能跟它在工作上走得更穩、更長遠。
