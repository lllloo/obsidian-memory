AI Labs 團隊花四天把 OpenAI 新發表的 GPT-5.6 Soul 用在自家產品（含自建社群平台）與客戶專案上。結論不是「Soul 比 Fable 更好或更差」，而是 Soul 的行為與 Fable 差異很大——用同一套方式操作兩個模型，等於兩邊都發揮不出實力。

## GPT-5.6 發表重點

OpenAI 這次一口氣推出三個模型：較小較便宜的 Luna 與 Terra，以及最強的 Soul。這一代主打「效率」——每個 token、每一塊錢榨出更多產出。

- OpenAI 宣稱 Soul 在 coding 與長任務上勝過 Fable，用的 token 更少、完成時間約為一半；整體智能與 Fable 相當，但成本更低。
- 原本獨立的 Codex 桌面 app 已併入 ChatGPT app；仍可透過 Codex CLI（終端版）使用 Soul。
- 新增 Ultra 模式：一次跑多個 agent，而非單一 agent。

**團隊的定調**：Soul 並不比 Fable 聰明。在沒有乾淨解法的難題上，Fable 仍能找到更好的答案。差異出現在「決策已定、接下來要把工作做完」的階段——Fable 擅長判斷「該做什麼」，Soul 擅長「一路做完每個步驟而不需要你把它拉回任務」。這個差異決定了你該怎麼用它。

## 法則 1：放手自主前先設好邊界

Fable 在覺得某動作有風險時通常會停下或拒絕；Soul 不同，它會一路採取行動直到把任務完成。實測中 Soul 遇到擋路的檔案與執行中的程序，會直接刪檔、直接終止程序而不先詢問。有其他測試者甚至遇到它幾乎刪光整台 Mac 檔案的極端情形。

設定方式：

- **開工前先建 checkpoint**：請 Codex 開一個獨立 git branch，把目前能運作的版本 commit 下來。branch 不會限制 Soul 能碰什麼，但給你一個乾淨的還原點。
- **在 Codex app 的設定裡**：approval policy 設為 `never`（Soul 不必等你就能持續工作），sandbox 設為 workspace-write（只能動這個專案內的檔案）。
- **切勿選 full access**——那會讓它連專案以外的檔案都能碰。

## 法則 2：交給 Soul 做 Fable 拒絕碰的 review

這裡指的不是偶爾路由到 Opus 4.8（多半發生在你要它解釋推理、或任務涉及有害內容時），而是 Fable 內建的安全限制本身。

團隊過去已用 Fable 做過這類 review，清楚它會在哪裡停手。把同樣的工作交給 Soul 時，它不會停在那些地方，會繼續檢查 Fable 一向拒絕檢視的部分，並在那些區塊找到問題。

## 法則 3：善用 computer use 做實機測試

Soul review 更好的第二個原因：它能打開完成的 app 親自測試。只要任務涉及畫面上看得到、點得到的東西，Soul 會自動啟用 computer use。在新的 ChatGPT app 裡，它的 computer use 可跨多個分頁、使用你已登入的網站、下載檔案——等於能走過你平常操作的畫面，而不只是讀專案內的檔案。

實例（自建社群的 store 功能）：這個 app 對不同帳號行為不同——admin 一組選項、一般會員另一組、$20 方案與 $100 方案能做的事也不同。所以只測一次不夠。Soul 以每一種帳號跑完整流程：分別登入、檢查各自能存取什麼、走完購買產品流程，再把這些檢查套到會隨帳號變動的其他部分。

**做法**：當功能對不同人行為不同時，在 build 完成後開一個新的 Soul 對話跑 review。給它各種帳號類型、說明每種帳號應該能做什麼，要它從頭到尾走完每條 journey，且只回報它能重現的問題。

## 法則 4：精簡 prompt 與 skill

較新的模型更會自己推導基本步驟，因此目標不是「把每個 prompt 縮到最短」，而是移除不會改變結果的指令、把真正重要的指令寫得更精確。OpenAI 在 GPT-5.6 Prompting Guide 中也是這個說法。

- **仍要給**：預期產出（outcome）、重要限制、以及「任務完成前必須成立的條件」。
- **不需要**：在資料夾命名已清楚時還逐一列出每個 folder、同一條規則在三個地方重複、描述模型該走的每一步。

以團隊的動畫系統為例：

- 保留了模型需要在 HTML 中複製的實際程式碼——與其描述動畫讓模型自行詮釋，不如給它可直接照抄的可運作範例。
- 保留了確切的背景 surface 與 accent 顏色，讓模型不會每次都自己挑新顏色。
- 更有用的是「找出可刪的部分」：原本有一條規則要模型把完成的動畫存進 output 資料夾，移除後再跑同類任務，Soul 仍存到那裡——這條指令沒有改變結果，因為模型自己就能推出成品該放哪。（團隊暫時仍保留這條，因為會在模型間切換，較弱的模型未必能自行推出同樣的模式。）

**該對自己的 prompt / skill 做的測試**：拿掉一條指令、跑同類任務、看結果是否改變；若模型仍能穩定做到，那條指令大概就不必要。OpenAI 回報這類清理讓它自己的結果改善 10–15%，同時少用 41–66% 的 token。

## 法則 5：暫時關掉 Ultra

Ultra 是 Soul 的多 agent 模式：不是跑一個 agent，而是把任務拆開、同時跑好幾個。OpenAI 把它定位為「最難工作」用的模式，但每個 agent 都消耗自己的 token，Ultra 因此會比一般 Soul 燒掉用量快得多。

團隊把跑過一般 Soul 的同類工作改用 Ultra 後，成品沒有明顯改善——用量因多個 agent 而增加，品質卻大致持平。OpenAI 自己的數據也顯示 Ultra 只把分數提高約兩三分（依測試而定）。

## 法則 6：用 Codex 訂閱時，別把小任務切給 Terra 或 Luna

Terra 與 Luna 走 API 較便宜，這在「你為自家產品送出的每個請求付費」時有意義。但透過 Codex 訂閱使用時，決策不同——你是在方案已含的用量內工作。

團隊把較輕的工作路由到小模型後發現：它們能完成任務，但品質下降，修正結果花的時間反而比用 Soul 還多。於是改回整個任務都用 Soul，而不是中途換模型。

## 法則 7：Fable 負責決策，Soul 負責執行

用過兩個模型於日常工作流後，最清楚的定位是：**Fable 是「coding 模型將走向何方」的預覽，Soul 則是「今天它們如何運作」的最完整版本。**

速度差異對工作流的影響比 benchmark 分數更大。日常使用中 Fable、Opus、Sonnet 完成同類工作都比較慢；Codex 模型則快得多——而且這還沒開 Codex 的 fast mode（會用掉 1.5 倍用量）。速度是團隊近來更常伸手拿 Codex 模型而非 Claude 的關鍵原因之一。

分工建議：

- **build 之前用 Fable**：需要幫你決定 app 該怎麼運作、功能該怎麼設計、某個難題為何一再發生時。
- **決策定了之後交給 Soul build**：完整功能、長時間任務、review，以及任何需要在畫面上檢查的東西。

四天下來，Soul 成了團隊的預設選擇（前提是已經知道成品該做什麼），而 Fable 仍處理需要更多判斷的決策。重點是：設好邊界、給每個模型對的工作、出貨前先 review 結果。
