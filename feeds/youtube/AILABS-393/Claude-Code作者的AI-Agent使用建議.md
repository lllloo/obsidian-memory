影片整理 Claude Code 作者 Boris Cherny 訪談中的實務建議。核心論點：多數人拿到新模型後仍沿用舊模型時代的用法，於是把「死重量」一路帶進 context，模型表現不好其實是用法過時，不是模型不行。

## 新模型發布就刪掉自己的設定

- 每次新模型上線就把自己的設定砍掉重來。Opus 5 推出時 Anthropic 自己對 Claude Code 就這麼做，刪掉約 80% 的 system prompt。
- 「設定」指所有你為了引導模型而加的東西：CLAUDE.md、自建 skills、hooks 等。它們在啟動時全部注入 context，並整段對話都留著。
- 這些內容多半不是為了描述你的專案，而是為了修正舊模型的錯誤；模型能力提升後，這種扶手反而變成阻礙。
- 用 `/usage` 看 5 小時視窗用掉多少、消耗來自哪裡（哪個 skill 最吃、哪些習慣在推高成本）。影片作者團隊的主因是同時開多個 session 跑 sub-agent，且長時間不 compact。
- 用 `/context` 在全新、還沒輸入任何字的 session 檢查：光是 system prompt 與內建工具就已占用約 3%（百萬 token 視窗）。這 3% 屬於 Claude 本身、動不了，其餘都是你自己的。
- 更乾脆的做法是 safe mode：關掉所有 CLAUDE.md、skills、plugins，只剩基礎 system prompt，再照常跑你的工作流看模型撐不撐得住。撐得住就開始刪。

### 什麼該留、什麼該刪

判準只有一句：**Claude 自己能不能想出來？** 能，就刪掉那行。

- 典型該刪的例子：`init` 產生的 CLAUDE.md 裡「用 `npm run dev` 啟動」這類行。舊模型不知道專案怎麼啟動才需要寫，現在模型自己會判斷並執行。
- 該留的是「你的做法與 Claude 預設不同」的部分。例如你要用 Vercel 的 agent browser 而不是它預設會抓的那個、你自訂的測試方式、必須先啟動的服務——這些它猜不到。
- 也可以用 `doctor` 指令自動修剪：它照同一條規則刪掉「Claude 自己能從專案推斷」的內容，保留曾出錯的地方、推理過程，以及與工具預設行為不同的部分。它會回一份健檢報告與建議清單，你逐項確認後才動，不會自己改。

### 安裝他人 skill 的風險已下降

Boris 表示模型現在較不易被 prompt injection 影響。影片作者實測從 GitHub 安裝一個內含「把資料送到某 URL」指令的 skill，Claude 沒有照做，也沒有靜默略過，而是在對話中直接說明該 skill 提出了這個要求、因為看起來不可信所以跳過。

## 用「會失敗的 eval」定義完成

刪掉設定之後，需要有東西告訴 agent 什麼時候真的做完了。Boris 認為這是大家最常做錯的一件事。

- eval 是一個固定的檢查，用來判定工作是否完成，而且**必須嚴格到有可能失敗**。「跑跑看是不是好一點」只是多繞幾步的猜測；不可能失敗的檢查不算檢查。
- 檢查要在動工前先寫下來，之後就沒有「到底完成沒」的爭論空間。
- 不一定要是測試，只要能回答「否」即可。例：頁面在手機螢幕上是否放得下、錯誤密碼是否確實無法登入、文字中是否沒有破折號。
- Anthropic 兩次大型改寫用了三種檢查：完整測試套件全綠；八個 reviewer agent，每個只負責找一類問題而非全部；parity check，把每個指令同時跑在舊版與新版比對輸出是否一致。
- 最值得抄的是 Boris 自己的例子：給 Claude 一個空 code base，要它用 Swift 重寫 Claude 桌面版，在虛擬 Mac 裡跑舊版、截圖、與自己的版本逐像素比對，不達標就不停。整個過程跑了兩週以上——正是那個比對機制讓它能持續這麼久。沒有東西告訴它「還沒完成」，agent 一小時內就會停滯，又得靠人盯著。

### 模型已內建部分檢查，但有上限

- 以前要在 prompt 裡明寫「去瀏覽器看看畫面」，現在它預設會開 headless Chrome（無視窗瀏覽器）截取不同區域，自行判斷有無元素重疊；也會回頭讀程式碼標出違規處。
- 但這些只抓得到「壞得很大聲」的問題。什麼叫「做完且正確」仍然只有你能定義。
- 檢查本身也會過期：Boris 說一組 eval 大約撐兩三個模型世代，之後就全部會通過，此時應整組丟掉，從模型現在會卡住的地方重寫。

## 說「要什麼」而不是「怎麼做」

- 過去要寫超長 prompt 把每個細節塞滿，因為留空隙模型就會跑偏。現在只要說目標，路徑讓它自己找。
- 如果你規定做法，成果上限就是你自己的做法。Boris 說資深工程師在這點上最吃虧，因為他們傾向要求模型完全照自己的方式做。
- 正確寫法是高層次的：描述任務、必須遵守的限制，以及「完成」長什麼樣，剩下交給模型。
- 同時把任務難度往上抬——刻意給比你以為它能處理的還難一點的工作。會寫一堆細節，通常代表你默默假設它做不到整件事，而這個假設已經過時。

### 同一個習慣在設計與發想上的變形

- 把靈感圖丟給 agent 說「照這個風格做 UI」，回來的多半是近乎複製品。改成用文字描述你要的風格與感覺，讓它自己推導做法。
- 發想也一樣：給它一個成功案例要它「多來幾個像這樣的」，產出會全都長得像那一個。
- 通則：任何具體的東西交給它，它都當成要複製的對象，而不是要學習的對象。改用描述，它才必須自己走到那裡。

## 四層階梯：模型一直做錯時該補什麼

刪掉多餘設定不代表什麼都不寫。Boris 認為每個團隊仍該寫 CLAUDE.md 與 skills，好讓 agent 不需額外說明就能在專案上工作。當模型持續做錯某件事，先判斷是哪一類缺口，成本由低到高：

1. **指令不夠清楚** — 改 prompt 就好。大部分情況屬於這類，成本為零。
2. **模型每次都需要知道的事** — 放 CLAUDE.md，但要保持輕量：專案用途一句話，加上會絆倒 agent 的點。它自己看得到的東西就是死重量。
3. **同一件事解釋到第五次** — 寫成 skill。skill 適合當輕量指南讓 Claude 需要時自己查，除非該領域真的需要才用規則鎖死。值得寫的是你或團隊特有的東西，通用最佳實務 Claude 已經會了，寫下來只是浪費。skill 變長就拆成多檔，讓它只載入需要的部分。
4. **資訊在 Claude 根本碰不到的地方** — 才用 MCP server 幫它接上。這一層不是用來解決誤解，也不是用來解決你重複說明，而是「真的沒有途徑知道」時才用。

**CLAUDE.md 與 skill 的差別在載入時機**：CLAUDE.md 每次 session 啟動都載入，skill 只在 Claude 真的需要時才讀。所以「短且永遠成立」的放 CLAUDE.md，「長或偶爾用」的放 skill，再由 CLAUDE.md 指路過去。影片作者的做法是頂層一份很短的 CLAUDE.md，細節放旁邊的 skills，例如驗證工作成果的步驟——那只有在檢查時才需要。同一份指令，一個每輪都收費，另一個不用到就不花錢。

## 一個 prompt 裝不下時：多 agent 的兩種路

- **Dynamic workflow**：說「use a workflow」，Claude 自己規劃拆分、一次派出一批 agent、等全部回報後再依結果派下一批。適用於需要數百個 agent 的規模，你完全不規劃。
- 影片作者**不建議**實際使用。最大案例是 bun 的改寫：兩週內以單一 prompt 重建百萬行程式碼（過程中人有介入導引），但少被提及的是它以 API 定價估算約花費 165,000 美元，且整合後仍有 19 處既有檢查沒抓到的損壞。錢還是小問題——一個 agent 出錯損失一小時，數百個 agent 跑兩週出錯就是整整兩週報銷，最後什麼都沒有，還查不出是哪一個開始歪掉。
- **Routines**：日常真正會用的形式。在雲端定期執行的重複性工作，關掉筆電也繼續跑。Anthropic 跨自家產品每天跑 20–30 個，每個只有一句話，例如：
  - 清掉不需要的東西，包含已移除功能留下的殘骸——因為 agent 每次翻找專案時都還會讀到它們。
  - 幫沒有測試的部分補測試，讓壞掉的時候是你先發現而不是使用者。
  - 找出同一件事被做了兩次的地方並合併——大型專案或第二大腦系統中，模型常忘記某些東西已經存在。
