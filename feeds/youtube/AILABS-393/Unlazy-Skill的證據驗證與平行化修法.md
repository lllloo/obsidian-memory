## Unlazy 要解決的問題

Unlazy 是 GitHub 趨勢榜第一作者（也是 design taste skill 的作者）推出的 skill，針對 AI agent「偷懶」設計。核心主張：**它不是告訴你 agent 做完了，而是證明做完了**——把工作對照一份 ledger（清單）驗證，每一項都必須附上完成的證據。支援 Claude Code、Codex 等主流 agent。

## Agent 為何會偷懶

- 模型本身沒有記憶，每次都要把先前所有訊息連同新 prompt 一起送進去。訊息越堆越多，模型同時要注意的東西也越多，對單一任務的專注度就下降。
- 全新的 context window 幾乎看不出問題，context 填滿後才明顯。
- 偷懶有兩種型態：
  1. **謊報完成**：叫它處理一批檔案，它只開了幾個就回報全部看過。真正的代價不在提早停手，而在提早停手還宣稱做完——你不自己驗證就不知道，之後在未完成的成果上疊加就會出事。
  2. **無聲縮減任務**：五個部分裡有一個難的，它做完四個簡單的、跳過難的，最後的摘要完全不提有東西缺漏。

## 既有解法的限制

| 做法 | 限制 |
|---|---|
| Ralph loop | 反覆送同一 prompt，直到輸出裡出現「完成」指標。但那條終點線只是 agent 自己寫的一段文字，很多任務無法用一句話判定是否真的完成 |
| Claude 的 goal 指令 | 用另一個較小的模型當裁判，讀「對話內容」判斷是否完成，而不是看成果本身，容易偏離實際需求 |
| 自建 task list + 檢查 | 檢查是真的，但打分的仍是 agent 自己 |

共通點：context 新鮮時都能運作，一深入真實工作就開始鬆動——而那正是最需要它撐住的時刻。

## 任務樹（tree）

- 收到大任務時不直接開工，先拆成小任務，再把每個小任務繼續往下拆，整體呈樹狀展開；停止分裂後，每個末端小任務交給各自的 sub-agent。
- 分裂次數由你指定，就是**樹的深度**。prompt 裡寫上 skill 名稱加一個數字；不給數字則自動取符合需求的最小值。
- 拆解的用意回到注意力問題：每個任務只有一個明確目標，執行的 agent 不必扛著整份工作。
- 但任務不能太小：**每個任務至少要值 10 分鐘的實際工作量**。深度設太高導致任務小於此標準時，skill 會自動把分裂次數降回預設值 3。

### 兩種執行模式

- **solo mode**（深度 3 以下，預設）：全部留在同一個 session，由同一個 agent 做完。
- **orchestrated mode**（深度 4 以上）：寫下一份 plan 檔記錄整份拆解，再為每個任務各寫一份 checklist。

## gates 檔：證據取代宣稱

前一版 skill 靠「叮嚀 agent 要仔細」來治偷懶，但指令正是長 session 中最先流失的東西——恰好是它想修的問題本身。因此這一版改成在任何工作開始前先寫進檔案。

gates 檔就是開頭說的 ledger，每一項稱為一個 **gate**：一個 checkbox，旁邊寫一個「必須為真才算完成」的 outcome。outcome 下方有三行：

1. 證明該 outcome 達成的**指令**
2. 該指令必須回傳的**確切字串**
3. **evidence**，初始值為 `pending`

skill 附帶一支 checker，執行時逐條跑那些指令。回傳內容含有該 gate 預期的字串就打勾，並把 `pending` 換成判定依據的那段回應。

**判定規則**：勾了但下面仍是 `pending`，代表是 agent 自己打的勾——等於又回到「agent 說它做完了」。這種情況算未達成，而且被視為**比空白 checkbox 更糟**，因為空白至少誠實反映工作進度。

在 orchestrated mode 下，主 agent 把單一任務交給全新的 agent，該 agent 只拿到 plan 與自己那份 gates 檔，對其餘工作一無所知。回報完成時主 agent 不採信，自行對該任務跑一次檢查，通過才在 plan 檔寫入一行並派下一個任務。

另有**誠實退場**機制：任務確實做不到時，agent 不是默默丟掉，而是寫下放棄該 gate 的名稱與理由，並納入最後的報告。

整體而言 Unlazy 是一套系統而非結尾的單一檢查，過程中**沒有任何一刻由 agent 自行決定工作是否完成**。

## 安裝

到官方 GitHub 頁面的 install 章節複製指令，在專案目錄下的終端機執行：

- 安裝程式先問**使用哪個 agent**。Codex 不需更動，它會裝進 Codex 本來就會讀的 `.agents` 資料夾；Claude Code 則從選單中勾選，可同時勾多個。
- 接著問 **scope**：只在當前專案生效，或全域可用。影片中選 project scope 以便先針對單一專案測試。
- 其餘照建議選項即可。

裝完在 VS Code 會看到 `.agents` 與 `.claude` 兩個資料夾，但不是兩份副本：skill 本體在 `.agents`，`.claude` 只是指向它的捷徑，讓 Claude Code 也能辨識，不會在同專案內重複。資料夾裡的 skill 檔案就是給 agent 的全部指引。

## 實測問題與修法

照原樣執行速度極慢：一次測試跑了約 3–4 小時，檢查進度時只做出一個登入頁。

**根因**：Claude Code 與 Codex 都能同時跑多個 sub-agent 平行處理不同任務，但這個 skill 派出一個任務後就等它完成，才派下一個。雖然有在用 agent，卻完全沒發揮平行能力。

**修法**：直接改 skill 本身的指令，讓它利用工具可同時執行多個 agent 的能力（影片中有可暫停複製的 prompt）。

修改後的執行方式：輸入 skill 名稱、樹的深度、再寫出要建的東西。從零開始做整個 app 用 5；只做單一功能則 2 或 3 就夠。深度給太高會自動下修，不必擔心選錯。

流程上它先寫 `plan.md`，再寫 `gates.md`。`plan.md` 裡還會註明哪個任務要動哪些檔案，避免兩個 agent 同時工作時互相覆寫。接著打好基礎，開始把工作同時派出去。

**結果**：10 個 agent 同時運作，跑了將近 2 小時，產出 demo app 的第一版，所有功能都照預期運作。

## 延伸

規模大時可搭配 model router skill：依任務性質分派模型，機械性的簡單工作走便宜模型、困難部分走強模型，避免太快撞到用量上限。
