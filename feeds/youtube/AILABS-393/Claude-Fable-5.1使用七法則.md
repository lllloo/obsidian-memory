## 先搞清楚：Fable 5.1 不是「做得更好」，是「做得更多、更便宜」

影片作者在自家客戶專案上讓 Fable 5 與 Fable 5.1 跑同樣任務、各跑數次（專案細節未公開）：

- **Fable 5 在多數任務上做出更好的成果**，Fable 5.1 只在其中一項勝出——而那是全部任務裡最難的一項，在該題上 Fable 5.1 品質更好、快約 40%、成本不到一半。
- 結論：**任務越難，Fable 5.1 越強。**
- 完成率上，Fable 5 有些嘗試會中途停下，Fable 5.1 每一次都跑完。
- 用 Claude Code 的 usage 指令估算（按量計費的等價成本），Fable 5.1 比 Fable 5 便宜約 47%。

### 便宜的原因是快取降價，不是 token 變少

模型不會記得上一則訊息，每次回應都得重送整段對話。Claude 會把已處理過的部分存成快取重複使用，也就是 **cached read**——仍要收費，但比一般 input/output 便宜。Fable 5.1 把 cached read 價格砍了 75%。

單則 prompt 上省不多（對話還短），但長任務裡同一段不斷膨脹的對話被反覆重送，省下的量隨每次回應累積。

**但輸出價格沒變**，而獨立評測機構 Artificial Analysis 發現 Fable 5.1 寫得比 Fable 5 多得多：輸出量約 1.7 倍，每項任務成本反而高約 20%。所以就算讀便宜了，帳單仍可能上升。

### 兩個要知道的代價

- **Guardrail 觸發後靜默降級**：Anthropic 說 Fable 5.1 的安全護欄打斷 Claude Code session 的頻率少約 60%，但一旦撞上，Claude Code 會**不告知你就切到較弱的模型**繼續跑，而且該 session 接下來全部由弱模型處理，即使你下一個請求與觸發原因毫無關係。已有案例：某人做遊戲，一個玩笑檔案裡出現 biological 一字就觸發，專案本身與生物學無關。若你的專案本身就落在護欄涵蓋的主題（如資安、生物），**沒有任何設定或措辭能避開**。
- **幻覺率上升**：Artificial Analysis 的測試中 Fable 5.1 準確度高於 Fable 5，但幻覺也更多——不知道答案時，Fable 5.1 有 72.6% 的機率編一個出來，Fable 5 是 63.6%。模型承認不知道反而比較好，因為你還能自己去查；編出來又被你相信，錯的東西就直接進了你的成果。做研究或寫作時影響尤其大。

## 七條規則

### 1. 把 effort 調低

Effort 是決定模型回答前做多少功的設定，同時影響品質與成本。

- 程式碼審查工具 Code Rabbit 用實際審查工作測 Fable 5.1：**low effort 抓到 61% 的問題，high effort 只有 57.1%**，而且快約 3 分鐘。
- 影片作者替自家社群網站加功能時看到同樣現象：high effort 在功能的某一部分來回卡很久，low effort 一次做完而且結果更好。

建議從 low 開始，只有在結果給你理由時才調高。

### 2. 刪掉為舊模型寫的指示

換到 Fable 5.1 後，那些為了修正舊模型行為而寫的指示還留在設定裡，但它們要修的問題已經不存在。Fable 5.1 仍得遵守一長串無用修正，白白吃掉用量，其中一些現在還會製造新問題。

- 手動驗證法：從 claude.md 拿掉一條指示，給 Claude 同類工作。結果一樣就代表那條不需要存在。
- 自動化：Claude Code 有 `claude api prompt audit` 指令，在終端機執行後會檢查你替 Claude 存的所有內容，指出哪些是為舊模型寫的並給出建議修改。它**不會自行改動**，你可以先看清單再選擇性核准。

### 3. 明講「沒人在旁邊看」

Anthropic 主打 Fable 5.1 適合長時間無人看管的任務，但它仍會在原始請求已涵蓋的步驟前停下來要權限——沒人回答時，等待等同於停擺。這是因為它的預設行為假設你就在旁邊協作。

Anthropic 的 Fable 5.1 prompting 指南建議：在 prompt 裡直接告訴它沒人在看，只要動作可回復，就繼續執行請求已涵蓋的一切。

### 4. 告訴它「什麼不要碰」

Fable 5.1 有做超過要求的習慣：叫它加一個功能，它可能順手修掉旁邊注意到的另一個問題，或把功能延伸超出你的描述。影片作者的客戶專案上，它去改了沒人要求它動的測試檔——這類額外編輯會改到你希望原封不動的部分。

做法：下任務時一併說明什麼不要動，並要求它若發現其他問題，在結尾提出而不是自行修掉。實際加上「不要編輯測試檔」後，它就只做了被要求的功能。

### 5. 要它就地編輯，不要整檔重寫

Fable 5.1 只需要改一小段時，仍傾向重寫整個檔案，即使其餘部分完全沒變。結果看起來沒問題，但每一行都算 output token，檔案一多就急速消耗用量。影片作者在自家 Second Brain 上就吃到這個虧。

做法：明確告訴它，當小改動能得到相同結果時，就只編輯那一部分。

### 6. 要求去掉 mannered prose

Anthropic 所稱的 mannered prose 是指模型用花俏措辭與比喻取代直說——例如不說「這個設定值得改」，而說成「這是一個值得轉動的旋鈕」。長篇研究任務裡這種語言會讓人抓不到重點。

Fable 5.1 用得比 Opus 5 和 Fable 5 少，套語與未解釋的行話也較少，但問題仍在；而且相較 Fable 5，它句子更長、分段更少，更難讀。直接叫它移除所有 mannered prose 即可同時解決兩者。

### 7. 給它大任務

Fable 5.1 的優勢在難題：作者的測試中最簡單的任務是 Fable 5 做得更好，最難的任務則 Fable 5.1 品質更好、快約 40%、成本低 58%。大任務才是「不中斷地把整件事做完」真正有價值的地方。

因此**不要把一個功能拆成很多小 prompt 逐步餵**，而是把整個功能一次交給它，並清楚描述你要的結果。
