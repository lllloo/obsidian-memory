Claude Code、Codex 與其他 agent 共通的問題：需要它們真正做決定時就露餡。模型能把問題想過一遍，但想不出新東西；找它們要點子，回來的是安全答案，你只好一再追問那些它本該自己發現的角度。影片介紹的 ADHD skill 就是把「注意力四處跳」變成 agent 的優勢——刻意把思考打散，而不是走一條直線。

## 為什麼 agent 不會發想

- agent 很擅長把大任務切成小塊丟給 sub-agent，各自在獨立 context window 裡工作，不必你開口就會建立 to-do 並盡量委派、平行推進。
- 但這種拆分**只發生在執行工作時**，要它發想時完全不會發生。跟它 brainstorm 同一個點子的不同角度，回來的東西讀起來像不一樣，其實都是同一個想法的不同措辭。
- 根本原因在訓練方式：agent 會伸手抓訓練資料中出現最頻繁的模式，因為「同一個答案反覆出現」正是教會它那是好答案的訊號。這不代表答案是錯的，通常也還可以，但問題還有其他它壓根沒看的角度——而那正是找它 brainstorm 的意義所在。
- 安全模式只是一半。另一半是它從不獨立評估每個點子：所有可能性都在同一個 context window 裡推演，想法互相滲透、context 被雜訊填滿，思考品質不升反降。所以它無法清楚評估任何東西，最後就是同一個想法換句話說。

## 運作方式：tree of thought

- 把發想（或任何方向很多的任務）拆給多個獨立 agent，形成 tree of thought：多條 sub-agent 分支像樹枝一樣岔開、各自隔離處理不同想法；最後每條分支各自定案一個可能性，再全部收回合併成最終答案。
- 這些 agent 完全隔離、零共享 context，彼此不知道對方在做什麼。這裡的隔離**不是為了分工**，而是為了讓各個想法無法互相影響。
- 隔離的手段是 **frame**——看待問題的不同鏡頭。skill 內含一整個 frame library，收錄 agent 可以走的各種方向；每個 agent 挑一個 frame，拿到該 frame 的 prompt 加上 system prompt 與問題本身。
- 接著由 **critic agent** 為所有回傳結果評分，決定哪些值得留下。三個評分項：
  - **novelty**：想法實際上有多新、多有創意
  - **viability**：現實中做不做得出來
  - **fit**：與你要解的問題契合度多高
- 評分在自己獨立的 agent 中進行，其 prompt 要求它扮演「多疑的資深工程師」，整份工作就是對讀到的東西嚴苛以待，再依分數決定該想法存活或淘汰。
- 最後 skill 列出最強的幾個想法，並走過 trap list——即每個想法若真的採用可能引發的問題——然後優先排序那些被標為「非顯而易見」的想法。

## 安裝

- 安裝指令在專案 GitHub repo 上，複製後在你要用的專案終端執行。
- 會問要裝給哪個 AI coding agent，支援 45 種以上，選你在用的即可。
- 再問是只在當前專案可用（project scope）還是任何專案都可用。只在一處需要就選 project scope。
- 完成後 skill 落在 `.agents` 資料夾——Codex 等許多 agent 用它放設定，但 Claude Code 預設只認 `.claude` 資料夾，所以用 Claude Code 的話把資料夾改名為 `.claude` 就會被抓到。
- 內容只有單一個 `SKILL.md`，全部自己搞定，旁邊沒有 reference 檔或相依項。
- 指示中明確逼 agent 越過前三個答案：檔案直說那前三個是模型訓練資料中最常見的回應，也是任何資深 agent 立刻就想得到的；資深 agent 真正做得到的有趣東西要在那之後才開始。

## pre-check：決定要不要啟動

開這麼多 agent 很燒 token，所以有一道前置檢查決定這個 skill 該不該跑。

- 用 slash command 呼叫或直接明講要用它 → 立即啟動，跳過 pre-check。
- 你沒提、由 agent 自行決定是否自動叫起時 → 先讓問題通過三個提問：
  1. **問題是不是開放式的**：有經驗的人在這裡會有好幾個都行得通的答案，還是只有一個正確答案？只有一個正解就沒必要多角度思考、純浪費 token，到此為止。
  2. **賭注是不是真的高**：如果顯而易見的那個答案結果是錯的，你是否會真的付出代價。
  3. **你怎麼問的**：用了 quick、standard 這類字眼，代表你要的就是直接答案，於是不啟動 skill。
- 前置步驟之外，檔案還列出整個 loop 的各階段、frame 對照表（發給各 agent 的不同方向），以及明確告訴 agent 要避開的模式。

## 用法一：TDD 的測試規劃

先寫測試再逐塊建到全部通過。需求嚴格寫成程式碼後，任何弄壞 app 的改動都會被測試抓到，agent 被迫遵守。

- 寫測試正好是該交給這個 skill 的問題，因為這正是 agent 弱的地方：它們不會涵蓋該涵蓋的所有情況，只圍繞常見答案寫測試，從不去看使用者可能走過 app 的其他路徑。
- 就算給很詳細的 prompt、甚至建一個專責寫測試的 agent，它們仍會退回同樣的模式。
- 執行前 agent 需要先知道你在做什麼：寫一份 PRD（app 該做什麼、解決什麼問題、目標、給誰用），另附一份技術規格文件鎖定技術細節，免得你反覆交代要用哪些工具。把這兩份連進 CLAUDE.md，讓它從一開始就取得脈絡。
- 用 slash command 叫起 skill，描述你在建的 app，要求它以 TDD 方式寫測試案例。因為是明確呼叫，它跳過 pre-check 直接開五個 agent，各自挑最貼合問題的 frame 往不同方向想，帶回不同的測試撰寫路數。
- 接著依前述準則評分、挑出前三名深入探索。全部完成後你會拿到一份詳細報告，含各測試方向與分數。分數用縮寫表示：`N9` 代表 novelty 九分、`V8` 代表 viability 八分、`F10` 代表 fit 滿分。每個想法另附實作草圖、風險與起手步驟。
- 產出的想法不像一般的測試組合：一般 agent 寫的測試只確認 app 運作正確，這個 skill 給的想法涵蓋更多邊界情況，也抓效能問題。最後得到的是分成三條深度探索分支的測試套件，各自測試 app 中不同的路徑。
- **要講清楚的限制**：這個 skill 只**規劃**測試，不實際寫測試，交回來的是策略。之後由你告訴 agent 要走哪個方向，它才去實作。可以只取一個方向，也可以三個都做；效能對你很關鍵就三個都要，但那要花不少時間，因為 agent 得一條一條走。
- 完成後可以明顯看出測試比原本詳細很多，因為整套測試策略在寫下第一行測試之前就已深入規劃完畢。適合在開始建置之前跑，先涵蓋大部分地面，降低日後弄壞 app 的機率。

## 用法二：上線前抓 churn 風險

另一個用法是在出貨前跑一次，請它評估使用者體驗，標出任何可能讓人在瀏覽或使用產品時卡住、進而導致 churn（已經開始用的人停止使用）的東西。

- churn 常在網站上線、真人開始使用後大量發生，付費產品尤然：一開始喜歡，後來因為某個功能不如預期而離開並要求退款。多數時候起因是建置期間被忽略的小東西進了正式版，之後才引爆。
- 影片作者在自家社群網站上實測，當時正在推出新功能、站上已有大量成員，任何新東西都必須仔細檢查，以免破壞既有成員的體驗。
- 用 slash command 叫起、給它該功能，請它推敲人們可能在哪裡流失、哪裡會有糟糕體驗。它先深入走過整個應用蒐集脈絡，再照同樣方式開 agent，浮現約 30 個不同想法，從中挑前三名深入探索。
- 最後所有發現都附上 novelty、viability、fit 三項評分。它抓到完全沒被發現的缺口，例如 PRD 中承諾但從未實作的功能——不修就會出貨一個與宣稱不符的東西——以及其他若干發現。每一項都附建議修法，並列出隨之而來的陷阱與風險。
- 與測試那邊一樣，它自己不修任何東西；你把想處理的發現交回給 agent，由它去實作。好處是這些全部在上線前處理完，而不是上線後。
