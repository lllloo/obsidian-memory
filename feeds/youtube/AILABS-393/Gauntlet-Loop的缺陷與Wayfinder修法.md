## 什麼是 loop

在 loop 出現之前，用 Claude 建東西時檢查的人是你：送出 prompt、拿回結果、看哪裡不對、再告訴它改，反覆直到滿意。

loop 是把你從這個一來一往裡拿掉：你給 agent 目標與它必須達到的標準，它自己持續檢查自己的產出，直到達標為止，你只在最後看結果。

## Gauntlet loop 的由來

- 起點是 Matt Schumer 在 X 上貼出的第一人稱射擊遊戲 demo，宣稱 Claude 用單一 prompt 建出來、沒有用任何現成素材。
- 這則貼文之所以爆紅，是因為「一個 prompt 產出完整可玩的遊戲」超出當時大家對模型能力的認知。
- 幾天後他公開了實際做法，並把這個方法命名為 gauntlet loop。
- 關鍵設計：他沒有叫 agent「把遊戲做好」——「好」是 agent 自己定義的，而**自己定標準的 agent 會讓自己的作品過關**。他改成給它一個真實存在的遊戲去對照。
- Andrej Karpathy（OpenAI 創始成員之一）評論這類結果的意義在於：過去這種品質的產出不值得投入成本去做，但模型沒有這個限制。

## 三行 prompt 的結構

Schumer 公開的 prompt 只有三行，每行負責一塊，簡單到你可以照樣改寫成自己的題目。

**第一行：建什麼 + 品質門檻**

- 前半定義要建的東西（他的案例是第一人稱射擊遊戲）。
- 後半定義要達到的品質等級：對標最新的 Call of Duty，明確要求 triple A（業界對最高預算遊戲的稱呼）品質，並逐項列出從貼圖到物理都必須到位。

**第二行：怎麼建（工作如何拆分）**

- 要求主 agent **自己**把目標拆成小塊，每塊交給獨立的 sub-agent。sub-agent 是主 agent 啟動的獨立 agent，各自在自己的記憶裡處理自己的小任務，互相看不到對方在做什麼。
- prompt 特別強調拆分要由 agent 自己完成，這樣拆解的麻煩就不會落到你頭上。
- 同時給每個被啟動的 sub-agent 掛一個 loop，並附上一個獨立的審查 sub-agent，稱為 **critic**。
- critic 的唯一職責是檢查產出，不夠好就退回給 builder agent 修，直到過關為止。critic 自己不建任何東西，且**開局沒有任何先前記憶**——它不知道這東西是誰做的、也不知道這塊已經被退回過幾次，它只需要嚴苛而誠實地打分。

**第三行：最終驗收標準**

- 告訴 critic 什麼時候可以停。Schumer 把 Call of Duty 設為遊戲外觀的標準。
- 指示 critic **盲測比較**兩者、說出哪個比較好。盲測的意思是不告訴它哪個是 Claude 做的，它只是挑出兩者中較好的那個。

**結尾關鍵字**：prompt 末尾還有一個 Claude Code 的關鍵字（轉錄為 `ultra code`），加上它會把流程轉成 dynamic workflow——一次跑一整批 sub-agent，而不是把工作只分給少數幾個。

## 這其實是 graph，不是單純的 loop

用這種方式跑工作時，實際畫出來的是 graph——graph 是 loop 的進階形式，是很多不同 sub-agent 各自在 loop，而不是單一 agent 自己 loop。

Gauntlet loop 畫出來的是**菱形 graph**：頂端一個任務散開成數個並行的 sub-agent，再收斂回單一 agent 把所有發現彙整成一個答案。

## 兩個致命問題

**問題一：檢查完全交給主 agent**

主 agent 自己決定怎麼開 critic、自己寫 critic 的指示。你既控制不了有哪些 agent，也控制不了評審 prompt 怎麼傳給 critic。你給的只有一個對照遊戲，其餘就是一句「當個嚴苛的評審、用視覺檢查」。

檢查應該被具體設定，而不是放給 agent 自行驗證。以這種規模在跑，長期下來出問題時你查不出原因。

**問題二：品質門檻依賴一個既存產品（決定這方法對你是否可用）**

- Call of Duty 是已上市的遊戲，critic 有真實對照物，這正是這方法成立的原因。
- 建遊戲、landing page、3D 世界都沒問題——永遠找得到對照物。
- 但**你建的是新東西時，沒有既存 app 可以當標準**。critic 只好自己編一個標準，並開始照那個標準放行工作。
- 等你發現它假設的方向不是你要的，時間與 token 已經燒掉一大堆——你拿回一堆一口氣建完、卻是照 agent 自己編的標準建出來的功能。
- **沒有對照物才是常態，不是例外**：要建自家公司運作的計費規則時，根本沒有現成的東西可以交給 critic 去比對。

結論：gauntlet loop 在「有夠接近的東西可抄」時有效，一旦沒有就崩掉。

## 修法：驗證 + Wayfinder

修法分兩部分：

1. **驗證**：把檢查事先規劃好，而不是放任 agent 自己發明（頻道另一支 graph engineering 影片的主題）。
2. **給 loop 具體的需求**，讓它不會偏離你要的東西——這就是 Wayfinder skill 的角色。

### Wayfinder 是什麼

- 由 Matt Pocock 製作，他發布了一整套可安裝使用的 skill，各自負責不同工作；Wayfinder 是其中的密集規劃用途那支。
- 依他自己的說法，它建立在他 AI 出現之前當開發者時學到的規劃基本功之上，**與寫程式無關**，任何需要規劃的事都能用。

### 它要解決的「迷霧」

用 agent 規劃大東西時，終點是清楚的，但抵達的路徑不是——中間這段 Pocock 稱為 **fog（迷霧）**。

agent 從來不會告訴你它正身處迷霧中，它會用自己的假設填補空缺，然後當作那件事已經定案繼續規劃下去。你拿回的是一份看起來完成、中間卻塞滿臆造內容的計畫。

### 運作方式

1. 建出一張 **map**，每個尚未拍板的決策都以「一個問題」的形式進到 map 上。
2. 問題分成兩組：**現在就能定案的**（所依賴的事項都已決定）、以及**仍在迷霧中的**（有你還沒查清楚的東西卡著）。
3. 關鍵在於：**Wayfinder 遇到迷霧時不猜**。它派 agent 去清除迷霧——手段可以是做研究、粗略做個東西出來看了再反應、或現實世界的動作（例如去註冊某個服務才能評估它）。
4. 每一項各自處理完後，答案回填到 map 上，解鎖原本卡在它後面的問題。
5. 一題一題走完 map，直到沒有迷霧為止。

最後你得到的是**每個決策都被寫下來、並附上理由**；Wayfinder 把這些整合成一份 **spec**——一份說明你在建什麼、以及為什麼的文件。

### 為何這能修好 gauntlet loop

就像 Call of Duty 對遊戲扮演的角色一樣，**spec 成為同樣的驗收基準**，標示什麼叫「做完了」。而且 spec 裡每個決策都是真的被定案過、不是被假設的，所以當你在建自家計費規則或任何沒有東西可抄的題目時，critic 依然有紮實的依據，不必自行發明標準。

## 實作示範：HR 系統

**改造原版 skill**

- 原版 Wayfinder 可從 GitHub 安裝（repo 內有可在 Claude Code 執行的安裝指令）。
- 但原版對他們來說**過度冗長**——它設計成一路帶你走到完整的 spec，而他們只要「取得清晰度」那一段：走完之後有完整計畫，其他不要。
- 原版會把問答過程中的每個決策各寫成一個獨立的需求檔案供 agent 回查。它定義了要建什麼，但他們要的是一把 agent 可以拿來自我對照的**答案鑰匙（answer key）**。
- 於是他們請 Claude 改寫這個 skill：把決策整合成單一 answer key，而非每個決策一個檔案。Claude 整支重寫，保留原版主要部分、其餘照新目標重塑。
- 成品簡單很多：**只產出兩個檔案（map 與 answer key）**，取代原版的一堆獨立工單。
- 另外，Wayfinder skill 本身不能單獨運作，它會呼叫 Matt Pocock 的其他 skill；他們的版本把依賴也減少到**只需三個 skill**。例如問答環節用的是 Grill Me 這支。

**執行流程**

1. 開 Claude Code，執行 Wayfinder 指令——這是 agent 不會自己啟動、必須手動觸發的那類 skill。
2. 告訴它要什麼（此例為 HR 系統，可用來請假、申訴等），它開始提問：這個 app 到底是給誰用、什麼必須有、什麼不必有、「完成」長什麼樣、上線給人用之後可能出什麼問題。
3. 這是一段很長的一來一往，**最後停在 34 個問題**。
4. 答完後它結束訪談，把兩個檔案寫進 `.wayfinder` 資料夾：
   - **map**：所有做過的決策、每個決策背後的理由、以及成品應該長什麼樣。
   - **answer key**：純粹只有檢查項，每一行的結果不是 pass 就是 fail。

**接上 gauntlet loop**

- 直接複製 Matt 貼出的原版 prompt 交給 Claude，請它照你要建的 app 改寫。
- **唯一要改的是對照基準**：把「某個遊戲」換成「真實來源是規劃產出的 `.wayfinder` 資料夾」，所有東西都照裡面的內容驗收——扮演的角色跟原版的 Call of Duty 完全一樣。
- Claude 會用同樣的 gauntlet loop 格式交回改寫版。

**執行結果**

- 跑法與原版相同，差別在 sub-agent 這次手上有 answer key 可以對照檢查。
- 他們明確告知「沒有『夠接近就好』、不准抄捷徑」。
- agent 先規劃要先建什麼、需要安裝哪些工具、再做地基工作讓後續 agent 有紮實的基礎，之後一次啟動大量 agent，各自負責系統的不同部分。
- **耗時 1 小時 33 分，用掉約 40% 的 session 額度**。
- 若改用 API 而非 max 方案，同樣這次建置**約需 116 美元**——相當貴。
- 成果是照規劃建出來的 app，想要的每個功能都正常運作；仍有一些問題，但整體是最接近他們需求的實作版本。
