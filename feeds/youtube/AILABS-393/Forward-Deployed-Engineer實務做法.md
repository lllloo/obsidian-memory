## FDE 是什麼

Forward Deployed Engineer（FDE）的整份工作就是**讓一間企業真的用上 AI**。這不是進去做顧問或交出一份策略文件，而是把 AI 跑進他們既有的系統裡，讓原本人工在做的事改由 AI 完成。

任何流程裡都只有三種東西在運作：**人**、**照固定規則跑的軟體**、或 **AI**。FDE 就是知道流程裡哪一段該交給這三者中的哪一個的人。

### 未被記錄的步驟：退款案例

某公司把退款申請交給 agent 處理，紙面上是成功的：它讀每筆申請、對照退款政策、駁回不符合的。但幾週後公司開始流失往來多年的客戶，沒人查得出原因——因為 agent 駁回的每一筆，政策上都該駁回。

FDE 去和原本做這份工作的人坐在一起，發現對方有一個**未被記錄的自訂步驟**：他們會先看這筆訂單是怎麼付款的，如果是用公司卡買的，就直接批准、不再往下讀。因為那些來自每個月都採購的企業客戶，為了一筆退款爭執會賠掉整個客戶關係。

政策裡完全沒寫這件事，那是他們自己在多年前摸索出來的。後來這道檢查被放進 workflow，成為排在模型任何判斷之前的固定規則。

### 為什麼需要有人專職做這件事

**人講不出自己真正需要什麼。** 他們會描述一個自己已經想像出來的東西，而不是實際遇到的問題。真正在做事的人只想把自己的工作完成、只希望產出越輕鬆越好，他們不會去看流程本身，所以很難建出他們願意採用的東西。

而這正是現在大多數企業的狀態：AI 紅了之後，他們在所有事情上加 AI，卻沒先確認自己是不是真的需要。

**沒有原本就在公司裡的人會做這件事**：工程師有自己的工作要趕；負責流程的人做了太久，流程裡那些繞路的做法在他們眼中已經完全正常。

- Palantir 曾為了一個這樣的繞路做法**卡了整整一年**：改用新檔案格式的計畫推不動，因為有位工程師一直說新格式比較差，沒人查得出為什麼——直到有人真的去看她怎麼工作。原來她一直是**用滑鼠雙擊打開檔案**來檢查資料，而新格式沒有東西可以雙擊。團隊當晚做了一個能用同樣方式打開新檔案的小工具給她，兩天後她就批准了這次遷移。

### 需求數據

- 這個職缺一年內成長 **729%**。
- AWS 投入十億美元建立一整個 forward deployed engineer 部門。
- OpenAI 自己的 FDE 團隊從一月的 2 人成長到 39 人。
- 光是 Y Combinator 內部就有超過 100 家新創在徵這個職位。
- 三年前基本上沒人需要 FDE。OpenAI forward deployed 團隊負責人 Colin Jarvis 表示外面的 FDE 就是不夠多——**需求出現得比人才早**。

## 為什麼工具不是難的部分：MIT 的 95% 研究

工具誰都能註冊，多數企業也早就註冊了。MIT 曾針對這點做研究，檢視 300 個 AI 專案並訪調這些公司內部數百人，發現**其中 95% 完全沒有產生任何可衡量的回報**。

MIT 自己的結論是：**失敗是公司自己造成的，不是模型造成的**。一無所獲的那些用的是 demo 上看起來很好、一碰到真實工作就散掉的通用工具，而且他們圍繞這些工具建的東西，從來沒有學會他們的生意實際上是怎麼運作的。

Vasuman Moza（曾任 Meta 工程師，現在開公司專門把 AI 裝進大企業，本質上就是 FDE）說：**AI 只是被拍在壞掉的流程上面，因為沒有人先去看流程**。他談過的一位主管在 3 個月內燒光了一筆原本要撐一年的一千萬美元預算——公司把工具發給所有人就放著不管，每個人各自開了自己想開的東西，錢花掉了，公司原本在做的任何事都沒有變得更好。

## 大公司實際做法的四個共通模式

作者彙整了 Anthropic、OpenAI 等公司近期公開的談話，分析後發現同樣的模式在每一套 workflow 裡重複出現。

**一、挑真正在花公司錢的流程 → 看「量」**

找的是那種**同一類訊息一天要處理 50 次**的人。自動化一則訊息對誰都沒有幫助，但自動化一週要送一千次的訊息，才是企業真正變得更有生產力、賺更多錢的地方。

這件事現在很容易找：企業的支援歷史紀錄裡就有它的全部過去，交給模型，它會告訴你量在哪裡。OpenAI 團隊在全球最大的銀行之一就是這麼做的——他們鎖定數千名理財顧問每天都在做的那一件工作，**最後約 98% 的顧問實際使用了他們建的東西**。

**二、建在企業既有的東西之上**

用 AI 時這件事比以前更重要，因為 **agent 的價值等同於它構得到的東西**。

如果團隊的工作都放在 Notion，不要為了讓 agent 好讀就另建一套系統並把資料全部搬過去，而是**用 MCP 把 agent 接上他們的 Notion**，所有人照原本的方式工作。多數專案都是這樣做的，因為企業不願意放棄自己已經投入大量時間與金錢的系統。Moza 有個客戶花了 500 萬美元、5 年才上線他們的財務系統，要他們搬離是不可能的，**整份工作就是讓公司裡其他所有東西都能跟這套系統對話**。

**三、不要過度改變人們的工作方式**

如果某人跑了一套 11 個步驟的流程好幾年，你交給他一個一步完成的版本，他會停止使用。他們原本邊做邊檢查，現在中間都不見了，卻被要求信任一個憑空出現的答案。

Moza 的建議是**讓流程看起來仍是他們熟悉的那一個**：讓 agent 在每個步驟裡面做事，但把步驟保留著，讓人還有東西可以看、可以確認答案是對的。

**四、給「建立信任」的時間要遠多於「建置」**

在同一家銀行，OpenAI 的技術面 6 到 8 週就完成了，接著又花了 **4 個月的試行與測試**，理財顧問才真的願意依賴它。

因為如果你過去一年每天都用同樣的方式做某件事，任何對這個流程的改變都必須自己掙來被接受的資格——不論對象是五千人還是五個人。

## 自己執行的五步驟路線圖

**第一步：先觀察，不要先建**

去看一份工作真正是怎麼做的，**按實際發生的順序把每一個步驟寫下來**。然後逐一問每個步驟為什麼要這樣做。如果沒人講得出具體理由，那通常是某人多年前放進去、之後再沒人質疑過的繞路做法。

**第二步：決定哪些部分該變成 AI、哪些不該**

把整件事交給模型，正是你落入那 95% 的方式。把寫下來的每個步驟過三道濾網：

| 濾網 | 判準 | 歸屬 |
|---|---|---|
| 1 | 這步驟是否遵循固定規則、且每次都必須正確 | 維持一般軟體，不需要用 AI 自動化 |
| 2 | 是否需要有人讀一堆雜亂的東西並做判斷 | 這才是模型真正該做的部分 |
| 3 | 出錯的代價有多大 | 出錯很貴的步驟即使模型做得到，仍留給人 |

跑完之後你幾乎不會得到「整個流程都該由 AI 跑」的結論——**有些步驟留給軟體、有些交給模型、有些留給人**。Moza 舉的一個八步驟流程例子：4 個步驟最後完全自動執行，另外 3 個由模型跑但有人在輸出送出前檢查，最後 1 個完全由人處理。那個完全由人的步驟是**商業判斷，AI 目前做不到**；不然就是出錯代價太高不能交出去，或是它出現的頻率不夠高、不值得為它動用模型。

**第三步：為失敗的路徑而建，不是只為順利的路徑**

Moza 說：**某件事只有一種方式會成功，但它有一千種方式會出錯。** 如果你只為順利的那條路建，你建的東西一文不值。

以 AI 而言，這主要是指**處理模型不確定的地方**——它不管有沒有把握都會給你一個答案，即使它完全不知道。

**第四步：在讓它碰到真實東西之前，先確認系統真的能用**

模型即使問同一個問題，每次的答案都會稍有不同。只測幾次的話，你會漏掉那些少見的翻車情況。

做法是：**從你寫下來的流程裡取出真實案例、而且是你已經知道正確答案的**，讓系統跑過全部案例、數它答對幾個，然後去讀它答錯的那些並修掉。

**第五步：把它值多少錢寫成一個數字**

你必須能說出它是**帶進了錢、減掉了成本、還是降低了風險**，其他都不算數。

Cursor 曾有人抱怨某個 agent 一天要花他 2000 美元。當他們問這個 agent 到底在做什麼，發現它是在挑派哪位工程師去修故障設備。於是他們反問他：**派錯人出去要花他多少錢**？答案高於一天 2000 美元。他當場就接受了——因為他一直只看 agent 花他多少，從沒看過它幫他省下多少。

## 作者自己的應用：內部 chatbot

這五個步驟正是作者的軟體公司建內部 chatbot 的方法。那個 chatbot 是一個聊天介面，讓團隊裡的非技術人員能使用 Claude Code 及其所有能力。

- 建它的原因是 HR 和會計的同事不是工程師，而 Claude Code 周邊的一切都預設你是工程師。Claude Code 要能對他們的工作產生用處，得先接上 Slack、email 以及他們每天在用的其他東西——那是他們絕不會自己去做的設定工作。所以這個聊天介面替他們把連線全部做掉，他們只要打字說出需求。
- **但他們沒有直接開始建**：工程師先去和 HR、會計的人坐在一起，因為工程部門對這些部門實際怎麼過完一天毫無概念。
- 他們在那些部門待了相當長的時間，**把每一件人工重複在做的事寫下來**，然後判斷其中哪些是模型可以合理接手的。
- **那份文件後來構成了這次建置的大部分內容**：那些寫下來的流程變成 agent 依循的指示，也變成 chatbot 回答問題的知識來源。
- 第一版交回給那些部門，讓他們在自己真實的工作上使用，他們回報確實省下了時間。

## 需要什麼能力才做得來

有一家專門招這個職位的公司要的是**在商業、流程、技術三個面向都有廣度、並在其中一項真正有深度**的人。他們說商業那一半可以在工作中教會，技術那一半不行。

但對你來說順序大概是反過來的：**你只需要專注在商業那一半，因為建置現在已經由 agent 處理掉了。** 這樣沒問題，因為一位 Palantir 主管說過，在這份工作上失敗的人是那種**追求程式碼十年後依然站得住的謹慎工程師**。這份工作是要快速把粗糙的東西放到真實使用者面前——而那基本上就是 Claude Code 這類 agent 第一輪就會交給你的東西。

## 怎麼開始：做一份 audit

從你能親自走進去的最小的生意開始——你工作的地方，或朋友經營的店。請負責人讓你花一小時，坐在店裡做最重複性工作的那個人旁邊、看他實際在做事。然後對你看到的東西跑一遍那五個步驟。

跑出來的東西叫做 **audit**，這是企業真的會付錢買的東西。在大企業裡執行 AI 專案的 Moza，**每一個專案都是從 audit 開始、之後才建任何東西**。他說第一階段是整份工作裡最大的瓶頸。

這份 audit 就是你去應徵 FDE 職缺、或直接向企業提案時要拿出來的東西——因為裡面有一間真實公司被寫下來的流程、你會交給 AI 的那些步驟、以及每一項對他們值多少錢。
