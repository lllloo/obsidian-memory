怎麼防它過期

圖會過期不是問題，過期而沒有人發現才是。這頁把「圖與程式碼一致性」拆成三層來看——其中兩層有現成做法可以直接抄，一層目前無解，而無解的那層恰好是你最想畫的那層。

component 層那條，具體長這樣

classes().should(adhereToPlantUmlDiagram(
    diagramFile, consideringAllDependencies()))

圖檔進 repo、測試進 CI，圖與碼不一致就紅燈。限制：僅支援 PlantUML component 圖，元件須用 [Name] 加 package stereotype，箭頭僅認 -->／<--；官方文件未提 C4／Structurizr 支援。

一個反向訊號：新工具正在放棄拿圖當基準

比工具清單更有訊息量的是這件事——2024 年後出現的漂移偵測工具，幾乎都不用圖當基準：

工具基準是什麼做法
drift已觀測到的 import把現有 directory-to-directory import 當基準，首次跨界即告警
ArchSteer自宣告 invariant算 Drift Index，CI 走 ratchet 只擋淨新增違規
erodeStructurizr／LikeC4 模型唯一仍以圖為基準，但靠 LLM 比對 PR diff，36★、無量化評估

前兩者都繞開「維護一張圖」。這暗示的業界共識是：圖太貴、太容易自己過期，不適合當 CI 基準。真正能守住的是「不准新增違規」這種相對規則，不是「必須符合這張圖」。

Backstage 的成本反諷值得記：多付的錢買的是「跨數十個服務的統一 catalog 與所有權對應」——組織級價值，單一專案完全吃不到。獨立的 techdocs-cli 早在 2021 就 archived 了，沒有「只用 TechDocs 不用 Backstage」這條路。

但防過期的真相：是流程，不是 CI

likec4 validate、Structurizr validate／inspect、PlantUML --check-syntax、d2 validate——這些全部只檢查你寫的模型檔本身有沒有壞，不檢查模型還對不對。

真正的防線是：模型檔與程式碼放同一個 repo、改碼的 PR 順手改模型、靠 review 抓。這是社會機制，CI 不會替你抓。

唯一的例外是 Structurizr 的 structurizr-component 模組（DSL 的 !components），用 BCEL + JavaParser 掃 codebase 自動發現 component——這是目前唯一真正「從程式碼反推架構模型」的現成路徑，但僅限 Java、僅 component 層，system／container 層仍純手寫。

Azure Well-Architected Framework 給了另一組可抄的、非技術的做法：圖要帶 metadata（標題、最後更新日、作者、版本）、廣傳後維護 change log、不再回答任何 stakeholder 問題的圖就退役、原始檔跟程式碼放同一個 repo 版控。

兩個仍然空白的問題

沒有任何研究或工程部落格量測過「用依賴規則 CI 檢查約束 AI 產碼」的效果（攔截率、違規數變化、品質差異）。先前從架構文件研究側查是零命中，這輪從工具生態側查也沒找到。這條路線被大量使用（見上表數字），但從未被量測。

也沒有查到「文字層架構約束（AGENTS.md／CLAUDE.md）對 agent 產碼效果」的實證。ADR 官方組織頁 adr.github.io 完全沒提 AI、LLM 或 coding agent。所以「prompt 層約束能不能取代 CI 層閘門」這個問題，目前兩邊都沒有數據可以回答。

本輪的方法限制

12 項平行查證中有 3 項未交件（大樣本調查窮盡確認、AGENTS.md 實證、ArchUnit 生態自查以外的部分），根因是 WebSearch 額度（200/200）在它們開工前就被整個 session 用光。其中量化數字部分我改用 API 直查補齊，但「窮盡搜尋」這件事本輪做不到——凡是寫「查不到」的地方，正確讀法是「在已檢索範圍內未出現」，不是「已證實不存在」。

本輪出現兩次網頁摘要失真並被複驗推翻：一次宣稱 Google 提供 PPT／Figma icon 包（實際只有 SVG／PNG），一次宣稱 D2 的 TALA 是開源（實際為 proprietary、收費）。只有摘要來源、未經原文複驗的值，都不應直接引用。
