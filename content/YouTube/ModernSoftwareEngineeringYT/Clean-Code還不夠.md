## Clean Code 的核心價值

- Clean Code 強調程式碼可讀性，因為程式碼讀的次數遠多於寫的次數
- 核心主張：小函式、清楚命名、避免重複、簡單優於聰明
- 小函式增加可測試性的表面積，讓測試更容易切入
- 清楚命名是一種壓縮意義的方式，降低理解系統的心智負擔
- DORA 研究支持：高績效團隊透過可讀、直覺的程式碼降低認知負擔

## Clean Code 的局限：規則而非護欄

- 最大問題不在書本內容本身，而是被應用的方式——semantic diffusion（語義擴散）
- 部分人將 Clean Code 當成風格指南而非工程紀律，追求「潔淨」勝於追求可變性
- 常見陷阱：為了小函式而把函式一切為二，沒有考慮「有意義」這件事
- 小而有意義的函式 vs 小而任意的函式：目標是找到一致的抽象層次

## Modern Software Engineering 補充的框架

Dave Farley 的觀點：工程的目標是優化「快速、安全地學習」。

- 複雜度以**影響**衡量，而非外觀：100 行函式可能比 5 層間接更簡單
- 程式碼的「潔淨」必須與真實世界的回饋掛鉤：如果讓測試更難、部署更慢，就不算 clean
- 衡量指標：cycle time、defect rate、deployment frequency、recovery speed
- Clean Code 給建議，Modern Software Engineering 給建議背後的**理由**

## 關鍵反轉：好工程產生好程式碼

- Clean Code 說：「把函式寫成散文」
- Modern Software Engineering 說：「建立小到讓複雜度無所遁形的回饋迴路」
- 如果工作結構正確（小步驟、自動化、快速回饋、持續整合），自然會產生更清晰的程式碼
- **在一個每隔幾分鐘就在改動的系統裡，你無法把複雜度藏起來**

## 對「模組化讓程式碼更難讀」的反駁

- 把程式碼分解成小塊（尤其透過 TDD）不是增加複雜度，而是**揭露問題本身固有的複雜度**
- Michael Feathers 的說法：這樣做是在暴露問題真正的表面積
- 人類在幾乎所有領域都靠分解複雜問題來應對複雜性——數學、科學、工程、寫作皆然
- 減少模組化並不會讓複雜度消失，只會讓各部分之間的互動與依賴更多、更難看清

## 兩者的互補關係

| 面向 | Clean Code | Modern Software Engineering |
|------|-----------|----------------------------|
| 關注點 | 如何結構化程式碼 | 如何結構化工作 |
| 抽象是 | 提升清晰度的工具 | 管理複雜度的工具 |
| 性質 | 工藝（craft） | 工程（engineering） |

- 兩者都提倡：簡單設計、小步驟、自動化測試、快速回饋、持續整合
- 理解兩者比只懂其一獲益更多
- Clean Code 成為工程的條件：當它與可測量的結果掛鉤，如降低認知負擔、提升可測試性、減少變更成本
