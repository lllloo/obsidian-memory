## 為什麼大多數軟體系統會失敗

失敗的根本原因不是微服務、不是單體架構、不是敏捷——而是**不可預測性**。

- 無法可靠判斷變更影響 → 無法安全演進系統
- 無法演進的系統 = 已經是 legacy 系統

**決定論（Determinism）** 是「在我的機器上能跑」到「在任何地方任何時候都能跑」之間的橋樑。

## 決定論的重要性

演進式架構的前提鏈：

```
可演進 → 可測量 → 可重現 → 必須是決定論的
```

- 若測試不穩定（flaky）、建置偶爾莫名失敗、並發導致隨機問題 → 交付 pipeline 不再是真正的學習系統
- 非決定論夠嚴重時，會淪為「發布劇場（release theater）」而非真正的發布

決定論是信任的前提：
- 沒有它，測試在說謊、pipeline 在說謊、架構在悄悄腐爛
- 有了它，可以每天執行數千次實驗、偵測非預期副作用、快速移動而不是在賭博

## 時間：讓非決定論變成參數

最常見的問題：程式碼直接呼叫 `DateTime.Now()`

```
// 壞的做法
var now = DateTime.Now;  // 每次執行結果不同，不可測試

// 好的做法：注入時鐘
public class Service(IClock clock) {
    var now = clock.Now;  // 可控制、可凍結、可快轉
}
```

效果：
- 可以在測試中凍結時間、快轉時間
- 可以重現生產環境的 bug（重播時間戳）
- 把「現在」變成一個輸入參數

## 並發：決定論消亡之處

執行緒排程決定執行順序 → 架構變成機率性的，出現競態條件（race conditions）和 Heisenbugs。

「99% 的時間都能正常工作」不是工程，是在玩輪盤賭。

有效的解決方案：
- **Actor model**（行為者模型）
- **單執行緒事件迴圈**
- **決定論式合併策略**
- **不可變狀態**：狀態不會被意外改變，執行順序就不那麼重要了

結構化模式：`輸入 → 決策 → 事件` 讓你重新掌控執行順序。

Elmax 案例：處理全球金融交易，每個服務完全是決定論的——給定相同起始狀態和相同事件序列，永遠得到完全相同的結果。

## 核心模式：決定論核心 + 命令式外殼

最重要的一個想法：**把「做決策的程式碼」與「執行動作的程式碼」分離**。

```
決定論核心（Deterministic Core）
  - 純邏輯：狀態輸入 → 決策輸出
  - 無資料庫互動、無時鐘、無隨機性
  - 等同於：六邊形架構的 Domain 層

命令式外殼（Imperative Shell）
  - 與資料庫溝通
  - 與網路溝通
  - 與時鐘溝通
  - 執行副作用
```

這是六邊形架構（Hexagonal Architecture）、Port & Adapters 的另一種表達方式，但更直接強調演進能力。

**測試的好處**：核心純粹時，不需要 mock、不需要框架、不需要複雜的測試鷹架。傳入狀態、斷言輸出，可在毫秒內執行數千個測試——這些就是你的 fitness functions。

## 控制狀態空間

非決定論不只來自執行緒或時鐘，也來自**不受控的狀態空間**。

若系統有 500 種隱式狀態且你不知道自己在哪種狀態，那是熵，不是架構。

解法：
- 設計較窄的範圍（narrower scopes）
- 使用明確的狀態機（explicit state machines）
- 讓元件邊界清晰
- 設計元件拒絕無效狀態

範圍越窄 → 狀態越受控 → 系統越決定論 → 變更越有信心

## 基礎設施層面的決定論

決定論不只是程式碼的事：

- **密封建置（Hermetic builds）**：每次建置產生完全相同的系統狀態
- **鎖定依賴版本（Pinned dependencies）**：避免依賴升級帶來的意外
- **冪等部署（Idempotent deployments）**：執行兩次部署，結果應該完全相同

若重複部署改變結果，你的基礎設施就是非決定論的，生產環境就是個謎。

## 為什麼這讓 Continuous Delivery 得以運作

最佳組織優化的不是功能數量，而是**學習速度**：

- 決定論縮短回饋迴圈
- 減少認知負擔
- 讓 debugging 可重現
- 讓激進的實驗成為可能

**Continuous delivery 之所以有效，不是因為 pipeline，而是因為決定論。Pipeline 只是放大鏡，讓你看清距離決定論還差多遠。**
