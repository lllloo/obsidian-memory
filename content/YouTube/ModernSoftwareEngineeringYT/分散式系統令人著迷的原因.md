## 微服務的核心問題：為什麼我們不得不分散？

- 企業採用微服務的根本原因是**獨立部署能力（independent deployability）**
- 但這只是因為大多數執行環境不支援真正的模組熱替換（hot swapping）
- 如果執行環境真的支援模組熱替換，我們就不需要這麼多分散式設計
- Java Jigsaw 原本令人期待，但最終任務被稀釋；Erlang 有這方面的能力，但使用者太少

## 分散式單體（Distributed Monolith）：最糟糕的結局

- 很多目標微服務的團隊得到了「分散」，卻沒有得到「獨立」
- 結果：在多個 process 之間執行一個 monolithic 應用
- 後果：需要中間管理者和 release manager 協調所有人的改動，架構師焦頭爛額，沒有任何進展

## 分散式系統的吸引力

- 組織擴展：讓多個團隊能夠獨立在同一軟體上協作
- 技術靈活性：更容易混合不同技術，在 process 邊界實驗（如：用 Rust 替換某個部分）
- 不同 runtime、不同 chipset、不同部署平台
- 現在更重要：整合 LLM 時幾乎必須如此，需要接觸專用硬體

## 分散式系統的三個黃金法則

（來自作者的著作《Building Resilient Distributed Systems》，第三條由同事 Ben Cole 補充）

1. **資訊不能瞬間傳遞**：訊息從一點到另一點需要時間，這是物理定律
2. **你想溝通的對象不一定在那裡**：網路分區、服務下線，雖然不常見但確實存在
3. **資源池不是無限的**：資源終究會耗盡

所有其他分散式系統的複雜性，都是從這三個基本問題延伸出來的。聽起來只有三件事很簡單——但這三件事是量子物理等級的難題。

## 學習建議

作者在寫書時的起點：**從 timeout 開始**。
- 什麼是 timeout？
- 為什麼需要它？
- 怎麼設定？

從最基本的問題出發，回到第一原理思考，比直接跳到 Byzantine 共識協議（如 Paxos vs Raft）更有幫助。
