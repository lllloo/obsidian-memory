## 測試金字塔的問題

測試金字塔由 Mike Cohn 在 2009 年的《Succeeding with Agile》中提出：

- **單元測試**：快速、廉價，幫助診斷問題
- **服務測試**：中層，從客戶角度撰寫
- **UI 測試**：緩慢、昂貴、脆弱

Martin Fowler 後來重繪時加上了明確的取捨軸：速度（快/慢）與成本（便宜/昂貴）——這是一大進步，因為它把討論從「這是不是單元測試」轉移到「這個測試夠快夠便宜嗎？」。

**核心批評**：測試金字塔假設測試粒度（granularity）與速度和成本直接相關，但這不一定成立：
- 有些系統的單元測試非常慢
- 有些系統的 UI 端對端測試夠快，足以支援重構

速度和成本更多取決於系統設計和架構，而不是測試的「類型標籤」。

## 術語混亂問題

**「單元測試」的歷史包袱**：
- 在 JUnit 出現之前，「unit test」是手動執行的，通常由獨立的測試小組負責，是瀑布式 V 模型的一部分
- Kent Beck 與 XP 提倡的是完全不同的概念——輕量、由開發者自己寫的自動化測試
- 當人們接觸新概念時，會將其重新詮釋成已知的東西，「unit test」這個詞本身就帶來混淆

**「服務測試」更糟**：
- 原本指「從客戶角度撰寫的測試」（接近 BDD 的概念）
- 現在被誤解為「整合測試」（V 模型中介於單元測試和系統測試之間的東西）
- 實際上被用來描述從「測試超過一個 class」到「測試含資料庫、Kafka queue 的完整微服務」的所有東西

## Test Desiderata 2.0：四個巨觀屬性

不談測試「類型」，改談測試套件應該具備的**可欲屬性（desiderata）**：

### 1. 快速（Fast）
- 測試套件整體執行速度要快
- 與其問「這是單元測試嗎？」，不如問「這個測試夠快嗎？」

### 2. 廉價（Cheap）
- 撰寫和維護成本要低
- 同樣是架構設計的函數，而不是測試類型的函數

### 3. 可預測部署成功（Predictive of deployment success）
- 測試必須能在上線前找到真正有趣的 bug
- 有些 bug 只有在完整 GUI 或完整系統運行時才會出現
- 測試金字塔把「透過 GUI 的測試」與「端對端測試」混為一談，但它們處理的是不同類型的風險

**重要觀念**：不同類型的測試處理不同類型的風險。與其問「我應該有多少層」，不如問「這個風險有沒有更快、更便宜的方式來驗證？」

### 4. 支援持續的程式碼設計變更（Support ongoing code design changes）
這是最常被忽略、但最有影響力的屬性：

- 在 TDD 或 BDD 流程中，**測試是設計的第一驅動力**
- 先寫測試 = 在實作存在之前先記錄意圖
- 帶來正向設計壓力：更可用的 API、更好的關注點分離
- 後寫測試的問題：傾向於使用大量 mock 來補償設計的缺陷，導致測試在重構時更脆弱、維護成本更高

**測試作為文件**：有意圖撰寫的測試能解釋程式碼「為什麼這樣設計」，而不只是「它做什麼」——從客戶或使用者的角度提供脈絡。

## AI 生成測試的限制

AI 工具在測試生成上的表現：

- **可以**：檢查現有程式碼並生成對行為敏感的測試（滿足「可預測」屬性）
- **可以**：使用 mock 讓測試快速執行
- **失敗點**：第四個屬性——「為什麼這些測試案例重要？這一切是為了什麼？」

你無法只從實作推斷出客戶或使用者的觀點。雖然可以在 prompt 中包含這些脈絡，但 AI 工具的訓練資料中這類「有意圖的測試」比例極低，很難突破這個限制。

## 結論

**測試金字塔的改進版**：加上速度和成本軸之後已經好很多，但仍然隱含了兩個重要維度沒有明說：

1. 測試能否預測生產環境的成功？
2. 測試能否支援持續的程式碼設計演進？

**Test Desiderata 2.0** 讓這四個目標明確化，是評估現有測試套件和制定測試策略更好的起點。

Mike Cohn 原本在測試金字塔中有提到「從客戶角度撰寫測試」，但這個重要觀念在後來對「單元到底多大」的爭論中完全消失了。是時候把重心放回**測試帶來的效益**，而不是測試的類型定義。
