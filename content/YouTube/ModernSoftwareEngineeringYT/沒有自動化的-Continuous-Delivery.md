## 核心問題

CD（Continuous Delivery）通常與自動化畫上等號，但如果拿掉部分或全部自動化，CD 還能成立嗎？

**Dave Farley 的 CD 定義：** 以工作方式確保軟體**隨時處於可發布狀態**。決定「是否可發布」通常靠自動化——因為這是最有效率的方式，但並不是唯一可能。

## CD 的哲學基礎先於工具

- 最早的 CI（Extreme Programming 時代）依靠**社會約定與團隊紀律**，而非自動化
- Kent Beck 在 *Extreme Programming Explained* 中描述的 CI，是以「一天多次整合」為社會事件，整個團隊參與，依賴團隊紀律
- 原始 Continuous Delivery 書中甚至提到用**鈴聲和橡皮雞**（bell and rubber chicken）來提示整合時機

## 自動化是「倍增器」，而非「前提條件」

- 自動化可以讓有效的工程實踐**更快更可靠**
- 但如果底層實踐本身有問題，自動化只是**把弱點放大**（garbage in, garbage out）
- 真實案例：一位在 LMAX 深信 CD 的工程師去帶領一個小型初創團隊，沒有自動化測試、沒有完整 CI，只是採用「小步驟提交」的節奏，結果**仍然比大多數沒有 CD 的團隊好**

## 規模決定自動化的必要性

- 程式碼越小、改動越小 → 手動驗證越可行
- 規模越大（如 Android 作業系統）、改動頻率越高 → 自動化越接近必要條件
- AI 生成程式碼加速了 code 產出速度，但**驗證速度必須同步跟上**，否則手動檢查根本來不及

## 常見陷阱：有工具卻沒有 CD

很多團隊說「我們有 CD pipeline」，但實際上：
- 不以小步驟工作，仍有大量 merge hell
- 跳過測試步驟
- 把 CD 當成「快速出 bug、快速修 bug」的循環，而非持續交付新功能

引用：「你建了一條下水道管線，不是 CD 管線。」

這和 AI 使用的問題類似：有工具，但加速的是「建造爛系統」的速度。

## CD 的真正基礎（與自動化無關）

1. **以小步驟工作**
2. **每個小步驟後驗證軟體是否可發布**
3. **獲得快速反饋**

自動化是讓這三件事在**任何規模和分散式團隊**下都可行的手段，但哲學本身不依賴自動化。

## 結論

- 在特定小規模情境下，沒有自動化的 CD 仍然可以運作，且可能比「有工具但沒紀律」的偽 CD 更有效
- 真正的問題是：**你的自動化是在放大什麼？** 是好的工程實踐，還是壞的流程？
- 人類不擅長 for 迴圈（重複且可靠的工作），這才是自動化真正的價值所在
