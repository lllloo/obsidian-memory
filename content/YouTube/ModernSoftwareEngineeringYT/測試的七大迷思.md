## 迷思一：測試員與開發者是對立關係，且這是必要的

**錯誤觀念：** 測試員必須獨立於開發者，才能客觀批評軟體。

**實際情況：**
- 對立關係滋生輕蔑：「他們要毀掉我的程式碼」vs「懶惰的開發者直接丟過來」
- 測試員不是要破壞你的程式碼，而是要打破你對程式碼的幻覺
- CD 中，大家在同一個團隊，朝同一個目標前進
- BDD（Behavior-Driven Development）提供了結構化協作框架，讓不同視角可以整合而不引發衝突

## 迷思二：開發者負責 unit testing，其他測試由專家負責

**錯誤觀念：** 開發者只需關心 unit tests，integration/system/performance tests 交給測試專家。

**問題：**
- 開發者與 pipeline 後段測試脫節，形成「我的 unit test 過了，我完成了」的心態
- 票進 done 欄後就不再關心

**正確做法：**
- Pipeline 中所有測試共同構成規格（specification）
- 開發者需要積極利用所有測試的反饋來指引開發決策
- 是誰寫的測試不重要，重要的是大家把它視為共同的標準

## 迷思三：業務人員指定 acceptance tests，開發者確保通過

**錯誤觀念：** Product Owner 決定「什麼（what）」，開發者決定「如何（how）」。

**問題：**
- 把所有關於「可接受性」的決定權集中在一個人身上，不健康
- 那個人也沒有時間和精力做到所需的細節層次

**正確做法：**
- 業務人員提供用戶需求的細微差別、業務情境和真實範例
- 開發者帶入技術可行性、系統現狀的理解和改善想法
- 還需要測試員、UX 設計師、效能專家、資料科學家的視角
- **共同發現**軟體應該做什麼，而非單向規格下達

## 迷思四：Unit testing 就是把 unit 隔離並 mock 掉所有依賴

**錯誤觀念：** 在程式碼中畫一個框，mock 所有依賴就是 unit test。

**問題：** mock 所有依賴會讓測試在功能邊界重構時極度脆弱

**現代理解的「隔離」有兩層意思：**
1. **測試與測試之間的隔離**：讓測試可以任意順序執行（JUnit 的設計目標）
2. **時間上的隔離**：每次 pipeline 執行都隔離一批變更，若測試失敗可以精確定位是「這批」改動造成的

CD 的核心優勢正是：以小批次工作，讓失敗的測試可以對應到具體的變更集合。

## 迷思五：Unit testing 中的「unit」指的是一段程式碼

**正確理解：** Unit 是**一片行為（a slice of behavior）**，不是一個類別或函式。

- 測試驅動開發的核心技能：把功能切成薄薄的行為切片
- 用具體範例劃定問題範圍，限制測試一次需要考量的 context
- 這是 TDD、CD 和敏捷開發的關鍵能力

## 迷思六：Unit testing 的目標之一是 100% coverage

**問題：Goodhart 定律** — 當一個指標變成目標，它就不再是好的指標。

**coverage 的正確使用方式：**
- 覆蓋率極低時值得注意（幾乎沒有合理理由）
- 覆蓋率突然下降值得警覺（AI coding agents 有刪除失敗測試而非修復的壞習慣）
- **不應設定具體目標**，高覆蓋率應是好工程實踐的副產品（如 TDD 的自然結果）
- 強制追求高覆蓋率很容易遊戲指標，反而得到差勁的工程

## 迷思七：先寫測試永遠比後寫更好

**例外情況確實存在（TDD 不一定更好的情境）：**
- 原型設計（Prototyping）
- 探索設計空間（Spiking）
- 評估選項
- 為**已有人寫且已知可運作**的程式碼補回歸測試（常見於 legacy code）

**先寫測試更好的情境：**
- 想限制當前開發範圍（只讓這個測試通過）
- 想得到更好的設計（testability as first-class citizen → 模組化、關注點分離）
- 想記錄開發意圖、識別下一步要實作的行為

## 總結

好的測試是整個團隊的責任，不是某個角色的專屬工作。測試的真正目的是支援開發決策，而非單純追求數字指標。
