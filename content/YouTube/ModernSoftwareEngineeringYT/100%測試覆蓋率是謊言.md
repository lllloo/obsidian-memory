## 什麼是測試覆蓋率

測試覆蓋率（test coverage）衡量生產程式碼中有多少行被測試套件實際執行過。例如 10 萬行的程式碼，若測試只跑了 2 萬行，覆蓋率就是 20%。

零覆蓋率幾乎必然是問題——代表你只能依賴緩慢易錯的手動測試，或直接採用「YOLO 部署策略」。自動化功能測試的價值在於提供快速回饋（fast feedback），而愈早發現問題，修正成本愈低。

## 測試覆蓋率的三大謊言

### 謊言一：有覆蓋就有測試品質

覆蓋率無法處理單行中多個布林條件（boolean predicates）——即使整行有覆蓋，也不知道哪個條件分支真的被測到。

此外，一行程式碼只有一個測試案例就算「覆蓋」，但可能完全沒測到邊界情況。例如一個接受字串的函式，只用一種輸入就達到 100% 覆蓋，卻沒有測過空字串、超長字串或格式錯誤的情況。

正確做法：同一段程式碼應該用多個測試案例驗證不同情境，而非以「有覆蓋」為目標。

### 謊言二：追求高覆蓋率會導致端對端測試偏重

若以提升覆蓋率為目標，最快的方式是增加 end-to-end tests——一支測試就能跑過大量生產程式碼。但這帶來兩個問題：

- **速度慢**：end-to-end tests 比 unit tests 慢得多
- **隔離性差**：測試失敗時，難以定位是哪個環節出錯，修復時間也更長

快速回饋與隔離性才是測試套件的核心價值，end-to-end tests 偏重會同時損害這兩者。

### 謊言三：高覆蓋率不代表有測試邏輯

一個真實案例：某銀行系統宣稱有 100% 覆蓋率。仔細查看後發現，所有測試只是啟動程式的 main method、確認沒有拋出例外，完全沒有任何斷言（assertion），也沒有提供任何輸入。

覆蓋率只能確認程式碼「有被執行」，無法確認測試「有在驗證正確性」。過度聚焦覆蓋率，容易讓測試淪為只為衝數字的打勾練習。

## 測試覆蓋率真正的用途

覆蓋率不是完全無用，但應該這樣使用：

- **追蹤趨勢而非特定目標**：覆蓋率下降是一個訊號，要去了解背後原因——是刻意移除昂貴的 end-to-end tests（可能是好事），還是開發者在測試失敗時直接把測試註解掉（需要立刻處理）
- **搭配其他指標**：build regression 速度、QA 環境與生產環境的 bug 數量，才能判斷測試組合是否健康
- **只追蹤 unit tests 的覆蓋率**：小範圍的 unit tests 對應 Mike Cohn 測試金字塔底層，覆蓋率在這層才有意義，也較難被「作弊」

## 進階測試技術

### Mutation Testing

Mutation testing 會自動修改生產程式碼（例如反轉 if 條件），然後確認測試套件是否失敗。若有測試覆蓋但修改後測試仍然通過，代表那段測試根本沒在驗證正確性。

這個概念由 Richard Lipton 在 1971 年提出，早期實作工具如 Jester（由 Ivan Moore 開發）。缺點是計算成本極高，在大型程式碼庫上很少實際使用。

### Property-Based Testing

Property-based testing 根據函式參數的型別自動產生多種輸入（短字串、長字串、含空白、不同格式等），不需要手動列舉測試案例。在強型別語言（strongly typed language）中特別有用，是測試邊界情況的有效方式，雖然在函式程式設計圈外仍屬小眾。

## 總結

- 程式碼被測試覆蓋，不等於被充分測試
- 追求覆蓋率容易引導出低品質、慢速度的大範圍測試
- 使用覆蓋率時，重點放在趨勢觀察而非數字目標
- 搭配 build 速度、bug 數等指標，確保測試組合正確
- 優先讓 unit tests 達到良好覆蓋率
