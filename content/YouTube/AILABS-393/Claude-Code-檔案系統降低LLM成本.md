## 核心概念：萬物皆檔案

隨著模型越來越強大，許多人開始建構整合模型的產品，但這些系統消耗大量 token，尤其是透過 API 整合時。解決方案比想像中簡單：最佳架構並非複雜的 pipeline 或高度調校，而是 Unix 系統的古老哲學——**萬物皆檔案**。

Vercel 的一位軟體工程師在文章中提出了這個概念。

## 為什麼 Agent 天生擅長檔案系統

模型在大量程式碼上訓練，因此對程式碼、目錄結構和開發者使用的 bash 指令有深刻理解。當 agent 使用 `grep` 和 `ls` 時，做的是它本來就熟悉的事，只是在更受控的環境中執行。

這個方式不限於程式碼——agent 可以瀏覽任何包含任何內容的目錄。工作流程：

1. 用 `ls` 和 `find` 等原生 bash 指令瀏覽檔案系統
2. 找到確切檔案後，用 `grep` 和 `cat` 進行模式比對搜尋相關內容
3. 只有小塊相關資訊送到模型，其餘保留在記憶體之外，維持 context window 的清潔

不消耗模型用不到的資料 token，agent 回傳結構化輸出。這個模式效果極佳，Vercel 因此將這個 bash tool 開源。

## 三種資訊提供方式的比較

| 方式 | 優點 | 缺點 |
|------|------|------|
| 詳細 system prompt | 簡單直接 | Token 上限限制資訊量 |
| 向量資料庫（RAG） | 處理大量資料 | 語義相似而非精確比對，依賴模型從 chunks 中提取正確內容 |
| 檔案系統 | 結構映射領域關係、精確比對、context 最小化 | 不適合模糊查詢 |

## 檔案系統的核心優勢

- **結構保留**：資料夾結構自然反映資料間的關係，不需要壓平成向量 chunks（語義搜尋中容易遺失層級關係）
- **精確檢索**：`grep` 和 bash 工具回傳精確比對，不像向量搜尋回傳模糊匹配的 chunks 再交由模型決定
- **Context 最小化**：agent 只取得需要的特定 chunk，避免不相關資料進入記憶體

Claude Code 和所有 CLI agent 已內建使用此方式——用 bash 函式配合模式比對縮小結果範圍。

## 實際應用案例

以公司政策查詢系統為例，資料以 JSON、Markdown、txt 格式按部門分類存放：

- 後端：提供文件資料夾路徑，給 agent `ls`、`cat`、`grep`、`find` 的存取權限，以及使用指南
- 使用 Gemini 2.5 Flash 模型，提供 Vercel 的 bash tool
- 測試時 agent 先用 `ls` 查看可用文件，再用 `grep` 進行模式比對搜尋
- 準確度達到與 RAG 系統相當的水準

## 安全考量

給 agent 在伺服器執行指令是強大但潛在危險的能力。此工具的安全機制：

- 在沙箱中執行，有隔離性
- 只存取提供的特定目錄，不修改其他內容
- Agent 在沒有 production 系統存取的情況下探索檔案

提供兩種隔離類型：

1. **記憶體內環境**：bash tool 只在有存取權的檔案上執行 bash 腳本
2. **完整 VM 隔離**：使用 Vercel sandbox，提供更強的安全保證

## 使用時機建議

**使用檔案系統（bash tool）：**
- 資料高度結構化
- 查詢意圖明確

**使用 RAG：**
- 需要比對詞語含義
- 查詢可能較模糊或非結構化
