## Git 解決什麼問題

每個人都有過「報告.docx」、「報告-第二版.docx」、「報告-最終版.docx」、「報告-真的最終版.docx」這種檔名爆炸的經驗，背後反映三種痛苦：

- 不確定這次改的方向對不對，本能想留舊的
- 改到後來分不清哪個才是要用的版本
- 跟同事協作時雙方各自改一版，搞不清以誰為準
- 改壞了想退回去，卻發現舊版沒留下

雲端檔案（Google Docs）能解一部分，但本機檔案還是需要 Git。Git 最早為工程師設計（一個功能改十幾個地方，改壞回不去就完蛋），但概念對任何在電腦上管檔案的人都適用。

## 三個核心概念

### 1. Commit（提交）= 拍快照

每次完成一個階段，把當前工作狀態拍成一張照片，並加上說明：

- 「新增第三章初稿」
- 「根據客戶意見修改第二章合約」

整個工作歷史就是一串按時間排列的快照。任何時候都能回到任一張照片的狀態，這個動作叫 **rollback（回滾）**——並不是真的回到過去，而是拿出那個時間點的備份還原。改壞了沒關係，找回對應快照即可。

### 2. Push / Pull = 本地與雲端同步

預設快照存在本機（本地倉庫），但本機壞掉、被偷、不見就全沒了。所以一般會配遠端倉庫（如 GitHub）做備份：

- **Push**：把本地的快照歷史推上雲端（備份）
- **Pull**：從雲端拉下別人或另一台電腦的更新（同步）

有遠端倉庫之後，本機出問題不怕，所有歷史都在雲端。

### 3. Branch（分支）= 平行宇宙

提案 A 客戶用，但你想試 B 方向又不想動到原版本：

- 開分支 = 開平行宇宙，主線繼續是 A，分支上做 B 嘗試，互不影響
- B 成功 → **merge** 回主線（兩個世界並一起）
- B 失敗 → 直接刪分支，主線完全不受影響
- 兩邊改到同一行 → **衝突（conflict）**，由你決定保留哪一邊，解完繼續合併

分支讓你大膽實驗，不怕破壞主線。

## 不需要學指令，只要懂概念

Claude Code 已經把 Git 操作包進對話：

- 「幫我做 commit」
- 「幫我 push」
- 「幫我 pull 下來」
- 「幫我 merge」
- 「幫我看看過去幾天的快照，分析這個問題從什麼時候開始出現」
- 「幫我判斷要不要還原」

重點不是學會 Git 指令，而是理解概念才能正確指揮 AI。

## 不該放進 Git 的東西

Git 會記錄所有歷史，下列東西放進去會出問題：

| 類型             | 風險                                                        |
| ---------------- | ----------------------------------------------------------- |
| 密碼、API Key、Credential | 雲端倉庫公開時全世界都看得到（每天都在發生的資料外洩來源） |
| 大型檔案（影片、音檔、幾百 MB 圖片） | Git 設計上追蹤文字變化，大檔會讓記錄越來越肥，速度變慢；改用雲端硬碟管 |
| 系統臨時資料（快取、log）     | 每台電腦自動產生一套，同步沒意義                             |

解法：在專案根目錄放 `.gitignore` 設定檔，把不想追蹤的東西寫進去，Git 自動忽略。設定一次以後不用再動。

## 非工程師的應用情境

- **提案／文件管理**：客戶說「我覺得第五版方向比較好」，幾秒鐘就能找回第五版，不用翻奇怪檔名
- **多人協作**：跟同事一起維護手冊、課綱、教材，清楚知道誰在什麼時間改了哪段、為什麼改，不靠對話記錄或口頭溝通猜
- **流程迭代**：想更新工作流程但不確定好不好用 → 開分支試新版，OK 就 merge，不行就刪分支回主線
