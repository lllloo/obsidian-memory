## 場景：書本 Skill 直接幫公司分紅制度抓盲點

學員把家裡與管理經營有關的書本（小團隊創業指南、文案心法等）一一灌成 Claude Code Skill，遇到問題時就把對應作者「請出來」當顧問。

這次示範是把自己公司的分紅制度評估指標檔丟進對話，請小團隊創業指南那本書的作者 Skill 評估：

- Skill 先讀指標檔案
- 接著套用書中的觀點輸出意見
- 不用每次把整本書貼進對話

## 那本書 Skill 對分紅制度提出的五大盲點

書本 Skill 給的不是空泛建議，而是依書中經驗點出制度的具體缺陷：

1. **整份制度沒有毛利率指標**：只獎勵達標率與超額完成，可能為了達標接低毛利訂單，整體毛利下滑、資本被燒光
2. **獎金支撐用淨利潤而非現金流**：忽略現金流壓力，建議改以現金流為基準
3. **完全沒有 AR（應收帳款）指標**：沒人對 AR 老化負責，獎金池應加入此項
4. **報價單準確率是錯誤指標**：作者明確判定 so poor
5. **保底獎金會養出 entitlement**：虧損還發獎金等於告訴員工「公司賠錢與我無關」

最後給的整體建議：

- 把規則壓到一頁
- 四人公司應把 80% 注意力放在毛利率與現金
- 老闆制度釋出六個月再開始挪用獎金，主要現金流不能只靠自律

## Skill 的主檔 + 副檔架構

書本 Skill 的拆法：

- **主檔**：定義這本書要解決什麼問題、什麼情境呼叫、書的關鍵概念清單、各章節導覽
- **副檔（按章節拆）**：主檔判斷使用者的問題像哪一章，再讓 AI 進該章節讀更深的細節
- **指令碼資料夾**：未來放可直接執行的小工具（例：算毛利率的程式），讓 Skill 不只給建議還能算

關鍵價值：限定 AI 的回答範圍。沒有 Skill 時 AI 會吃自己訓練過的海量資料、回答帶隨機性；有了書本 Skill 後，回答以使用者認同的理念為基礎，品質穩定許多。

## 現場用 Plan Mode 把第二本書轉成 Skill

學員拿出卞之翰老師的課程逐字稿（自購，避免授權問題），請 Claude Code 把這本書也轉成 Skill。為了先看 AI 怎麼拆，切到 **Plan Mode**：

Claude 接到任務後做的事：

1. **先看既有 Skill 長相**：去讀使用者之前做過的書本 Skill，理解格式慣例，不亂做
2. **拉 Google Drive 上所有 document**：一次撈完課程的全部講次
3. **啟動 ask user question 工具**：對缺乏的資訊主動發問

Plan Mode 內 ask-user-question 會問：

- Skill 名稱要叫什麼（中文 vs `compensation design` 之類英文）
- 第一、二講缺漏處理（學員主動跳過，因為那兩講只是吐槽現行 KPI 制度）
- reference 用什麼語言寫
- 安裝層級：user level（所有專案可用）或專案層級

> 學員提示：很多 Skill 拿到手後可以「魔改」，把不認同的章節直接刪掉。

## 用四個子 Agent 平行處理 17 萬字

書本一共 16 講、17 萬字。讓單一 AI 一次吞下會注意力渙散，Claude 自動把工作拆給四個子 Agent：

- 主 Agent 化身「對 AI 下指令的人」，分派任務給四個下手 Agent
- 每個子 Agent 只負責一小段章節，把指定範圍濃縮成 reference 檔案
- 任務指令一次說清楚：來源在哪、輸出格式（核心論點、關鍵術語、可操作框架、案例、何時引用）、寫作原則（保留具體用語、引用時機）

精簡模式下使用者只看到階段性結果；切到完整模式可以看到主 Agent 分派任務的完整 prompt，這些 prompt 都來自使用者過往對 Skill 格式的定義，不是 AI 憑空生的。

## Skill 對 Token 與上下文的兩大好處

學員結尾補充 Skill 的兩個關鍵特色，是把書「變成」Skill 而不是直接貼到對話的根本原因：

- **不需要時不灌入模型**：模型一吃到文字就開始計費，Skill 只在需要時才被讀取
- **不佔用聊天視窗**：聊天視窗文字越多，後面模型表現越差；Skill 把專家知識留在外部，需要時才取用

## 重點工作流總結

學員整體流程：

1. 把每本自己讀過、認同的管理經營書都做成 Skill
2. 遇到實際工作問題時（如評估公司分紅制度），把問題檔案丟進對話、呼叫對應作者 Skill
3. 多本 Skill 互相 review 同一份制度，等於請多位顧問
4. 持續用 Plan Mode + 子 Agent 工作流把新書轉成 Skill，並按需求魔改
