現在搜尋「最佳 Claude Code 記憶系統」，結果多得讓人眼花繚亂：Mem0、Karpathy 的 Obsidian Wiki、openclaw、Hermes、MemPalace、LightRAG、ClaudeMem、ClawMem，根本跟不上。這支影片把六個層級的 AI 記憶方式全部拆解清楚，從你已有的基礎工具，一路到跨所有 AI 應用程式共用的統一大腦。看完你就會知道哪個層級適合你的需求，哪些可以直接跳過。

## 逐字稿

### 簡介：Claude Code 記憶的六個層級

如果現在去搜尋最佳的 Claude Code 記憶系統，你會被淹沒在一堆選項裡：Mem0、Karpathy 的 Obsidian Wiki、openclaw 和 Hermes、MemPalace、LightRAG、ClaudeMem、ClawMem。光是追蹤這些東西就已經很荒謬了。但在花了很多時間研究之後，我發現這些工具其實並不是在競爭——它們只是根據不同使用情境處理記憶的不同方式。我之所以深入研究這個問題，是因為我正在打造自己的 agentic 作業系統，基本上就是一個橫跨我所有工作的「業務大腦」。

所以我需要弄清楚什麼真的有效、什麼能夠擴展，以及什麼只是在我現有的設定上增加複雜度。在這支影片裡，我會帶你走過六個層級的記憶系統，它們是一層疊一層建立起來的，一路延伸到可以跨所有 AI 工具使用的系統。看完之後，你就會清楚知道哪個層級適合你的使用情境，哪些可以完全忽略。

在進入各個層級之前，有一件事我想讓你先了解，因為這樣後面的內容會更好懂：每一套記憶系統回答的都是完全相同的問題。當你給 Claude Code 一個任務時，它如何在正確的時機取得正確的上下文？我要展示給你看的各層級之間的差異，只有兩件事：第一是你的記憶存在哪裡，也就是儲存機制——資料放在什麼地方、檔案結構長什麼樣，是 markdown 還是儲存成 vector；第二是 Claude 實際上如何取得那份資料，也就是召回階段。有些東西會自動複製進 Claude 的 context，有些東西會放在 database 裡，在需要的時候才搜尋取出。

有些東西會存在你的筆電上，有些則在雲端，諸如此類。現在讓我們直接進入第一層級。你可以把 Level 1 想成 Claude Code 原生內建的東西。大多數人已經聽說過 CLAUDE.md，有些人聽說過 memory.md，但很少有人真的把兩者一起正確使用。先從 CLAUDE.md 開始說。

### Level 1：Claude Code 原生內建功能

大多數人已經知道這個了，所以我簡單帶過：它基本上就是放在你專案資料夾內的一個純 markdown 檔案，用來儲存你的規則、品牌相關資訊、跟客戶合作的方式、程式碼風格等等，而且每次你在終端機開啟新 session 時，它都會被載入。你可以把它想成放在 context 開頭的一份筆記，幾乎就像是你給 Claude 的 system prompt。

你可以在 Claude 的專案資料夾層級設置 CLAUDE.md，讓所有 Claude 實例共用；如果你有多個專案放在同一個資料夾下，也可以設在根目錄層級；甚至可以在個別專案層級設置，用於特定的專案指令。資料夾結構越往下，仍然會繼承上層的 CLAUDE.md，但遇到衝突的規則時，永遠以本地的 CLAUDE.md 為準。

但這裡有一件事大多數人都搞錯了——我看過很多次——就是把太多東西塞進 CLAUDE.md。把完整的品牌指南、語調文件、完整的客戶清單全部放進去。想想看 Claude 每次啟動 session 時，它都得把這些全部讀過一遍、燒掉大量的 context window。所以這些確實是重要的上下文，但只有在正確的時機載入才有意義。

這正是我們要解決的「context rot」問題：AI 和 LLM 模型隨著載入的 context 量增加，無法 100% 召回所有已載入資訊的現象。一個通用的原則是：把 CLAUDE.md 控制在 200 行以內。如果你有更多上下文，比如品牌語調文件，可以放在一個獨立的外部檔案，並從 CLAUDE.md 引用它，這樣它就只會在需要的時候才被載入。

Claude Code 內建的第二套記憶系統叫做 automemory，它會形成一個 memory.md 檔案。你可以在現有的專案資料夾中輸入 `/memory` 來查看。你會看到幾個不同的東西：如果你使用了其他記憶系統，可能會有 imported memory；還有 project 和 user memory，本質上就是你在根目錄不同層級的 CLAUDE.md 檔案。

打開 automemory 資料夾，你會看到在每個專案基礎上，有一個帶有 memory 檔案的記憶結構。打開這些 memory.md 裡的所有檔案，你會看到一個索引，指向許多 Claude Code 可以參考並開啟的記憶檔案。所以它並不是把大量記憶全部堆在同一個地方。它做的是：在每個專案層級，有針對該專案的特定回饋，在更宏觀的層面，有針對特定事項的各種回饋，以獨立文件的形式保存。這正是我們說過的做法：不要在單一檔案裡塞超過 200 行，永遠引用獨立檔案，把 memory.md 或 CLAUDE.md 當成索引，再指向其他檔案。

為了進一步說明，如果打開一個空白資料夾，你會發現裡面沒有 memory.md 或 CLAUDE.md。執行 `/memory` 指令後，自動開啟 memory 資料夾，可以看到因為是專案層級的運作，這裡沒有任何記憶整合。所以你其實不需要自己建立 memory.md 檔案，它會在背景中靜靜地記錄你的任務和回饋，並建立出一個以索引組織的檔案結構。所以 CLAUDE.md 和 memory.md 就是 Claude 今天擁有的東西，而 Anthropic 顯然也在積極處理這個問題。

有趣的是，幾週前 Claude Code 的原始碼意外外洩，人們在其中發現了一個叫做 Chyros 的系統或框架的引用。這是一個尚未發佈的、始終運行的背景守護程序，持續監看你的專案，決定什麼值得記住，然後在你睡覺時整合舊筆記。目前還沒有出現在任何公開版本中，但 Anthropic 顯然在背後努力解決 context rot 問題，改善原生記憶系統，只會越來越好。

所以 Level 1 的設定已經幫你完成了，在背景靜靜運作，完全免費，你只需要正確使用它們。如果你常常重複告訴 Claude 你認為它早該知道的事，就是 Level 2 登場的時候了。

### Level 2：強制可靠的記憶召回

Level 2 改善了在正確時機載入記憶檔案的可靠性，同時也改善了 CLAUDE.md 內建的結構。我找到一篇由 John Connelly 寫的文章，他採用了 Paweł Huryn（科技界的重量級人物）的概念，Paweł 在 2 月 18 日寫道：「如何給 Claude Code 記憶——把這個貼到你的專案 CLAUDE.md 中」。這是在 Claude 宣布擁有 automemory 功能之前寫的，但它現在做的是在那個結構之上繼續強化，再結合 John 的系統，我們就有了在每次 session 開始時自動注入記憶的能力。

基本上，我們要在 CLAUDE.md 裡加入一大段關於如何管理記憶和記憶規則的 prompt，形成一個以 `~/.claude/memory` 為根目錄的雙層結構化記憶系統。我們已經看過 Claude 的自動記憶系統，但現在有了更清晰的結構：`memory.md` 和 `general.md` 儲存跨專案的事實、偏好、環境設定，另外還有領域知識，每個主題可以有自己的 markdown 檔案，以及每個工具各自的設定（如 `slack.md`）。

我們要把這些加入 CLAUDE.md，並使用 Claude Code 的 session start hook，確保每次開啟新終端機或啟動子 agent 時，自動將記憶索引（memory.md）載入 session。如果你沒用過 hook，它就是一小段腳本，在特定時機（如 session 啟動）把上下文注入 Claude。我們不是載入完整的上下文，只是載入 memory.md 這個索引，讓它知道有哪些記憶檔案可以存取。

這個系統另一個令人興奮的潛力是團隊間的分享。想像一下你可以在團隊成員之間同步那些領域檔案——不同的產品和專案，如果有人在做另一個專案，他們可以把相關的記憶檔案儲存到共享資料夾，讓所有人都能存取。這些記憶應該是 Claude Code 真正能發揮作用所需要的具體細節。

**實際設定步驟如下：**

前往說明文章中的連結，複製 Part 1 的整個 markdown 段落，貼入 CLAUDE.md。這個 prompt 會建立全局記憶目錄結構（你可能已有的部分），更新 CLAUDE.md，並初始化專案 memory.md 檔案。它主要做的是當你說「reorganize memory」時，讀取所有記憶檔案、移除重複和過時條目、合併相關條目、拆分涵蓋太多主題的檔案、依日期排序，並更新 memory.md 索引。

在新終端機中打開一個現有或空白的專案，切換到 plan mode（按兩次 shift+tab），貼入整個 prompt。Claude 會規劃記憶檔案的結構和要加入 CLAUDE.md 的內容。完成 Part 1 的計畫後，再切回 plan mode 執行「reorganize memory」，整理記憶檔案，看看從現有專案中整理出什麼來。

等它回報計畫後，可以看到它正在探索記憶系統的狀態，建立一個結構化的持久記憶管理系統。以範例專案為例，它發現根 CLAUDE.md 存在但是空的，`~/.claude/memory` 不存在，28 個專案中只有一個有 memory.md 檔案。可以看到它往上檢查了整個父目錄樹，了解最高層級存在什麼，那些東西會往下繼承。

它會建立全局記憶目錄結構（含 general、tools、domain），更新 CLAUDE.md 加入五個部分：記憶管理、全局記憶、repo 記憶、auto init（在 session 啟動時自動建立 memory.md）。然後瀏覽所有檔案，建立記憶系統和結構，讓我們可以用來重新整理記憶，設定各種 domain 和工具檔案。

重新整理記憶後，它找到了 11 或 12 個空的每日記憶檔案（空的模板、空的 session），並決定直接刪除它們，因為載入它們毫無意義。它還解決了 stale 的 open threads：讀取特定每日記憶中的執行緒，找出那些行動後來實際發生了什麼，確保它們得到更新。然後為不同專案加入交叉引用，更新 memory.md 中的索引，並執行驗證。

最終結果：刪除 13 個檔案，修剪 6 個 session，完成 9 個 open threads，加入 10 個交叉引用，3 個 pattern 被加入 general.md，剩餘 12 個有實質內容的每日檔案，清除了所有客戶資料夾中的空白記憶目錄。

接著執行第二個 prompt，在 plan mode 下執行，然後執行計畫以加入 settings.json。這樣每次啟動新 session 時，hook 就會自動注入記憶索引。hook 基本上說的是：在 pre-tool use 時，確保執行 pre-tool-memory.sh 這個腳本，來載入我們剛剛建立的記憶檔案，而不是依賴 Claude 自己去讀取並採取行動。

使用 5 天後，記憶檔案數量顯著增加（增加 90%），行數也大幅增加，但 memory.md 和 general.md 本身沒有增大太多，因為那些只是指向工具、domain 和其他檔案的索引。

對很多人來說，這樣就夠了。但一旦你用了超過幾週，你會遇到兩個問題：檔案開始變得很混亂，而且當你成長和擴展時，在少量檔案裡有效的關鍵字搜尋就會開始失效。這就是 Level 3 登場的地方——我們開始認真對待記憶的組織方式和可搜尋性。

### Level 3：語意搜尋而非關鍵字

只有在以下兩個條件都成立時，才需要從 Level 2 升級到 Level 3：一、你已經使用 Claude Code 超過一個月，記憶檔案已增長到不只幾個；二、你曾對 Claude 提問，知道答案就在你的筆記某處，但 Claude 就是找不到。

在 Level 2，我們讓 Claude 更可靠地載入記憶。但當你持續使用這個系統——跨多個客戶或專案運行好幾個月——結構最終就無法繼續擴展。你最後會有一個巨大的 general.md 檔案，無法有效率地被讀取。因為它儲存的是關鍵主題的摘要而非逐字文本，關鍵字搜尋也開始失效。Level 3 就是為了同時解決這兩個問題而設計的。

Level 3 的模板來自一個你可能熟悉的 AI agent，叫做 openclaw。openclaw 的檔案結構來自那個獨立的 openclaw agent，雖然不是 Claude Code 的東西，但他們的記憶設計系統真的很強大、很乾淨。它有三個不同的層次：

第一層是 memory.md，儲存長期耐久的事實，也就是不常變動的東西，如偏好、決策、關於你業務的事實，在每次 session 開始時載入。第二層是每日筆記檔案，每天一個檔案，你可以把它想成一份記錄日誌——今天發生了什麼、做了什麼決定、發布了什麼、什麼沒有成功，今天和昨天的筆記會自動載入，更舊的則留在磁碟上但不載入 context。第三層是一個可選的「dreaming」機制：一個背景程序，讀取你的每日筆記、為它們評分，把反覆出現的內容提升到長期記憶 memory.md 中，舊的東西則會被完全遺忘，避免撐爆你的 context。

這樣你就有了一個像樣的短期記憶，通過「dreaming」這個程序決定什麼真正嵌入長期記憶並輸入給 Claude。這就引出了一個叫做 memsearch 的框架，它是一個 plugin，把 openclaw 的框架移植到 Claude Code 中。它由一家叫做 Zilliz 的公司打造，這個團隊是最受歡迎的開源 vector database 之一的背後推手，所以他們對語意搜尋和意義搜尋很有一套，而這正是這個工具設計的用途。

他們把 openclaw 的記憶架構提取成一個獨立的函式庫，只需兩行指令就能安裝進 Claude Code。它保留了 openclaw 方法的所有優點——markdown 優先的哲學，讓所有東西都可以查看、閱讀，也可以移植到其他系統，與 openclaw 相同的分塊策略，相同的檔案結構（memory.md 和每日筆記），但現在在 Claude Code 內也能運作。

它的運作方式是把你的文件、你寫的所有內容分塊成語意向量，這樣在搜尋資訊時，它理解的是你問題背後的意義，以及你儲存內容背後的意義，而不只是用關鍵字搜尋。它更進一步，使用了我們已經看過的 hooks 概念：通過 UserPromptSubmit hook 自動把語意搜尋的前幾名結果注入每個 prompt。所以當你輸入 prompt 時，它會從記憶檔案中把最相關的三個語意匹配直接注入 Claude Code 的 context。你不需要記得要求 Claude 去搜尋，相關的記憶會在你打查詢時就自動注入。

**安裝方式：**

在 Claude Code 中執行 `/plugin marketplace`，搜尋並加入 `zilliztech memsearch`，然後安裝 memsearch plugin 到本地 repo。執行後可以看到 settings.local.json 中已啟用 memsearch plugin。執行 `/reload plugins` 以啟動它，再重新開啟 Claude Code。驗證方式是先進行幾段對話，然後執行 `ls memsearch/memory-files`，應該可以看到今日日期的記憶檔案。你也可以使用 memsearch 內建的技能：在 slash command 中執行 `memory recall`。

這個系統和我們在自己的 agentic OS 中使用的非常相似，用每日記錄檔加上長期記憶檔，在正確時機以語意方式注入 context。

另外還有一個值得了解的替代方案叫做 ClaudeMem。它是一個 Claude Code plugin，自動捕捉 Claude 在你的程式碼 session 中所做的一切，用 AI 壓縮，再把相關 context 注入未來的 session。聽起來幾乎一樣，而且非常流行，但哲學不同。ClaudeMem 使用 MCP tools 和三層儲存模型（摘要、時間軸、觀察），功能比 memsearch 多，例如有搜尋記憶的 dashboard、團隊協作功能、費用追蹤、隱私標籤。

但在我看來，對我們真正需要的東西來說有點過度。ClaudeMem 是 MCP 型，這意味著 Claude 必須主動決定呼叫搜尋工具，而不是像 memsearch 那樣從本地 database 注入。另一個主要差異是 ClaudeMem 會在背景儲存所有東西，而 memsearch 將所有東西保存為純 markdown，你可以直接閱讀。

總結 Level 3 的優點：自動注入、所有東西都是可讀的 markdown，以及 openclaw 優秀的記憶模式——而且不需要離開 Claude Code。

### Level 4：逐字召回對話內容

Level 3 找到我們的筆記和摘要，Level 4 則是設計來找到做決定時用的確切文字。使用一個叫做 MemPalace 的框架。只有在你發現自己心想「我知道我們幾週前討論過這個，但我不記得到底決定了什麼」時，才需要到這個層級。

MemPalace 最大的優點是所有東西都儲存在你本地的系統上。跟之前幾個層級相比，這是一個正規的 RAG 系統，完全免費，而且目前據說有史上任何記憶系統中最高的 benchmark 分數。因為它是逐字儲存，沒有任何東西被摘要，所以理論上什麼都不會遺失。

MemPalace 使用兩種不同的語言來呈現資訊：上方的索引使用一種 LLM 可以一眼掃過的密集符號方言（類似「古代羅馬地址」的格式），指向下方資料庫中具體資料的位置——也就是他們稱之為「抽屜」的地方。例如：「我兒子叫 Noah，9 月 12 日滿六歲，他喜歡恐龍」，這段話的指針就會被索引為：Noah、兒子、六歲、生日，並在對應的抽屜（wing 42、room 11、drawer 007）中儲存完整資訊。

記憶宮殿（memory palace）是一種古老的記憶方法，MemPalace 以此架構儲存資訊：wing 代表人物、專案和主題；rooms 可以是日期、session 或執行緒；closets 可以是主題或 bundle；抽屜裡放的是逐字文本。這樣的巢狀結構讓它能直接定位到正確位置。因為索引使用符號語言，讓模型可以在一次掃描中瀏覽數千個抽屜，速度很快。

這個系統使用兩個獨立的 database：一個 SQL database 追蹤實體和它們之間的關係，以及一個 Chroma vector database 將每段對話以可搜尋的分塊形式儲存。與前幾個層級類似，它也使用背景 hooks 靜靜地儲存和索引資訊——在 session end（session 結束）時歸檔和索引，在 pre-compaction（即將壓縮時）也會觸發 hook。

**安裝方式很簡單：**

執行一個指令安裝，初始化後它會建立 palace 結構（wings、rooms、drawers），在 settings.json 中註冊所有 hooks，然後開始工作。你甚至可以用 `mine` 函數來回溯挖掘之前的對話 session。

到了這個層級，Claude 可以用普通英語逐字搜尋你曾經進行過的每一段對話，因為一切都已在背景中以記憶宮殿的檔案結構建立索引。一個缺點是逐字內容不是以 markdown 格式直接呈現，所以不能直接閱讀，但可以快速輕鬆地取回資訊。

到目前為止，我們談到的所有東西幾乎都鎖在你的本地機器上。但如果你幾個月前在 ChatGPT 裡做的研究、在手機上的腦力激盪呢？這就是 Level 5 和 Level 6 的用武之地，它們完全不同，因為已經不再是記憶對話而已，而是如何跨工具對話，以及如何可靠地儲存連結所有不同資訊的研究成果。

### Level 5：建立自組織知識庫

Level 5 和 6 完全不同，它們不再是記憶對話。MemPalace 大概是逐字記憶對話的巔峰之作。現在的問題是：如果你想建立一個跨工具的互聯知識庫。

如果你滿足以下條件，才需要加入 Level 5：你定期消化想要長期保存和連結的資訊，例如文章、影片、podcast、客戶筆記，也就是你在大量閱讀但記不住自己學了什麼的地方。你可以把這些全部連結成一個互聯的知識庫。這比較不是關於一次性的專案，而是建立你真正關心的主題上的「第二大腦」。如果你只是隨意消化內容，不需要回頭查閱，那我建議跳過這個層級。

最受歡迎的方法就是 Andrej Karpathy 的 GitHub repo，叫做 LLM Wiki——一個關於為任何你關心的主題用 Claude 建立「living wiki」想法的文件，獲得了大量關注。它的特點是：在專案中建立兩個資料夾。`raw` 資料夾放你的來源文件（文章、報告、podcast 逐字稿、YouTube 影片逐字稿、PDF），Claude 從這個資料夾讀取但永遠不寫入。`wiki` 資料夾完全由 Claude 負責，它會寫入每個檔案、維護結構、更新交叉引用，你自己則永遠不寫入 wiki。整個系統只需要普通的 markdown 檔案，不需要外部或 vector database，而且完全可讀。

在 Obsidian 中整合所有資源後，你會得到一個知識圖譜，顯示不同資源如何互相連結。這個方法最適合的使用情境是：你有一個「以後再看」的資料夾，裡面堆滿了書籤的 Slack 執行緒、YouTube 影片、客戶筆記，你想看到它們之間的關聯，或者有效地建立一個關於特定主題的 Wikipedia。這是針對互聯主題進行深度研究的工具。

但就我個人而言，在像業務 OS 或 agentic OS 這樣的系統中，我看不到它直接適用的使用情境。我倒是可以看到一些用途，比如為你正在研究的特定關鍵主題領域開啟 wiki，讓這些知識被視覺化和互聯。但就我們用它來建立業務用途的專案的方式，我不確定它是使用記憶系統的最佳方式，除非你是在對特定主題做深度研究。

也有人提到一個叫做 Recall 的類似替代方案，因為它在網路上爆紅了。Recall 是一個代管服務，基本上就是「幫你搞定的 Karpathy LLM Wiki」。你安裝瀏覽器擴充套件，儲存文章、podcast、PDF 等，Recall 自動摘要、打標籤，並自動為你建立知識圖譜，省去設定麻煩。它還有自己的 AI 聊天介面，可以跟你儲存的內容對話，在手機上也能用，還有 MCP 存取，可以直接連接到 Claude Code。

為什麼 Recall 在我看來不如 Karpathy 的模式：第一是所有權，你不真正擁有資料，Recall 允許匯出 markdown，但在使用期間，資料是活在他們的伺服器上，等於是在租而不是擁有你自己的資訊。第二，Recall 是為內容消費建立的，而不是操作性記憶——它非常適合「我看了 40 支關於 Claude Code 的 YouTube 影片，哪支談到了記憶？」的使用情境，但不是為「我們三月時決定了客戶 X 的登陸頁面和轉換率是什麼」這樣的問題設計的。第三，作為現成的軟體，Recall 有定價的考量。

如果你非技術背景且主要想整理文章、影片和 podcast，Recall 很棒；如果你想要最大控制權並仍想建立 Wikipedia，LLM wiki 一定比較合適。

還有一個值得快速提及的重量級替代方案叫做 LightRAG，它是一個企業級知識圖譜，設計用於更重量級的實體提取和雙層次召回，基本上是完整的研究級解決方案。但對 99% 的業務負責人來說完全過度，不需要設定麻煩，不需要背後的巨大 database。

到了這個階段，我們已經涵蓋了大量內容。值得注意的是，到目前為止，所有東西都存在於 Claude Code 之內。但 Level 6 是關於如果你不只用 Claude Code 的情況。

### Level 6：跨工具共用的單一大腦

Level 6 是一個我看到叫做 OpenBrain 的方法，由 Nate Jones 提出。它的目的是讓你可以在不同 AI 工具之間自由切換——在手機上的 ChatGPT、在桌面的 Claude Code——而且這是目前唯一一個讓你使用的所有不同 AI 都能即時自動看到相同記憶的系統。

這個系統使用你自己擁有的 Postgres database 來儲存記憶，所以可以說是最具未來可移植性的方案。當下一個重大 AI 工具在 6 個月後推出時，只需把它連接到你現有的 Postgres 大腦，完全不需要遷移。如果你主要還是在一台機器上使用 Claude Code，那可能值得跳過這部分。

它就是其名稱所說的：你思維的基礎設施層。一個 database、一個聊天頻道，任何你使用的 AI 都可以接進來，如果你跨應用程式工作，這就非常強大。不依附於任何 SaaS，而且執行成本非常低，每月不到一美元。

它在 Supabase 上建立的 Postgres database 中，基本上有一個叫做 `thoughts` 的資料表，每一行就是一筆記憶：一段文字、一個 embedding vector（用於搜尋）、一些標籤，以及關聯的時間戳記。然後它使用內建的擴充套件來處理所有語意搜尋。

基本上是一個 MCP server 從 Claude Code 運行，連接到 Supabase 的 edge functions，作為每個想要讀取 database 的 AI 工具的前門。Claude Code 可以查詢它，ChatGPT 也可以，Claude Desktop 可以，Cursor 也可以，所有工具使用的都是同一個大腦。

設定上確實需要更長的時間來理解和完成，有完整的設定指南（Nate 本人也有 YouTube 影片教學），以及幫助你從現有 Claude Code 記憶系統遷移記憶到 OpenBrain 的輔助 prompt。Nate 的指南是為非技術人士編寫的，大概 30 到 45 分鐘就可以完成設定。如果你想讓記憶可移植、不依附於 Claude Code，這可能是你的正確解決方案。

另外也值得提及 **Mem0**，另一個跨工具記憶層。它資金充足、行銷做得很好，已被廣泛的開發者使用（據說 100,000 名開發者，來自多家大公司）。設定快速，不到一分鐘就能開始使用，能為你的 LLM 應用程式提供通用的自我改進 AI 記憶層，完全跨工具。如果你實際上在發布 AI 產品，Mem0 可能是個明智的選擇。

但 Mem0 的一個缺點是你的資料會永久存在他們的伺服器上，而 OpenBrain 讓你實際擁有 Supabase 專案，可以隨時匯出完整的 Postgres database，並控制多種不同工具的存取。

就 Level 6 的整體比較而言：OpenBrain 是其中設定最複雜的，也是唯一一個會引入每月顯著費用的（雖然只有 10-30 便士，在 Supabase 免費方案上）。與其他層級相比的缺點：我們仍然把資料存在筆電之外，資料安全存在 database 中，但這意味著每次都需要查詢一個外部資料庫，這會增加一些延遲。但如果你希望使用的每個 AI 工具都能共用同一份記憶，這可能是你願意做出的取捨。

### 最後建議：從哪裡開始？

整理一下如何開始以及該選哪個方案：

**剛開始入門**：不要擔心這些記憶系統。啟用 Level 1，正確使用你的 CLAUDE.md 和 memory.md 檔案。花 10 分鐘，對內建記憶是一個巨大的改善。

**已經用了一段時間**：升到 Level 2，安裝 John 的 hook，然後大多數人應該就在這裡停下來。

**累積了大量 context，跨幾個月的工作正在遺失舊的決策**：可以升到 Level 3（安裝 memsearch），或 Level 4（MemPalace，逐字召回）。

**Level 5 和 Level 6** 把我們帶入了完全不同的領域：Level 5（Karpathy 的 LLM wiki）最適合對特定主題做深度研究，並引用子主題間的關聯。Level 6（OpenBrain 或 Mem0）適合你想要一個你自己擁有、相對便宜，且可以接入任何外部 AI 工具或 LLM 的系統。

好消息是今天介紹的很多東西可以疊加使用——Level 1、2、3 可以一起跑，資料夾結構也相當相似，可以讓 Claude Code 幫你整合。

就我個人實作的方向而言，我正在 agentic 作業系統中實作到 Level 3：遵循 openclaw 的慣例，同時加入語意搜尋能力和在特定時機注入特定 context 的 hooks，這樣可以改善業務作業系統中的搜尋和召回功能。
