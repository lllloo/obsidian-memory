## 資料保留時間

輸入給 Claude 的資料會在後端殘留多久，依使用身分與設定而不同：

- 一般個人使用者：伺服器最多殘留 **30 天**。
- 某段對話被判定違規：該記錄保留 **2 年**。
- 設定隱私中勾選「協助改善 Claude」：資料最長保留 **5 年**。
- Zero Data Retention（ZDR，零資料保留）：資料一秒都不留在 Claude 端，需選用 Claude 的 **Team 方案、Enterprise 方案，或相對昂貴的按量計費 API**。

ZDR 有兩個但書：

- **不適用所有功能**：例如 Claude 的副產品 CoWork 就不在 ZDR 範圍內。
- **刪除檔案要走 compliance API**：若曾上傳檔案，僅從介面刪除不夠，必須透過 compliance API 才算真正刪除。

此外，即便滿足上述條件，**牽涉法律訴訟時資料仍可能被強制取得**，不受保密特權保護——這不是 Claude 特有問題，所有平台皆然。

小結：個人方案（Pro / Max）輸入內容最多保留 30 天；企業方案（Team / Enterprise / API）可做到零資料保留，但極端狀況仍可能被強制取得。真正敏感的資料，輸入前先處理好。

## 輸入最小化原則

只給 Claude Code 完成任務「真的需要」的資料：

- 密碼、憑證、金鑰不要直接貼進去；可請 Claude Code 教你怎麼部署，或自己手動輸入。
- 要分析銷售數字就只給數字，不要連客戶聯絡方式一起放進去。

## 三道防線

**第一道：本地模型去敏（代號化）**

用本地模型把資料中的敏感訊息換成代號（客戶 A、客戶 B、客戶 C），留一份代號對應真實資料的對照表，把代號化後的資料送給 Claude 處理，拿回結果後再依對照表還原。加密與還原都在本地完成，遠端伺服器不會留下真實資料。

**第二道：Claude Code Deny List**

在 Claude Code 設定 deny list，讓模型完全碰不到某些敏感區域或無法做某些敏感操作（例如存放憑證、token、金鑰的位置）。同時要把這些檔案加進 `.gitignore`，避免金鑰檔、憑證檔、客戶原始資料目錄洩漏進版本控制。

**第三道：API Key 保護（傳統好習慣）**

API key、密碼、金鑰不要進 git commit、不要寫死在程式碼裡，而是存在環境變數或金鑰管理員，讓程式去讀環境變數。一旦進程式碼就會進版本控制留下記錄。若發現金鑰已外洩，唯一的路是到平台上把金鑰作廢、輪換密碼，沒有別的選項。

## Coding Agent 安全操作

當 Claude Code 執行改程式碼、跑部署等較複雜任務時：

- **憑證一律用測試環境（staging）的，不要用正式憑證**。測試環境搞砸了可以重來，正式環境很難重來。流程應是先讓 AI 部署到測試環境，測試確認沒問題後，再由人工手動部署到正式環境。
- **改完程式碼、執行或部署前，人工掃一眼它動了什麼**。不必讀懂每一行，只要確認修改範圍符合你交辦的事、沒有動到不預期的地方。
- 若團隊已有自動化部署流程，務必加上**自動掃描金鑰**與**自動掃描 commit 記錄**當最後一道關卡，避免機密外洩。

## 第三方套件風險

安裝 MCP、CLI、GitHub 開源套件、skill 時，這些都是第三方開發者的東西，可能藏有無意或有意留下的資安風險與惡意程式碼。

- 保持**不信任原則**：所有東西裝進來之前都先安全掃描一次。可做一個安全掃描 skill，讓模型在裝任何東西前都先過這個 skill 掃描惡意程式碼與資安風險。
- 這個風險並不遙遠：2026 年開始已出現多起 skill / MCP / 外掛藏木馬、惡意提示詞注入，甚至熱門套件被入侵、供應鏈投毒藏後門的案例，下載者完全不知情，造成大量資料外洩與損失。

## 企業合規框架：三軸

合規判準不是只問「能不能裝、能不能用」，而是三個軸同時看：

1. **資料分級**
2. **Agent 的權限模式**
3. **路徑隔離**

三軸都考慮到，導入才有依據，也才能釐清為什麼某些工作可以交給 agent、某些不行。具體可思考：

- 公司有沒有跟 Anthropic 簽**資料處理協議（DPA）**——這是企業合規的基礎，何時簽由公司與 IT 討論。
- 是否確保所用方案有 **ZDR 零資料保留**。
- 若公司政策完全不允許資料離開自家系統，是否做好**本地模型部署**、**資料路徑隔離**與模型 **deny list** 設定。
- 也可用 **AWS Bedrock**，讓 AI 的呼叫記錄全部留在自己的 AWS 帳戶內。

現實上已有許多台灣與國外大企業開始使用 AI agent，不一定用本地模型，也有不少使用 Codex。這件事並非無解，但必須在政策、合規與技術三個層面預先想好一套完善架構。

## 四個不能放手的基礎

不管選哪種方案、用什麼工具，有四件事不能放手：

1. **心態**：AI 是協作的高效幫手，但人是最後負責的驗證者；人一鬆懈，再強的 AI 都可能出包。
2. **合規**：AI 不能幫我們處理合規，必須在政策面、制度面先幫它規劃好合規環境。
3. **隱私與權限管理**：要事先幫 AI 做好。
4. **驗證**：規劃出人與 AI 一起合作、驗證產出的機制，讓產出品質穩定、風險降低、過程看得懂、結果可被稽核。

## 企業 AI 導入 7 題自查清單

1. 公司有沒有 AI 工具使用政策？
2. 客戶資料是否屬於 NDA 保護範圍？
3. 是否有需要簽資料處理協議（DPA）？
4. 是否確定所用方案已有 ZDR 零保留？
5. 帳號是個人帳號還是企業帳號？
6. 安裝外部套件 / MCP / Claude Code skill 之前，是否有 IT 稽核機制與 CI 流程？
7. 是否有加入金鑰掃描與記錄掃描？

完成這些準備後，就能放心跟 AI 協作，並帶上同仁一起進入 Claude Code 的世界。
